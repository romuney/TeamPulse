# Разбор корпоративного сравнения

В репозиторий включены только выводы и обезличенные времена. Исходный архив,
снимки содержимого отчётов и корпоративные данные не публикуются.

## Что подтверждено

Пять запросов при входе запускаются параллельно. При смене подразделения
перезапрашиваются четыре части; справочник главного чарта остаётся на месте.
Применение данных всё равно требует core соответствующего выбора и версии данных.
Если core приходит последним, первым появляется сразу полный отчёт — это
не последовательное выполнение запросов.

В приложенном NEW-switch-2: четыре POST на 774–775 мс, people на 1386,
aux на 1418, flow на 1504, core на 1730; единственный полный run на 1778,
его завершение ran на 2082. В тексте первоначального отчёта этот пример
ошибочно описан как ранний core-only кадр.

## Поправки к оценке скорости

У NEW first_useful_ms соответствует началу run. До завершения синхронной
работы остаётся ещё примерно 0,3–1,2 с. Ни run, ни ran не являются подтверждением
показанного браузером изображения.

Ниже восстановлены медианы трёх основных повторов без пилотов:

| Сценарий | OLD: исходная iframe-проба | NEW: завершение первого применения | NEW: завершение последнего применения |
|---|---:|---:|---:|
| Вход | 7 914 мс | 4 144 мс | 5 403 мс |
| Повторное открытие | 7 640 мс | 4 717 мс | 6 004 мс |
| Смена подразделения | 4 547 мс | 2 035 мс | 2 035 мс |
| Смена фильтра | 5 707 мс | 4 812 мс | 4 812 мс |

Это разные инструментальные прокси: код опроса OLD не приложен, paint не измерен.
Таблица поддерживает вывод о пользе разделения, но не точный процент ускорения
видимого экрана. В худшем парном фильтре NEW завершился за 12 462 мс против
9 968 мс у OLD; новая версия не быстрее в каждом запуске.

В network.csv начало части запросов switch объединено с длительностями предыдущего
открытия: например, 1605 мс у core совпадают со старым запросом, тогда как
фактический новый запрос в timeline длится 956 мс. Фазы TTFB/download
нельзя использовать для оптимизации до повторной привязки по requestId.

Разрыв «dict доставлен → start» составил 1921 мс в одном открытии,
но 70 и 116 мс в начальных загрузках других приложенных шкал.
Постоянная стоимость распаковки в 1,9 с и обещание убрать две секунды не доказаны.
Отсутствие browser cache-hit также не доказывает повторное исполнение SQL.

## Корректность и найденная регрессия

В десяти парах сохранённых снимков совпали 328 пар class/text суммарно.
Это не полный обход всех подвкладок и не доказательство равенства всех результатов.
Девять полных текстов совпали; в структуре обнаружена потеря «Стримов».
Снимок onepager-small фактически содержит структуру малой команды.

Причина потери стримов воспроизведена локально: список подвкладок и разрезы
главы фиксировались до people. Исправлены обе регистрации; расширенная проверка
теперь сравнивает 23 подвкладки с обычной поставкой и переходы между командами
со стримами и без них. Числовая модель и формулы не изменены.

## Границы оптимизации

Устранён ранний ready-marker: родитель мог получать сигнал до сборки модели
и интерфейса. Он перенесён после возможности отрисовки; устаревшие корни отсекаются.
Это исправление последовательности показа, а не измеренное сокращение SQL.

Кэш декодированного текста справочника устраняет повторное преобразование
побайтно одинаковой строки. Кэш ограничен одной записью и не содержит
результатов формул, прав доступа или фильтрации. На синтетическом большом
справочнике подтверждено сокращение повторной работы; ускорение первого
открытия из этого не следует.

Нельзя применять people/flow нового выбора к старому core даже с предупреждением.
Это нарушило бы эталонную логику. Серверный приоритет core, условия async 202
и стоимость платформы требуют измерений внутри Proteus.

Для следующего прогона достаточно локальных проверок pass/fail и обезличенных
фаз: [методика без передачи ЧД](6.%20Проверка%20без%20ЧД.md).
Изображения, DOM-тексты, данные датасетов и сырые профили не требуются.

## Дополнительная оптимизация клиента по имеющимся данным

Один синхронный рендер многократно собирал одинаковые выводы: каждый пункт меню
заново проходил весь набор метрик. Теперь повторное использование действует
только внутри одного рендера, при точном совпадении аргументов. Возвращаемые
объекты копируются; расчёт severity каждого блока остаётся эталонным. После
рендера, ошибки или вложенного рендера записи очищаются.

Изолированный замер этой правки: Chromium, 504 синтетических узла, 23 месяца,
справочник около 2 МБ; три пары AB/BA/AB на базе 619656d, одинаковые ответы.
Инструментирована только локальная тестовая копия. Медианы:

| Операция | До | После |
|---|---:|---:|
| Вызовы подготовки фактов в последнем рендере | 198 | 22 |
| Вызовы построения карточек | 45 | 10 |
| Последний рендер сводки | 87,4 мс | 58,9 мс |
| Последнее синхронное применение данных | 127 мс | 99 мс |
| Все четыре рендера суммарно | 208,9 мс | 181,6 мс |

Первые три рендера почти не изменились. Разбор модели и подготовка API не
ускорились; итоговые тексты и значения во всех шести запусках совпали.
Эти числа не измеряют SQL, передачу кода или скорость открытия в корпоративной сети.

Вторая правка разделяет фоновую подготовку на отдельные задачи браузера:
модель → API → применение. Живые данные и DOM меняются только в последней задаче;
между задачами можно обработать ввод. Новый выбор или ответ отменяет устаревшую
подготовку, диалог приостанавливает её. Первый core сохраняет прежний приоритет.
Расчёты внутри каждого этапа синхронные; устранение всех длинных задач не обещается.

Проверки: prepare/cooperative/insight-cache; браузерная сверка с ordinary всех
23 подвкладок и модели, промежуточных строк, смены подразделения и нулей;
регрессии загрузки, фокуса, чтения, настроек, отсутствующих и поздних ответов.

### Отклик на ввод во время фонового обновления

Отдельный стресс-замер итоговой сборки относительно 619656d: 504 синтетических
узла × 23 месяца, одинаковое замедление CPU ×4 после первого показа. 32 запуска:
раскрытие строки, вкладка, настройки, прокрутка; ответы вместе и по очереди;
две версии, два повтора с порядком AB/BA. Ввод посылался через CDP через 10 мс
после начала фонового обновления, без ожидания готовности элемента автоматизацией.
Измерялись 44 события click/wheel на каждую версию.

| Показатель | 619656d | Новая сборка |
|---|---:|---:|
| Медиана худшей задержки обработчика в каждом запуске | 486 мс | 141 мс |
| Медиана худшего интервала событие → возможность отрисовки | 515 мс | 222 мс |
| Медиана максимального промежутка между кадрами | 517 мс | 233 мс |
| Самый большой промежуток между кадрами | 800 мс | 300 мс |
| Успешные пользовательские действия | 14 из 16 | 16 из 16 |

В обоих baseline-запусках одновременной догрузки клик раскрытия строки пришёл
после длинного применения: строка сместилась и клик попал мимо. Новая сборка
обработала оба раскрытия. На 1530 наблюдениях кадров не обнаружено рассогласования
модели, доступности частей и DOM. Это выборочная проверка синтетического сценария,
не доказательство отсутствия любой возможной гонки.

Без сценария настроек медиана «последняя часть получена → полное применение»
сократилась с 553 до 472 мс, до возможности отрисовки — с 596 до 481 мс.
При одновременной догрузке и открытии настроек обработчик сработал раньше
(489 → 141 мс), но полное обновление позже (647 → 924 мс до возможности отрисовки):
новая версия успела открыть диалог и правильно ждала его закрытия. При ответах
по очереди этот сценарий сократился с 1357 до 1146 мс.

Прокрутка улучшилась слабее: медианы худших задержек обработчика — 539 → 393 мс
при одновременных ответах и 506 → 379 мс при последовательном приходе.
Сами model/render всё ещё синхронны, рывки полностью не устранены. Узлы строк DOM
при обновлении заменяются в обеих версиях; проверенные фокус, раскрытие и место
чтения сохраняются. Эти результаты описывают клиент под искусственной нагрузкой,
не скорость SQL и не прогноз секунд ожидания в Proteus.
