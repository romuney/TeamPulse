# TeamPulse Hub «по частям» — что куда и как проверить

12.11.2026. Экспериментальная копия поставки: тот же отчёт, но данные грузят несколько чартов параллельно.
Обычная поставка (`Поставка — TeamPulse Hub`, один чарт) не меняется и работает как раньше.
По сообщению владельца, предыдущая раздельная версия уже работала быстрее в Proteus.
**Эта итерация проверена локально на синтетических ответах**, её поведение в Proteus ещё нужно проверить на тестовом дашборде.

## Новое: ждём открытую вкладку

При смене фильтра прежний экран остаётся с отметкой обновления до готовности открытой вкладки:

| Открытая вкладка | Нужные ответы |
|---|---|
| One-pager | core |
| Структура, Рост HQ, Мониторинг, Офис | core + people |
| Движение, Отток, Найм | core + people + flow |
| AI | core + aux |

Остальные ответы догружаются в фоне. Это правило ожидания интерфейса: порядок запросов на сервере
по-прежнему определяет Proteus. Core остаётся обязательным для любой вкладки.
Сравнение с похожими подразделениями уточняется после aux; его приход может обновить текущий экран.

При первом входе отчёт открывается по core. На вкладке, которой пока не хватает деталей,
уже доступны основные графики из core; отсутствующие разбивки остаются в состоянии загрузки.
На AI без aux основных графиков ещё нет. Через 20 секунд ожидания появляется объяснение,
а готовые показатели остаются на экране.

При догрузке того же ответа обновляется модель данных, сохраняются корень отчёта, обработчики,
открытия и текущая вкладка. Догрузка чужой части не перерисовывает содержимое текущей вкладки
(например, flow не перерисовывает Мониторинг). Открытые настройки и тур защищены от обновления
до закрытия. Новый фильтр по-прежнему полностью применяет новый core.
Если предварительные графики уже прокручены, они остаются на месте до явного перехода:
внизу экрана появляется кнопка «Подробности готовы · открыть». Поиск сохраняет фокус и выделение.
Последний выбранный фильтр имеет приоритет даже после окончания загрузки: поздний старый ответ
не возвращает прежнее подразделение. Возврат к уже показанному выбору отменяет другой ожидаемый
выбор; переключение вкладки сразу пересматривает, каких ответов ещё не хватает.
Быстрый таймер core больше не откладывается приходом фоновых частей; повторные запросы
внутри страницы адресованы только недостающим частям.

### Что заменить на тестовом дашборде

1. Код главного чарта целиком из файла **3** этой папки.
2. Код каждого из четырёх загрузчиков целиком из файла **3а** этой папки.
3. Датасеты, CSS и JSON областей для этой итерации не меняются.

Проверка: открыть Мониторинг → изменить подразделение в настройках → убедиться, что
новые показатели доступны до завершения остальных запросов. Повторить на AI и Движении.
На первой загрузке открыть Отток, пока people ещё в пути: динамика уже видна, детали догружаются.
Проверить числа, выбор вкладки, открытые настройки, прокрутку и обработку неответившего загрузчика.
Ускорение SQL и сокращение core в эту итерацию не входят.

## Зачем

Сейчас один чарт: один большой датасет и 642 КиБ кода, который уходит на сервер при **каждом** выборе подразделения или фильтра.
Здесь отчёт разложен на пять чартов одного дашборда:

| Чарт | Датасет | Код | Что делает |
|---|---|---|---|
| Главный (виден) | `2.0` dict — справочник подразделений | файл `3` (652 КиБ) | Весь интерфейс. Сам себя не фильтрует — после выбора подразделения его код больше никуда не едет |
| Загрузчик 1 (скрыт) | `2.1` core — ряды метрик, строка HQ | файл `3а` (1,8 КБ) | Первый экран: One-pager, таблица подразделений, графики динамики |
| Загрузчик 2 (скрыт) | `2.2` people — разрезы людей | файл `3а` | Структура, отток, «Рост», мониторинг, офис |
| Загрузчик 3 (скрыт) | `2.3` flow — переводы, водопад, вакансии | файл `3а` | Движение, найм |
| Загрузчик 4 (скрыт) | `2.4` aux — AI и база похожих подразделений | файл `3а` | Вкладка AI, сравнение с похожими |

Загрузчики получают ответ и передают его главному чарту внутри страницы. Экран появляется, как только пришла часть core.
Вкладка, чьи детали ещё в пути, показывает кольцо загрузки на значке; основные графики доступны по core.

## Что это даёт (стенд масштаба боя)

Стенд: 11 932 подразделения, около 72 тысяч человек активной численности, таблицы по нынешней схеме
(`stand/hub_scale_clone.py`). Время сервера на запрос — разбор текста по модели Proteus плюс ClickHouse.

| Запрос | Компания | Блок 3-го уровня | Команда 7-го уровня + HQ | Ответ (компания) |
|---|---|---|---|---|
| Один чарт, целый датасет | 16,7 с | 15,6 с | 15,5 с | 10,5 МБ |
| Часть core — первый экран | 6,1 с | 6,5 с | 5,7 с | 2,1 МБ |
| Часть people | 4,3 с | 4,8 с | 4,2 с | 3,0 МБ |
| Часть flow | 3,6 с | 3,4 с | 3,0 с | 2,0 МБ |
| Часть aux | 1,8 с | 2,5 с | 1,9 с | 1,7 МБ |
| Часть dict (только при открытии) | 1,5 с | — | — | 1,9 МБ |

- После выбора подразделения первый экран по серверу — в 2,5–2,7 раза быстрее (≈ 6 с против ≈ 16 с), и код главного чарта
  (642 КиБ, ≈ 13 с отправки при 50 КБ/с) больше не уходит: в запросах только код загрузчика, 4 × 1,8 КБ.
- Все вкладки готовы за ≈ 6 с, если Proteus исполняет четыре запроса параллельно. Если ставит в очередь — сумма частей
  ≈ 16 с, то есть как сейчас; выигрыш тогда только в первом экране и в отправке кода.
- Первое открытие дашборда ускоряется меньше: код главного чарта один раз всё равно уходит на сервер.

Стенд тяжелее боя по чтению (таблицы без ключа сортировки, строк с запасом) и легче по числу значений разрезов; секунды
на бою будут другими, соотношение — ориентир. Точный ответ — замер на копии боевого дашборда.

## Установка

Ноутбук и таблицы **не меняются**: тот же файл 1 обычной поставки, перезапуск не нужен.

1. **Пять виртуальных датасетов** (база CROSS) — файлы `2.0`…`2.4`. Тексты отличаются одной строкой `{% set PART = '…' %}`.
   Список полного доступа `{% set FULL = [...] %}` впишите **одинаковый во все пять** (как в боевом датасете).
2. **Пять чартов** типа ECHARTS:
   - главный — датасет dict, код из файла `3`;
   - четыре загрузчика — датасеты core, people, flow, aux, код из файла `3а` (один и тот же).

   У всех: «Измерения» — `role id pid lvl nm kids j ms mx`, метрик и сортировки нет, лимит строк 50 000.
3. **Дашборд-копия.** Первый ряд — четыре загрузчика, второй ряд — главный чарт. Все пять — на одной вкладке.
4. **CSS** — файл `4` в конец CSS дашборда. В нём номера-заглушки чартов (900000…900004): замените на свои (Ctrl+H) или
   пришлите пять номеров — подставлю скриптом.
5. **JSON-метаданные дашборда** — блок из файла `5` (те же номера): главный чарт фильтрует только загрузчики, себя — нет;
   загрузчики не фильтруют никого. Сохранить свойства → сохранить дашборд → обновить страницу.
   Настройку кросс-фильтров этих чартов в интерфейсе потом не открывать: она перезапишет области.

Менять только вместе: файлы `3`, `3а` и пять датасетов — одна версия протокола. Главный чарт со старым загрузчиком данных не получит.

## Проверка на бою

1. Дашборд открылся, под отчётом и над ним нет пустой полосы от загрузчиков.
2. DevTools → Network → фильтр `chart/data`. Выбрать подразделение: ушло **четыре** запроса (загрузчики), запроса главного
   чарта **нет**. Если главный тоже ушёл — области из файла `5` не применились (отчёт работает, но медленно).
3. Сразу после открытия перейти на «Структуру»: либо экран уже есть, либо «Загружаю данные вкладки…», который сменяется экраном.
4. Числа One-pager и двух-трёх вкладок совпадают с обычным дашбордом при том же подразделении и фильтрах.
5. Если что-то не так — в консоли DevTools выбрать фрейм главного чарта и выполнить
   `window.__pvtState.tp.parts.log` — журнал «что и когда пришло»; пришлите его.

## Что может не сработать на бою (не проверено)

- **Скрытие загрузчиков.** CSS оставляет их в окне размером 1×1 px. `display: none` не используется намеренно: скрытый так
  чарт Proteus может не загрузить. Если загрузчики всё же не грузятся — закомментируйте блок 8 в CSS и проверьте без скрытия.
- **Области кросс-фильтров** — применяются только через JSON; проверка — пункт 2 выше.
- **Параллельные запросы.** Пять запросов одного пользователя разом: если кластер ставит их в очередь, выигрыш будет меньше.
- **Кэш частей.** Части кэшируются порознь. После обновления таблиц одна может прийти из старого кэша — отчёт это видит
  (отметка сборки данных) и сам перезапрашивает загрузчики мимо кэша.

## Для разработки

Экспериментальные изменения изолированы в `src/`, `tests/` и `build.cjs` этой папки.
Общие исходники читаются без изменения; несовместимые точки вставки останавливают сборку.
Из корня репозитория:

```bash
node "Team Pulse/Поставка — TeamPulse Hub (по частям)/build.cjs"
node "Team Pulse/Поставка — TeamPulse Hub (по частям)/tests/scheduler.cjs"
python "Team Pulse/Поставка — TeamPulse Hub (по частям)/tests/fixture_server.py"
# В другом терминале, с установленными Playwright и Chromium:
python "Team Pulse/Поставка — TeamPulse Hub (по частям)/tests/browser.py"
```

Сборка использует зависимости из `Team Pulse/proteus/node_modules`, пишет только файлы 3 и 3а
этой папки и проверяет ES5, ограничения Proteus и прежний бюджет 664 КиБ.
Обычный `proteus/build.js` пока собирает прежнюю раздельную версию: после него для эксперимента
нужно выполнить команду выше. SQL, CSS и JSON по-прежнему собираются через `stand/mk_split.py`;
он переписывает и эту инструкцию, поэтому не запускать его ради изменений только JavaScript.

Локальные проверки: первый запуск по core через 30 мс, даже если рядом пришли другие части;
ожидание нужных частей для всех девяти вкладок; сверка текста всех вкладок/подвкладок с обычным
чартом до и после фильтра; неизменность DOM-корня и текущего экрана при чужой догрузке;
сохранение настроек; поздний/пропавший ответ; восстановление после старого кэша.
Это проверки клиентской логики на синтетике, не замеры скорости корпоративного сервера.


## Независимая проверка критиками — 12.11.2026

После сборки три критика отдельно прошли сценарии в Chromium с искусственными задержками.
Повторная проверка после исправлений: плавность **8,5/10**, скорость/готовность **8/10**,
понятность **9/10**. Найденные блокеры в проверенных сценариях закрыты.

Исправлено по результатам проверки: поздний ответ первого фильтра после второго; возврат
B → A → B во время ожидания; переход на вкладку с уже готовыми данными; потеря фокуса поиска;
замена читаемого графика другим видом; противоречивые статусы AI и ошибки; невидимая после
прокрутки кнопка готовых подробностей. Регрессии включены в `tests/browser.py`.

На малой синтетике, при искусственной задержке нужной части 2 с и чужих 7–8 с:
Мониторинг стал доступен примерно через 2,11 с, AI — 2,09 с. Движение при последнем нужном
ответе на 2,2 с — через 2,30 с. Первый рендер занимал около 103–108 мс; обработка фоновой
части flow на Мониторинге — около 6 мс без перерисовки содержимого. Эти числа описывают
локальную проверку клиентской логики, не обещают такую скорость на боевом объёме.
