# TeamPulse Hub — бизнес-анализ проекта

**Дата анализа:** 07.10.2026
**Продукт:** TeamPulse Hub — верхнеуровневый HR-борт для руководителей (интерактивный прототип)
**Стадия:** прототип собран (итерация 27), осталась визуальная приёмка и правки по замечаниям
**Платформа/стек:** чистый HTML+CSS+JS, **без библиотек** — вся графика на голом SVG; сдача одним self-contained файлом `index.standalone.html` (~260–300 КБ), точки входа — GitHub Pages (`index.html`)

> Анализ носит продуктово-функциональный характер по состоянию документации
> (`SPEC.md`, `AGENTS.md`, `PROGRESS.md`, `SOURCES.md`, `REVIEW_2.0.md`, `README.md`)
> и кода. Числовые значения метрик — на мок-данных, не финальные.

## 1. Место продукта и роль в управлении

TeamPulse Hub — **один верхнеуровневый борт вместо нескольких дашбордов TeamPulse**
(HQ-версии и версии по всей управленческой структуре). Разделение аудитории
обеспечивается не отдельными отчётами, а **четырьмя управляющими фильтрами**
и персональными ссылками.

Закрывает операционный управленческий контур HR: **«сколько людей → как нанимаем →
как развиваем → как удерживаем → как работает команда → как используются офисы»**.

**Ключевое бизнес-свойство:** все цифры на борде не константы — они пересчитываются
от выбранного подразделения, четырёх фильтров и среза состава. Отчёт отвечает на вопрос
руководителя *«что происходит именно у меня»* и сравнивает это с согласованной базой
(«вся компания» / «всё HQ» и т.д.) или с утверждённым KPI.

**Целевая аудитория:**
- руководители подразделений (LINE/уровни −1/−2 от выбранного узла);
- HQ/руководство — стратегический срез (покраска HQ, грейды, карьерный рост);
- ключевой ограничитель: **конечный инструмент заказчика не поддерживает библиотеки**,
  поэтому продукт архитектурно построен без них.

## 2. Бизнес-задачи и продуктовый контур

| Бизнес-задача | Как закрывается |
|---|---|
| Оперативный контроль численности | блок «Структура» + «Движение»: активная/общая численность, разрезы состава, водопад движения (найм − отток ± переводы), прирост с начала года |
| Управление наймом | блок «Найм и вакансии»: открытые/закрытые вакансии, срок закрытия (time-to-fill), воронка |
| Удержание | блок «Отток и текучесть»: месячная и накопительная текучесть YTD, YoY, regret (нежелательный отток) с KPI, причины увольнений |
| Развитие и карьера | блок «T-рост»: конверсия, прошли/отказано по заявкам на повышение |
| Эффективность и риски | блок «Мониторинг работы»: низкопроизводительные, недоработка |
| Использование площадей | блок «Посещаемость офисов»: календарь, рейтинг офисов, динамика |
| Быстрая диагностика «что изменилось» | OnePager + «Пульс команды»: 19 метрик, MoM/YoY, спарклайны, счёт сигналов к ориентиру, главные сдвиги за год |
| Персональная настройка | выбор состава метрик, конструктор «Свой срез» состава, персональная ссылка с фильтрами |

## 3. Структура: 19 метрик в 7 блоках

| Блок | Метрики (ключ) | Тип / направление |
|---|---|---|
| 1. Структура численности | `hc_active`, `hc_total` + разрезы состава (грейд, сеньорность, пол, возраст, стаж, занятость, формат, юрлицо, стрим/специализация) | int / flat (оценка не ставится) |
| 2. Движение персонала | `hire`, `attrition`, `transfer_in`, `transfer_out`, `net_ytd` | int / flat, `net_ytd` — прирост с начала года |
| 3. Отток и текучесть | `turnover_m`, `turnover_y`, `regret` (+ разрезы: причины увольнений) | % / lower; `regret` — KPI по HQ `{green:4, red:7}` |
| 4. Найм и вакансии | `vac_open`, `vac_closed`, `time_to_fill` | int / days, lower |
| 5. T-рост | `tgrowth_pass`, `tgrowth_deny`, `tgrowth_conv` | int / %, higher |
| 6. Мониторинг работы | `low_perf`, `underwork` | % / lower |
| 7. Посещаемость офисов | `office_att` | % / higher |

**Разрезы состава — не метрики:** не попадают в список метрик, не выбираются в модалке
и не сравниваются с базой. Пользователь может собрать срез по нескольким категориям
сразу и матрицу «строки × колонки» из любых двух атрибутов.

## 4. Ключевые продуктовые правила (бизнес-логика)

1. **База сравнения выводится из фильтров, а не из подразделения.** Отчёт сравнивает
   «свою команду» с согласованным периметром (вся компания / всё HQ / всё HQ IT / …),
   а не с подразделением выше. Дрилл вглубь дерева базу не меняет — это честная
   методология сравнения.
2. **Есть утверждённый KPI — сравнение только с ним.** Цель отменяет сравнение со
   средней, а не дополняет его. Держится единообразно в карточках, таблицах,
   спарклайнах и на графиках. (Формулировка заказчика: «если есть конкретный KPI,
   вообще тогда неправильно сравнивать с базой»).
3. **Сравниваются только относительные метрики (8 из 19).** Счётные (численность,
   найм, вакансии в штуках) с базой не сравниваются: «212 человек против 2 968»
   — это масштаб, а не оценка. Для них в UI — пометка «не сравнивается» / контекст
   из той же метрики.
4. **Состав метрик выбирает пользователь** (пресеты: Всё · Текучесть · Найм · Минимум;
   скрытие переносится в персональную ссылку). Активная и общая численность
   (`hc_active`, `hc_total`) — заблокированы, выключить нельзя.
5. **Светофор — только зелёный/красный, без жёлтого.** «На уровне» красится серым,
   чтобы жёлтая пилюля не притягивала внимание там, где вмешиваться не нужно.
6. **Изменение подписано месяцем и знаком, а не стрелкой:** «+3 к маю»; знак =
   направление, цвет/класс = оценка. Два ориентира рядом (MoM и YoY) не путаются.

## 5. Персонализация и доставка

- **4 управляющих фильтра:** подразделение (unit) · покраска (HQ/Line/Support) ·
  IT-разрез · тип занятости (штат/не штат).
- **Срез состава по клику:** клик по строке разбивки пересчитывает карточки, сводную
  таблицу и соседние разбивки; не протекает в другие блоки.
- **Персональная ссылка:** сохраняет фильтры, активный раздел, срез состава, оси
  конструктора и скрытые метрики.
- **Способы просмотра:** локальный HTTP-сервер для разработки; автономный
  self-contained файл для заказчика (без единой внешней ссылки, шрифт деградирует
  до Helvetica/Arial); GitHub Pages как короткая точка входа.
- **Адаптив:** планшет/телефон, клавиатурная навигация, печатная версия, onboarding
  «Как читать отчёт» при первом входе.

## 6. Модель данных и источники (перспектива прода)

Прототип использует мок-данные (детерминированный генератор на seed), но документация
`SOURCES.md` задаёт целевую архитектуру:

- **Разделение ролей:** Greenplum владеет определениями и гранулярностью, ClickHouse —
  агрегацией под фильтры. **Ни один процент не приезжает из GP готовым** — только
  парой «числитель + знаменатель» (Правило 2), иначе группировки по подразделениям и
  фильтрам «врут» тем сильнее, чем больше разница в размерах.
- **Витрины по гранулярности, а не по экранам** (5 фактов + 2 справочника):
  `f_person_month` (опора: численность, лоу-перф, недоработка), `f_person_event`
  (найм, отток, переводы, T-рост), `f_vacancy_month`, `f_attendance_day/month`,
  справочники `d_unit` (материализованный путь) и `d_attr`.
- **Ключевое наблюдение по объёму:** потоки дёшевы (≈3–5% от H в месяц), запасы дороги
  (слепок ≈ H), подневная посещаемость — единственное сознательное ограничение
  (скользящее окно 90 дней, только фильтрующий атрибут `employment`).
- **`person_id` в кубе численности не едет** — это одновременно сжатие данных и
  снятие половины вопросов ИБ.
- **API:** 7 эндпоинтов (`/series`, `/units`, `/mix`, `/matrix`, `/reasons`,
  `/attendance`, `/meta`); `data.js` на проде становится адаптером.

## 7. Бизнес-ценность и сценарии использования

1. **«Что у меня изменилось» за минуту:** OnePager + Пульс команды отвечают на вопрос
   без перехода в детали (счёт сигналов, три главных сдвига, MoM/YoY, месяц назван).
2. **Сопоставимость:** согласованная база из фильтров и KPI вместо разрозненных
   сравнений — руководитель не выбирает, «с чем сравнивать», ответ заложен.
3. **Управление наймом и удержанием:** прозрачная воронка вакансий, срок закрытия,
   разбор оттока по инициатору/причинам/стажу, контроль нежелательного оттока (regret).
4. **Развитие и карьера:** конверсия T-роста как индикатор эффективности внутреннего
   карьерного трека (инструмент удержания).
5. **Работа с рисками:** низкопроизводительные и недоработка — ранний сигнал выгорания
   и перегрузки.
6. **Эффективность площадей:** посещаемость и календарь бронирования — основа для
   оптимизации офисов.
7. **Масштабируемость продукта:** `data.js` → адаптер на проде; дизайн-система
   (`DESIGN_SYSTEM.md`) переиспользуема для следующих отчётов.

## 8. Текущее состояние и качество

- **Прототип собран:** 17 экранов (7 блоков + детальные вкладки + OnePager).
- **Автоматическая проверка:** `smoke.js` — прогон всех экранов и **167 проверок правил**
  без браузера (ось от нуля, формула текучести, сходимость разбивок и матриц,
  светофор, выравнивание, ссылки и т.д.). Хотя бы один FAIL — работа не сдана.
- **Проверено в Chromium** на 1440/1280/900/420 px (нет горизонтального скролла,
  сценарии кликов отработаны).
- **Журнал:** 27 итераций приёмок, включая финальный акцент-кобальт `#245FD4`.
- **Осталось:** визуальная приёмка в браузере и правки по замечаниям; решение по
  правилу «ось всегда от нуля» (шкала линий по данным — противоречит текущему правилу).

## 10. Выводы и рекомендации

**Сильные стороны:**
- архитектурно вынужденно (без библиотек) и потому крайне переносимо; сдача одним файлом;
- честная методология сравнения (база из фильтров, KPI вместо базы, сравнимы только
  относительные метрики) — снижает риск неправильной интерпретации цифр;
- автоматическая проверка 167 правил — низкая цена регрессий;
- глубокая персонализация (состав метрик, срез, конструктор, персональная ссылка);
- целевая архитектура источников уже продумана до витрин и API — прототип не «выброс».

**Точки роста / риски:**
- **данные моковые** — решения по метрикам нельзя принимать по абсолютным числам, пока
  не подключены реальные источники (это явно зафиксировано);
- **первый экран долго был «без ответа»** — частично закрыт Пульсом команды и героями;
  счётные метрики по-прежнему без оценки;
- **длинный скролл OnePager** — мини-навигация добавлена, но 7 таблиц подряд всё ещё
  требуют ориентиров;
- **открыто правило шкалы** («ось всегда от нуля» vs шкала по данным) — нужен выбор
  заказчика;
- визуальная приёмка в браузере и финальная выверка перед сдачей ещё не завершены.

**Рекомендации:**
1. Приоритет — подключение реальных данных по роудмапу `SOURCES.md`, начиная с
   оргдерева и куба численности; верифицировать метрики на реальных числах.
2. Принять решение по правилу шкалы линий (ось от нуля vs подбор по данным) — оно
   влияет на читаемость конверсии T-роста и посещаемости.
3. Добавить первые 4 производные метрики (run-rate, коэффициент замещения, найм/отток
   на 100 чел., доля внутреннего найма) — дёшево и повышают сравнимость счётных метрик.
4. Учесть рекомендации `REVIEW_2.0` по читаемости (линия для счётных спарклайнов,
   приглушение пустых подразделений).
5. Перед сдачей — полная визуальная приёмка в браузере и проверка автономного файла
   (без интернета, шрифт деградирует корректно).
