# Входные данные TeamPulse Hub — в каком виде отдавать

Для владельца витрины `prod_proteus.hr_structure_overall` и для модели, которая строит по ней срезы.
Состояние на 16.10.2026: схема 49 колонок, ответ 0д (первый заход).

Датасет пробника (файл 2) — виртуальный: Jinja + один запрос ClickHouse на каждое открытие
отчёта и каждую смену юнита или фильтра. Всё, чего нет в таблице в готовом виде, он
восстанавливает сам — дерево, нынешнюю структуру, склейку копий. Это стоит времени запроса,
строк SQL и точности. Ниже — что именно восстанавливается сейчас и в каком виде данные
снимают эту работу.

Как при этом раскладывать физические таблицы и что это даёт в цифрах (с SQL сборки) —
`Предложения — физическая таблица под датасет.md`. Готовая копия ноутбука TP 2.0 под отчёт, где
всё это уже сделано, — `1. Helicopter — ноут TeamPulse Hub.yaml`, датасет на ней — `2а`.

## Главное — 8 правил

1. **Строка — люди своего юнита.** Месяц × юнит, где человек числится, × атрибуты человека.
   Без накопления по поддереву: итог узла собирается суммой. Так таблица устроена уже сейчас
   (ответ 0д) — нужно закрепить это в описании витрины, чтобы смысл не поменялся молча.
2. **Путь — ключами, а не именами.** `lvl1_rk … lvl11_rk` рядом с `lvl1_nm … lvl11_nm`.
   Имена повторяются и меняются, ключи — нет.
3. **Путь — в нынешней структуре.** Отдельно от «как было в том месяце» — путь последнего
   закрытого месяца для всех месяцев истории: `cur_lvl1_rk … cur_lvl11_rk`. Тогда ряды
   команды за два года сравнимы, даже если её переносили.
4. **Без копий строк.** Юнит с двумя родителями — один основной путь. Если второй нужен —
   отдельной колонкой-признаком, а не второй строкой с теми же людьми.
5. **Справочник юнитов отдельно.** Месяц × юнит: ключ, родитель, уровень, имя, руководитель.
   Дерево перестаёт зависеть от того, есть ли у уровня свои люди.
6. **Переводы — с обеих сторон.** Юнит «откуда» и юнит «куда» в одной записи. Иначе на
   верхних уровнях переходы между своими же подразделениями считаются как приход и уход.
7. **Значения без NULL и с договорённостью.** Атрибуты — `String` с явным «Не указано», меры —
   `UInt32` / `Float64` с нулём. Список значений каждого атрибута — фиксированный справочник.
8. **Закрытый месяц — признаком.** `is_closed` (или дата закрытия), а не догадка «последний
   месяц в таблице, если он не текущий календарный».

## Что датасет делает сейчас и что убирает каждое правило

| Сейчас в таблице | Что делает датасет | Чем плохо | Правило |
|---|---|---|---|
| Путь — только имена уровней | Склеивает имена в строку, ключ узла — md5 пути | Два юнита с одним именем под одним родителем сливаются (в 0д — 2 общих пути); переименование уровня рвёт ряд | 2 |
| Путь — на месяц строки | Ищет путь каждого юнита в последнем месяце и переносит на него всю историю | Закрытый юнит, у которого переименовали родителя, теряет историю на этом уровне | 3 |
| Юнит с двумя путями — две строки | Отбирает строки меньшего пути юнита в каждом месяце (подзапрос по всей таблице) | Лишний проход по таблице на каждый запрос; до поставки 25 — склейка по ключу атрибутов, где забытая колонка занижала численность | 4 |
| Дерева нет, только пути | Строит узлы из всех начал путей последнего месяца | Уровень без своих людей появляется только через детей; уровень, где все ушли, исчезает из выбора | 5 |
| Переводы — числа у юнита | Складывает `transfer_in` / `transfer_out` по ветке | «Перевели в ветку» и «перевели из ветки» завышены; верно только сальдо | 6 |
| Всё `Nullable` | `ifNull` на каждой колонке; скалярные подзапросы оборачиваются, чтобы не уронить функции массивов | Лишний код и ошибки анализатора (`Nested type Array(String) cannot be inside Nullable`) | 7 |
| Нет признака закрытого месяца | Сравнивает последний месяц с `today()` | Месяц, закрытый задним числом, или пустой текущий месяц ломают окно отчёта | 8 |

## Схема, к которой стоит прийти

### Вариант А — минимальные правки нынешней таблицы

Добавить колонки, ничего не удаляя. Датасет упрощается сразу: узел — один ключ на своём
уровне, ветка — фильтр `cur_lvl{d}_rk = :unit`, подразделения под ней — `GROUP BY
cur_lvl{d+1}_rk`.

```sql
-- добавить к prod_proteus.hr_structure_overall
lvl1_rk … lvl11_rk           String,   -- ключи пути на месяц строки ('' ниже leaf_lvl)
cur_lvl1_rk … cur_lvl11_rk   String,   -- ключи пути в структуре последнего закрытого месяца
cur_leaf_lvl                 UInt8,    -- глубина юнита в нынешней структуре
is_closed                    UInt8,    -- 1 — месяц закрыт, его можно показывать
-- договорённости
--   строк-копий нет: юнит с двумя родителями — один путь;
--   NULL нет: атрибут без значения — 'Не указано', мера без значения — 0;
--   fire_reason_group / fire_initiative заполнены только там, где fire_amt > 0;
--   ORDER BY (report_month, cur_lvl1_rk, cur_lvl2_rk, cur_lvl3_rk, …) — фильтр по ветке
--   читает только её гранулы.
```

### Вариант Б — три таблицы (если витрину пересобирают)

```sql
-- 1. Юниты: дерево и подписи, месяц × юнит
hr_unit (
    report_month     Date,
    unit_rk          String,
    parent_unit_rk   String,          -- '' у корня
    unit_lvl         UInt8,
    unit_nm          String,
    path_rk          Array(String),   -- ключи от корня до юнита
    cur_unit_rk      String,          -- в какой юнит последнего месяца он вошёл (реорганизация)
    head_login       String,          -- руководитель: колонка «Руководитель» в таблицах
    head_fio         String,
    is_closed        UInt8
)

-- 2. Факты: люди своего юнита, месяц × юнит × атрибуты — нынешние меры без изменений
hr_fact (
    report_month                    Date,
    unit_rk                         String,
    gender, type_age, experience_group_nm, grade, seniority,
    employee_contract_type, legal_organization, employee_stream,
    employment_relation_type, employment_relation_type_gr_nm,
    active_type_gr_nm, emp_specialization_it_code,
    fire_reason_group, fire_initiative                     LowCardinality(String),
    hc_total_cnt, hc_active_cnt, lag_hc_active_cnt,
    hire_amt, fire_amt, regret_fire_amt                   UInt32,
    ssch_hc_active_cnt, perf_normal, perf_low, perf_high, perf_gray,
    work_day_amt, office_visit_amt                        Float64,
    grt_approve_cnt, grt_decline_cnt, grt_cancel_cnt, grt_inprogress_cnt UInt32
)

-- 3. Переводы: откуда и куда в одной записи
hr_transfer (
    report_month     Date,
    from_unit_rk     String,
    to_unit_rk       String,
    gender, type_age, experience_group_nm, grade, seniority, employee_stream  LowCardinality(String),
    transfer_cnt     UInt32
)
```

С таблицей переводов «пришли в ветку X» — записи, где `to` в X, а `from` — нет. Переходы
внутри ветки в этот счёт не попадают.

Если Proteus работает только с одной таблицей на датасет — вариант А. Если датасет может
читать несколько таблиц (JOIN в виртуальном датасете разрешён) — вариант Б: справочник юнитов
маленький, факт не дублирует путь в каждой строке.

## Меры: что можно складывать

| Мера | По юнитам | По месяцам | Как показывать |
|---|---|---|---|
| `hc_total_cnt`, `hc_active_cnt` | да | нет — на конец месяца | значение месяца |
| `ssch_hc_active_cnt` | да, если считана по узлу или по людям | да — для текучести за период | знаменатель текучести; LAG по сочетаниям атрибутов (как в TP 2.0) не годится — датасет считает ССЧ из ряда узла сам |
| `hire_amt`, `fire_amt`, `regret_fire_amt` | да | да | числитель |
| `transfer_in_amt`, `transfer_out_amt` | только сальдо (см. правило 6) | да | числитель |
| `perf_*` | да | да | доля категории от суммы четырёх |
| `work_day_amt`, `office_visit_amt` | да | да | посещаемость = посещения / дни |
| `grt_*` | да | да | конверсия = одобрено / (одобрено + отклонено) |

Процентов и долей в таблице быть не должно: доля не складывается по юнитам. Только числитель
и знаменатель — делит чарт.

## Что подтвердить у владельца витрины

- Строка — люди своего юнита (ответ 0д: верхний юнит — 3 человека, у 2 705 из 3 095 юнитов
  дети больше родителя). Нужна строчка в описании витрины.
- Сколько корней на уровне 1 и что в них: если корней несколько, «вся компания» — один корень
  или все строки (второй заход 0д это покажет).
- Два ключа с одним путём (в 0д — 2): это один юнит под двумя ключами или два разных.
- Как считаются переводы внутри ветки и можно ли отдать юнит «откуда» / «куда».
- Значения `employment_relation_type_gr_nm` и `active_type_gr_nm`: полный список и смысл.
- `employee_contract_type` — это формат работы (гибрид / офис / удалённо), не тип договора:
  в чарте он подписан «Формат работы».

## Как проверить, что данные отданы правильно

Те же запросы, что в файлах 0д и 5, на новой схеме должны давать:

1. Сумма `hc_total_cnt` всех строк месяца = численность компании из HR-отчётности.
2. Для любого юнита: сумма строк его ветки (`cur_lvl{d}_rk = юнит`) = его численность в
   оргструктуре.
3. Строк с одинаковыми «месяц × юнит × атрибуты» — ноль (нет копий).
4. `countIf(lvl{leaf_lvl}_rk != mng_unit_rk) = 0` — путь кончается самим юнитом.
5. `countIf(isNull(…))` по каждой колонке = 0.
6. Сумма `transfer_cnt` по всей компании в `hr_transfer` = сумма `transfer_in_amt` = сумма
   `transfer_out_amt` (каждый перевод — один раз с каждой стороны).
