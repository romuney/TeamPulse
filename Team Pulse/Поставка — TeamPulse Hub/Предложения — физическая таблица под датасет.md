# Предложения: физическая таблица под виртуальный датасет

Для владельца витрины `prod_proteus.hr_structure_overall` и инженера данных. Как собирать физику,
чтобы виртуальный датасет TeamPulse Hub (файл 2) был коротким и быстрым. Дополняет
`Входные данные — формат для датасета.md`: там — что отдавать и что значит строка, здесь — как
раскладывать таблицы, с замерами. Всё проверено на стенде, SQL сборки — в приложении.

## Коротко

- **Сейчас датасет на каждое открытие отчёта, смену юнита или фильтра заново строит из 2,5 млн
  строк то, что меняется раз в месяц**: календарь, дерево юнитов, нынешние пути, склейку копий.
  ClickHouse не запоминает результаты `WITH`: каждое обращение к ним — новое чтение. В плане
  запроса большая таблица читается **55 раз**.
- **Предложение — три таблицы рядом с нынешней**: календарь с признаком закрытого месяца,
  справочник узлов нынешней структуры и свёртка по узлам (плюс две промежуточные). Собираются раз
  в месяц одним SQL **из нынешней таблицы** — источник витрины менять не нужно.
- **На стенде в масштабе боя** ответ тот же байт в байт, запрос быстрее в 5–16 раз, разбор SQL
  в Superset при холодном открытии — 1,7 с вместо 2,8 с, текст запроса короче на треть. Файл 3
  (чарт) не меняется: формат ответа тот же.

## Замеры

Стенд: 2,43 млн строк, 81 тыс. в месяц (в бою — 2,56 млн и ~75 тыс.), 800 юнитов и 6 уровней (в
бою — 11,5 тыс. и 11). ClickHouse 24.8 (chdb), 4 ядра, лучшая из двух попыток, настройки боя
(новый анализатор, `prefer_column_name_to_alias = 1`). Дерево в бою больше, чем на стенде, —
выигрыш там скорее больше: эту часть нынешний датасет строит из большой таблицы.

| | Сейчас | А — факт с путём ключами | Б — свёртка по узлам |
|---|---|---|---|
| Компания, без фильтров | 11,4 с | 2,8 с | **1,2 с** |
| Фильтр IT | 7,2 с | 1,4 с | **1,2 с** |
| Фильтр «штат» | 8,5 с | 2,0 с | **1,4 с** |
| Юнит третьего уровня | 9,8 с | 0,85 с | **0,6 с** |
| IT + штат | 6,4 с | 1,2 с | 1,25 с |
| IT + штат, старый анализатор | 23,3 с | 3,4 с | 3,6 с |
| Чтений таблиц в плане | 55 — большая таблица | 3 — факт, 22 — справочник | 3 — свёртка, 22 — справочник |
| SQL после Jinja | 17,2 тыс. знаков | 11,6 тыс. | 11,6 тыс. |
| Разбор SQL в Superset, холодное открытие | 2,8 с | — | 1,7 с |
| Ответ против нынешнего | — | тот же байт в байт | тот же байт в байт |

Ответ сверен в пяти случаях (компания, IT, штат, юнит уровнем ниже, IT + штат) при настройках
боя, а случай «IT + штат» — ещё и при шести настройках сервера ClickHouse. Строк: факт без
копий — 2,42 млн (как сейчас), свёртка — 6,7 млн (в 2,75 раза больше: средняя глубина пути на
стенде 4,7, верхние уровни схлопывают одинаковые сочетания атрибутов), справочник — 802,
календарь — 34. Сборка на стенде: факт 13 с, свёртка 18 с.
**В бою свёртка — оценочно 12–22 млн строк** (средняя глубина 8,8 по ответу `0д`): для ClickHouse
немного, а запрос читает из неё только узлы ответа.

## Почему сейчас медленно

На каждый запрос датасет делает шесть шагов, результат которых меняется раз в месяц:

1. **Календарь** — `max(report_month)` по всей таблице и догадка через `today()`.
2. **Нынешний путь каждого юнита** — строки последнего месяца, склейка 11 колонок имён в путь.
3. **Дерево** — все начала путей, родитель, уровень, число подразделений.
4. **Склейка копий** — `GROUP BY` по 16 строковым колонкам за 21 месяц (~1,7 млн строк).
5. **История в нынешней структуре** — `JOIN` строк с нынешними путями юнитов.
6. **Раскладка строк по узлам ответа** — `ARRAY JOIN` начал пути с фильтром по глубине.

`WITH` в ClickHouse — подстановка текста, не временная таблица: шаги 1–3 выполняются заново при
каждом обращении к ним, отсюда 55 чтений. Плюс обвязка `ifNull` на каждой колонке: все колонки
`Nullable`, а скалярный подзапрос из них ломает функции массивов (`Nested type Array(String) cannot
be inside Nullable` — в поставке 23 пришлось обходить).

## Предложения

Порядок — по выигрышу. Каждое можно делать отдельно, 1–3 вместе дают вариант Б из замеров.

### 1. Календарь с признаком закрытого месяца

`hr_calendar (report_month Date, is_closed UInt8)` — 34 строки.
- **Датасету:** окно отчёта — из маленькой таблицы, без `today()`. Месяц, закрытый задним числом
  или открытый заново, — просто признак, отчёт не гадает.
- **Цена:** строка при закрытии месяца.

### 2. Справочник узлов нынешней структуры

`hr_unit (rk, prk, lv, nm, path)` — все узлы, в том числе уровни без своих людей (корень,
промежуточные звенья); `path` — ключи от корня до узла. Желательно — руководитель (логин, ФИО).
- **Датасету:** дерево, выбор юнита, путь от корня, «ниже ещё N» — из ~12 тыс. строк вместо
  2,5 млн. 22 из 25 чтений плана — по нему. С руководителем колонка «Руководитель» в таблицах
  подразделений станет живой.
- **Цена:** ~12 тыс. строк, раз в месяц.

### 3. Свёртка по узлам (вариант Б)

`hr_fact_node` — узел нынешней структуры × месяц × атрибуты; строка узла несёт всё его поддерево.
`ORDER BY (node_rk, report_month)`.
- **Датасету:** читает только узлы ответа — выбранный юнит, базу и три уровня под ним — по
  первичному ключу. Склейка копий, пути, история в нынешней структуре, раскладка по узлам —
  уходят из запроса целиком. Самый быстрый вариант: время растёт с числом сочетаний атрибутов
  в узлах ответа, а не с размером всей таблицы.
- **Цена:** строк больше, чем в факте: на стенде в 2,75 раза, в бою оценочно в 5–9 раз.
  Пересобирать целиком раз в месяц: меняется структура — меняется и свёртка всей истории. На
  стенде — 18 секунд.
- По сути это возврат к накопительной таблице 08.10, но собранной по нынешней структуре и без
  копий путей — то, что сейчас датасет делает на лету.

### 4. Если свёртка не подходит — факт с путём ключами (вариант А)

`hr_fact` — без копий путей, без NULL, путь строки — ключи узлов нынешней структуры
(`cur_path Array(String)`). Того же размера, что нынешняя таблица; он же — шаг сборки свёртки.
- **Датасету:** строка раскладывается по узлам ответа одним `arrayFilter` по её пути. В 4–12 раз
  быстрее нынешнего, но время растёт с размером компании: читается весь период.
- **Цена:** пересборка раз в месяц, 13 секунд на стенде.

### 5. Типы без NULL

Атрибуты — `LowCardinality(String)`, месяц — `Date`, меры — числа; пустое — договорённое
значение (`''` или «Не указано», у IT-кода — `-`).
- **Датасету:** ни одного `ifNull`, нет ловушки `Nullable` в скалярных подзапросах и массивах,
  `GROUP BY` по атрибутам быстрее.

### 6. Ключ узла — ключ юнита, а не имена

Сейчас узел — md5 пути имён: другого ключа уровня в таблице нет. Имя переименовали — ряд рвётся,
ссылка на юнит (кросс-фильтр `unit_f`) перестаёт работать; две команды с одним именем под одним
родителем сливаются в одну (в `0д` — 2 таких пути). С ключами уровней (`lvl1_rk … lvl11_rk`,
«Входные данные», правило 2) `rk` узла — ключ юнита, а SQL сборки не меняется: вместо md5 имён —
ключ.

### 7. Переводы «откуда — куда» и чистые переводы в свёртке

С таблицей переводов (`from_unit_rk`, `to_unit_rk`, «Входные данные», правило 6) свёртка сразу
кладёт в узел X только переводы через его границу: «пришли» — `to` в X, `from` не в X. Оговорка
отчёта «на верхних уровнях в и из завышены» уходит, датасет об этом не знает.

### 8. Стабильный контракт — представление с версией

Датасет читает представление `…_v1` с зафиксированными колонками и смыслом строки; перестройки
витрины — за ним. Новый смысл — `…_v2` рядом, старое живёт до переключения отчёта. За неделю схема
менялась трижды (12.10, 15.10, 16.10), и один раз смысл строки поменялся без смены колонок
(накопительная → люди своего юнита) — отчёт узнал об этом только из `0д`.

### 9. Проверки при сборке

После пересборки — пять запросов, ответ каждого — одно число:
- строк с одинаковым «узел × месяц × атрибуты» в свёртке — 0;
- свёртка корня = сумма факта по месяцу (по каждой мере);
- узел = сумма своих строк и детей (выборочно, по уровням);
- узлов без родителя, кроме корня, — 0; корней — 1 (или договорённость, что «вся компания»);
- `NULL` — 0 по каждой колонке.

### Чего делать не нужно

- **Партиции** — таблицы маленькие; `ORDER BY` достаточно.
- **Материализованные представления** «на вставку» — свёртка по нынешней структуре пересчитывает
  всю историю при каждом изменении дерева, инкрементально её не собрать.
- **Проекции и skip-индексы** на нынешней таблице — узкое место не в чтении, а в том, что
  запрос строит дерево и склейку заново.

## Что станет с датасетом

- **Уходят:** нынешние пути юнитов (`lmr`), дерево из путей, склейка копий (`b00`), история в
  нынешней структуре (`b01`), раскладка по узлам и глубины (`b0`, `dep`), обвязка `ifNull`,
  календарь через `today()`.
- **Остаются:** фильтры Jinja, узлы ответа (`pick`), ряды по месяцам, разрезы `mx`, служебные
  строки `meta`, `dict`, `end`. Формат ответа тот же — чарт (файл 3) не меняется.
- Строки по узлам ответа в варианте Б — весь «тяжёлый» шаг:

## Как перейти, не останавливая отчёт

1. Владелец витрины собирает таблицы рядом с нынешней (SQL ниже) — в той же базе CROSS, с правом
   чтения для датасета — и ставит пересборку после закрытия месяца.
2. Мы отдаём файл 2 под новые таблицы — вариант Б готов и сверен на стенде — и запрос для SQL Lab:
   ответы старого и нового датасета совпадают.
3. Файл 2 заменяется → Save. Нынешняя таблица остаётся источником, откатиться — вернуть файл 2.

Повторить замер: `python3 stand/bench_layout.py <hso.csv из stand/sim_hso.py> <папка>` — строит
стенд в масштабе боя, собирает таблицы SQL-ем из приложения ниже (как есть) и сверяет ответы.

## Приложение: SQL сборки (ClickHouse 24.8)

```sql
-- Собирается из нынешней prod_proteus.hr_structure_overall целиком, по порядку 1 → 5.
-- Пересобирать раз в месяц после закрытия месяца (и при правках структуры): DROP + CREATE
-- или новые таблицы рядом и EXCHANGE TABLES. Колонки при CREATE … AS SELECT встают
-- по позиции — псевдонимы нарочно не совпадают с именами колонок источника.

-- 1. Календарь: месяц и признак «закрыт». Здесь — по нынешнему правилу датасета («текущий
--    календарный месяц не закрыт»). В витрине его лучше ставить при закрытии месяца
CREATE TABLE prod_proteus.hr_calendar (report_month Date, is_closed UInt8)
ENGINE = MergeTree ORDER BY report_month AS
SELECT DISTINCT toDate(assumeNotNull(report_month)) AS m0,
       toUInt8(assumeNotNull(report_month) < toStartOfMonth(today())) AS c0
FROM prod_proteus.hr_structure_overall;

-- 2. Путь каждого юнита в последнем закрытом месяце (служебная, из двух путей — меньший)
CREATE TABLE prod_proteus.hr_unit_path (unit_rk String, path_nm String)
ENGINE = MergeTree ORDER BY unit_rk AS
SELECT ifNull(mng_unit_rk, '') AS u0,
       min(arrayStringConcat(arraySlice(arrayMap(x -> translate(ifNull(x, ''), '\t\n', '  '),
           [lvl1_nm, lvl2_nm, lvl3_nm, lvl4_nm, lvl5_nm, lvl6_nm, lvl7_nm, lvl8_nm, lvl9_nm, lvl10_nm, lvl11_nm]),
           1, toInt32(ifNull(leaf_lvl, 0))), '\t')) AS p0
FROM prod_proteus.hr_structure_overall
WHERE report_month = (SELECT max(report_month) FROM prod_proteus.hr_calendar WHERE is_closed = 1)
  AND mng_unit_rk IS NOT NULL AND ifNull(leaf_lvl, 0) > 0
GROUP BY u0;

-- 3. Справочник узлов нынешней структуры — все начала путей, в том числе уровни без своих
--    людей. rk — ключ узла (здесь 12 знаков md5 пути имён, как в датасете, появятся ключи
--    уровней — брать их), prk — родитель, lv — уровень, nm — имя, path — ключи от корня до узла
CREATE TABLE prod_proteus.hr_unit (rk String, prk String, lv Int32, nm String, path Array(String))
ENGINE = MergeTree ORDER BY rk AS
SELECT DISTINCT lower(hex(substring(MD5(p), 1, 6))) AS k0,
       if(d = 1, '', lower(hex(substring(MD5(pp), 1, 6)))) AS k1,
       toInt32(d) AS k2, a[d] AS k3,
       arrayMap(j -> lower(hex(substring(MD5(arrayStringConcat(arraySlice(a, 1, j), '\t')), 1, 6))), range(1, d + 1)) AS k4
FROM (SELECT splitByChar('\t', path_nm) AS a FROM prod_proteus.hr_unit_path WHERE path_nm != '')
ARRAY JOIN arrayEnumerate(a) AS d
ARRAY JOIN [arrayStringConcat(arraySlice(a, 1, d), '\t')] AS p
ARRAY JOIN [arrayStringConcat(arraySlice(a, 1, d - 1), '\t')] AS pp;

-- 4. Факт: копии путей — один раз (max по ключу «месяц × юнит × атрибуты»), NULL нет,
--    путь строки — ключи узлов нынешней структуры (cur_path). Юнита в последнем месяце
--    нет — его путь из самой строки
CREATE TABLE prod_proteus.hr_fact
(
    report_month Date,
    gender LowCardinality(String), type_age LowCardinality(String),
    experience_group_nm LowCardinality(String), grade LowCardinality(String),
    seniority LowCardinality(String), employee_contract_type LowCardinality(String),
    legal_organization LowCardinality(String), employee_stream LowCardinality(String),
    employment_relation_type LowCardinality(String), employment_relation_type_gr_nm LowCardinality(String),
    active_type_gr_nm LowCardinality(String), emp_specialization_it_code LowCardinality(String),
    fire_reason_group LowCardinality(String), fire_initiative LowCardinality(String),
    hc_total_cnt Float64, hc_active_cnt Float64, ssch_hc_active_cnt Float64, hire_amt Float64,
    fire_amt Float64, regret_fire_amt Float64, transfer_in_amt Float64, transfer_out_amt Float64,
    perf_normal Float64, perf_low Float64, perf_high Float64, perf_gray Float64, work_day_amt Float64,
    office_visit_amt Float64, grt_approve_cnt Float64, grt_decline_cnt Float64,
    cur_path Array(String)
)
ENGINE = MergeTree ORDER BY report_month AS
SELECT m1,
       x_gender, x_type_age, x_experience_group_nm, x_grade, x_seniority, x_employee_contract_type,
       x_legal_organization, x_employee_stream, x_employment_relation_type, x_employment_relation_type_gr_nm,
       x_active_type_gr_nm, x_emp_specialization_it_code, x_fire_reason_group, x_fire_initiative,
       v_hc_total_cnt, v_hc_active_cnt, v_ssch_hc_active_cnt, v_hire_amt, v_fire_amt, v_regret_fire_amt,
       v_transfer_in_amt, v_transfer_out_amt, v_perf_normal, v_perf_low, v_perf_high, v_perf_gray,
       v_work_day_amt, v_office_visit_amt, v_grt_approve_cnt, v_grt_decline_cnt,
       arrayMap(j -> lower(hex(substring(MD5(arrayStringConcat(arraySlice(splitByChar('\t', cp), 1, j), '\t')), 1, 6))),
                range(1, length(splitByChar('\t', cp)) + 1)) AS cur_path0
FROM
(
  SELECT b.*, if(ifNull(t.path_nm, '') != '', t.path_nm, b.pr) AS cp
  FROM
  (
    SELECT toDate(assumeNotNull(report_month)) AS m1, ifNull(mng_unit_rk, '') AS u1,
           translate(ifNull(gender, ''), '\t\n|', '  /') AS x_gender,
           translate(ifNull(type_age, ''), '\t\n|', '  /') AS x_type_age,
           translate(ifNull(experience_group_nm, ''), '\t\n|', '  /') AS x_experience_group_nm,
           translate(ifNull(grade, ''), '\t\n|', '  /') AS x_grade,
           translate(ifNull(seniority, ''), '\t\n|', '  /') AS x_seniority,
           translate(ifNull(employee_contract_type, ''), '\t\n|', '  /') AS x_employee_contract_type,
           translate(ifNull(legal_organization, ''), '\t\n|', '  /') AS x_legal_organization,
           translate(ifNull(employee_stream, ''), '\t\n|', '  /') AS x_employee_stream,
           translate(ifNull(employment_relation_type, ''), '\t\n|', '  /') AS x_employment_relation_type,
           translate(ifNull(employment_relation_type_gr_nm, ''), '\t\n|', '  /') AS x_employment_relation_type_gr_nm,
           translate(ifNull(active_type_gr_nm, ''), '\t\n|', '  /') AS x_active_type_gr_nm,
           if(emp_specialization_it_code IS NULL, '-', translate(emp_specialization_it_code, '\t\n|', '  /')) AS x_emp_specialization_it_code,
           translate(ifNull(fire_reason_group, ''), '\t\n|', '  /') AS x_fire_reason_group,
           translate(ifNull(fire_initiative, ''), '\t\n|', '  /') AS x_fire_initiative,
           min(arrayStringConcat(arraySlice(arrayMap(x -> translate(ifNull(x, ''), '\t\n', '  '),
               [lvl1_nm, lvl2_nm, lvl3_nm, lvl4_nm, lvl5_nm, lvl6_nm, lvl7_nm, lvl8_nm, lvl9_nm, lvl10_nm, lvl11_nm]),
               1, toInt32(ifNull(leaf_lvl, 0))), '\t')) AS pr,
           max(toFloat64(ifNull(hc_total_cnt, 0))) AS v_hc_total_cnt,
           max(toFloat64(ifNull(hc_active_cnt, 0))) AS v_hc_active_cnt,
           max(ifNull(ssch_hc_active_cnt, 0)) AS v_ssch_hc_active_cnt,
           max(toFloat64(ifNull(hire_amt, 0))) AS v_hire_amt,
           max(toFloat64(ifNull(fire_amt, 0))) AS v_fire_amt,
           max(toFloat64(ifNull(regret_fire_amt, 0))) AS v_regret_fire_amt,
           max(toFloat64(ifNull(transfer_in_amt, 0))) AS v_transfer_in_amt,
           max(toFloat64(ifNull(transfer_out_amt, 0))) AS v_transfer_out_amt,
           max(ifNull(perf_normal, 0)) AS v_perf_normal,
           max(ifNull(perf_low, 0)) AS v_perf_low,
           max(ifNull(perf_high, 0)) AS v_perf_high,
           max(ifNull(perf_gray, 0)) AS v_perf_gray,
           max(ifNull(work_day_amt, 0)) AS v_work_day_amt,
           max(ifNull(office_visit_amt, 0)) AS v_office_visit_amt,
           max(toFloat64(ifNull(grt_approve_cnt, 0))) AS v_grt_approve_cnt,
           max(toFloat64(ifNull(grt_decline_cnt, 0))) AS v_grt_decline_cnt
    FROM prod_proteus.hr_structure_overall
    GROUP BY m1, u1, x_gender, x_type_age, x_experience_group_nm, x_grade, x_seniority, x_employee_contract_type, x_legal_organization, x_employee_stream, x_employment_relation_type, x_employment_relation_type_gr_nm, x_active_type_gr_nm, x_emp_specialization_it_code, x_fire_reason_group, x_fire_initiative
  ) AS b
  LEFT JOIN prod_proteus.hr_unit_path AS t ON t.unit_rk = b.u1
);

-- 5. Свёртка по узлам: строка узла несёт всё его поддерево (узел × месяц × атрибуты).
--    ORDER BY (node_rk, report_month) — запрос читает только узлы ответа
CREATE TABLE prod_proteus.hr_fact_node
(
    node_rk String,
    report_month Date,
    gender LowCardinality(String), type_age LowCardinality(String),
    experience_group_nm LowCardinality(String), grade LowCardinality(String),
    seniority LowCardinality(String), employee_contract_type LowCardinality(String),
    legal_organization LowCardinality(String), employee_stream LowCardinality(String),
    employment_relation_type LowCardinality(String), employment_relation_type_gr_nm LowCardinality(String),
    active_type_gr_nm LowCardinality(String), emp_specialization_it_code LowCardinality(String),
    fire_reason_group LowCardinality(String), fire_initiative LowCardinality(String),
    hc_total_cnt Float64, hc_active_cnt Float64, ssch_hc_active_cnt Float64, hire_amt Float64,
    fire_amt Float64, regret_fire_amt Float64, transfer_in_amt Float64, transfer_out_amt Float64,
    perf_normal Float64, perf_low Float64, perf_high Float64, perf_gray Float64, work_day_amt Float64,
    office_visit_amt Float64, grt_approve_cnt Float64, grt_decline_cnt Float64
)
ENGINE = MergeTree ORDER BY (node_rk, report_month) AS
SELECT n0, report_month,
       gender, type_age, experience_group_nm, grade, seniority, employee_contract_type, legal_organization,
       employee_stream, employment_relation_type, employment_relation_type_gr_nm, active_type_gr_nm,
       emp_specialization_it_code, fire_reason_group, fire_initiative,
       sum(hc_total_cnt) AS s_hc_total_cnt, sum(hc_active_cnt) AS s_hc_active_cnt,

       sum(office_visit_amt) AS s_office_visit_amt, sum(grt_approve_cnt) AS s_grt_approve_cnt,
       sum(grt_decline_cnt) AS s_grt_decline_cnt
FROM prod_proteus.hr_fact
ARRAY JOIN cur_path AS n0
GROUP BY n0, report_month, gender, type_age, experience_group_nm, grade, seniority, employee_contract_type, legal_organization, employee_stream, employment_relation_type, employment_relation_type_gr_nm, active_type_gr_nm, emp_specialization_it_code, fire_reason_group, fire_initiative;
```
