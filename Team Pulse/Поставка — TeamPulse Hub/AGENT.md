## Поставка 136 — понятность выводов, мониторинг, One Pager, посещаемость (10.11, ноутбук, датасет и чарт)

- **Одно сравнение в выводе.** Метрика изменилась к тому же периоду прошлого года на 10% и больше (относительно, в
  любую сторону) — вывод о годе; иначе — о сравнении с ориентиром (база, вся компания). У метрик с целью — всегда с
  целью. В карточке One Pager — одна метрика: её значение с периодом, одно сравнение в чипе, разница в людях.
  «Больше половины» заменено на «N из M этой разницы — в «X»». Карточки «подразделение хуже по трём метрикам» нет.

## Поставка 135 — численность одна на всех вкладках (10.11, чарт; ноутбук — справочная проверка)

- **Что было:** «Движение персонала» показывало одну численность, «Структура численности» (сумма женщин и мужчин,
  «Всего») — другую, больше.
- **Причина:** в витрине у части узлов два родителя (у людей одного подразделения цепочки идут через разных
  руководителей). Тогда строки дерева пересекаются: один человек входит в два соседних подразделения, и в сумме они
  больше узла. Численность отчёт брал у самого узла, а состав складывал по строкам дерева — с лишними людьми. Так же
  завышались разбивки, которые складываются по строкам: причины ухода, виды найма, статусы T-роста, мониторинг.
- **Что теперь:** состав и все разбивки считаются по самому узлу, как численность. Дерево и привязка людей — из
  витрины как есть, не менялись. Число людей в таблицах ноутбука то же — менялся только чарт.
- **hub checks:** № 37 (справочно) — люди, у которых один узел стоит в цепочке дважды. Не ноль — пришлите значение:
  такой человек входит в узел дважды уже в витрине, это вопрос к её владельцам.
- **Файл 5, блок 14:** у выбранного подразделения `hc` = `sostav_pol`, `d_sostav` = 0; ниже — узлы, где подразделения
  в сумме больше узла (`kids_hc` > `hc`). По ним видно, где раньше расходилась «Структура». `lishnie_v_strukture` —
  на сколько человек «Структура» старого чарта показывала больше численности у подразделения из параметра `unit`
  (приблизительно): сверьте с разницей на экране.
- **Замена:** чарт (файл 3). Ноутбук (файл 1) — по желанию: добавлена только проверка № 37. Датасет не менялся.

## Поставка 134 — человек не считается дважды ни при каких фильтрах (10.11, ноутбук и чарт)

- **Правило:** за день человек в одном подразделении даёт не больше одного входа (найм или перевод «в») и одного выхода
  (перевод «из»; в день увольнения — отток). Это теперь свойство самой таблицы переводов: ноутбук сводит строки дня в
  одну, какие бы признаки ни сменились в этот день. От набора фильтров не зависит.
- **hub checks:** № 36 (обязательная) — у человека за день в узле одна строка входа и одна выхода; № 35 (справочно) —
  сколько повторных строк пришлось свести. Если № 35 не ноль — числа верные, но пришлите значение: разберу, какие
  события источника пересеклись.
- **Отчёт:** в «Движении по специализациям» нет строки «Итого» (сумма переводов по специализациям больше переводов
  команды — в неё входит смена специализации внутри команды).
- **Замена:** ноутбук (файл 1) → прогон; чарт (файл 3). Датасет не менялся.

## Поставка 133 — переводы по специализациям при фильтре HQ (10.11, ноутбук)

- **Бой:** у выбранного подразделения при фильтре HQ начало, конец, найм и отток по специализации совпадали с
  мастер-отчётом, а «переводы в» и «из» были больше, и строка не сходилась.
- **Причина:** человек в один день сменил покраску (стал HQ или перестал им быть) и специализацию, не меняя
  подразделение. Ноутбук писал на такой день две строки перевода; без фильтра по покраске считалась одна, с фильтром — обе.
- **Стало:** один день человека — одна строка, она несёт все флаги дня (как у мастера). То же для IT-кода и штата.

- ветка `hv` и `cv_k` у строки U «в» — переход «кандидат → боевая» и «стажёр → штат» строкой найма (`in_ok = 0`,
  в переводы не идёт): на ней стоят найм по дню события и виды найма в чарте.

**До каких чисел дойти:**

1. **Водопад сходится — «прочее» = 0** в каждом месяце у корня и у A / B / C. Сейчас на GP у корня «прочее»
   отрицательное каждый месяц (сотни человек): численность растёт меньше, чем объясняют события. Формула — как
   считает отчёт (найм по дню события):
   - `hc` = Σ `series.hc_cnt`; `fire` = Σ `series.fire_cnt`
   - `hire` = Σ `trf.trf_cnt` где `trf_kind = 'h'` или (`trf_kind = 'i'` и `in_ok = 0` и (`fu = 1` или `fa = 1`))
   - `tin` = Σ `trf.trf_cnt` где `trf_kind = 'i'` и `in_ok = 1` и (`fu = 1` или `fa = 1`)
   - `tout` = Σ `trf.trf_cnt` где `trf_kind = 'o'` и (`fu = 1` или `fa = 1`)
   - везде `node_rk` = узел, `act_cd = 'Активная'`, по `report_month`
   - `prochee = hc(m) − hc(m−1) − (hire − fire + tin − tout)`

   Ненулевое «прочее» — разобрать, кто это: запрос 9 файла 5 (по людям из `all_metrics_…` и флагам источника — тип
   на конец прошлого и этого месяца, флаги перехода / увольнения / найма; только счётчики). Для каждой крупной
   категории ответить: это перевод, который правило переводов пропускает (тогда — какое условие правила его теряет и
   считает ли его мастер-отчёт), или особенность источника (человек пропал из данных без увольнения и т. п.).
   **Правило переводов при фильтре по умолчанию сверено с мастером — не менять его без согласования**; предложение —
   отдельным пунктом.
2. **Переводы = эталоны мастер-отчётов** (как у тебя 168 / 168): `tin` / `tout` по формуле п. 1 у A / B / C по месяцам.
3. **Мониторинг по месяцам = мастер-дашборд**, узел и срез сверки — Активная + покраска HQ: категории (`pnor` `plow`
   `phig` `pgry`), часы в день `hrs_sum_amt ÷ plan_day_cnt`, доля звонков `100 × tlk_sum_amt ÷ hrs_sum_amt` (series).
   По неделям не сверять — недельный мониторинг снят 06.11 (источник не готов).
4. **Месячная текучесть** `fire_cnt ÷ avg_cnt × 100` по месяцам = мастер-источник (тот же срез).
5. **Срок закрытия вакансий** — медиана `ttf_d` по закрытым в месяце и за период (январь..`cm`) = дашборд подбора.
6. **Мониторинг по месяцам**: Σ (`pnor` + `plow` + `phig` + `pgry`) = `hc_cnt` (на GP уже сходится).

## Узлы, срезы, периоды

- **Узел** — юнит нынешней структуры (последний месяц). Ряды узла — по всему его поддереву; человек, переехавший в
  другой юнит, едет туда со своей историей. Путь юнита — `teampulse_hub_unit.path_rk` (ключи через `|`). Узел
  `<юнит>:d` в `teampulse_hub_trf` — «напрямую в юните» (люди в самом юните, без подразделений).
- **Срез** (колонки во всех таблицах людей): `paint_cd` покраска HQ / Line / Support · `it_cd` IT / Digital / NonIT ·
  `staff_cd` Штат / Не штат · `act_cd` тип численности целиком (по умолчанию в отчёте — «Активная», без подрядчиков).
  Датасет фильтрует их в `cond()`. Вакансии и AI — не люди: срезы на них не действуют.
- **Периоды** (`teampulse_hub_cal`): `lm` — последний месяц данных (может быть неполным), `dt` — дата данных,
  `cm` — последний закрытый месяц, сетка — с января прошлого года. «С начала года» = январь..`cm`.
  Численность — на конец месяца (у `lm` — на `dt`), события — за месяц по дням.

## Метрики — как считаются

| Метрика | Формула (ноутбук → датасет → чарт) |
|---|---|
| Численность | люди на конец месяца: последняя строка человека в месяце (`rn = 1`) и не уволен в этот день (`hc_total_cnt`) |
| ССЧ | (численность на конец прошлого месяца + на конец этого) / 2 — `avg_cnt` |
| Найм | найм в компанию (`hire_flg`) + при выбранном типе «Активная»: из учебной группы в боевую и стажёр в штат (строки `trf` вида i с `in_ok = 0`, вид `cv_k` c / s — ветка `hv` в `hub · 5`); чарт берёт найм по дню события |
| Отток | `fire_flg` за месяц; нежелательные — `regrettable`, желательные — `non_regrettable` |
| Текучесть месячная | отток месяца ÷ ССЧ месяца × 100; в таблице подразделений — значение последнего закрытого месяца |
| Текучесть накопительная | сумма месячных с января |
| HQ-текучести («Как уходит HQ?») | те же формулы на активной численности HQ, без целей; сравнение — с прошлым годом |
| Переводы | правило агента 104 (сверено с мастер-отчётом на Trino, `hub · 5`): **U** — юнит-переход по паре соседних строк (вчера флаг `out` уровня, сегодня — новая строка), «в» в узлы новой строки, «из» — старой; **TI** — вход в активную численность (`transfer_to_active_type_flg`, `active_count_flg = 1`, `prev_active_count_flg = 0`); **TO-a** — выход из активной без смены юнита; **TO-b** — уход «в оформление» (нет строки источника на следующий день). Кандидаты и стажёры в «в» не идут. Смена покраски / IT / штата **без** перевода юнита — как в 103: по флагу смены, засчитывается только при фильтре по этому срезу; дни с событием U / TI / TO исключены (их строки уже несут флаги срезов). К TI и TO-a — парная строка другой стороны перехода с её типом численности (не «Активная»): при фильтре по умолчанию её отсекает фильтр типа, при фильтре из нескольких типов (Активная + Подрядчики) переход внутри фильтра даёт «в» и «из», водопад сходится. Дневные строки схлопнуты, флаги 0/1. **Проверено на стенде:** при фильтре по умолчанию переводы «в» / «из» / по уровню юнита = правилу агента без добавок в каждой ячейке узел × месяц × срез |
| Водопад | с поставки 105 — `teampulse_hub_flow` (`hub · 4в`): принадлежность строке — последняя строка человека в месяце (как численность series); «в» — стал принадлежать строке, «из» — перестал; найм — строке конца месяца, отток — строке прошлого месяца; конец = начало + найм − отток + в − из тождественно, «прочего» нет. Перевод — вход в периметр (узел + выбранные фильтры) или выход из него: пришёл в узел извне / ушёл (`chg_unit`) или другая сторона перехода вне фильтров (`oth_*`). Переводы водопада ≠ карточкам «Переводы» (`trf`, флаги источника) — разная семантика, так задумано |
| Движение по специализациям | переводы — только флаг юнита уровня узла (`fu`); смена специализации/среза без перевода — «Внутри юнита» (`tci` / `tco`) |
| Мониторинг | категория перформанса (норма / недоработка / переработка / не размечено) — только у численности на конец месяца; без записи — «не размечено». Сумма категорий = численность. Вкладка есть и когда все «не размечено» |
| Мониторинг по неделям | **снят 06.11** — источник недель ещё не готов. Параграф агента хранится в репозитории (stand/hub_nb/sql_3w_mon.sql), в ноутбук не входит; в отчёте только месяцы, незакрытый месяц — бледнее, с пометкой |
| Средняя рабочая активность | часы в день взвешенно: `hrs_sum_amt ÷ plan_day_cnt` (часы плановых дней ÷ плановые дни); старая таблица без колонок — среднее по людям |
| Средняя доля звонков в Толк | `100 × tlk_sum_amt ÷ hrs_sum_amt` |
| Посещаемость | посещения офиса ÷ рабочие дни × 100 |
| T-рост | заявки HQ без стажёров и черновиков, актуальная версия; решение — в месяц итога (`finish_month`); юнит — человека в месяце начала |
| Вакансии | открытые — в работе на конец месяца (группа «Согласованные»), по всем каналам; закрытые — `close_flg`, только каналы из списка; новые — согласованы в месяце |
| Срок закрытия | медиана: срок вакансии = дни от первого согласования до закрытия без дней в Hold (`ttf_d`); за месяц — по закрытым в месяце, за период — по всем вакансиям периода |
| Доля джунов | закрытые джунами ÷ закрытые с начала года |
| AI | только по неделям: проникновение = WAU ÷ численность той же недели без стажёров (count distinct) |
| Средний возраст | по людям на последний день данных (профили), в срезе — по людям среза |
| Пересечения разрезов | по профилям: сумма `cnt` строк, где совпали выбранные значения; больше 40 000 строк в ответе — оценкой |
| Источник найма | `source_type_nm` со дня найма (поле `fields` с `at_hire: True`), пусто в день найма — «-» |

## Как отлаживать

- Меняй SQL параграфов ноутбука; имена и колонки выходных таблиц `teampulse_hub_*` сохраняй (контракт выше). Нужна
  новая колонка или ключ `mx_key` — запиши, что датасету нужно её читать.
- Диалект ноутбука — Greenplum 6 (PostgreSQL 9.4): нет `array_position`, `group by all`, `distinct on` есть. В
  датасете — ClickHouse 24.8 + Jinja Proteus.
- Логина, ФИО, табельного, ключей и имён юнитов в выводы для обсуждения не выноси — только счёт и суммы.
- Литералы конкретных юнитов (rk, имена) в ноутбук не вписывай — ключи берутся из структуры.
- После правки — ноутбук целиком (с первого параграфа, меняется `build_all_metrics`), `hub checks` без FAIL, затем
  запросы файла 5 на контрольном подразделении.
