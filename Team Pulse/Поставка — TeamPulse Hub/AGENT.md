## Поставка 111 — ответ датасета вдвое легче (07.11, датасет и чарт)

Замер боя (файл 8г): ответ компании — 23,6 МБ JSON, а сумма его колонок — около 9,5 млн знаков. Разница — упаковка
Proteus: каждая русская буква в JSON записана как `\u04xx` (6 знаков вместо одного).

- **Датасет** в последнем SELECT кодирует текстовые колонки `nm`, `j`, `mx` (кроме `j` строки `meta`): латиница и знаки
  `!#$%&*+;<=>?@_^` получают префикс `^`, затем 66 букв (а–я, ё, А–Я, Ё) → `a–z A–Z !#$%&*+;<=>?@_` (`translateUTF8`,
  ClickHouse 22.7+). В `meta` — признак `"enc":"a1"`. Числа, строки и их порядок не меняются.
- **Чарт** расшифровывает ответ по `meta.enc` до любого чтения (`real.js`, `unarm`); старый ответ без признака читает как раньше.
- **Проверка на стенде:** шесть наборов фильтров — после расшифровки ответы совпадают с прежними байт в байт; JSON с
  `\u`-экранированием легче на 34–43% (на бою справочник почти весь кириллицей — ожидаем больше: 23,6 → ~9–12 МБ).
- Модель разбора Proteus: +0,0–0,3 с на запрос (три функции в конце текста).
- **Если в SQL Lab `translateUTF8` нет** (`SELECT translateUTF8('ёж', 'ёж', 'ab')` — ошибка): датасет 111 не ставить,
  вернуть датасет 110; чарт 111 читает оба ответа.

## Поставка 109 — скорость: датасет короче и легче (07.11)

Применение фильтров = новый запрос датасета: Proteus разбирает и переформатирует его текст (sqlparse `reindent`), ClickHouse
считает, чарт разбирает ответ. Модель Proteus (`proteus-playbook/kit`, тот же sqlparse 0.4.3) показала, что разбор
текста вырос до ~10 с на запрос: `reindent` для каждой скобки заново проходит текст от начала, стоимость ≈ число скобок ×
их позиция. Правки — **только датасет**, ответ при этом тот же (проверено: ответы до и после совпадают байт в байт на шести
наборах фильтров стенда, сверка стенда — все наборы при шести профилях настроек ClickHouse):

- **`fsm`** (замкнутый водопад специализаций) — только с января года последнего месяца: начало `b` — январь, конец `e` —
  последний месяц, события `h f i o` помесячно. Чарт другие месяцы не читал; было ~56% ответа.
- **`tsm` / `xsm`** (помесячная детализация до поставки 105) — в ответ не идут: их заменил `fsm`.
- **Матчеры колонок** (`arrayConcat(… COLUMNS('^x$') …)`, 91 место, `act_cd` — 26 раз) — прямые обращения: все эти колонки
  есть в таблицах ноутбука с поставки 107. **Датасет 109 требует таблицы ноутбука 107+.**
- **Строка `hq`** (светофор «Как уходит HQ?») считает 7 рядов (hc act avg hire fire reg nreg), остальные — нули.
- **Не делать:** скалярные псевдонимы WITH (`(SELECT lm FROM cx) AS cx_lm`) вместо подзапросов `(SELECT lm FROM cx)` —
  разбор короче, но старый анализатор ClickHouse копирует список WITH в каждый подзапрос, и запрос съедает всю память
  (стенд 07.11). Подзапросы к `cx` оставлены.
- **Суммы метрик** — `sum(toFloat64(x))` и один `ifNull` на отрезок массива; флаги переводов внутри сумм без `ifNull`
  (NULL в сумме не считается, как и 0; под `NOT` и у `in_ok` — `ifNull` оставлен); `fsm` и переводы по специализациям —
  `arrayZip` вместо кортежей; JSON строки meta — в ранней CTE `mj`.

**Итог на стенде:** ответ компании (JSON, как его получает чарт) 958 → 518 КБ; модель разбора Proteus: компания 10,0 → 5,4 с,
команда + HQ 10,8 → 5,8 с (из них reindent 7,5 → 3,6 с); ClickHouse (новый анализатор, как на проде) 2,7 → 2,2 с, старый
анализатор 18,6 → 16,8 с. На проде замерить файлами 8 (консоль борда: сервер / приём / КБ) и 8б (SQL Lab:
блоки «компания», «команда + HQ», «только план») — оба в «Архив поставки», 8б пересобран под этот датасет.

## Метрики — как считаются

| Метрика | Формула (ноутбук → датасет → чарт) |
|---|---|
| Численность | люди на конец месяца: последняя строка человека в месяце (`rn = 1`) и не уволен в этот день (`hc_total_cnt`) |
| ССЧ | (численность на конец прошлого месяца + на конец этого) / 2 — `avg_cnt` |
| Найм | найм в компанию (`hire_flg`) + при выбранном типе «Активная»: из учебной группы в боевую и стажёр в штат (строки `trf` вида i с `in_ok = 0`, вид `cv_k` c / s — ветка `hv` в `hub · 5`); чарт берёт найм по дню события |
| Отток | `fire_flg` за месяц; нежелательные — `regrettable`, желательные — `non_regrettable` |
| Текучесть месячная | отток месяца ÷ ССЧ месяца × 100; в таблице подразделений — значение последнего закрытого месяца |
| Текучесть накопительная | сумма месячных с января |
| HQ-текучести («Как уходит HQ?») | те же формулы на активной численности HQ, без целей; сравнение — с прошлым годом |
| Переводы | правило агента 104 (сверено с мастер-отчётом на Trino, `hub · 5`): **U** — юнит-переход по паре соседних строк (вчера флаг `out` уровня, сегодня — новая строка), «в» в узлы новой строки, «из» — старой; **TI** — вход в активную численность (`transfer_to_active_type_flg`, `active_count_flg = 1`, `prev_active_count_flg = 0`); **TO-a** — выход из активной без смены юнита; **TO-b** — уход «в оформление» (нет строки источника на следующий день). Кандидаты и стажёры в «в» не идут. Смена покраски / IT / штата **без** перевода юнита — как в 103: по флагу смены, засчитывается только при фильтре по этому срезу; дни с событием U / TI / TO исключены (их строки уже несут флаги срезов). К TI и TO-a — парная строка другой стороны перехода с её типом численности (не «Активная»): при фильтре по умолчанию её отсекает фильтр типа, при фильтре из нескольких типов (Активная + Подрядчики) переход внутри фильтра даёт «в» и «из», водопад сходится. Дневные строки схлопнуты, флаги 0/1. **Проверено на стенде:** при фильтре по умолчанию переводы «в» / «из» / по уровню юнита = правилу агента без добавок в каждой ячейке узел × месяц × срез |
| Водопад | с поставки 105 — `teampulse_hub_flow` (`hub · 4в`): принадлежность строке — последняя строка человека в месяце (как численность series); «в» — стал принадлежать строке, «из» — перестал; найм — строке конца месяца, отток — строке прошлого месяца; конец = начало + найм − отток + в − из тождественно, «прочего» нет. Перевод — вход в периметр (узел + выбранные фильтры) или выход из него: пришёл в узел извне / ушёл (`chg_unit`) или другая сторона перехода вне фильтров (`oth_*`). Переводы водопада ≠ карточкам «Переводы» (`trf`, флаги источника) — разная семантика, так задумано |
| Движение по специализациям | переводы — только флаг юнита уровня узла (`fu`); смена специализации/среза без перевода — «Внутри юнита» (`tci` / `tco`) |
| Мониторинг | категория перформанса (норма / недоработка / переработка / не размечено) — только у численности на конец месяца; без записи — «не размечено». Сумма категорий = численность. Вкладка есть и когда все «не размечено» |

| Средняя рабочая активность | часы в день взвешенно: `hrs_sum_amt ÷ plan_day_cnt` (часы плановых дней ÷ плановые дни); старая таблица без колонок — среднее по людям |

## Проверки

1. **`hub checks`** (последний gp-параграф перед выгрузкой) — каждая строка одно число. `FAIL` у обязательной —
   выгрузка не идёт. Главные: корень = источник по численности, увольнениям, перформансу; профили = численность;
   мониторинг = численность; источник найма со дня найма = 0; без повторов ключа «узел × месяц × срез».
2. **Файл 6 (GOLDEN)** — на сверенном ноутбуке снять снимок, после любой правки — сравнить: все колонки и отпечатки md5
   один в один, иначе правка меняет сверенные числа. Отпечаток переводов берёт только строки, которые отчёт считает
   при настройках по умолчанию: снимок на ноутбуке агента (Trino-сверка) и на ноутбуке 104 одинаков.
3. **Файл 5** — запросы для сверки с мастер-источником на одном подразделении и месяце (параметры в блоке `p`):
   водопад, мониторинг по покраске, месячная текучесть, медиана срока, повторы строк источника, переводы по
   специализациям, профили и возраст, источник найма. Ожидаемое — в комментарии к каждому запросу.
4. Отчёт: сверять число на одной вкладке, одном подразделении, одном месяце, тех же фильтрах. Сначала численность,
   потом события, потом доли.

## Как отлаживать

- Меняй SQL параграфов ноутбука; имена и колонки выходных таблиц `teampulse_hub_*` сохраняй (контракт выше). Нужна
  новая колонка или ключ `mx_key` — запиши, что датасету нужно её читать.
- Диалект ноутбука — Greenplum 6 (PostgreSQL 9.4): нет `array_position`, `group by all`, `distinct on` есть. В
  датасете — ClickHouse 24.8 + Jinja Proteus.
- Логина, ФИО, табельного, ключей и имён юнитов в выводы для обсуждения не выноси — только счёт и суммы.
- Литералы конкретных юнитов (rk, имена) в ноутбук не вписывай — ключи берутся из структуры.
- После правки — ноутбук целиком (с первого параграфа, меняется `build_all_metrics`), `hub checks` без FAIL, затем
  запросы файла 5 на контрольном подразделении.
