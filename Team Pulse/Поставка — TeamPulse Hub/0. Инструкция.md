# TeamPulse Hub — что куда вставлять

Отчёт в Proteus собирается так же, как HRBP HUB: **таблица ClickHouse → один датасет → один
чарт**. Сейчас стоит **пробник**: весь отчёт — вкладки, дерево юнитов, фильтры, графики — на
живых данных `prod_proteus.hr_structure_overall` там, где они есть, и с заглушками «демо» там,
где источника пока нет. Что живое и в каком порядке подключается остальное — `План метрик.md`.
Как отчёт выглядит и работает — макет (`index.standalone.html`, он же GitHub Pages) и правила
в `AGENTS.md`; откуда данные — `SOURCES.md` §18.

## С чего начать — пробник за пять шагов

1. **Датасет.** Proteus → Datasets → новый виртуальный датасет, база **CROSS**, имя
   `teampulse_hub`. SQL — файл 2 целиком. Сохранение исполняет запрос без фильтров —
   должно пройти за секунды. Колонок 24: `role, id, pid, lvl, nm, kids, j`, 16 × `m_*` и `mx`.
   Если меняли SQL у существующего датасета и колонки изменились — **«Синхронизировать
   столбцы»**, иначе чарт падает с 500.
2. **Чарт.** Новый чарт на датасете `teampulse_hub`, тип **ECHARTS**, имя «TeamPulse Hub».
   **Измерения** — колонки точными именами:
   ```
   role  id  pid  lvl  nm  kids  j
   m_hc  m_act  m_avg  m_hire  m_fire  m_reg  m_tin  m_tout
   m_pnor  m_plow  m_phig  m_pgry  mx
   m_wday  m_ovis  m_gapr  m_gdec
   ```
   Последние четыре необязательные: без них отчёт работает, а посещаемость и T-рост
   остаются «в разработке». `m_prat` с 17-й поставки нет: если стоит в «Измерениях» — уберите.
   Мер нет, сортировки нет. **Лимит строк — 50 000** (Proteus молча режет ответ лимитом;
   у большого юнита три уровня вниз — тысячи строк). Серверная пагинация — выкл.
   JS — файл 3 целиком. Сохранить в новый дашборд «TeamPulse Hub».
3. **Дашборд.** Чарт во всю ширину, высота ячейки 1 100–1 400 px — внутри отчёт
   прокручивается сам.
4. **Кросс-фильтры: чарт должен фильтровать САМ СЕБЯ.** Переход в юнит, «← Назад», путь
   над отчётом и фильтры (IT, штат) — это кросс-фильтр чарта самому себе: без
   него ничего из этого не применится, и через 45 секунд отчёт скажет об этом жёлтым чипом.
   Мышкой это не настраивается — JSON-метаданными дашборда, как в HRBP HUB:
   1. id чарта: меню чарта «⋮» → «Редактировать график» — число после `slice_id=` в адресе;
   2. дашборд → «…» → «Редактировать свойства» → «Дополнительно» → «JSON метаданные»;
   3. `"cross_filters_enabled": true` (нет такого ключа — добавьте строку);
   4. блок `"chart_configuration"` целиком (вместо `ID` — число; в ключе — в кавычках):
      ```json
      "chart_configuration": {
        "ID": {
          "id": ID,
          "crossFilters": {
            "scope": {"rootPath": ["ROOT_ID"], "excluded": []},
            "chartsInScope": [ID]
          }
        }
      },
      ```
      Главное — пустой `"excluded": []`: по умолчанию там стоит сам чарт, и свой фильтр
      до него не доходит;
   5. сохранить свойства → сохранить дашборд → обновить страницу.
5. **CSS** — файл 4 в конец CSS дашборда, как есть: в нём id чарта 814002 (борд Team Pulse 2.0). Если
   чарт пересоздан и id другой — 814002 → новый id (Ctrl+H, все места): иначе вокруг отчёта белая
   рамка, сверху вторая шапка «Team Pulse 2.0 ⋯», а отчёт не на высоту окна.

**Готово, когда:** отчёт открывается с «Компании» (если у корня один юнит — с него),
в шапке чип «Пробник · часть данных в разработке». Выберите строку в таблице подразделений,
нажмите иконку «Открыть юнит» у правого края имени — через несколько секунд открывается
юнит, над отчётом путь и «← Назад». «Настрой свой дашборд» → «Только штат» → «Применить» —
в шапке чип «штат» и база «всё штат». Цифры сверьте запросами 1 и 2 файла 5.

**Доступ.** В пробнике дашборд видят все, кому выдан доступ в Proteus, и каждый видит всю
компанию. Ограничить руководителя его периметром — отдельное решение (`План метрик.md`).

## Если что-то не так

| Симптом | Причина и что сделать |
|---|---|
| Жёлтый чип «Ответ не пришёл за 45 секунд…» после перехода или фильтра | кросс-фильтры выключены или чарт в `excluded` своего фильтра — шаг 4 |
| Жёлтый чип «Фильтры не применились: здесь нет кросс-фильтра…» | чарт открыт не на дашборде (в редакторе чарта кросс-фильтра нет) — откройте дашборд |
| Жёлтый чип «В данных чарта нет колонок: …» | не все 20 обязательных полей в «Измерениях» или не синхронизированы столбцы — шаги 1–2 |
| Посещаемость и T-рост с меткой «демо», хотя файл 2 новый | в «Измерения» не добавлены `m_wday m_ovis m_gapr m_gdec` — шаг 2 |
| Жёлтый чип «Ответ датасета обрезан лимитом строк…» или «нет служебной строки meta» | «Лимит строк» меньше ответа — поставьте 50 000 (шаг 2) |
| Красный текст «TeamPulse Hub: ошибка чарта — …» на месте отчёта | пришлите текст ошибки целиком |
| Вокруг отчёта белая рамка, сверху «TeamPulse Hub ⋯» | не вставлен файл 4 или в нём не тот id чарта |
| Низ отчёта уходит за окно или под ним пусто | файл 6 в консоли страницы борда — он напишет, на какое число заменить 149 в блоке 7 файла 4 |
| «Юнит не открылся: его нет в данных последнего полного месяца» | юнит расформирован или переименован в последнем полном месяце — откройте его родителя |
| Цифра с меткой «демо» | заглушка: источника пока нет, этап — `План метрик.md` |
| Цифры не сходятся с HR-отчётностью | запросы 1–2 файла 5; пришлите, какая цифра и насколько — не сами числа |

## Новые источники и уточнения

SQL Lab в Proteus пропускает только `SELECT` и `DESCRIBE`, а служебные таблицы ClickHouse
в нём закрыты (запрос со словом `system` он не выполняет даже в комментарии).

- **Новая таблица для этапа плана** — файл `0а`: запросы по одному, от `DESCRIBE` до
  профиля колонок; таблицу впишите вместо `prod_proteus.hr_structure_overall`.
  **Персональные данные не присылайте:** запросы 1–4 показывают только имена колонок,
  типы и счётчики; в 5 и 6 колонки с ФИО, почтой, логином, табельным номером и зарплатой
  исключены через `EXCEPT` (он молча пропускает имя, которого нет, — сверьте имена с
  ответом на запрос 1), ключ сотрудника показан хешем.
- **Уточнение по `hr_structure_overall`** — файл `0д` (схема 15.10): вставить целиком,
  ответ — в конец `Разведка`. Он маскирован, как `0б`–`0г`: имён и ключей юнитов нет,
  суммы — в промилле (на 1000 от численности компании), видны только значения
  справочников — пол, возраст, грейд, тип оформления, причины увольнения. Перед тем как
  класть ответ в репозиторий, просмотрите раздел «1»: если какие-то значения внутренние
  (названия юрлиц, стримов), — скажите, замаскирую. После разбора в `Разведка` снова
  останутся схема и главное.

## Что нового

### 20.10, сорок четвёртая поставка — у карточки графиков всегда видны края: файл 3

**Заменить целиком только файл 3** (JS чарта) → Save, на борде Cmd+Shift+R.

По вашему скриншоту: карточка графиков ехала страницей, и её верх уходил под край окна (без скругления), а
низ уходил за экран ниже таблицы. Теперь шапка карточки («Отток и текучесть по месяцам», переключатель
«Подразделения») прилипает к верху окна на одной высоте с таблицей, а скруглённый низ — к низу окна на
одной линии с низом таблицы; графики прокручиваются между ними. В самом конце страницы края тоже совпадают.

Проверено в модели песочницы Proteus: в середине прокрутки и в конце страницы шапка и таблица — 12 px от
верха, низ карточки и таблицы — 725 px (окно 751). Смоук, ESLint, проверка ES5 — без ошибок.

### 20.10, сорок третья поставка — один скролл: таблица подразделений прилипает, графики едут: файл 3

**Заменить целиком только файл 3** (JS чарта) → Save, на борде Cmd+Shift+R.

По вашему видео («двойной скролл»): раньше рабочая зона во вкладке блока держала высоту экрана, и
сначала листалась страница, а потом отдельно — панель графиков. Теперь, как в почте или Figma («список
и детали»):
- **страница листается одним скроллом** — графики главы, выводы и «что сделать» идут своей высотой,
  своей прокрутки у панели графиков нет;
- **таблица подразделений прилипает к верху экрана** и едет рядом с графиками — выбранное
  подразделение всегда на виду;
- **своя прокрутка у таблицы — только если она выше экрана** (большой юнит, раскрытое дерево): навели
  на неё — листается она; дойдя до края, страницу не дёргает;
- на узком окне (до 1120 px, таблица над графиками) — как было.

Проверено в модели песочницы Proteus: страница прокручена на 900 px — таблица у верха окна, графики
листаются страницей; раскрытое дерево (30 подразделений) листается внутри таблицы. Смоук макета и
пробника, ESLint, проверка ES5 — без ошибок.

### 20.10, сорок вторая поставка — отчёт больше не «прыгает» наверх: файл 3

**Заменить целиком только файл 3** (JS чарта) → Save, на борде Cmd+Shift+R.

По вашему видео: во вкладке блока отчёт каждые пару секунд прыгал к выводу наверху. Причина — Proteus
перезапускает скрипт чарта не только на новый ответ датасета, но и при перерисовке ячейки (ресайз и
т. п.); отчёт при этом собирался заново и начинал с верха страницы. Теперь прокрутка страницы и панелей
(таблица подразделений, графики главы) запоминается и возвращается при таком перезапуске, графики не
проигрывают анимацию заново. Наверх отчёт уходит только после своего запроса — смены юнита или фильтров.

Проверено в модели песочницы Proteus: прокрутили вкладку «Отток и текучесть» вниз, перезапустили скрипт
тем же ответом дважды — прошлая версия уходила наверх (594 → 0), новая остаётся на месте (594 → 594).
Смоук макета и пробника, ESLint, проверка ES5 — без ошибок.

### 20.10, сорок первая поставка — выводы с огоньками, без KPI на главной, таблицы всегда открыты: файл 3

**Заменить целиком только файл 3** (JS чарта) → Save, на борде Cmd+Shift+R.

По вашим правкам:
- **Огоньки по смыслу вместо AI-огонька** (выводы считаются правилами, не ИИ): «Требует действий» —
  встревоженный, «Посмотреть» — насторожённый, «Хорошая новость» — улыбается, «Всё спокойно» —
  спокойный. Сводку на главной рассказывает огонёк, который показывает рукой.
- **Карточки выводов** — мягкий градиент фона по смыслу (красноватый, жёлтый, зелёный), как у прежних
  плашек; полосы слева нет.
- **Главная:** KPI-карточек нет. Сверху сводка и выводы, «В норме», ниже сразу таблицы всех метрик —
  ничего не свёрнуто.
- **Вкладка блока:** вывод и «Где это происходит» — одна плотная карточка с огоньком по настроению,
  без пустого места; «Подробнее — в таблице подразделений ниже ↓» прокручивает к таблице. Таблица
  подразделений и главы всегда открыты.

Проверено: смоук макета и пробника на трёх ответах, ESLint, проверка ES5, модель песочницы — без
ошибок. Файл 3 — 459 КиБ.

### 20.10, сороковая поставка — датасет снова сохраняется: файл 2а (и 2, 0е)

**Заменить SQL датасета файлом 2а целиком → Save** (если отчёт на файле 2 — файлом 2). Колонки ответа те
же, «Синхронизировать столбцы» не нужно. Ноутбук и чарт не меняются.

Ошибка «Некорректный SQL запрос: →… — fdv) fdb AS ( SELECT ifNull(node_rk, '') AS u7, …←» — моя, из
поставки 36: тип численности и найм в компанию читаются матчером `COLUMNS('^act_cd$') APPLY toString`.
ClickHouse такую запись понимает, а проверка Proteus при сохранении — только со скобками:
`APPLY(toString)`. Исправлено во всех трёх файлах с матчером (2а, 2 и запрос 0е). Проверка сохранения на
стенде (та же, что у Proteus) теперь проходит; раньше она молча пропускала этот разбор — это тоже
исправлено.

### 20.10, тридцать девятая поставка — ответ 0е разобран, запрос 0е обновлён: файл 0е

**Ничего в отчёте менять не нужно.** Разбор ответа — в «Разведке» («Ответ 0е, 20.10»). Коротко: таблицы
собраны ноутбуком поставки 36, дерево, ряды и разрезы сходятся. «Дубли» и «ССЧ ≠» в ответе — ошибка
самого запроса: он был написан до типа численности `act_cd` и считал две строки среза («Активная» и
«Прочие») дублем.

По желанию — выполнить **обновлённый 0е** в SQL Lab и прислать ответ: он покажет, что `act_cd` и
`hco_cnt` на месте, дублей по полному ключу нет, ССЧ сходится, и как сходится водопад у корня с начала
года отдельно по активной и по всей численности («прочие изменения» в ‰).
