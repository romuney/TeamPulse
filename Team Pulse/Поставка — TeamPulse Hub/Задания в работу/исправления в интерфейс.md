# Новая итерация: вкладка «Ревью»

## Цель

Добавить в дашборд вкладку «Ревью», которая показывает:

- охват сотрудников ревью;
- изменение оценок относительно предыдущего ревью;
- первые полученные оценки;
- распределение оценок по грейду, стажу и специализации.

Данные для новой вкладки поступают из отдельного YAML-файла.

---

## 1. Источник данных

### Требование

Подключить новый YAML-файл как источник данных вкладки «Ревью».

### Что нужно сделать

- Изучить фактическую структуру предоставленного файла.
- Определить поля, необходимые для построения вкладки:
  - идентификатор сотрудника;
  - принадлежность к eligible-популяции;
  - период ревью;
  - текущая оценка;
  - предыдущая оценка;
  - грейд;
  - стаж или категория стажа;
  - специализация;
  - поля для поддерживаемых фильтров.
- Проверить, содержит ли файл общую численность или данные для её расчёта.
- Проверить, как представлены:
  - числовые значения оценок;
  - названия оценок;
  - отсутствие оценки;
  - отсутствие предыдущего ревью;
  - признак eligible.

### Ограничения

- Не придумывать структуру YAML до изучения файла.
- Не определять eligible-популяцию по наличию оценки.
- Не считать отсутствующее значение оценкой `0`.
- Не объединять сотрудников из разных периодов без явного правила.
- Если данных для какого-либо блока недостаточно, зафиксировать недостающее поле или правило и запросить уточнение.
- Не подменять недостающие реальные данные демонстрационными.

---

## 2. Структура вкладки

Добавить в основную навигацию вкладку:

**Ревью**

Внутри неё создать две подвкладки:

1. **Кого оцениваем**
2. **Как оцениваем**

### Общее пояснение

В верхней части вкладки разместить заметный текст:

> Аналитика результатов ревью показана только по eligible-популяции — сотрудникам, включённым в оцениваемую популяцию выбранного периода. Общая численность приведена отдельно для сравнения охвата.

Для термина **eligible-популяция** добавить ссылку на соответствующее определение в словаре.

### Область расчётов

- Все результаты ревью рассчитывать только по eligible-популяции.
- Исключение — общая численность в блоке сравнения охвата.
- Общая численность и eligible-популяция должны относиться к одному периоду и сопоставимой области фильтрации.
- Название периода ревью показывать явно.
- Если периоды представлены в файле, использовать их фактические значения.
- Не выбирать предыдущий период автоматически без проверки структуры данных и правила сравнения.

---

## 3. Подвкладка «Кого оцениваем»

### 3.1. Общая численность и eligible-популяция

Показать график, сравнивающий:

- общую численность;
- количество eligible-сотрудников.

### Визуализация

Использовать один из вариантов:

- воронка;
- горизонтальные бары.

Выбрать вариант, который лучше соответствует существующему интерфейсу и сохраняет читаемость.

### Требования

- Показывать абсолютное количество сотрудников.
- Явно подписать обе категории.
- Не изображать общую численность и eligible-популяцию как две непересекающиеся группы: eligible является частью общей численности.
- В тултипе пояснить, что eligible — сотрудники, включённые в оцениваемую популяцию.
- Если общая численность недоступна, не подменять её количеством записей с оценками.

### Ожидаемый результат

Пользователь видит размер общей популяции и понимает, какая её часть включена в ревью.

---

### 3.2. Изменение оценки

Показать график с количеством сотрудников, которые:

- улучшили оценку;
- ухудшили оценку;
- получили первую оценку.

### Правила классификации

**Улучшили оценку:**

- есть текущая и предыдущая сопоставимые оценки;
- текущая оценка выше предыдущей по подтверждённой шкале.

**Ухудшили оценку:**

- есть текущая и предыдущая сопоставимые оценки;
- текущая оценка ниже предыдущей по подтверждённой шкале.

**Получили первую оценку:**

- есть текущая оценка;
- отсутствие предыдущей оценки означает именно первое оценивание, а не пропуск данных.

### Дополнительные требования

- Все три категории рассчитывать только по eligible-популяции.
- Считать сотрудников, а не строки YAML.
- Порядок оценок определять по фактической шкале, а не по алфавиту названий.
- Не включать сотрудников с неизменившейся оценкой в улучшения или ухудшения.
- Не включать сотрудников без текущей оценки в получивших первую оценку.
- В пояснении указать, что график отражает только перечисленные категории и не обязательно охватывает всю eligible-популяцию.
- Если `n/a` не позволяет отличить первое оценивание от отсутствующих данных, запросить правило классификации.

---

## 4. Подвкладка «Как оцениваем»

### 4.1. Переходы между оценками

Показать разбивку изменений оценки:

**Предыдущая оценка → текущая оценка → количество сотрудников**

Пример отображения:

> Хорошо → Огонь — 6 человек.

### Представление

Использовать читаемый график переходов или таблицу:

| Предыдущая оценка | Текущая оценка | Количество сотрудников |
|---|---|---:|
| Хорошо | Огонь | 6 |

> Числа и названия в примере иллюстративные. Фактические значения брать из YAML.

### Требования

- Учитывать только eligible-сотрудников с двумя сопоставимыми оценками.
- Показывать переходы с изменением оценки.
- Первые оценки вынести в отдельный блок.
- В заголовке или пояснении указать сравниваемые периоды.
- Использовать единые названия и порядок оценок во всех блоках.
- Суммы повышающих и понижающих переходов должны совпадать с соответствующими категориями на подвкладке «Кого оцениваем».

---

### 4.2. Первые оценки

Показать, какую первую оценку получили сотрудники.

Пример:

> n/a → Огонь — 7 человек.

### Представление

Использовать график или таблицу:

| Предыдущая оценка | Первая оценка | Количество сотрудников |
|---|---|---:|
| n/a | Огонь | 7 |

> Числа и названия в примере иллюстративные.

### Требования

- Включать только eligible-сотрудников, для которых подтверждено первое оценивание.
- Не смешивать первое оценивание с неизвестной предыдущей оценкой.
- Показывать количество сотрудников по каждой полученной оценке.
- Сумма значений блока должна совпадать с количеством впервые оценённых сотрудников на подвкладке «Кого оцениваем».

---

### 4.3. Распределение оценок по грейду

Показать таблицу:

- строки — грейды;
- столбцы — количество сотрудников по каждой текущей оценке;
- два крайних правых столбца:
  1. доля сотрудников с оценкой `0` или `1`;
  2. доля сотрудников с оценкой `3` или `4`.

Пример структуры для шкалы `0–4`:

| Грейд | Оценка 0 | Оценка 1 | Оценка 2 | Оценка 3 | Оценка 4 | Доля с оценкой 0–1 | Доля с оценкой 3–4 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Название грейда | … | … | … | … | … | …% | …% |

### Требования

- Фактические столбцы оценок формировать по подтверждённой шкале.
- В ячейках оценок показывать абсолютное количество сотрудников.
- Доли рассчитывать внутри соответствующего грейда.
- Для обозначений грейдов, включая `H1`, `G1–G3` и другие используемые значения, добавить ссылки на определения в словаре.
- Использовать содержательный порядок грейдов, если он задан справочником.

---

### 4.4. Распределение оценок по стажу

Показать аналогичную таблицу:

- строки — категории стажа;
- столбцы — количество сотрудников по каждой текущей оценке;
- два крайних правых столбца:
  1. доля сотрудников с оценкой `0` или `1`;
  2. доля сотрудников с оценкой `3` или `4`.

### Требования

- Использовать категории стажа из источника или уже согласованного справочника.
- Не придумывать интервалы стажа.
- Если стаж нужно рассчитывать из дат, уточнить дату расчёта и границы интервалов.
- Категории сортировать по возрастанию стажа.
- Доли рассчитывать внутри соответствующей категории стажа.

---

### 4.5. Распределение оценок по специализации

Показать аналогичную таблицу:

- строки — специализации;
- столбцы — количество сотрудников по каждой текущей оценке;
- два крайних правых столбца:
  1. доля сотрудников с оценкой `0` или `1`;
  2. доля сотрудников с оценкой `3` или `4`.

### Требования

- Названия специализаций брать из источника или согласованного справочника.
- Не объединять специализации самостоятельно.
- Доли рассчитывать внутри соответствующей специализации.
- Для длинных названий предусмотреть читаемое отображение.

---

## 5. Расчёт долей в таблицах

### Числители

Для каждой строки:

- количество eligible-сотрудников с текущей оценкой `0` или `1`;
- количество eligible-сотрудников с текущей оценкой `3` или `4`.

### Знаменатель

Нужно явно определить, что используется в знаменателе:

- все eligible-сотрудники соответствующей строки;
- либо только eligible-сотрудники строки с текущей валидной оценкой.

**Если правило не задано в источнике или действующем словаре, согласовать его до реализации. Не выбирать знаменатель самостоятельно.**

Выбранное правило должно быть одинаковым для всех трёх таблиц и указано в тултипе заголовков долей.

### Формат формул

После согласования знаменателя зафиксировать:

`Доля_с_оценкой_0_или_1 = 100 × количество_сотрудников_с_оценкой_0_или_1 / согласованный_знаменатель`

`(P_01 = 100 · N_01 / D)`

`Доля_с_оценкой_3_или_4 = 100 × количество_сотрудников_с_оценкой_3_или_4 / согласованный_знаменатель`

`(P_34 = 100 · N_34 / D)`

Где:

- `P_01` — доля сотрудников с оценкой `0` или `1`, %;
- `P_34` — доля сотрудников с оценкой `3` или `4`, %;
- `N_01` — количество сотрудников строки с оценкой `0` или `1`;
- `N_34` — количество сотрудников строки с оценкой `3` или `4`;
- `D` — согласованный знаменатель для этой строки.

При нулевом знаменателе показывать отсутствие рассчитываемого значения, а не `0%`.

## 6. Общие требования к данным и интерфейсу

### Качество данных

- Установить уникальный ключ сотрудника в рамках периода.
- Проверить дубли и правило их обработки.
- Проверить соответствие числовых оценок их текстовым названиям.
- Не считать неизвестное значение оценкой `0`.
- Отдельно обрабатывать отсутствие текущей и предыдущей оценки.
- Не исключать незаметно сотрудников без грейда, стажа или специализации: показывать категорию «Не указано» либо явно описывать ограничение.
- Не допускать попадания неeligible-сотрудников в аналитику результатов.

### Фильтры

- Использовать существующие фильтры дашборда, если в источнике есть необходимые поля.
- Применять фильтры согласованно ко всем блокам вкладки.
- Не создавать видимость работающего фильтра, если источник не поддерживает его применение.
- Ограничения фильтрации явно описывать.

### Состояния интерфейса

Предусмотреть:

- загрузку данных;
- ошибку чтения YAML;
- пустую выборку после фильтрации;
- отсутствие текущих оценок;
- отсутствие сопоставимых предыдущих оценок;
- отсутствие впервые оценённых сотрудников.

Нулевое количество сотрудников не должно смешиваться с отсутствием данных.
