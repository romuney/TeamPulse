# Новая итерация: доработка эталонного словаря метрик

## Цель

Доработать эталонный словарь метрик так, чтобы:

1. Все формулы были понятны человеку без знания исходного кода.
2. Формулы содержали человекопонятное описание и краткую математическую запись внутри скобок.
3. Подтверждение выполнялось только для словаря целиком, а не для отдельных метрик.
4. Все обозначения и категории, например `H1`, `G1–G3`, имели ссылки на соответствующие разделы словаря.
5. В словаре не появлялись придуманные формулы или неподтверждённые правила расчёта.

---

## Общие правила

- Не переносить в эту итерацию задачи, не относящиеся к словарю метрик.
- Не менять фактическую логику расчёта метрик в рамках подготовки словаря.
- Описывать фактическую реализацию, найденную в коде, SQL-запросах, источниках и расчётных полях.
- Не восстанавливать формулы только по названию метрики.
- Не использовать стандартную или предполагаемую формулу без подтверждения в реализации.
- Если формулу невозможно установить, явно указать это в карточке метрики.
- Не скрывать неизвестные правила и расхождения.
- Все изменения структуры словаря зафиксировать в истории изменений.
- Итоговый файл должен быть полным и не содержать незаполненных обязательных разделов без явной пометки о необходимости уточнения.
- Не использовать вложенный блок Markdown с четырьмя обратными кавычками внутри этого файла, чтобы не разорвать внешний блок.

# 1. Формулы должны быть читаемыми

## Где

Во всех карточках рассчитываемых метрик в словаре.

## Что нужно сделать

Для каждой метрики с расчётом указать:

- назначение метрики;
- человекопонятное описание расчёта;
- формулу с понятными названиями показателей;
- краткую математическую запись внутри скобок;
- расшифровку всех сокращений;
- числитель;
- знаменатель;
- период расчёта;
- единицы измерения;
- условия включения данных;
- условия исключения данных;
- правила агрегации;
- правила обработки дублей;
- правила обработки пустых значений;
- контрольный пример;
- ссылку на фактическую реализацию.

## Обязательный формат

Каждая формула должна быть оформлена следующим образом:

```md
### Формула

<Человекопонятное описание расчёта.>

`Название_метрики = понятная формула`

В математической записи:

`(<краткое обозначение> = <математическая формула>)`
```

## Пример

```md
### Формула

Текучесть месячная рассчитывается как количество уволенных за месяц,
делённое на среднесписочную численность за месяц и умноженное на 100.

`Текучесть_месячная =
100 × количество_уволенных_за_месяц /
среднесписочная_численность_за_месяц`

В математической записи:

`(T_m = 100 · fire_m / avg_m)`
```

## Расшифровка обозначений

```md
Где:

- `T_m` — месячная текучесть, %;
- `fire_m` — количество уволенных за месяц;
- `avg_m` — среднесписочная численность за месяц.
```

## Требования к записи формул

- Человекопонятное описание должно быть понятно без знания кода.
- В основной формуле использовать полные названия показателей.
- Сокращения использовать только в краткой математической записи.
- Каждое сокращение расшифровывать.
- Явно указывать числитель и знаменатель.
- Указывать период, к которому относятся все части формулы.
- Указывать единицу измерения результата.
- Объяснять назначение всех коэффициентов.
- Не округлять промежуточные значения, если это не предусмотрено фактической логикой.
- Отдельно описывать правила отображения и округления.
- Не заменять неизвестную формулу предположением.

## Коэффициенты

Если в формуле используются коэффициенты, необходимо объяснить их назначение.

Пример:

```md
- `100` — перевод результата в проценты.
- `12` — годовой пересчёт месячного значения, если это предусмотрено реализацией.
- `1000` — перевод значения в промилле, если это предусмотрено реализацией.
```

Каждый коэффициент должен быть подтверждён фактической реализацией.

## Если формула не установлена

Если формулу невозможно определить по доступным материалам, использовать формулировку:

```md
Формула не установлена по доступной реализации.
Требуется уточнение.
```

Дополнительно указать:

- какая часть расчёта неизвестна;
- какие источники были проверены;
- какой источник или файл недоступен;
- какие данные нужны для подтверждения;
- какие части логики уже установлены.

Запрещено заменять неизвестную формулу словами:

- «вероятно»;
- «скорее всего»;
- «обычно»;
- «по стандартной логике»;
- «предположительно».

# 2. Убрать статус проверки отдельных метрик

## Где

Во всём словаре:

- в реестре метрик;
- в карточках метрик;
- в карточках категорий и обозначений;
- в шаблонах;
- в таблицах;
- в оглавлении;
- в чек-листах;
- в других разделах документа.

## Что нужно убрать

Удалить:

- колонку «Статус проверки»;
- статус проверки из карточек отдельных метрик;
- статусы «Подтверждено»;
- статусы «Частично подтверждено»;
- статусы «Не подтверждено»;
- статусы «Не установлено» как статус отдельной метрики;
- цветовые обозначения статуса;
- дату проверки отдельной метрики;
- отметку о самостоятельном подтверждении отдельной карточки.

## Общий статус документа

Статус должен относиться только ко всему словарю.

В начале документа указать:

```md
## Статус документа

- **Статус:** Черновик до полной проверки.
- **Дата создания:** `YYYY-MM-DD`.
- **Дата последнего изменения:** `YYYY-MM-DD`.
- **Версия словаря:** `0.1`.
- **Версия реализации:** указать commit, релиз или другую версию.
- **Ответственный за проверку:** указать ответственного.
```

После полной проверки изменить статус на:

```md
- **Статус:** Утверждённый эталонный словарь.
```

## Что означает полная проверка

Полная проверка должна охватывать весь документ:

- все метрики;
- все формулы;
- все источники;
- все составы выборки;
- все периоды;
- все фильтры;
- все правила агрегации;
- все правила дедупликации;
- все особые случаи;
- все контрольные примеры;
- все ссылки;
- все расхождения;
- все открытые вопросы.

До завершения полной проверки словарь нельзя считать утверждённым.

## Как фиксировать неизвестную информацию

Удаление статусов не означает, что неизвестную информацию нужно скрывать.

Если формула неизвестна:

```md
Формула не установлена по доступной реализации.
Требуется уточнение.
```

Если источник неизвестен:

```md
Источник не установлен по доступным материалам.
Требуется уточнение.
```

Если состав выборки неизвестен:

```md
Состав выборки не установлен.
Необходимо уточнить правило включения и исключения записей.
```

Если обнаружено расхождение:

```md
Обнаружено расхождение между фактической реализацией и описанием.
Требуется согласование.
```

Не использовать для этих случаев статус отдельной метрики.

## Реестр метрик

Реестр должен иметь структуру:

| ID | Название метрики | Разделы использования | Единица измерения | Ссылка |
|---|---|---|---|---|
| `M-001` | Текучесть месячная | One Pager, Отток | % | [Описание](#m-001-текучесть-месячная) |
| `M-002` | Проникновение AI | AI-инструменты, One Pager | % | [Описание](#m-002-проникновение-ai) |
| `M-003` | Активные пользователи AI | AI-инструменты, One Pager | чел. | [Описание](#m-003-активные-пользователи-ai) |

В реестре не должно быть:

- статуса проверки;
- отметки о подтверждении отдельной метрики;
- цветового индикатора;
- даты проверки отдельной карточки.

# 3. Добавить ссылки на словарь для H1, G1–G3 и других обозначений

## Где

Во всех местах, где используются обозначения или сущности, описанные в словаре:

- `H1`;
- `G1–G3`;
- `G1`;
- `G2`;
- `G3`;
- другие грейды;
- категории сотрудников;
- типы численности;
- активный сотрудник;
- активный пользователь;
- стажёр;
- штатный сотрудник;
- нештатный сотрудник;
- юнит;
- подразделение;
- покраска;
- названия метрик;
- специальные обозначения;
- термины, используемые в формулах и описаниях.

## Что нужно сделать

- Для каждого обозначения создать отдельную карточку в словаре.
- Присвоить карточке уникальный ID.
- Создать стабильный якорь.
- Добавить ссылку на карточку во всех местах использования.
- Ссылку размещать рядом с обозначением или названием сущности.
- Не направлять ссылку только на начало файла.
- Проверить, что ссылка ведёт именно на нужное определение.

## Требования к ссылкам

- Каждый якорь должен существовать.
- Каждый якорь должен быть уникальным.
- Ссылка должна вести непосредственно на нужный раздел.
- Не должно быть ссылок на удалённые разделы.
- Не должно быть ссылок на устаревшие названия.
- После изменения заголовка необходимо обновить все связанные ссылки.
- Разные сущности нельзя объединять в одну ссылку без общего определения.
- Внешние ссылки должны открываться по правилам проекта.
- HTML-ссылки должны иметь доступное описание через `aria-label`, если назначение ссылки неочевидно.

# 7. Правила округления и отображения

Эти правила описывать отдельно от расчётных формул.

## Расчёт

- Расчёты выполнять по исходным значениям.
- Промежуточные значения не округлять без подтверждённого правила.
- Округление применять только к отображаемому результату.
- Сортировку выполнять по исходным значениям.
- Пороговые проверки выполнять по исходным значениям.
- Сравнения выполнять по исходным значениям.
- Не смешивать отсутствие данных и нулевое значение.

## Отображение

- Дробные числа округлять до одного знака после запятой.
- Целые числа отображать без дробной части.
- Значения, ставшие целыми после округления, отображать без `,0`.
- Использовать запятую как десятичный разделитель.
- Отрицательный ноль отображать как `0`.
- Сохранять единицы измерения.
- Для процентов использовать знак `%`.
- Для процентных пунктов использовать `п.п.`, если это предусмотрено интерфейсом.

## Примеры

| Исходное значение | Отображение |
|---:|---:|
| `12,34` | `12,3` |
| `12,36` | `12,4` |
| `12,00` | `12` |
| `12,96` | `13` |
| `-3,27` | `-3,3` |
| `-0,04` | `0` |
| `15,00%` | `15%` |
| `15,26%` | `15,3%` |
| `0,44 п.п.` | `0,4 п.п.` |

# 9. Расхождения

Все расхождения между кодом, интерфейсом, источниками и описанием фиксировать отдельно.

| ID | Метрика или обозначение | Где найдено | Фактическая реализация | Ожидаемое описание | Что требуется согласовать |
|---|---|---|---|---|---|
| `R-001` | Указать | Файл, запрос или блок | Указать факт | Указать ожидание | Указать решение |

## Правила работы с расхождениями

- Не скрывать расхождения.
- Не исправлять расхождение только в тексте словаря.
- Не менять формулу без согласования.
- Указывать источник, на основании которого найдено расхождение.
- После решения обновлять карточку метрики.
- После изменения обновлять контрольный пример.
- Фиксировать изменение в истории.

# 11. Правила утверждения словаря

## До утверждения

- Документ имеет статус «Черновик до полной проверки».
- Все неизвестные формулы отмечены явно.
- Все неизвестные источники отмечены явно.
- Все неизвестные правила выборки отмечены явно.
- Все расхождения вынесены в отдельный раздел.
- Все открытые вопросы вынесены в отдельный раздел.
- Отдельные метрики не имеют статуса подтверждения.

## Для утверждения необходимо проверить

- [ ] Все метрики.
- [ ] Все формулы.
- [ ] Все источники.
- [ ] Все составы выборки.
- [ ] Все периоды.
- [ ] Все фильтры.
- [ ] Все правила агрегации.
- [ ] Все правила дедупликации.
- [ ] Все особые случаи.
- [ ] Все контрольные примеры.
- [ ] Все ссылки.
- [ ] Все якоря.
- [ ] Все расхождения.
- [ ] Все открытые вопросы.

## После утверждения

Изменить статус документа на:

```md
Статус: Утверждённый эталонный словарь.
```

После утверждения:

- нельзя добавлять формулы без согласования;
- нельзя менять существующие формулы без согласования;
- нельзя менять выборку без согласования;
- нельзя менять периоды без согласования;
- нельзя менять знаменатели без согласования;
- нельзя менять правила агрегации без согласования;
- нельзя менять правила классификации без согласования;
- нельзя выбирать трактовку отсутствующего правила самостоятельно;
- каждое изменение необходимо фиксировать в истории;
- одновременно необходимо обновлять описание, формулу и контрольный пример.
