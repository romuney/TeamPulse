## Поставка 61: «Активная» — без подрядчиков

«Активная» — только тип численности «Активная». Подрядчики в неё не входят: это отдельный тип, его добавляют в
фильтре отчёта. В поставке 60 «Активная» включала подрядчиков — так больше не считаем.

Меняется один параграф — `_PARAMS_` (№ 1 ниже): в `FIXED_DIMS` условие `active_type_nm = 'Активная'`. От него
зависят активная численность, ССЧ и найм по методологии HR. Датасет 2а — заменить вместе с ноутбуком: без фильтра он
берёт тип «Активная».

## Поставка 60: тип численности целиком

- Тип численности целиком (`active_type_nm`) теперь есть в таблицах отчёта. По нему фильтр — любой набор типов.
- Переводы считаются при любом наборе типов: перевод — когда человек пересёк границу выбора. Подрядчик перешёл в
  «Активную»: при выборе «Активная» и «Подрядчики» он остался внутри выбора — это не перевод; при одной
  «Активной» — перевод «в».

| Параграф | Что меняется |
|---|---|
| _PARAMS_ | «Активная» — по типу численности (`FIXED_DIMS`), а не по флагу `active_count_flg` |
| EXEC build_all_metrics | в `HUB_FIELDS` — тип численности целиком: `active_type_nm` → `act_type_nm` |
| hub · 0 колонки | нужны `act_type_nm` в `all_metrics…` и `active_type_nm` в дневном источнике; `active_count_flg` не нужен |
| hub · 3 справочник и ряды, hub · 4 разрезы | срез — тип численности целиком |
| hub · 5 переходы | тип численности дня и соседнего дня — целиком |

**Датасет 2а заменить вместе с ноутбуком.** На прежних таблицах фильтра по типу численности в 2а нет.

## Поставка 59: переводы — как в мастер-отчёте

- Событие — строка источника за день с флагом. Флаг юнита — своего уровня (`lvlN_mngt_unit_in_trsf_flg`,
  `lvlN_mngt_unit_out_trsf_flg`). Флаг типа (`transfer_to_*`, `transfer_out_*`) — только для фильтра, который
  стоит в отчёте. «В» и «из» считаются отдельно.
- «В» — без найма (`hire_flg = 0`), «из» — без увольнения (`fire_flg = 0`). «Из» в последний день месяца идёт
  следующим месяцем (`last_day_of_month_flg`).
- Подразделение — то, где человек был в этот день: структура того дня, а не текущая.

В поставке 59 менялись три параграфа: «hub · 0 колонки», «hub · 5 переходы», «hub checks»; у `teampulse_hub_trf`
новые колонки.

## Поставка 58: сборка параграфами gp

Таблицы `teampulse_hub_*` собирают параграфы gp, а не Python-параграф `build_hub_detect`.

**Почему падало.** Python здесь данных не гонял. Каждый шаг — SQL, он выполняется внутри GP, а Python только
отправлял текст запроса и ждал ответа. Но в одном параграфе он ждал больше ста запросов подряд: ряды и разрезы —
по запросу на каждый месяц, переходы — 22 прохода по дневному источнику. Параграф упирался в таймаут.

**Что стало.**
- Восемь параграфов gp и один короткий Python. Каждый шаг виден отдельно: если что-то упадёт, видно где.
- Тяжёлые шаги — за один проход. Ряды и разрезы — 4 запроса по нужным колонкам вместо ~55 запросов, которые
  тащили все ~80 колонок источника. Дневной источник читается один раз вместо 22.
- Даты в SQL — не литералами. Последний месяц и дата данных лежат в `teampulse_hub_cal`. Дневной источник
  отсекается по `current_date`: по ней GP режет партиции.
- Python остался в параграфе «hub · 2 логины и AI». Там сначала нужно проверить, есть ли источник логинов и AI, —
  SQL так не умеет. Это два коротких запроса.

На стенде (источник ×25, 6 млн строк по дням): было {{T_PY}} с и {{Q_PY}} запросов к GP, стало {{T_SQL}} с и
{{Q_SQL}} запросов{{T_59}}.
