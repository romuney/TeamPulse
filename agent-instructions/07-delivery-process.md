# 07. Процесс агента и поставка владельцу

Боя агент не видит: ClickHouse, Proteus и Helicopter доступны только владельцу. Он вставляет файлы руками и присылает
факты: текст ошибки, скриншот, ответ SQL Lab, поля DevTools. Сессии рвутся — знание живёт в репозитории, решения
опираются на замеры. Подробно — [14-delivery.md](../proteus-playbook/14-delivery.md) (DV),
[15-process.md](../proteus-playbook/15-process.md) (PR), [13-stand.md](../proteus-playbook/13-stand.md) (ST),
[checklists/](../proteus-playbook/checklists/). Стоп-лист — [06-antipatterns.md](06-antipatterns.md).

**Главное.**
1. Цикл: воспроизвести → план в NOTES → правка исходника → гейт стенда → замер до/после → поставка → инвариант в CLAUDE.md.
2. Одна папка поставки на отчёт, номер файла закреплён навсегда, правка — «замени из файла N целиком» (DV-01).
3. Каждый шаг владельца — со стоп-точкой: «красное — дальше не идти, прислать текст ошибки целиком» (DV-13).
4. «Долго» — сначала протокол DevTools и раскладка по слагаемым; «сломалось» — сначала факты (PR-08, PR-10).
5. В репозитории — инструменты, исходники, поставка и выводы; ни скратча, ни данных боя (PR-06, AC-16).

## 1. Цикл одной задачи

| Шаг | Что делать | Готово, когда |
|---|---|---|
| 0. Вход | `git pull`; CLAUDE.md целиком → NOTES.md чарта → нужный раздел `docs/`; разобрать `inbox/` (PR-01, PR-21) | знаешь, что стоит в бою и на каком шаге работа |
| 1. Воспроизвести | ровно симптом владельца на файлах **стоящей** поставки (штамп, тег), тем же доступом, на мире масштаба боя, в модели борда; смотреть видимый текст (PR-09) | в NOTES: «воспроизведено: шаг, логин, версия» |
| 2. План в NOTES | гипотеза, правка, чем проверим, что меряем — **до** кода, со статусом (PR-03) | следующий шаг записан до начала |
| 3. Правка | только исходник (`proteus/*`), не файл поставки; одна область за заход | папка поставки не тронута |
| 4. Гейт стенда | маршрут §7 на исходнике и на файлах поставки; FAIL — гипотеза (ST-33, PR-13) | 0 провалов, иначе коммит «WIP — не для установки» |
| 5. Замер | тот же сценарий на 24.8, медиана из трёх; ответ тот же (`same.py`); «было → стало» с единицами (PR-11) | медленнее хоть где-то — откат или цена числами |
| 6. Поставка | `pack.py` → `--check` → «Что нового» → «проверено / не проверено» → коммит «N-я поставка: …», тег (DV-11, PR-22) | владелец ставит без вопросов |
| 7. Инвариант | решение владельца — в CLAUDE.md с датой и цитатой тем же коммитом; подтверждённое в бою — в «Бой: что известно»; факт платформы — в гайд и grep по проектам (PR-02, PR-05, PR-25) | нет двух противоречащих правил |
| 8. Уборка | скратч удалить, опыт — одной строкой-правилом (PR-06) | `git status` чистый |

Владелец не ответил — не стой: делай по умолчанию, запиши решение в NOTES §4 так, чтобы его меняла одна правка
(константа `CFG`, `{% set %}`) (PR-15).

## 2. Память проекта — точка восстановления

- **CLAUDE.md** — короткий вход до 30 КБ: что это, ветка, «Куда идти» (задача → файл → маршрут проверок командами), стенд,
  «Инварианты», «Что не проверено стендом», «Бой: что известно». Длинное — в `docs/architecture.md`. Пути в нём
  существуют — проверка в PR-01.
- **NOTES.md по чарту**: §0 план со статусами TODO / DOING / DONE, §1 реестр макета, §3 поля «макет ↔ SQL», §4 решения
  владельца (дата, дословно), §5 БЛОКИ скилла, §6 хвосты. После обрыва — NOTES целиком, продолжать с первого пункта
  ≠ DONE; `.chart.js` не перечитывать целиком — grep или offset (PR-03).
- **docs/architecture.md** — как устроено и почему, с отвергнутыми вариантами; текущее переписывай на месте (PR-04).
- Память сессии — не замена репозиторию. Опровергнутое правь там, где стоит, тем же коммитом (PR-07).

## 3. Папка поставки

```
Поставка — <Отчёт>/                 ← одна на отчёт, в ветке владельца
  0. Инструкция.md                  ← единственный файл, написанный руками
  0б. SQL Lab — разведка.sql        ← до проекта датасета, маскирован
  1. Helicopter — ноут.yaml         ← 1а — только изменённые параграфы, без переимпорта
  2. Датасет «<имя>».sql            ← по файлу на датасет
  3. Чарт «<имя>».js                ← сжатая сборка одной строкой
  4. CSS борда.css                  ← весь CSS отчёта, id подставлены
  5. JSON-метаданные борда.json     ← блок chart_configuration
  6–9. SQL Lab: проверки после выгрузки, один запрос, «где время»; сниппет разметки (DevTools)
История поставок.md, inbox/         ← рядом
```

- **Номер закреплён за объектом**: «файл 3» — всегда чарт; буква — дополнение (1а, 2b). Номера не сдвигай, датированных
  папок не заводи (DV-01).
- **Правка — одной фразой: «замени из файла N целиком».** Внутри файла — только заглушки из шапки, с числом мест:
  «Ctrl+H `ваш_логин` → твой логин (все 3 места)» (DV-05).
- **Собирает скрипт** (`stand/pack.py` по `kit/pack_template.py`): сжатый JS, id, SQL Lab-файлы, штамп «поставка N · дата ·
  sha12» в каждом файле и в `meta.build`; `--check` сверяет копии; список изменённых файлов = строка «Заменить:» (DV-03, DV-09).
- **Одно рискованное изменение на поставку** — пробой на одном чарте копии борда («Проба — <что>/» с откатом).
  Безопасность — отдельной срочной поставкой. Мелкое — копить до вечера (DV-08, DV-23, DV-33).

**«0. Инструкция.md»** ([шаблон](../proteus-playbook/templates/instruction.template.md)) по порядку: 2–3 строки об отчёте;
«Текущая поставка N от дд.мм · sha12», ветка; правило «красное на любом шаге — дальше не идти, прислать текст ошибки
целиком; подозрительное — скриншот всего экрана»; таблица «Файл | Куда вставлять | Менялся в поставке»; «Если у вас стоит
≤ K»; «Что нового» — 2–3 последние поставки, остальное — в «История поставок.md» (DV-12); «С чего начать» — «шаг | где |
что сделать | готово, когда»; «Если что-то не так» — симптом **дословно** → причина → что сделать, со строками «стоит
старая версия файла N» и «поставлено в неверном порядке» (DV-14); «Что проверено» числами; «Что стендом не проверено» —
риск → чем подтвердить в бою (DV-15); проверки на бою.

**«Что нового»** — по одному формату (DV-11):

```markdown
## Что нового (N-я поставка, дд.мм — <главное словами владельца>)
**Заменить: файлы 2 и 3 (сначала 3, потом 2: старый чарт новый ответ не прочтёт).** Не менялись: 1, 4–9.
**<Симптом словами владельца>.** Причина: … Сделано: … Было → стало: ClickHouse 4,2 → 1,1 с (стенд),
ответ 6,8 → 2,1 МБ, код чарта 232 → 139 КБ. Для пользователей: <что увидят / «ничего не меняется»>.
- **Проверить (минута):** <что увидеть>.  - **Прислать:** <что и зачем>. Не легло — <откат>.
```

- Формат ответа меняй совместимо в обе стороны: новый JS читает старый ответ, новый SQL добавляет роли. Тогда порядок
  установки любой; иначе — порядок с причиной (DV-10).
- После замены датасета — предупреди о холодном кэше числами (DV-22).

**Шаги после вставки — целиком** (DV-18):
- датасет: SQL целиком → Save → колонки менялись — «Синхронизировать столбцы» → «Измерения» в чартах → Save; «Время жизни
  кэша» — пусто или 0, не −1;
- чарт: JS целиком → Update chart → Save → жёсткая перезагрузка борда (Cmd/Ctrl+Shift+R);
- CSS: прежний блок отчёта удалить, файл — целиком в конец → Сохранить → жёсткая перезагрузка;
- JSON: вставить → сохранить свойства и дашборд → опубликовать → обновить → открыть JSON и сверить.

Для развилки дай однострочник в консоли, ответ которого выбирает следующую ветку (DV-13).

## 4. Что просить у владельца

**SQL Lab** (PL-04, DV-27, DV-28): один запрос, первое слово `SELECT` или `DESCRIBE`; слов `system` и `SHOW` нет нигде,
даже в комментариях; `WITH` первым не пиши. Файл собирает скрипт из исходника датасета, уже отрендеренный, без Jinja;
логин — заглушкой. Ответ — таблица «часть · метрика · значение · пояснение» на 50–400 строк. Настройки — `getSetting`,
версия — `version()`. Время: первый прогон после простоя, повтор — с меткой **в запросе** (`2 AS run`): комментарии SQL Lab
вырезает. Ответ поедет в репозиторий — маска в самом запросе: промилле, хеши, `EXCEPT` по именам из `DESCRIBE` (AC-15).

**DevTools** (DV-29): F12 → Network → фильтр `api/v1` → «Обновить дашборд». Холодный чарт: POST `chart/data` → 202 →
`async_event` → GET `qc-…`; из кэша — один POST 200. Бланк ответа:

```
вкладка / чарт: …
POST chart/data: Status …, Size …, Time … (отправка … / ожидание … / приём …)
GET qc-…: Size …, Time …, раз …;  Payload: размер …, url_params …
Response: cache_key у меня … / у коллеги …; cache_timeout …;  SQL Lab «где время»: … с / … с
```

| Хочу узнать | Попроси |
|---|---|
| где время | бланк выше + файл «где время» |
| кэш личный или общий | `cache_key` у двух людей при тех же фильтрах: разный — личный |
| есть ли `GROUP BY` в обёртке | Response → `result[0].query` |
| почему пропал чарт | текст на месте чарта, Console целиком, скриншот всего экрана |
| почему CSS не лёг | вывод сниппета разметки: он сам пишет «замени 209 на 201» |
| что стоит | штамп в подсказке «Как работать» |

Не проси HAR, тела ответов и «сохрани всё»: там данные сотрудников (PR-20). Ответы владелец кладёт веб-интерфейсом
GitHub в `inbox/`; разбор — в `docs/`, сырое — почистить до схемы и главного (PR-21).

## 5. «Долго грузится»

1. Уточни одной просьбой: чарт и действие (открытие, «Применить», клик); всегда или первый раз; у кого; сколько секунд;
   стоящая поставка.
2. Факты до правки: протокол DevTools, «где время» тремя прогонами, тот же сценарий на стенде. Таблица слагаемых — в NOTES.
3. Рычаг — по **самому большому** слагаемому (PR-08):

| Слагаемое | Где видно | Ориентир | Рычаг |
|---|---|---|---|
| отправка кода чарта (каждый POST) | Timing «отправка» | 50 КБ ≈ 1 с | сжатая сборка (CJ-21) |
| разбор Superset ради ключа | «ожидание» у POST 200 | ≤ 0,5 с | короче текст, логин в ключе только где нужно (SP-22) |
| `reindent` + ClickHouse | 202 → готово; SQL Lab | ≤ 1 с; ≤ 15 с холодно на стенде | линейные CTE, скаляр-контекст (CH-05) |
| приём ответа | Size, Timing приёма | 1 МБ ≈ 2 с | колонки, словарь, base64 (DS-18) |
| «первый раз у каждого» | — | — | общий кэш для общего ответа (AC-06) |

4. Замер «было → стало» с тем же ответом → «Что нового» → подтверждение в бою тем же протоколом (PR-11). Полностью —
   [perf-triage.md](../proteus-playbook/checklists/perf-triage.md).

## 6. «Сломалось»

1. **Сначала факты:** текст на месте чарта целиком, скриншот всего экрана, Console целиком; для данных — Response и
   Payload `chart/data`; номер стоящей поставки (PR-10).
2. **Откат до прошлой рабочей поставки — можно без фактов.** Новая правка — только с фактами или пробой на копии.
3. Текст — в таблицу симптомов: «Некорректный SQL запрос: →…←» — сохранение (SP-04); «multiple statements» — лексер
   (SP-06, SP-07); отрисовался и пропал — песочница (SB-03); жёлтая плашка — области кросс-фильтров (MC-09); «нет
   колонок» — «Измерения» и синхронизация (DV-18). «У соседа старое» — сначала жёсткая перезагрузка.
4. Воспроизведи на старом коде, поправь, проверь новый (PR-09). В коммите — ссылка на присланный факт; симптом — новой
   строкой в «Если что-то не так» той же поставкой (DV-14).

## 7. Стенд и kit: что гонять перед сдачей

Стенд — в первый день, до кода датасета: `bash ../proteus-playbook/kit/setup.sh` ставит chdb 2.1.1 (= ClickHouse 24.8),
sqlparse 0.4.3 + патч Superset 2.1.0 (модель боя), второй venv с 0.4.4 (запас), terser 5.51.2, eslint 10.1.0, playwright
1.56.1. `version()` не 24.8 — прогон падает (ST-01). Флаги — [kit/README.md](../proteus-playbook/kit/README.md).

| Что | Чем | Норма |
|---|---|---|
| Ответ | `stand/check.py`: Nullable и plain, режимы, оракул | 0 провалов |
| Путь Superset, ключ, бюджет | `kit/superset201.py --run --hostile --matrix` в **обоих** venv | ответ после пути = прямой; ЛИЧНЫЙ / ОБЩИЙ где задумано; < 256 КиБ, `reindent` ≤ 1 с |
| Сохранение | `kit/sqlgate.py` | 0 ошибок |
| Ответ тот же | `stand/same.py` против тега прошлой поставки | 0 расхождений |
| Чарт | `node --check` → ESLint no-undef → `check.py` скилла | 0 ошибок, оспоренных ≤ 2 |
| Песочница | `kit/sbx/run.cjs` / `live.py` + `click.cjs`: каждый контрол, полосы Windows, тур | 0 ошибок консоли |
| Сборка | `pack.py --check`, `kit/min.cjs --verify` | ES5, ≤ бюджета КБ |
| Файлы поставки | те же прогоны с `DIST=1`; validate скилла — только по исходнику | 0 провалов |
| SQL Lab-файлы | `sqlgate.py --sqllab`, исполнение на 24.8 | без `system`, SHOW |

Полностью — [before-delivery.md](../proteus-playbook/checklists/before-delivery.md), после вставки —
[after-delivery.md](../proteus-playbook/checklists/after-delivery.md). Среда блокирует проверку — 2–3 попытки, дальше
отказ дословно и вопрос; не обходи другим инструментом и не перебирай флаги Chrome (PR-14).

## 8. Гигиена репозитория

- В репозитории — `stand/`, `proteus/`, папка поставки, выгрузка борда владельца (оракул и откат), `docs/`, `inbox/`.
  Пробы, дампы, миры chdb, скриншоты, логи — в скратче сессии вне репозитория; по закрытии этапа удалить (PR-06).
- Опыт — строкой-правилом в CLAUDE.md или гайд, а не файлом пробы.
- Данные боя — только агрегатами. HAR, тела `chart/data`, логины и ФИО не коммитить; попало — удалить из истории и
  сказать владельцу (AC-16). Репозиторий может быть публичным.
- Перед коммитом — `git status` и grep изменённых файлов на `"result":`, `.har`, логины и домены боя.
- Ветка — та, что читает владелец, её имя — в CLAUDE.md и инструкции; поставки различают теги `<проект>-N` (PR-23, DV-34).
- Применённые и перекрытые поставки удаляй тем же коммитом, где они стали ненужны.

## 9. Тексты и общение

- **Интерфейс — на «ты»**: подсказки, пометки, пустые состояния, тур, плашки («сними выбор», «твой логин») — решение
  владельца 09.10.
- Владельцу — так же коротко и повелительно: «замени файл 3 целиком», «пришли текст ошибки». Обращения не смешивай.
- Симптом — словами владельца, числа — с единицами, стенд и бой — раздельно.
- Вопрос — с вариантами и умолчанием: «A или B? Не ответишь — сделаю A, меняется одной строкой» (PR-19).
- Каждая просьба — что прислать, зачем и в каком виде, с бланком. Не проси невыполнимого: служебные таблицы SQL Lab
  не читает, собирать запрос из датасета с Jinja владелец не должен.
- Новое, чего владелец не видел, — сначала макетом на синтетике в `Идеи/` (PR-17).

Полный — [templates/CLAUDE.md.template](../proteus-playbook/templates/CLAUDE.md.template). Короткий каркас:

```markdown
# CLAUDE.md

<Отчёт> — борд <N> в Proteus (форк Superset 2.1.0, JS-чарты react_sanbbox в iframe, ClickHouse 24.8): <чарты,
датасеты, источники>. Бой отсюда недоступен: владелец вставляет файлы руками по инструкции поставки.

**Поставка:** `Поставка — <Отчёт>/`, текущая — <N> от <дд.мм>, тег `<проект>-<N>`.

## Инструкции команды
Перед работой прочитай `agent-instructions/README.md` и файлы под задачу: вид — 01, SQL — 02, JS чарта — 03,
CSS борда — 04, поведение — 05; перед сдачей — 06 и 07. Полный гайд с кодами правил — `proteus-playbook/SKILL.md`.
Решения владельца этого проекта важнее — записывай их в «Инварианты».

## Куда идти
| Задача | Файл → маршрут (красное — стоп) |
|---|---|
| Датасет | `proteus/<x>.data.sql` → `stand/check.py` → `kit/superset201.py` (оба venv) → `kit/sqlgate.py` → `stand/same.py` |
| Чарт | `proteus/<x>.chart.js` → `node --check` → ESLint no-undef → `check.py` скилла → модель песочницы |
| Отдать владельцу | `checklists/before-delivery.md` → `stand/pack.py --check` → «Что нового» → коммит и тег |

## Стенд
<команды с комментарием; синтетические логины мира и их доступ>

## Инварианты — не ломать
- **<Правило>** (владелец, дд.мм: «<цитата>»). Почему: <инцидент с числами>. Проверка: <шаг регресса>.

## Что не проверено стендом
- <риск> → чем закрыть: <файл N / DevTools / вопрос владельцу>.

## Бой: что известно
- <факт с числом и единицей> (<источник>, дд.мм).
```
