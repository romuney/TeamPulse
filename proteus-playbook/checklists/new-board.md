# Чек-лист: новый борд — от разведки источника до первой поставки

**Зачем.** Новый борд в Proteus проходит одни и те же шаги, и пропуск любого стоит поставки: датасет, спроектированный
до разведки, считает не то; чарт без модели песочницы гаснет у коллег; CSS дельтой не ложится на новый борд. Здесь —
порядок работ с критерием «готово, когда» у каждого шага и ссылками на правила. Перед сдачей —
checklists/before-delivery.md, после — checklists/after-delivery.md.

**Главное в 5 пунктах.**
1. **PR-16, DV-31.** Сначала разведка источника одним маскированным запросом, потом архитектура датасета.
2. **AC-06, DS-09, DS-10.** Число датасетов решают ключ кэша и параллельность: зависящее от пользователя — личный
   датасет (логин в `{{ }}`), общее и тяжёлое — общий датасет без логина.
3. **ST-01, ST-05, ST-12.** Стенд в первый день: ClickHouse 24.8, мир масштаба боя, путь Superset 2.0.1 в двух моделях
   лексера.
4. **SB-03, SB-20, CJ-21.** Чарт — по скиллу, но с обёрткой `onerror`, в модели песочницы и сжатой сборкой.
5. **DV-01, DV-03, ST-33.** Одна папка поставки, собранная скриптом; отдавать — только после зелёного гейта.

Метки уверенности правил — в главах. Здесь `<playbook>` — путь к гайду, `<kit>` — `<playbook>/kit`, `<скилл>` —
`<путь к adoption>/skills/proteus-echarts-builder` (коммит `e77d754`).

## 1. Разведка источника — до архитектуры

- [ ] Файл «0б. SQL Lab — разведка <источник> одним запросом.sql» собран генератором `stand/recon.py` (DV-31):
      один SELECT (первое слово SELECT или DESCRIBE), без слов `system` и `SHOW` даже в комментариях (PL-04); ответ —
      длинная таблица `часть · метрика · значение · пояснение`, 50–400 строк.
- [ ] Маскирование в самом запросе (AC-15): ни имён, ни ключей юнитов, суммы — в промилле, ПДн — `* EXCEPT (…)`,
      сверенный с `DESCRIBE TABLE`, ключ сотрудника — `cityHash64(key) % 100000`. **Готово, когда:** на симуляции
      источника (`truth.json`) запрос находит всё заложенное, а в ответе нет имён, ключей и абсолютных сумм (ST-07).
- [ ] Что спрашивает разведка (GP-10, PR-16):
  - [ ] накопительность: строка родителя против суммы детей на последний месяц;
  - [ ] уровни и кардинальности: юнитов по уровням, значений справочников, элементов массивов на человека;
  - [ ] повторы и дубли: юнит ниже по пути заполнен им же (узлов ≫ листов, DS-21), юнит под двумя родителями;
  - [ ] пустые и спецзначения: «-», «не указано», NULL, символы `]`, `'`, `--`, `;`, слэш в конце;
  - [ ] свежесть и закрытые периоды (DS-06, DS-07); выгрузка: Nullable, `array_type_cast`, `order_by` (GP-19, GP-20);
  - [ ] таблица доступа: по какому логину, виды доступа, есть ли склейка логинов (AC-01).
- [ ] Ответ владелец кладёт в `inbox/` веб-интерфейсом GitHub; разбор — в `docs/` (или SOURCES.md) с датой, сырое —
      почищено до схемы (PR-21). Числа разведки сверены с пределами и соседними числами (PR-12).
- [ ] Вопросы владельцу — с вариантами и умолчанием «не ответите — сделаю A» (PR-19); без ответа — умолчания в NOTES §7,
      каждое меняется одной правкой (PR-15). Второй заход разведки пробник не блокирует.

## 2. Архитектура — в `docs/architecture.md` до кода

- [ ] Число чартов и датасетов (MC-01, MC-17, DS-09): один экран — сколько запросов параллельно, кто кого фильтрует.
      Ответ зависит от пользователя → личный датасет; не зависит → общий, без логина (AC-06, DS-10, AC-10: в общем —
      ничего скрываемого, цена согласована с владельцем).
- [ ] Контракт: узкие колонки (`role k v n j`), роли строк, форматы полей, носители и их пределы — шапкой датасета
      (DS-01, DS-26) и в `proteus/FIELDS.md` (чек-лист «Настроить руками» — галочки ставит владелец).
- [ ] Что едет одним ответом, чтобы взаимодействия шли без запроса (DS-11, MC-19, MC-21); что считает JS той же
      семантикой, что SQL (DS-12, MC-20); датасет отдаёт аддитивные компоненты, доли — JS (DS-04).
- [ ] Бюджеты записаны числами: вес ответа на боевой кардинальности — JSON и на проводе (DS-16); холодный худший запрос
      на стенде ≤ 15 с, клик ≈ 1 с (PL-02); сжатая сборка чарта ≤ 150 КБ (DV-06); строк ответа ≪ 50 000 (DS-24).
- [ ] Свои витрины в Helicopter — только если без них не уложиться (GP-14): предагрегат раз в сутки, `order_by` под
      фильтр, `array_type_cast=True` у таблиц с массивами, стоп-проверки перед выгрузкой (GP-08, GP-19, GP-20).
- [ ] Предложение, которого владелец не видел, — сначала макетом на синтетике в `Идеи/` (PR-17).
