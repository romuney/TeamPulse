# 03. Доступ внутри датасета и кэш Proteus (AC)

**Зачем глава.** Права Proteus на дашборд и датасет — обычные: строки по пользователю они не режут. Кто какие
данные видит, решает SQL датасета по `current_username()`. При этом кэш Proteus (12 ч) может отдать ответ одного
пользователя другому, если логин не попал в ключ. Может и наоборот: делать холодным первое открытие у каждого
коллеги там, где ответ у всех одинаковый. В главе — как строить доступ, как решать «личный ключ или общий кэш»,
как закрывать дыру кэша, когда прогрев полезен, а когда это утечка, как чистить ввод, разведывать боевые таблицы и
проверять всё это на коллеге. Механика пути и ключа кэша — в 02-superset-path.md (SP-20…SP-24).

**Главное в 5 пунктах.**
1. **AC-01, AC-02.** Доступ — только внутри датасета, по логину сессии. Отказ — штатный ответ (`meta` с `ok = 0`), а не ошибка.
2. **AC-06.** Ключ кэша выбирай по зависимости ответа. Ответ зависит от пользователя — логин в ключе. Не зависит — общий кэш. Смешанный ответ раздели на два датасета.
3. **AC-07, AC-08.** Логин в ключ попадает только через вызов внутри `{{ … }}` на одной строке. Регресс проверяет это регуляркой Superset по сырому тексту.
4. **AC-12, AC-13.** Дыру кэша закрывай срочно: реальная правка, Save, `cache_key` у двух логинов. Прогревай только общий кэш.
5. **AC-14, AC-16.** Ввод носителей — только через макросы с пределами и белыми списками. Данные боя в репозиторий не клади.

Метки уверенности — как в 01-platform.md: [бой], [стенд 24.8], [исходник 2.0.1], [владелец дд.мм], [вывод],
[не проверено в бою].

## Доступ внутри датасета

### AC-01. Решай доступ только внутри датасета по `current_username()`
- **Почему:** Proteus не режет строки по пользователю. Права на дашборд и датасеты — общие, а есть ли у форка RLS, неизвестно (01-platform.md, «Что ещё не известно»). Все запросы в ClickHouse идут под одной учёткой подключения, поэтому `currentUser()` ClickHouse — сервисная учётка, а не зритель борда. Единственный носитель личности — `current_username()` в Jinja.
- **Как:** Цепочка доступа стоит в начале запроса, одной CTE или скаляром:
  1. Логин сессии нормализуй один раз: `(current_username() or '')|string|trim|lower`.
  2. Если логины в компании менялись, переводи логин в актуальный по таблице склейки — тем же каноном, каким склеены владельцы и авторы (ETL, 06-helicopter-gp.md).
  3. По таблице доступа получи корни зоны и роль.
  4. Запрошенный фильтром юнит пропускай, только если корень зоны есть в его пути. Иначе откатывай на свою зону, а откат отдавай в эхо `meta`.

  ```sql
  acc AS (
    SELECT arrayDistinct(if(notEmpty(r_all), r_all, r_zone)) AS roots,
           multiIf(has(rl, 'super'), 'super', notEmpty(r_zone), 'hrbp', 'none') AS my_role
    FROM (
      SELECT groupArrayIf(ifNull(root_id, ''), ifNull(role, '') = 'super') AS r_all,
             groupArrayIf(ifNull(root_id, ''), ifNull(role, '') = 'hrbp') AS r_zone,
             groupArray(ifNull(role, '')) AS rl
      FROM <схема>.<таблица_доступа>
      WHERE login = {{ qs((current_username() or '')|string|trim|lower) }}
    )
  ),
  un AS (
    SELECT groupArrayIf(uid, has({{ qa(unit_req) }}, uid) AND hasAny(path, acc.roots)) AS req_ok …
  )
  ```

  `currentUser()` и `user()` ClickHouse для доступа не используй.
- **Проверка:** На стенде мир с логинами всех видов доступа (AC-04): у каждого логина в ответе только его зона. Запрос чужого юнита даёт откат на свою зону и пометку в `meta`.
- **Уверенность:** [стенд 24.8] — логика; [вывод] [не проверено в бою] — `currentUser()` = учётка подключения.
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (CTE `acc` и `un`: роль, корни зоны, `req_ok`); adoption:Виджеты/pa-reports-body.data.sql (секция `me`: перевод логина по таблице склейки).

### AC-02. Отдавай отказ в доступе штатным ответом, а не ошибкой
- **Почему:** Логин без строки доступа — нормальная ситуация: новый сотрудник, коллега на пробе, сам владелец при Save. Сохранение и синхронизация исполняют датасет с логином сохраняющего (02-superset-path.md, SP-05). Прежний датасет DL у такого логина падал: «Scalar subquery returned empty result». В чарте ошибка датасета выглядит как поломка отчёта, а не как «нет доступа». А при Save под логином без строки доступа упало бы и сохранение.
- **Как:**
  - Строку доступа читай агрегатом, который не бывает пустым (`arrayElement((SELECT groupArray(…)), 1)` и `count()`), — техника в 04-clickhouse.md, CH-09.
  - При нуле строк ответ — только `meta` с `ok = 0`, без людей и без ошибки; итоги в `meta` закрыты условием (05-dataset.md, DS-08).
  - Реши с владельцем, что человек без доступа видит в общих чартах: значения фильтров, счётчики, справочник (AC-10). Запиши это в инструкцию.
  - Чарт по `ok = 0` пишет «Нет доступа к отчёту» и куда обратиться за доступом.
- **Проверка:** На стенде логин `nobody` (без строки доступа) на каждом виде и каждом наборе фильтров отдаёт только `meta` с `ok = 0`, без ошибки, на обоих анализаторах. Режим AlwaysTrue под `nobody` исполняется.
- **Уверенность:** [стенд 24.8] (Code 125 на пустом кортеже-скаляре); [владелец 08.10] — что видит логин без доступа в DL.
- **Образец:** detail_list:proteus/detail-list.data.sql (скаляры `warden_array` и `warden_n`, макрос `gate`, `'ok'` в `meta`).

### AC-03. Не отдавай ничего вне зоны: ни юнитов, ни справочника, ни эха
- **Почему:** Утечка бывает не только в строках таблицы: справочник для поиска, список HRBP, цели KPI, дерево, подсказки, эхо запрошенного юнита. HRBP держит инвариант «юниты вне зоны не приезжают ни в каком виде». Справочник там — вся зона логина на всю глубину, плюс предки корней ради пути в шапке.
- **Как:** Каждая часть ответа (роль строки) берёт юниты только из отфильтрованного по зоне множества (`acc.roots`, `req_ok`). Предков корней отдавай без чисел, только для пути. В эхо — только то, что прошло проверку. Пересчёт счётчиков (фасеты, окно фильтров) — тоже внутри зоны.
- **Проверка:** На стенде для каждого логина собери множество id из всего ответа (все роли, все поля, `meta`) и сравни с зоной плюс предками корней: лишних нет.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:stand/check.py (раздел доступа: зона, откат, `nobody`).

### AC-04. Переноси логику доступа дословно и сверяй с прежним датасетом-оракулом
- **Почему:** Требование владельца — «доступ не слабее текущего». Логику доступа (флаги, исключения, маски полей, персональные правила по задачам) пересказать нельзя. Условия флагов DL совпадают с обоими прежними датасетами дословно (сверка текста 06.10).
- **Как:**
  - Блок доступа переноси из прежнего датасета (выгрузки борда владельца) слово в слово. Меняй только обвязку: скаляры (AC-02), `ifNull`.
  - Прежний датасет исполняй на стенде как оракул: при тех же логинах и фильтрах новый обязан дать тех же людей, те же значения и те же маски.
  - Логины мира стенда — по одному на каждый вид доступа:
    - полный (`hr.super`, `a.sergeeva`);
    - частичный с масками (`a.user`);
    - лидер профессии или HRBP с зоной (`p.lead`, `b.kotov`);
    - две корневые ветки и младший внутри (`s.volkov`);
    - без строки доступа (`nobody`).
  - Персональные правила с конкретными логинами из прежнего датасета остаются только в SQL датасета. В документы, гайд и публичные репозитории их не копируй.
- **Проверка:** На стенде: виды доступа × наборы фильтров, ответ нового = ответу оракула (у DL — 4 × 17). В бою — проба на коллеге (AC-18).
- **Уверенность:** [стенд 24.8] + [владелец 06.10] (требование «не слабее»).
- **Образец:** detail_list:stand/check.py (раздел 1: сверка с прежним датасетом по видам доступа).

### AC-05. Прячь поля коротким маркером `'⛔'`, полный текст рисует чарт
- **Почему:** Прежний датасет DL отдавал вместо скрытого поля длинный текст, и ответ частичного доступа весил 84 МБ против 74 МБ у суперпользователя. Доступ в DL прячет поля, а не строки: человек виден, его оценка — нет.
- **Как:** Датасет отдаёт `'⛔'`. Чарт показывает «⛔️ Нет доступа к данным», а в «Копировать» отдаёт прежний текст. Если общий чарт (панель фильтров, счётчики) построен по тем же данным, проверь, что его атрибуты не пересекаются со скрываемыми полями. В DL 23 скрываемых поля не входят в атрибуты панели, поэтому счётчики панели скрытого не раскрывают.
- **Проверка:** На стенде у частичного доступа скрытые поля = `'⛔'`, остальные совпадают с оракулом. Пересечение «атрибуты общих чартов ∩ скрываемые поля» пусто.
- **Уверенность:** [стенд 24.8].
- **Образец:** detail_list:proteus/detail-list.data.sql (маска `'⛔'`) и detail_list:proteus/detail-list.chart.js (подпись и текст для «Копировать»).

## Ключ кэша: личный или общий

### AC-06. Выбирай ключ кэша по зависимости ответа: личный — только там, где ответ зависит от пользователя
- **Почему:**
  - Ответ, зависящий от пользователя, в общем кэше уходит другим на 12 ч. 07.10 так было в трёх отчётах: зона админа у HRBP, маски доступа у DL, «Мои» у adoption.
  - Ответ, одинаковый у всех, с личным ключом холоден у каждого. DL 22–24-я поставки: панель (3–7 с ClickHouse, ≈ 4,2 с разбора, 6–8 МБ) у каждого коллеги считалась заново. Отзыв 08.10: «фильтры не грузятся или грузятся очень долго; второй раз — быстро».
  - Владелец 08.10: логин в ключ — только по зависимости ответа.
- **Как:**

  | Ответ зависит от… | Ключ | Как | Пример |
  |---|---|---|---|
  | пользователя: зона, маски, «Мои» | личный | вызов в `{{ … }}` (AC-07) | HRBP целиком; DL список; adoption каталог |
  | только фильтров и данных | общий | ни одного вызова нигде (AC-09) | DL панель фильтров; adoption шапка и панель; TeamPulse |
  | и того, и другого | раздели на два датасета и два чарта | личный — лёгкий (AC-11), общий — тяжёлый | DL: список (личный) + панель (общая) |

  Тяжёлое и общее держи в датасете без логина. Сколько датасетов заводить и что положить в общий — 05-dataset.md, DS-09 и DS-10. Если личного в ответе мало (например, кнопка «Мои» над общим каталогом), рассмотри вынос личного в отдельный лёгкий датасет. Это [вывод], решение — за владельцем.
- **Проверка:** На стенде регресс регулярок (AC-08): у личных вызов находится, у общих — нет. В бою — `cache_key` у двух логинов при тех же фильтрах: у личного разный, у общего одинаковый.
- **Уверенность:** [владелец 08.10] + [бой] (инциденты 07.10 и 08.10).
- **Образец:** detail_list (датасеты 1–2 с логином в ключе, 3–4 — общие; `ch.view_text` в stand/ch.py).

### AC-07. Ставь логин в ключ вызовом внутри `{{ … }}` в одной строке
- **Почему:** Регулярка Superset 2.0–4.0.2 ищет вызов только внутри `{{ … }}` на одной строке, по сырому тексту (02-superset-path.md, SP-20). `{% set me = current_username() %}` она не видит: Superset не рендерит датасет ради ключа, и ответ первого открывшего уходит всем. 07.10 — одна и та же дыра в трёх отчётах:
  - adoption: «Мои» показывал логин того, кто открыл борд первым. Первая правка — `cache_key_wrapper` в `{% set %}` — не помогла, помогла вторая (вызов в тексте SQL).
  - HRBP: ответ кэшировался общим, HRBP мог получить зону админа (17-я поставка, срочно).
  - DL: ответ с масками доступа одного пользователя мог уйти другому на 12 ч (22-я поставка).
- **Как:** Вызов стоит там, где логин и так нужен — в условии доступа:

  ```jinja
  WHERE login = {{ qs((current_username() or '')|string|trim|lower) }}
  ```

  Или макросом, у которого тело — одна строка с `{{ … }}`. Тогда регулярка находит строку определения, а вызывать его можно где угодно:

  ```jinja
  {% macro login_q() -%}{{ qs((current_username() or '')|string|trim|lower) }}{%- endmacro %}
  … WHERE ad_login = {{ login_q() }}
  ```

  Годится и `'{{ cache_key_wrapper(current_username()) }}'`, но без экрана: лучше через `qs` (02-superset-path.md, SP-06).

  Не работают в 2.0:

  | Форма | Почему |
  |---|---|
  | `{% set me = current_username() %}` | нет `{{` |
  | `{% set _ = cache_key_wrapper(me) %}` | нет `{{` |
  | `{{\n current_username()\n}}` | вызов на трёх строках, регулярка без DOTALL |
  | `{# {{ current_username() }} #}` | регулярка найдёт, но вызова при рендере нет — логин в ключ не попадёт |
- **Проверка:** На стенде регресс AC-08. В бою после Save — `cache_key` в Response у двух логинов при тех же фильтрах разный.
- **Уверенность:** [бой] (три инцидента 07.10) + [исходник 2.0.1] (`ExtraCache.regex`).
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (CTE `acc`, условие `WHERE login = {{ qs(…) }}`); detail_list:proteus/detail-list.data.sql (макрос `login_q`).

### AC-08. Проверяй ключ регуляркой Superset по сырому тексту в регрессе
- **Почему:** Стенд adoption записывал логин в ключ при **любом** вызове `cache_key_wrapper`, без регулярки. Поэтому правка «в `{% set %}`» прошла регресс (§12 `check_one`) и в бою не сработала: понадобились три итерации за ночь. Регулярка — единственный путь логина в ключ, и регресс обязан делать то же, что Superset.
- **Как:**

  ```python
  import re
  R20 = re.compile(r"\{\{.*(current_user_id\(.*\)|current_username\(.*\)|cache_key_wrapper\(.*\)|url_param\(.*\)).*\}\}")
  R41 = re.compile(r"(\{\{|\{%)[^{}]*?(current_user_id\([^()]*\)|current_username\([^()]*\)|current_user_email\([^()]*\)"
                   r"|cache_key_wrapper\([^()]*\)|url_param\([^()]*\))[^{}]*?(\}\}|\%\})")
  raw = open(dataset_path, encoding='utf-8').read()          # текст, который владелец вставит в Proteus
  code = re.sub(r'\{#.*?#\}', '', raw, flags=re.S)            # без комментариев Jinja
  if personal:   # вызов должен найтись в КОДЕ (закомментированный логин в ключ не кладёт)
      assert R20.search(code) and R41.search(code), 'логин не попадёт в ключ кэша'
  else:          # общий кэш: ни одного совпадения даже в СЫРОМ тексте с комментариями
      assert not R20.search(raw) and not R41.search(raw) and 'current_username(' not in code
  assert not R20.search("{% set me = current_username() %}")  # анти-пример держит регулярку честной
  ```

  - Регресс проверяет **файлы поставки**, а не только исходник: сборка могла подменить строку.
  - Эмуляция `current_username` и `cache_key_wrapper` на стенде кладёт значение в ключ, только если `R20` нашла вызов в сыром тексте.
  - При рендере каждый `current_username` вызывается с `add_to_cache_keys=True` — это тоже проверь.
- **Проверка:** Регресс падает на анти-примере в датасете. В бою — сверка `cache_key` (AC-07).
- **Уверенность:** [бой] (adoption 07.10) + [исходник 2.0.1].
- **Образец:** detail_list:stand/parse.py (`CACHE_RX`, `cache_problem`: обе регулярки, общий — по сырому тексту); HRBP_HUB:stand/check.py (раздел 7: комментарии вырезаются, проверка `add_to_cache_keys`).

### AC-09. Для общего кэша убери все вызовы — из кода, комментариев, предиката и RLS — и докажи, что ответ одинаков у всех
- **Почему:**
  - Регулярка читает сырой текст вместе с комментариями, а ещё предикат автозаполнения, WHERE/HAVING чарта и RLS. Одно совпадение — и Superset рендерит датасет ради ключа на каждом запросе.
  - Регулярка 4.1+ видит и `{% set L = url_param(…) %}`: после обновления Proteus общий кэш тихо станет личным.
  - Без совпадений ключ считается без рендера и без sqlparse, кэш общий на 12 ч, холодно платит один человек. Панель DL: разбор у первого ≈ 4,2 → 2,1–2,25 с, у остальных 0 с — ответ из кэша сразу на POST.
- **Как:**
  1. В тексте общего датасета нет `current_username(`, `current_user_id(`, `cache_key_wrapper(`, `url_param(` — ни в SQL, ни в `{# #}`, ни в `--`.
  2. Если общий датасет собирается из того же исходника, что личный, сборка заменяет макрос логина заглушкой. Заодно вырезает чтение таблицы доступа и строку `url_param`, а `ok` ставит в 1:

     ```python
     LOGIN_SRC   = "{% macro login_q() -%}{{ qs((current_username() or '')|string|trim|lower) }}{%- endmacro %}\n"
     LOGIN_PANEL = "{% macro login_q() -%}''{%- endmacro %}\n"
     assert text.count(LOGIN_SRC) == 1
     shared_text = text.replace(LOGIN_SRC, LOGIN_PANEL)
     ```

  3. Комментарии с упоминанием этих функций в общем датасете сборка вырезает: правка комментария не должна включить личный кэш.
  4. «Предикат автозаполнения» у датасета пуст (02-superset-path.md, SP-24).
  5. Докажи на стенде: отрендеренный текст SQL и ответ совпадают **до байта** у всех логинов мира, включая логин без строки доступа.
- **Проверка:** Регресс AC-08 (вызовов нет даже в сыром тексте). Сравнение md5 текста и ответа по всем логинам. В бою — одинаковый `cache_key` у двух логинов и POST 200 сразу из кэша у второго.
- **Уверенность:** [владелец 08.10] + [исходник 2.0.1]; [стенд 24.8] — одинаковость ответа.
- **Образец:** detail_list:stand/ch.py (`view_text`: `LOGIN_SRC` → `LOGIN_PANEL`) и stand/check.py («панель одна на всех»: тот же текст SQL и ответ у любого логина). Вырезать комментарии с `current_username(` из файлов 3–4 — ещё не сделано.

### AC-10. Отдавай в общий кэш только ответ без скрываемого и согласуй цену с владельцем
- **Почему:** Общий кэш значит, что ответ видят все, у кого есть права на дашборд, — включая логины без строки доступа. Владелец DL 08.10 принял цену: логин без строки доступа видит значения фильтров и счётчики панели, а список ему закрыт.
- **Как:** В общий ответ не клади ни людей, ни полей, которые прячет доступ, ни сумм по зонам, которые доступ скрывает. Цену записывай словами в инструкцию и в FIELDS или NOTES: «что увидит человек без доступа». Если цена неприемлема — датасет личный (AC-06).
- **Проверка:** На стенде ответ общего датасета не содержит ни одного значения скрываемых полей. Пересечение с AC-05 пусто. Решение владельца записано с датой.
- **Уверенность:** [владелец 08.10].
- **Образец:** detail_list:CLAUDE.md (инвариант «Доступ»: атрибуты панели и скрываемые поля не пересекаются, решение 08.10).

### AC-11. Держи датасет с личным ключом коротким: он платит разбор на каждом запросе
- **Почему:** С логином в ключе Superset рендерит и разбирает текст на каждом расчёте ключа, даже при ответе из кэша. Холодное «Применить» — это ≥ 4 рендера и разбора (02-superset-path.md, SP-22). DL список: 0,4–0,6 с на запрос. HRBP: 34 КБ → ≈ 2 с на каждый шаг и 20 с на «Применить», 13,6 КБ → 0,53 с.
- **Как:** Правку «логин в ключ» выпускай вместе с бюджетом текста (SP-15). Ориентир разбора ради ключа — ≤ 0,5 с на худшем рендере. Тяжёлое и общее выноси в общий датасет (AC-06).
- **Проверка:** На стенде шаги Superset со временем на 0.3.0 с патчем. В бою — Timing POST `chart/data` из кэша против времени SQL Lab.
- **Уверенность:** [бой] (HRBP 08.10) + [стенд 24.8]; порог — [вывод].
- **Образец:** HRBP_HUB:stand/superset.py и HRBP_HUB:stand/check.py (бюджет КБ и скобок).

### AC-12. Закрывай дыру кэша срочной поставкой: реальная правка и Save, сверка `cache_key` у двух логинов
- **Почему:**
  - `changed_on` датасета входит в ключ: после Save старые записи кэша больше не используются.
  - Пересохранение **без правки** `changed_on` не меняет — SQLAlchemy 1.3 не делает UPDATE при равных значениях.
  - У владельца может стоять любая из прошлых версий файла. HRBP 17-я поставка (07.10) закрыла общий кэш однострочником, который годился для любой стоящей версии.
- **Как:** В «Что нового» — пометка «как можно скорее» и пять пунктов:
  1. Что могло утечь, кому и с какого числа.
  2. Однострочник «найдите → замените», проверенный на всех прошлых версиях файла, и полный файл.
  3. Save датасета с реальной правкой: «Описание» = номер поставки.
  4. Проверка: DevTools → `cache_key` у двух логинов при тех же фильтрах разный.
  5. Какие пробы доступа повторить (AC-18).

  Правку безопасности не смешивай в одной поставке с рискованными изменениями: в DL 22-я поставка закрыла кэш вместе с загрузчиком, и загрузчик сломал чарты.
- **Проверка:** На стенде регресс AC-08 на файле поставки и на однострочнике, применённом к каждой прошлой версии из git. В бою — сверка `cache_key`.
- **Уверенность:** [бой] (HRBP, DL, adoption 07.10); [исходник 2.0.1] — `changed_on` в ключе, поведение SQLAlchemy.
- **Образец:** HRBP_HUB:Поставка — HRBP HUB v2/0. Инструкция.md (раздел 17-й поставки: однострочник, Save, проверка `cache_key`).

### AC-13. Прогревай только общий кэш — и тем же ключом, что у первого открытия
- **Почему:** Прогрев (`refresh_dashboard` из ноута Helicopter, ручное открытие утром) идёт под одной учёткой:
  - датасет с логином в ключе греется только для этой учётки — прогрев бесполезен;
  - датасет без логина в ключе, но с ответом по пользователю, раздаёт всем ответ этой учётки (админа) — это утечка. HRBP, параграф 17 до 07.10 наполнял общий кэш ответом админа;
  - датасет с общим кэшем после прогрева тёплый для всех на 12 ч.

  После Save датасета первое открытие холодное у каждого (личный ключ) или один раз (общий).
- **Как:**
  - Прогрев включай только для чартов с общим кэшем (AC-06, AC-09), а у персональных выключай и подписывай почему.
  - Ключ прогрева должен совпасть с ключом первого открытия у людей: те же фильтры по умолчанию, тот же лимит строк, тот же порядок значений (02-superset-path.md, SP-21). С какими фильтрами `refresh_dashboard` грузит чарты, не проверено.
  - В «Что нового» каждой поставки, где менялись общие датасеты, — шаг «сразу после Save откройте вкладки N и M».
  - Противоречащие строки (`включите прогрев` рядом с `держите выключенным`) из документов удаляй.
- **Проверка:** В бою — у второго пользователя POST 200 сразу (из кэша) на общем чарте после прогрева. Grep по поставке: формулировки про прогрев не противоречат друг другу.
- **Уверенность:** [бой] (HRBP 07.10); [вывод] [не проверено в бою] — совпадение ключа прогрева.
- **Образец:** detail_list:Поставка — Детальные списки/0. Инструкция.md (шаг «первое открытие каждой вкладки» после замены общих датасетов). В HRBP «включите прогрев» осталось в инструкции и FIELDS.md — убрать.

## Ввод, разведка, данные боя

### AC-14. Пропускай ввод носителей только через макросы с пределами и белыми списками
- **Почему:**
  - Носители кросс-фильтра и параметры адреса — пользовательский ввод: кто угодно может открыть борд с любой ссылкой.
  - Ошибка экрана ломает путь Superset (апостроф, «]», слэш — 02-superset-path.md, SP-06…SP-11).
  - Слишком большой список упирается в `max_query_size` (SP-16).
  - `has` и `hasAny` по большому литералу перебирают его на каждой строке: `hasAny` по пути из 13 узлов и 500 значениям — 26,8 с против 0,57 с у `IN` (04-clickhouse.md, CH-20).
  - Зонд adoption 17.09: значение `x\` ронял запрос — штатный `where_in` удваивает только кавычку.
- **Как:**
  - Значения попадают в SQL только через макросы: `qs` (строка), `qa` (массив; `array(…)` при «]»), `qt` (кортеж для `IN`).
  - Числа — `|int` после `isdigit()`. Перечисления — белым списком с умолчанием. Пустой массив — `CAST([], 'Array(String)')`.
  - Пределы на каждый носитель: число значений, длина, дедуп, без пустых. Неверное значение отбрасывается, сортировка и лимит возвращаются к умолчанию.
  - Пересечение с множеством — через `IN` по кортежу-константе WITH, а не `has([…])` (CH-20).
  - Те же пределы — в маске чарта (09-multi-chart.md), чтобы чарт не просил того, что датасет отбросит.

  ```jinja
  {% set MU = [] %}{% for v in (filter_values('mu_f') or []) %}{% set s = v|string|trim %}{% if s and s|length <= 64 and s.isalnum() and MU|length < 50 and s not in MU %}{% set _ = MU.append(s) %}{% endif %}{% endfor %}
  {% set LIM_L = [] %}{% for v in (filter_values('lim_f') or []) %}{% if LIM_L|length < 1 and (v|string).isdigit() %}{% set _ = LIM_L.append((v|string)|int) %}{% endif %}{% endfor %}
  {% set LIM = LIM_L|first if (LIM_L and LIM_L|first in [5000, 10000, 25000]) else 5000 %}
  ```

  Пределы DL для примера: ≤ 200 значений на атрибут и ≤ 500 всего, логинов ≤ 2 000, rk — буквы и цифры ≤ 64 знаков и ≤ 50 штук, путь ≤ 3 000 знаков и ≤ 20 путей, метка ≤ 40, ссылка ≤ 12 000, лимит из {5 000, 10 000, 25 000}. HRBP: юнитов ≤ 50, значений ≤ 200 на разрез.
- **Проверка:** На стенде враждебный ввод через путь Superset (SP-11): лишнее отброшено, эхо в `meta` без мусора. Худший набор пределов укладывается в `max_query_size` после reindent.
- **Уверенность:** [стенд 24.8].
- **Образец:** detail_list:proteus/detail-list.data.sql (блок «носители кросс-фильтра»: пределы, `isalnum`, `isdigit`, белые списки; `qt`/`qa`). Экран кавычки там — `\'`, перевести на `''` (SP-06). Adoption:Виджеты/pa-one.data.sql — `|int` и белые списки.

### AC-15. Маскируй разведку боевой таблицы в самом запросе
- **Почему:** Ответ разведки владелец присылает в репозиторий, а репозиторий может быть публичным (TeamPulse). Шифровать ответ бессмысленно: ключ лежал бы рядом. Решение владельца 08.10 (TeamPulse) — маскировать в запросе.
- **Как:**
  - Имён и ключей юнитов наружу не отдавай: только счётчики, `min/max(length(…))` и сверки внутри запроса.
  - Абсолютные суммы — в промилле от численности: `round(x / greatest(base, 1) * 1000, 2)`. Отношения от этого не меняются.
  - Колонки ПДн (ФИО, почта, логин, табельный, зарплата) убирай через `* EXCEPT (…)` и сверяй их имена с `DESCRIBE TABLE`: `EXCEPT` молча пропускает несуществующее имя.
  - Ключ сотрудника — `cityHash64(key) % 100000`.
  - Неизвестные имена колонок — заглушками `<…>`: до подстановки запрос просто не выполнится.
  - Один запрос — длинная таблица `раздел · что · значение` через `UNION ALL` и `ARRAY JOIN` массива кортежей (01-platform.md, PL-04).
  - Генератор проверяет маскирование на симуляции таблицы по людям: в ответе нет ни одного имени, ключа и абсолютной суммы.
- **Проверка:** На стенде запрос на симуляции находит всё, что в неё заложено, и в ответе нет имён, ключей и абсолютных чисел. В бою владелец отдаёт ответ как есть.
- **Уверенность:** [владелец 08.10].
- **Образец:** TeamPulse:Team Pulse/Поставка — TeamPulse Hub/0б. SQL Lab — разведка hr_structure_overall одним запросом.sql (шапка «ответ маскирован», промилле, длины вместо имён).

### AC-16. Не клади данные боя в репозиторий
- **Почему:** 07.10 в DL файл замера DevTools содержал ответы с данными сотрудников — его пришлось удалять вместе с историей. HAR и тела ответов `chart/data` несут всё, что видит пользователь, включая скрытое от других.
- **Как:**
  - HAR, тела ответов, скриншоты с данными и выгрузки SQL Lab с людьми не коммить. Если попали — удаляй из репозитория **и** из истории.
  - В `docs/` — только выводы и агрегатные числа: секунды, КБ, число строк.
  - У владельца проси скриншоты колонок Network (Status, Size, Time) и отдельные поля (`cache_key`, `cache_timeout`, `result[0].query`, `queries[0].url_params`), а не HAR (01-platform.md, PL-06).
  - В публичный репозиторий не клади и абсолютные бизнес-числа: о расхождении владелец пишет словами («какая цифра и насколько»).
  - Логины и ФИО сотрудников — ни в документы, ни в тесты. Тестовые логины — синтетические.
- **Проверка:** Перед коммитом grep по изменённым файлам: `"result":`, `.har`, домены и логины из боя. В инструкции просьба к владельцу сформулирована как «скриншот колонок и поле X».
- **Уверенность:** [бой] (DL 07.10).
- **Образец:** TeamPulse:Team Pulse/Поставка — TeamPulse Hub/5. SQL Lab — проверки после выгрузки.sql (шапка: что можно присылать в публичный репозиторий).

### AC-17. Клади в «Проверки» запрос «кто я для Proteus»
- **Почему:** Когда личное поведение неверно («Мои» пустые, чужая зона), надо отделить проблему сессии (Proteus видит другой логин, прежний логин после переименования) от проблемы кэша (AC-07) и от проблемы данных (нет строки доступа). Adoption 07.10 положил такой запрос рядом с кнопкой «Мои».
- **Как:** Один SELECT в SQL Lab:

  ```sql
  SELECT '1. логин сессии' AS what, lower(trim('{{ current_username() }}')) AS v
  UNION ALL
  SELECT '2. актуальный логин', ifNull(nullIf((SELECT any(toString(canon)) FROM <схема>.<таблица_склейки>
         WHERE login = lower(trim('{{ current_username() }}'))), ''), lower(trim('{{ current_username() }}')))
  UNION ALL
  SELECT '3. строк доступа', toString((SELECT count() FROM <схема>.<таблица_доступа>
         WHERE login = lower(trim('{{ current_username() }}'))))
  ```

  В шапке файла напиши:
  - если в ответе буквально `{{ current_username() }}`, шаблоны в SQL Lab выключены — логин сессии смотри в профиле Proteus;
  - если в строке 1 не тот, под кем вошли, — дело в сессии (выйти полностью, другой браузер), а не в кэше;
  - если в строке 3 ноль — нет строки доступа (AC-02).

  Ванильный 2.0.1 рендерит Jinja в SQL Lab под тем же флагом, что датасеты. В форке это не проверено.
- **Проверка:** На стенде запрос рендерится под логинами мира и исполняется на chdb 24.8. В бою владелец выполняет его под собой и под коллегой.
- **Уверенность:** [исходник 2.0.1] [не проверено в бою] — рендер Jinja в SQL Lab.
- **Образец:** adoption:Единый лист — актуальные файлы/Проверки/SQL Lab — кто я для Proteus (кнопка Мои).sql.

### AC-18. Перед пробой на коллеге опубликуй черновик и выдай права на все новые датасеты
- **Почему:** В 2.0.1 чужой пользователь видит дашборд, только если тот опубликован **и** у пользователя есть `datasource_access` хотя бы к одному датасету его чартов (`DashboardAccessFilter`). Чарт на новом датасете без прав покажет ошибку доступа — это права Proteus, а не таблица доступа отчёта. Видит ли коллега черновик до публикации, в бою не проверено.
- **Как:** Перед пробой:
  1. Опубликуй черновик.
  2. Выдай права на дашборд и на **все** новые датасеты — так же, как на прежние.
  3. Проба — минимум два логина разных видов доступа: полный и частичный, плюс по возможности логин без строки доступа.
  4. Сравни: зона и маски по ожиданию (AC-04), `cache_key` у личного датасета разный, у общего одинаковый (AC-06).
  5. Ошибку «нет доступа к датасету» решают права Proteus, «Нет доступа к отчёту» в чарте — таблица доступа.
- **Проверка:** Чек-лист пробы в инструкции поставки с ожидаемым результатом на каждый логин.
- **Уверенность:** [исходник 2.0.1] (`dashboards/filters.py`); [вывод] [не проверено в бою] — видимость черновика.
- **Образец:** detail_list:Поставка — Детальные списки/0. Инструкция.md (чек-лист пробы на коллеге и права на новые датасеты).
