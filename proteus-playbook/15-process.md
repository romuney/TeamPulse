# 15. Процесс агента (PR)

**Зачем глава.** Агент работает сессиями с суточными лимитами: контекст обрывается, следующая сессия начинает с
нуля. Бой видит только владелец, и всё, что агент знает о бое, приходит от него файлами и скриншотами. Поэтому знание
проекта живёт в репозитории — в CLAUDE.md, NOTES.md и docs, — а решения опираются на замеры и факты, а не на память
сессии. Здесь — как вести память проекта, как принимать решения, как говорить с владельцем, как вести git и что делать,
когда из боя пришли новые данные. Стенд — 13-stand.md, поставка — 14-delivery.md.

**Главное в 5 пунктах.**
1. **PR-01.** CLAUDE.md — короткий вход: что это, «Куда идти» таблицей с маршрутом проверок, стенд, инварианты с датами решений владельца, «Что не проверено стендом», «Бой: что известно».
2. **PR-03.** NOTES.md по каждому чарту — точка восстановления: пиши до кода и до следующего действия; после обрыва продолжай с первого пункта ≠ DONE.
3. **PR-09, PR-10.** Воспроизведи ровно симптом владельца на той версии файлов, что стоит в бою. На «сломалось» сначала факты (текст, консоль, Network), потом правка; откат — можно и без фактов.
4. **PR-11.** Любая оптимизация — замер до и после на 24.8 и тот же ответ (`same.py`); числа — в коммит и в «Что нового».
5. **PR-24.** Пришли данные из боя — по порядку: сверка с пределами, «Бой: что известно», факт платформы — в гайд, калибровка стенда, воспроизведение, чистка сырого.

Метки уверенности — как в 01-platform.md: [бой], [стенд 24.8], [исходник 2.0.1], [владелец дд.мм], [вывод],
[не проверено в бою].

## Цикл одной задачи

```
1. Прочитать CLAUDE.md (весь) → NOTES.md чарта (весь) → нужный раздел docs/          PR-01, PR-03, PR-04
2. git pull: забрать файлы, которые владелец положил через веб GitHub                 PR-21, PR-23
3. Понять симптом: воспроизвести на стенде с боевой версией файлов                   PR-09, PR-10
   (долго — разложить время: PR-08; новое из боя — PR-24)
4. План в NOTES.md → правка исходника → регресс и гейт стенда (13-stand.md, ST-33)   PR-03, PR-13
5. Замер до → после, ответ тот же                                                    PR-11
6. pack.py → «Что нового» → «Что проверено» / «не проверено»                         14-delivery.md
7. Решение владельца — в инвариант CLAUDE.md; коммит «N-я поставка: …»; тег          PR-02, PR-22
8. Скратч удалить; опыт — одной строкой-правилом                                     PR-06
```

## Структура репозитория отчёта

```
<репозиторий отчёта>/
  CLAUDE.md                      ← вход: «Куда идти», стенд, инварианты, не проверено, бой (PR-01)
  docs/architecture.md           ← как устроено и почему, объёмы и скорость, как проверено (PR-04)
  proteus/<x>.data.sql           ← исходник датасета (Jinja)
  proteus/<x>.chart.js           ← исходник чарта: ES5, с комментариями; в поставку — сборка
  proteus/<x>.board.css          ← CSS борда с заглушками id
  proteus/<x>.board-check.js     ← сниппет DevTools разметки борда
  proteus/<x>.NOTES.md           ← рабочая память по чарту (PR-03)
  proteus/FIELDS.md              ← контракт колонок и чек-лист «настроить руками»
  proteus/SELF_CHECK.md          ← вердикт check.py скилла последнего прогона
  helicopter/paragraphs/         ← если у отчёта свои витрины (06-helicopter-gp.md)
  stand/                         ← живые инструменты стенда (13-stand.md)
  Поставка — <Отчёт>/            ← собирает stand/pack.py (14-delivery.md)
  charts/ datasets/ dashboards/  ← выгрузка борда владельца: оракул и откат
  inbox/                         ← входящее от владельца (PR-21)
  Идеи/                          ← макеты предложений до согласования (PR-17)
```

## Шаблон CLAUDE.md


## A. Память проекта

### PR-01. Держи CLAUDE.md коротким входом: «Куда идти», стенд, инварианты, «не проверено», «бой»
- **Почему:**
  - У пользователя жёсткие суточные лимиты (решение 31.07): каждая сессия начинается с чтения CLAUDE.md, и длинный журнал съедает работу.
  - HRBP и DL ведут CLAUDE.md по этой схеме и восстанавливаются между сессиями без потерь (19 и 27 поставок). У TP CLAUDE.md нет: `AGENTS.md` — 162 КБ, `DESIGN_SYSTEM` — 131 КБ, `SOURCES` — 125 КБ, `PROGRESS` — 74 КБ, плюс устаревшее «Папка не под git».
  - Adoption: CLAUDE.md ссылается на инструменты, которых в репозитории нет (`.gen_*`, `.jt*`, `.render/`) — команды у преемника не работают.
- **Как:** структура — по шаблону выше.
  - **Что это**: один абзац — отчёт, борд, чарты, источники, «боя нет, владелец вставляет руками», где читать первым.
  - **Куда идти**: таблица «задача → файл → обязательный маршрут проверок». Маршрут — цепочкой команд, а не словами «проверить».
  - **Стенд**: команды с однострочным комментарием; venv, версии, логины мира.
  - **Инварианты — не ломать**: правило, решение владельца с датой и цитатой, инцидент с числами, чем проверяется (PR-02).
  - **Что не проверено стендом**: риск → чем закрыть.
  - **Бой: что известно**: числа с датой и источником (PR-05).
  - Длинное — в docs по ссылке. Ориентир — до 30 КБ (HRBP — 28 КБ; DL — 56 КБ, это уже много).
  - Все пути в CLAUDE.md существуют:

    ```sh
    grep -o '`[^` <]*\.\(py\|cjs\|js\|sql\|md\|css\)`' CLAUDE.md | tr -d '`' | sort -u \
      | while read p; do [ -e "$p" ] || echo "нет файла: $p"; done
    ```

- **Проверка:** новая сессия по одному CLAUDE.md отвечает «как поменять датасет и что прогнать»; проверка путей пуста.
- **Уверенность:** [владелец 31.07] (лимиты) + [бой] (практика HRBP и DL); ориентир 30 КБ — [вывод].
- **Образец:** HRBP_HUB:CLAUDE.md (компактный); detail_list:CLAUDE.md (полный набор разделов, «Бой: что известно» с числами).

### PR-02. Записывай решение владельца инвариантом CLAUDE.md — с датой и цитатой, в том же коммите
- **Почему:** решения, которые живут только в чате, следующая сессия не знает и отменяет. Например: «все колонки в каждом ответе» (DL, 06.10: колонки по запросу у владельца не выбирались), «панель — общий кэш» (DL, 08.10), «одна папка поставки» (adoption, 25.09), «чем больше одним чартом, тем лучше» (HRBP, 28.09). Каждое меняло архитектуру, и откат по незнанию стоил бы поставки.
- **Как:**
  - В инвариант: что нельзя ломать; «владелец, дд.мм: «дословная цитата»»; почему (инцидент с числами); чем проверяется (раздел регресса, шаг прогона).
  - Тот же коммит, что и правка по решению.
  - В NOTES.md чарта — таблица §4 «дата | вопрос | дословно | решение с замерами» (PR-03).
  - Решение изменилось — правь инвариант на месте с новой датой и причиной, а не дописывай противоположное ниже.
- **Проверка:** у каждого инварианта есть дата и источник; grep по CLAUDE.md не находит двух противоречащих правил.
- **Уверенность:** [бой] (практика HRBP и DL).
- **Образец:** detail_list:CLAUDE.md (раздел «Инварианты — не ломать»: «Колонки списка — все в каждом ответе (владелец, 06.10 …)», «Ключ кэша Proteus: у списка — по логину, у панели — общий (владелец, 08.10)»).

### PR-03. Веди NOTES.md по каждому чарту как точку восстановления: до кода и до следующего действия
- **Почему:** чарт на 3 000+ строк (HRBP — 405 КБ) и 19–27 поставок в одну сессию не помещаются. RETRO 52–53: контекст кончался на БЛОКАХ 5–6. Требование владельца adoption 14.09: «всё логировать в память».
- **Как:**
  - Разделы: §0 план со статусами (TODO / DOING / DONE) и режимом; §1 реестр макета (элемент → место в JS); §2 прочитано; §3 поля «что ждёт макет ↔ что даёт SQL»; §4 вопросы и решения владельца; §5 БЛОКИ 1–7 шаблона скилла; §6 открытые хвосты.
  - Пиши **до** кода (план) и **до** следующего действия (статус), а не «потом соберу».
  - После обрыва сессии: прочитай NOTES целиком, найди первый пункт ≠ DONE, продолжай с него. Свой `.chart.js` целиком не перечитывай — grep или чтение с offset.
  - SELF_CHECK.md — машинный вердикт `check.py` скилла плюс суждения с доказательством (не правится руками ради «зелёного»).
  - NOTES в поставку не идёт и в Proteus не вставляется.
- **Проверка:** по NOTES видно, на каком шаге работа и почему принято каждое решение; статус последнего действия совпадает с последним коммитом.
- **Уверенность:** [бой] (практика трёх проектов) + [владелец 14.09].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.NOTES.md (§0–§6, таблица §4 решений); шаблон — adoption:skills/proteus-echarts-builder (раздел про NOTES в SKILL.md).

### PR-04. Держи docs/architecture.md: как устроено, почему, сколько стоит и как проверено
- **Почему:** CLAUDE.md говорит «куда идти», но не «почему так». Без архитектурного документа агент повторяет отвергнутые варианты: загрузчик кода, кэш по логину у панели, догрузку частей ответа.
- **Как:**
  - Разделы: главные решения (с альтернативами и почему нет); поток данных; таблицы с ключами сортировки; контракт датасета (роли, форматы, носители); чарт (состояние, блоки, каналы); объёмы и скорость (стенд и бой — в разных колонках); как проверено; что сверить в бою.
  - Раздел «реализация и отличия от плана», если план и сделанное разошлись.
  - Текущее — переписывай на месте; историю итераций не копи, кроме уроков («почему не загрузчик» — урок, его оставь).
  - CLAUDE.md ссылается на нужный раздел, а не повторяет его.
- **Проверка:** на вопрос «почему так» ответ — ссылка на раздел; разделы не противоречат CLAUDE.md.
- **Уверенность:** [бой] (практика HRBP и DL).
- **Образец:** HRBP_HUB:docs/architecture.md (решения, таблицы, датасет, чарт, «Объёмы и скорость», «Как проверено», «Что сверить на боевых данных»); detail_list:docs/analysis.md (раздел 9 — реализация и отличия от плана).

### PR-05. Переноси подтверждённое из «Что не проверено» в «Бой: что известно» с датой и источником
- **Почему:** списки «не проверено» отстают от боя. DL: после замера 07.10 (ответы приходят zstd) в CLAUDE.md и инструкции осталось «есть ли gzip». HRBP: в FIELDS.md — «чарт скажет через 9 с» (стало 45 с) и «самовлияние через интерфейс» (только JSON). Устаревший пункт тянет агента проверять уже известное и вводит владельца в заблуждение.
- **Как:**
  - Подтверждено в бою → строка в «Бой: что известно»: факт, число с единицей, дата, источник (SQL Lab, DevTools, скриншот, слова владельца). Пример: «ClickHouse 24.8.15.1, новый анализатор, `max_execution_time` 30 с (файл 11, SQL Lab владельца, 08.10)».
  - Из «не проверено» строку убери в том же коммите. Опровергнутое — тоже убери и поправь правила, которые на нём стояли.
  - Перед каждой поставкой пройди оба списка: что закрылось, что устарело.
  - Факт платформы — ещё и в таблицу фактов гайда (PR-25).
- **Проверка:** grep по CLAUDE.md, инструкции и FIELDS.md не находит вопросов, на которые уже есть ответ в «Бой: что известно».
- **Уверенность:** [бой] (устаревшие пункты у DL и HRBP).
- **Образец:** detail_list:CLAUDE.md (разделы «Что не проверено стендом» и «Бой: что известно (SQL Lab владельца, 08.10, файлы 10 и 11)»).

### PR-06. Не клади в репозиторий скратч и данные боя; опыт фиксируй одной строкой-правилом
- **Почему:** adoption 19.09, владелец: «открываю папку — миллион файлов» — удалили ≈400 файлов скратча. DL 07.10: файл замера DevTools содержал ответы с данными сотрудников, его пришлось удалять вместе с историей. Репозиторий может быть публичным (TeamPulse — GitHub Pages).
- **Как:**
  - В репозиторий — только живые инструменты (`stand/`), исходники, папка поставки и выводы (`docs/`). Пробы, дампы, разовые скрипты, скриншоты, журналы — в каталог скратча сессии вне репозитория; по закрытии этапа удалять.
  - Опыт — одной строкой-правилом в CLAUDE.md или в гайд, а не файлом пробы.
  - HAR, тела ответов `chart/data`, выгрузки SQL Lab с людьми — не коммитить; попали — удалить из репозитория **и из истории** и сказать владельцу (03-access-cache.md, AC-16).
  - Ответ разведки, который владелец кладёт в репозиторий, — только маскированный; после разбора чисти до схемы и главного (PR-21).
- **Проверка:** перед коммитом `git status` и grep по изменённым файлам: `"result":`, `.har`, домены и логины боя, файлы с префиксом `_`.
- **Уверенность:** [владелец 19.09] + [бой] (ПДн, DL 07.10).
- **Образец:** detail_list (в корне — только живые инструменты и выводы; правило в CLAUDE.md: «Скратч в репозиторий не кладём»).

### PR-07. Держи документы правдой: устаревшее и ссылки в пустоту убирай в том же коммите
- **Почему:** тексты отстают от кода, и агент верит устаревшему. Примеры на 08.10: шапка `pack.py` DL описывает файл 11 как «журнал запросов ClickHouse» (запрещён); `proteus/FIELDS.md` DL описывает прежние роли ответа; таблица скорости инструкции DL — «код чарта 129 КБ», а файл уже 138,6 КБ; CLAUDE.md adoption ссылается на отсутствующие `.gen_*`, `.jt*`, `.render/`.
- **Как:**
  - Правка кода, которая меняет описанное, — в том же коммите правит описание: шапку скрипта, FIELDS.md, таблицы инструкции, CLAUDE.md.
  - Числа в документах, которые считает скрипт (размеры, счётчики проверок), берутся из вывода скрипта, а не переписываются руками.
  - Ссылки на отсутствующие файлы удаляй сразу (проверка путей — PR-01).
- **Проверка:** проверка путей CLAUDE.md пуста; `pack.py --check` ищет устаревшие формулировки по списку (14-delivery.md, DV-12).
- **Уверенность:** [бой] (расхождения найдены 08.10 во всех проектах).
- **Образец:** detail_list:stand/pack.py (шапка описывает каждый файл поставки — держать в актуальном виде).

## B. Как принимать решения

### PR-08. Прежде чем оптимизировать — разложи время по слагаемым и бери самое большое
- **Почему:** DL 07.10: на «долго грузит» замер показал, что сервер отвечал из кэша за 0,3–0,4 с, а время уходило на сеть: отправку кода чарта и приём ответа. Помогли сжатие JS и форма ответа (21-я поставка). HRBP 08.10, владелец: «оптимизация пошла не туда» — ClickHouse ≈2 с, а 18 из 20 с «Применить» — разбор текста SQL в Proteus.
- **Как:**

  | Слагаемое | Чем мерить | Рычаг |
  |---|---|---|
  | Proteus до запросов чартов | DevTools (7,7 с у владельца) | вне поставки |
  | отправка кода чарта | Payload и Timing POST `chart/data` | сжатая сборка (07-chart.md, CJ-21) |
  | разбор Superset (ключ кэша, `reindent`) | `stand/superset.py` или `kit/superset201.py` в обеих моделях лексера, в расчёт — большее | короче текст (02-superset-path.md, SP-15), логин в ключе только где нужно (SP-22) |
  | ClickHouse | файл «где время» (14-delivery.md, DV-28), EXPLAIN на стенде | 04-clickhouse.md |
  | приём ответа | Size и Timing приёма | форма ответа (05-dataset.md, DS-16…DS-18) |

- **Проверка:** в `inbox/` нет сырых ответов старше разбора; в docs есть ссылка «из файла X владельца, дд.мм».

  ```
  Поставка: файлы 2, 3 (сначала 3: <почему>); тег <проект>-N.
  ```

- **Образец:** detail_list (коммит 27-й поставки: тема, правила, итоги `check.py`, `parse.py`, `click.cjs`); HRBP_HUB (коммиты 2c4c112, a8fcf29, b154e0d).

### PR-23. Работай в ветке, которую читает владелец; начинай с `git pull`; коммить, пушь и ставь теги, когда это входит в задачу
- **Почему:** владелец берёт папку поставки из определённой ветки и туда же кладёт свои файлы (PR-21). Поставка в другой ветке для него не существует, а его загрузки не видны агенту без `pull`. В проектах ветки разные: DL — рабочая ветка `claude/…`, HRBP и TP — `main` (с неё же публикуется GitHub Pages), adoption — `new`.
- **Как:**
  - Ветку называет задача или владелец; её имя — в CLAUDE.md и в шапке инструкции поставки (14-delivery.md, DV-01).
  - Без указания на ветке по умолчанию не работай: заведи рабочую и скажи владельцу, где поставка.
  - Начало сессии — `git pull` (или `fetch` + сверка): забрать загрузки владельца.
  - Новую ветку на каждую поставку не заводи: поставки различают теги (DV-34).
  - Коммит, пуш и тег — когда задача это предполагает или пользователь попросил; в чужие репозитории — только чтение.
  - Историю не переписывай, кроме удаления ПДн (PR-06), — и тогда предупреди владельца.
- **Проверка:** `git status` чистый после сдачи; ветка поставки = ветка из инструкции; загрузки владельца в истории ветки.
- **Уверенность:** [вывод] (из устройства проектов и канала обратной связи).
- **Образец:** detail_list:CLAUDE.md (поставка в рабочей ветке, выгрузки владельца в корне той же ветки).
