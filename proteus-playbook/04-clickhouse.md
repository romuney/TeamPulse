# 04. ClickHouse 24.8 и новый анализатор

Зачем глава: датасет борда исполняется в боевом ClickHouse 24.8.15.1 с новым анализатором. В бою запрос живёт не дольше
30 с, а его текст до ClickHouse проходит путь Superset 2.0.1. Здесь собраны правила SQL, которые одинаково работают в бою
и на стенде, не падают на Nullable-выгрузке и не тратят секунды на планирование. Как устроен ответ (роли, вес, пачки),
описано в 05-dataset.md. Путь текста SQL до ClickHouse (Jinja, sqlparse, обёртка, reindent) — в 02-superset-path.md.

**Главное в 5 пунктах**

1. **CH-03.** Каждый вариант рендера гоняй в матрице режимов: новый и старый анализатор, `prefer_column_name_to_alias`,
   `join_use_nulls`, `group_by_use_nulls`. Ответ должен совпасть. Время мерь только новым анализатором (CH-02).
2. **CH-05, CH-06.** CTE — это подстановка текста. Держи цепочку линейной, а контекст запроса (доступ → юниты → месяц)
   сворачивай в один скаляр-кортеж с одинаковым текстом и читай его проекциями.
3. **CH-14.** Nullable-броня: `ifNull` на каждом входе до агрегатов, CAST, `arrayConcat`, JOIN и на каждом выходе.
   Ключи и элементы кортежей — не-Nullable.
4. **CH-20, CH-21.** Список значений проверяй через `IN` по константе WITH (кортеж или `[…]`), а не `has`/`hasAny` по
   литералу. Перекодировку в коды делай через `transform`, а не `indexOf`: `has`/`hasAny` и `indexOf` перебирают массив на
   каждой строке и стоят десятки секунд на масштабе.
5. **CH-31.** Любую оптимизацию доказывай A/B на масштабе боя: попеременные прогоны, новый анализатор, ответ байт в байт со
   старой версией. Отвергнутое записывай с числами.

## A. Платформа и как проверять

### CH-01. Целься в ClickHouse 24.8 с новым анализатором; стенд — только движок 24.8
- **Почему:** в бою 24.8.15.1 с `allow_experimental_analyzer = 1`, `max_execution_time` 30 с (дольше запрос падает),
  `max_threads` 12, `max_memory_usage` 10 ГиБ, кэш результатов и кэш несжатых блоков выключены (SQL Lab владельца, 08.10).
  На chdb 4.x (ClickHouse 26.x) другой планировщик. С 26.1 несовместимые типы молча сводятся к Variant, а в бою это Code 386.
  С 26.9 старого анализатора нет, поэтому матрица CH-03 там невозможна. Соотношение бой/стенд: холодный бой примерно вдвое
  медленнее стенда 24.8 (панель detail_list 7,0 с против 3,3 с; adoption 5,7 с против ≈2,6 с), повторный примерно равен
  ему (3,3 с). «В 4 раза» выходит только против стенда на 26.x (adoption: 5,68 с в бою против 1,35 с на chdb 4.4).
- **Как:** стенд — chdb 2.1.1 или 3.1.2 (оба = 24.8.4.1) в отдельном venv. chdb 4.x допустим только для проверки логики,
  и только с `SET use_variant_as_common_type = 0`. Решения о скорости и типах по нему не принимай. Тега `24.8.15.1` в
  публичном репозитории ClickHouse нет (это сборка поставщика), документацию бери с `v24.8.14.39-lts`. Бюджет стенда на клик
  держи около 1 с: бой в 1–4 раза медленнее стенда (это оценка, а не замер; пороги ожидания — ST-19, 13-stand.md).
  ```python
  S = chdb.session.Session(DB)
  VERSION = S.query('SELECT version()', 'CSV').bytes().decode().strip().strip('"')
  if int(VERSION.split('.')[0]) >= 25:
      S.query('SET use_variant_as_common_type = 0')   # как бой 24.8: без Variant как общего типа
  ANALYZER_OFF = 'allow_experimental_analyzer = 0' if int(VERSION.split('.')[0]) < 25 else None  # с 26.9 его нет
  ```
- **Проверка:** стенд — `SELECT version()` возвращает `24.8.4.1`. В бою — SQL Lab:
  `SELECT version(), getSetting('allow_experimental_analyzer'), getSetting('max_execution_time'), getSetting('max_threads')`.
  Слова `system` в запросе быть не должно (PL-04, 01-platform.md).
- **Уверенность:** [бой] (настройки, 08.10) [стенд 24.8] (версии chdb, Variant) [вывод] (множитель бой/стенд).
- **Образец:** HRBP_HUB:stand/ch.py (выбор каталога по версии chdb, `use_variant_as_common_type = 0`, `ANALYZER_OFF`);
  detail_list:CLAUDE.md (раздел «Бой: что известно»).

### CH-02. Время мерь новым анализатором; старый — только для сверки ответа
- **Почему:** в бою работает новый анализатор. Старый в 24.8 медленнее в 1,1–10 раз, и направление оптимизации на нём может
  оказаться обратным. HRBP, зона HRBP: контекст скаляром (CH-06) на новом 2,37 → 1,30 с, на старом 7,8 → 12,5 с (стенд,
  08.10). TeamPulse на масштабе боя: 1,03 с на новом против 5,45 с на старом. detail_list: списки в 2,6–2,9 раза медленнее
  на старом, панели — в 1,1–1,2 раза (стенд, 08.10).
- **Как:** все замеры времени — с `allow_experimental_analyzer = 1`. Старый анализатор гоняй только в матрице CH-03 ради
  совпадения ответа. Его время в отчёты о скорости не пиши.
- **Проверка:** скрипт замера печатает анализатор рядом с каждым числом. В бою сверяй с SQL Lab: тот же отрендеренный SQL,
  холодный прогон (первый после простоя) и тёплый — с меткой внутри запроса (PL-05, 01-platform.md).
- **Уверенность:** [стенд 24.8] [бой] (анализатор в бою, 08.10).
- **Образец:** TeamPulse:Team Pulse/stand/dataset.py (замер по режимам); HRBP_HUB:stand/scale.py.

### CH-03. Гоняй каждый вариант рендера в матрице режимов ClickHouse; ответ должен совпасть
- **Почему:** профиль ClickHouse Proteus, кроме анализатора, не снят. adoption в бою 23.09 получил Code 215 на клике (HAVING
  по алиасу-омониму). На стенде это воспроизводится только сочетанием «новый анализатор + `prefer_column_name_to_alias = 1`»,
  а «старый + prefer» молча отдаёт 3 вместо 31 (стенд, 08.10). Значит, в боевом профиле, вероятно, `prefer = 1` (F14,
  01-platform.md). Ключи ROLLUP при `group_by_use_nulls = 1` становятся NULL, при `join_use_nulls = 1` признак пары LEFT JOIN
  тоже NULL.
- **Как:** режимы снаружи текста датасета (SETTINGS стендового прогона, не в SQL): по умолчанию;
  `allow_experimental_analyzer = 0`; `prefer_column_name_to_alias = 1`; `join_use_nulls = 1`; `group_by_use_nulls = 1`; все
  четыре вместе и со старым, и с новым анализатором. Сравнивай отсортированный ответ (подпись или md5 строк), а порядок строк
  проверяй отдельно (DS-25, 05-dataset.md).
  ```python
  MODES = {
      'default': '',
      'old': 'allow_experimental_analyzer = 0',
      'prefer': 'prefer_column_name_to_alias = 1',
      'jun': 'join_use_nulls = 1',
      'gbn': 'group_by_use_nulls = 1',
      'old+all': 'allow_experimental_analyzer = 0, prefer_column_name_to_alias = 1, join_use_nulls = 1, group_by_use_nulls = 1',
      'new+all': 'allow_experimental_analyzer = 1, prefer_column_name_to_alias = 1, join_use_nulls = 1, group_by_use_nulls = 1',
  }
  ```
- **Проверка:** регресс стенда печатает «режим → md5 ответа», все строки одинаковы. В бою владелец снимает
  `getSetting('prefer_column_name_to_alias')`, `getSetting('join_use_nulls')`, `getSetting('group_by_use_nulls')`
  в файле «где время» (PL-05, 01-platform.md; пока открытый вопрос — 17-open-questions.md).
- **Уверенность:** [стенд 24.8] [бой] (Code 215, 23.09) [вывод] [не проверено в бою] (`prefer = 1` в профиле боя).
- **Образец:** detail_list:stand/check.py (раздел режимов ClickHouse) + TeamPulse:Team Pulse/stand/dataset.py (`CFG`, режим
  «new + nulls + prefer»: «все вместе» с новым анализатором есть только здесь).

### CH-04. Не пиши в датасете SETTINGS, FORMAT, `AS MATERIALIZED` и «;» в середине
- **Почему:** датасет всегда становится подзапросом. Зонд с SETTINGS в бою дал «Fatal error» (adoption, 18.09), `WITH t AS
  MATERIALIZED` — HTTP 500 (в 24.8 это Code 62, материализованные CTE появились только в 26.3 и экспериментально). «;» в
  середине даёт «Virtual dataset query cannot consist of multiple statements». Механизм «Fatal error»: «Синхронизировать
  столбцы» и сохранение в 2.0.1 исполняют датасет без обёртки и дописывают `\nLIMIT N` после текста. После SETTINGS или
  FORMAT это Code 62. SETTINGS в подзапросе действует только внутри него (на стенде `getSetting('max_threads')` внутри 3,
  снаружи 4), а `allow_experimental_analyzer` в подзапросе — Code 80.
- **Как:** нужная настройка ClickHouse задаётся только профилем пользователя или подключения, это решает владелец. В extra
  базы Proteus стоит `allow_query_settings: true` (F12, 01-platform.md), но штатный ли это путь передать настройки из чарта,
  не проверено — не опирайся на него без пробы на копии борда. Повторное использование результата делай скаляром (CH-06), а
  не MATERIALIZED. Хвостовую «;» Superset срезает сам, но лучше её не ставить. Слово SETTINGS в комментарии безвредно:
  на пути чарта комментарии вырезает `strip_comments`, а на пути сохранения они доходят до ClickHouse, и тот их пропускает.
- **Проверка:** grep по SQL поставки: `rg -n '^\s*(SETTINGS|FORMAT)\b|AS\s+MATERIALIZED|;\s*\S' proteus/*.data.sql`
  (совпадения в комментариях и строковых литералах разбери глазами, в коде их быть не должно). Гейт сохранения исполняет
  рендер как `<текст>\nLIMIT 1000` без обёртки (SP-05, 02-superset-path.md; F9, 01-platform.md).
- **Уверенность:** [бой] (18.09) [исходник 2.0.1] (путь синхронизации) [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (без SETTINGS, режимы только снаружи в `stand/check.py`).

## B. План запроса: CTE, скаляры, плечи

### CH-05. Держи CTE линейной цепочкой: каждая CTE упомянута один раз
- **Почему:** в 24.8 CTE — подстановка текста. Каждая ссылка исполняется заново, а новый анализатор ещё и разбирает всю
  цепочку в каждом месте ссылки. Бой adoption (18.09): одна ссылка — 2,1 с, шесть ссылок — 11,7 с (×5,5). HRBP (08.10):
  EXPLAIN — 1,9 из 2,4 с ответа ушло на планирование подстановок. Стенд 24.8: CTE в трёх плечах UNION — 0,51 с против 0,17 с
  при одной ссылке; `rand64()` в CTE с двумя ссылками даёт разные значения.
- **Как:** цепочка «вход → контекст → проекция». Если CTE нужна дважды, сверни её в скаляр (CH-06) или размножь роль строки
  (CH-07), но не ставь вторую ссылку. Ссылки на `ctx` дёшевы: это проекция одного скаляра (CH-06), а не цепочка, поэтому
  плечи и подзапросы вида `id IN (SELECT arrayJoin(roots) FROM ctx)` берут контекст только через неё.
- **Проверка:** `EXPLAIN PLAN` на стенде — число чтений одной и той же таблицы. Время планирования: `EXPLAIN` против полного
  запроса. Если `EXPLAIN` занимает заметную долю ответа (у HRBP до правки — 1,9 из 2,4 с), ищи повторно разбираемую цепочку.
- **Уверенность:** [бой] (adoption 18.09) [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (цепочка `acc` → `un` → `lm` → `ctx0`; плечи ссылаются только на `ctx` / `ex`).

### CH-06. Сворачивай контекст запроса в один скаляр-кортеж с одинаковым текстом и читай его проекциями
- **Почему:** одинаковый по тексту скалярный подзапрос ClickHouse считает один раз, а каждый другой скаляр над той же
  цепочкой пересчитывает её целиком. Стенд 24.8, 150 млн строк: один скаляр дважды — 0,19 с (как один раз), два разных
  скаляра над одной CTE — 0,33 с. HRBP, масштаб 100 тыс., новый анализатор, ответ байт в байт на 832 случаях (08.10):
  зона HRBP 2,37 → 1,30 с, компания 2,47 → 1,76 с, блок с «all» 3,69 → 1,70 с, компания + «Штат» 3,79 → 2,94 с.
  Каждый лишний разный скаляр над `ex` стоит ≈+0,2 с, ссылка на тот же EX — +0,06 с.
- **Как:** доступ, юниты, последний месяц, область, диапазоны ключей для плеч — одним кортежем. В Jinja текст скаляра
  задаётся один раз строкой, плечи читают `tupleElement`.
  ```sql
  {% set EX = '(SELECT ext FROM ex0)' %}   {#- в шапке шаблона: один текст скаляра на весь запрос -#}
  …
  ctx0 AS (
    SELECT (roots, my_role, scope, single, anc, zone_n, last_m) AS ctxt
    FROM (SELECT … FROM acc CROSS JOIN un CROSS JOIN lm)
  ),
  ctx AS (
    SELECT c.1 AS roots, c.2 AS my_role, c.3 AS scope, c.4 AS single, c.5 AS anc, c.6 AS zone_n, c.7 AS last_m
    FROM (SELECT (SELECT ctxt FROM ctx0) AS c)
  )
  … WHERE path_s >= tupleElement({{ EX }}, 1) AND path_s < tupleElement({{ EX }}, 2)
  ```
  Новые ссылки плеч — только на `ctx` / `ex` и эти скаляры, не на промежуточные CTE. Если плечу в данном режиме нечего
  читать, отдай ему пустой диапазон в том же кортеже (CH-18), а не вторую версию SQL.
- **Проверка:** A/B (CH-31): время на новом анализаторе, ответ байт в байт; grep, что плечи не ссылаются на `acc` / `un` / `lm`.
- **Уверенность:** [стенд 24.8] [не проверено в бою] (боевой замер после 19-й поставки HRBP не прислан).
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (CTE `ctx0` / `ctx`, `ex0` / `ex`, скаляры `EX` и `FZ`).

### CH-07. Пускай плечи UNION ALL только по своим диапазонам, а общий скан размножай ролью через arrayJoin
- **Почему:** плечи поверх общей тяжёлой CTE перемножают сканы: считай подстановки, ПЕРЕМНОЖАЯ глубину, а не складывая
  ссылки. Прототип adoption «весь верх одним датасетом» (22.09) упал в бою с «Превышено время ожидания»: CTE стояла в 8
  плечах, каждая ссылка раскрывалась в две, итого 8 × 2 + 1 = 17 сканов факта. После перехода на роли (v7.1) — один скан и
  один GROUP BY; в бою 30.09 весь лист отвечал за 3–5,7 с (общий выигрыш v7 вместе с предагрегатом — GP-14,
  06-helicopter-gp.md). Стенд 24.8 (`max_threads = 1`): CTE в трёх плечах — 0,51 с, роль через `arrayJoin` — 0,19 с,
  скаляр-кортеж в трёх плечах — 0,20 с.
- **Как:** ветки делят один скан, поэтому строку размножь набором `(role, key, …)` через `arrayJoin`, сделай один GROUP BY
  и лимиты секций `row_number() OVER (PARTITION BY role …)`. Тяжёлые состояния гаси условием по роли
  (`if(role = …, arr, [])` до `sumMap`, `groupArrayIf`). Фасеты фильтров и разбивку по тем же разрезам считай одним проходом.
  Плечи допустимы, когда каждое читает свой диапазон или свою таблицу, а общий контекст берёт скаляром (HRBP — 9 плеч).
  ```sql
  SELECT if(kk = 1, 'f', 'tr') AS role, fk.2 AS id, fk.1 AS pid, …
  FROM (
    SELECT (fv.1, fv.2) AS fk, sum(hn) AS n_f, countIf(fv.3 = 1) AS n_tr,
           arrayMap(x -> ifNull(x, 0), sumForEachIf(v, fv.3 = 1)) AS s
    FROM (SELECT arrayJoin(arrayConcat(
            if(<остальные разрезы>, [('paint', ifNull(paint, '-'), toUInt8(<все разрезы>))], []), …)) AS fv, … FROM cube …)
    GROUP BY fk
  )
  ARRAY JOIN [1, 2] AS kk
  WHERE kk = 1 OR n_tr > 0
  ```
- **Проверка:** `EXPLAIN PLAN` — таблица факта читается один раз. Регресс считает колонки каждого плеча механически
  (Code 53 «UNION different number of columns» ловится до боя).
- **Уверенность:** [бой] (adoption 22.09) [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (плечо «фасеты фильтров и трансформер по разрезам» — один проход,
  `ARRAY JOIN [1, 2] AS kk`); adoption:Виджеты/pa-one.data.sql (роли через `arrayJoin`).

### CH-08. Держи вычисляемые WITH-алиасы только на верхнем уровне; в подзапросы передавай CTE и CROSS JOIN ctx
- **Почему:** неконстантный алиас внешнего `WITH expr AS x` в подзапросе не виден ни одному анализатору 24.8: новый даёт
  Code 47 UNKNOWN_IDENTIFIER или Code 1 «Resolve identifier from parent scope only supported for constants and CTE», старый —
  «Missing columns». Хуже коррелированный подзапрос: старый анализатор не падает, а молча считает выражение заново в области
  подзапроса и отдаёт неверный ответ (стенд, 08.10).
- **Как:** контекст — CTE-подзапросом `name AS (SELECT …)` и `CROSS JOIN ctx`. На верхнем уровне допустимы константы
  (`(…) AS dl_x`) и скаляры `(SELECT …) AS z`.
- **Проверка:** матрица CH-03. Рендер с каждым носителем — ответ одинаков на обоих анализаторах.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (комментарий «Контекст запроса — цепочкой CTE, а не WITH-выражениями»);
  detail_list:proteus/detail-list.data.sql (WITH только с константами `dl_*` и скалярами warden).

### CH-09. Бери скаляр, который может оказаться пустым, агрегатом без GROUP BY
- **Почему:** пустой скалярный подзапрос с типом Tuple или Array в 24.8 падает: Code 125 «Scalar subquery returned empty
  result … which cannot be Nullable». Так падал прежний датасет detail_list у логина без строки доступа (стенд, 29.09). Пустой
  скаляр Int или String молча даёт NULL, и тот доезжает до CAST (Code 349, CH-14).
- **Как:** строку доступа или контекст бери агрегатом без GROUP BY: он всегда возвращает ровно одну строку, даже на пустом
  входе. Строку и счётчик — одним скаляром-кортежем (CH-06), а не двумя разными скалярами над одной таблицей. Нет строки —
  значения по умолчанию (`''`, пустые массивы) и `ok = 0` в meta (DS-08, 05-dataset.md), а не падение.
  ```sql
  WITH (SELECT (groupArray((ifNull(role, ''), arrayMap(x -> ifNull(x, ''), roots))), count())
        FROM prod_proteus.<доступ> WHERE login = {{ login_q() }}) AS acc
  SELECT arrayElement(acc.1, 1) AS acc_row,   -- нет строки: ('', []) — значения по умолчанию
         acc.2 AS acc_n                      -- 0 → ответ из одной meta с ok = 0
  ```
- **Проверка:** регресс с логином без строки доступа (`nobody` в мирах стендов) отвечает одной meta с `ok = 0` на обоих

  `('hrbp', ['u1', ''])` и 1, нет строки — `('', [])` и 0, ошибки нет.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (CTE `acc`: `groupArrayIf` без GROUP BY, роль и корни одной строкой);

## C. Анализаторы и режимы: ловушки

### CH-10. Давай уникальные явные имена всем колонкам первого плеча UNION ALL
- **Почему:** имена колонок UNION берутся из первого плеча. Безымянные одинаковые литералы ломают оба анализатора под
  обёрткой: `SELECT 'a' AS r, '', '' UNION ALL SELECT 'b', 'x', 'y'` старый склеивает в 2 колонки вместо 3, а новый молча
  отдаёт `b, x, x` вместо `b, x, y` (стенд, 08.10). Если первое плечо названо, безымянные остальные плечи проходят оба
  анализатора, в том числе под обёрткой с GROUP BY (стенд, 08.10). adoption 30.09: pa_head падал под обёрткой на старом
  анализаторе и перестал после AS во всех плечах (стенд); простой формой с названным первым плечом этот сбой не
  воспроизводится, поэтому AS во всех плечах — дешёвая страховка, а не доказанная необходимость.
- **Как:** в первом плече у каждой колонки уникальный `AS`. В остальных плечах — тоже, это дешёвая страховка и читаемость.
  Колонки выхода датасета приводи к типу и имени в одном месте, во внешнем SELECT.
  ```sql
  SELECT ifNull(role, '') AS role, ifNull(k, '') AS k, ifNull(v, '') AS v, toInt64(ifNull(n, 0)) AS n, ifNull(j, '') AS j
  FROM ( SELECT 'meta' AS role, … UNION ALL SELECT 'D' AS role, … )
  ```
- **Проверка:** стенд исполняет SQL под обёрткой `SELECT <Измерения> FROM (…) AS virtual_table GROUP BY … LIMIT N`
  (SP-13, 02-superset-path.md) — число колонок и значения совпадают с прямым запросом.
- **Уверенность:** [стенд 24.8].
- **Образец:** detail_list:proteus/detail-list.data.sql (внешний SELECT `role k v n j` с `ifNull` и явными AS в каждом плече).

### CH-11. Не давай алиасу имя входной колонки
- **Почему:** алиас-омоним подменяет колонку. В WHERE того же SELECT подмена идёт на обоих анализаторах по умолчанию:
  `toInt64(0) AS n` отсеял все AD-группы (adoption, стенд 30.09). В HAVING `groupBitOr(msk) AS msk` даёт верный ответ по
  умолчанию, Code 215 NOT_AN_AGGREGATE при «новый + prefer» (так было в бою adoption 23.09) и молча неверный ответ при
  «старый + prefer» (3 вместо 31). Пример подмены: `SELECT number + 1 AS number, number * 10 AS y FROM numbers(2)` даёт
  `y = 10, 20`, а с `prefer_column_name_to_alias = 1` — `0, 10`.
- **Как:** входные колонки переименовывай во внутреннем подзапросе (`ifNull(mngt_unit_rk, '') AS u0` → снаружи `u0 AS rk`).
  Если алиас-омоним неизбежен, ссылайся на колонку через алиас таблицы (`z.n`, `lp.login`).
- **Проверка:** матрица CH-03 (режимы prefer с обоими анализаторами).
- **Уверенность:** [бой] (Code 215, 23.09) [стенд 24.8].
- **Образец:** TeamPulse:Team Pulse/Поставка — TeamPulse Hub/2. Proteus — датасет teampulse_hub.sql (CTE `st`: `u0`, `p0`,
  `l0`, `n0`); adoption:Виджеты/pa-head.data.sql (секция `adg`: `z.n` вместо `n`).

### CH-12. Обходи ловушки старого анализатора, чтобы матрица сходилась
- **Почему:** бой работает на новом анализаторе, но матрица CH-03 держит запрос устойчивым к смене профиля. Находки стендов
  29.09–08.10:
  - `ARRAY JOIN` по алиасу `WITH` старый анализатор не принимает (Code 206), в том числе в подзапросе;
  - `x IN (c.lo, c.hi)` по колонкам CROSS JOIN падает на обоих (новый — Code 1, старый — Code 47);
  - `x IN (SELECT массив)` и `x IN (SELECT кортеж)` — Code 53 на обоих;
  - `WITH (SELECT groupArray(…) …) AS a … WHERE x IN a` (скаляр-массив из данных) — новый Code 1 «Function 'in' is
    supported only if second argument is constant or table expression», старый Code 53;
    `has(a, x)` и `x IN (SELECT … FROM …)` работают на обоих;
  - `x IN ((SELECT lo …), (SELECT hi …))` (кортеж скалярных подзапросов) и `BETWEEN (SELECT …) AND (SELECT …)` работают
    на обоих (стенд, перепроверено 09.10).
- **Как:** для `ARRAY JOIN` подставь литерал из Jinja с пределом длины (например, до 50 rk). Диапазон бери `BETWEEN` или
  `>= / <` по скалярам `tupleElement({{ EX }}, k)`. Список id из контекста — `IN (SELECT arrayJoin(scope) FROM ctx)`
  (хеш-множество, годится для любой длины). Различай: `IN` по константе Jinja (CH-20) и по подзапросу работает, а `IN` по
  скаляру-массиву из данных — нет; `has(a, x)` по такому массиву работает, но линейно (CH-20), поэтому — только для коротких.
- **Проверка:** матрица CH-03, особенно `old` и `old+all`.
- **Уверенность:** [стенд 24.8].
- **Образец:** detail_list:proteus/detail-list.data.sql (списки — константами WITH, `ARRAY JOIN` только по выражениям строки);
  HRBP_HUB:proteus/hrbp-hub.data.sql (`id IN (SELECT arrayJoin(scope) FROM ctx)`).

### CH-13. Приводи ветки if/multiIf, элементы массивов и плечи UNION к одному типу явно
- **Почему:** в бою 23.09 запрос упал с Code 386 «There is no supertype for types Int64, UInt64» на
  `if(length(lv), arrayFirstIndex(…) - 1, …)`. На стенде chdb 4.x всё прошло: типы молча свелись к Variant.

- **Проверка:** стенд на 24.8 (CH-01). На 26.x — только с `use_variant_as_common_type = 0`.
- **Уверенность:** [бой] (23.09) [стенд 24.8].
- **Образец:** adoption:Виджеты/pa-one.data.sql (`ol`: `if(arrayFirstIndex(…) = 0, toUInt32(length(lv)),

## D. Nullable, массивы, типы

### CH-14. Ставь Nullable-броню: ifNull на каждом входе и каждом выходе
- **Почему:** выгрузка gp_to_click делает Nullable все колонки и элементы массивов (GP-20, 06-helicopter-gp.md). Инциденты в
  бою: Code 349 — `CAST(views AS Int64)` получил NULL (22.09), Code 70 на Nullable-ключе JOIN (SQL Lab 22.09; на стенде
  24.8.4.1 в четырёх формах не воспроизвёлся), 500 CANNOT_INSERT_NULL после LEFT JOIN меты (18.09). `arrayConcat` приводит
  к общему супертипу, поэтому Nullable расползается на весь массив,
  кортежи и скаляры (`Array(Tuple(UInt8, Nullable(String)))` при любом порядке аргументов), и следующий CAST к не-Nullable
  даёт 349. Сентинел в ключе JOIN меняет смысл, если значение есть в домене: `ifNull(toInt32OrNull(k), toInt32(0))` приклеил
  строку `'x'` к `dashboard_id = 0` (стенд, 08.10).
- **Как:**
  - `ifNull` на каждой входной колонке до агрегатов, CAST, `arrayConcat`, сравнений;
  - элементы массивов — `arrayMap(x -> ifNull(x, ''), path)`;
  - ключи и элементы кортежей строго не-Nullable: `toString(ifNull(x, ''))`;
  - ключ JOIN ON — сентинел вне домена (`-1` для id ≥ 0; `''` — только если пустого ключа в данных нет);
  - при `join_use_nulls` признак пары — `ifNull(x.hit, 0)` до любого CAST;
  - `ifNull` на каждом выходе датасета.
  ```sql
  arrayJoin(arrayConcat(
    [(toUInt8(0), '')],
    arrayMap(o -> (toUInt8(2), toString(ifNull(o, ''))), owners),
    arrayMap(c -> (toUInt8(3), toString(ifNull(c, ''))), arrayFilter(c -> isNotNull(c) AND c != '', collections))
  )) AS kk
  ```
- **Проверка:** стенд грузит таблицы как gp_to_click: все колонки Nullable, в данных есть NULL. Плюс режим plain (без
  Nullable) — ответ тот же. Матрица CH-03 с `join_use_nulls = 1`.
- **Уверенность:** [бой] (18–22.09) [стенд 24.8].
- **Образец:** HRBP_HUB:stand/ch.py (`load nullable|plain`); HRBP_HUB:proteus/hrbp-hub.data.sql (ifNull на путях и ключах);
  adoption:Виджеты/pa-reports-body.data.sql (CTE `kx`: кортежи `(toUInt8, String)`).

### CH-15. Снимай NULL в массивах после свёртки, а не на каждой строке
- **Почему:** `sum` и `sumForEach` пропускают NULL: `sumForEach([1, NULL], [NULL, 2])` = `[1, 2]`, а слот из одних NULL
  даёт NULL. `arrayMap(ifNull)` на каждой строке куба — лишняя работа на строку и лишние скобки в тексте SQL (их цена —
  SP-15, 02-superset-path.md).
- **Как:** `arrayMap(x -> ifNull(x, 0), sumForEach(v))` после GROUP BY.
- **Проверка:** стенд на Nullable-таблицах с NULL в массивах — ответ равен режиму plain.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (плечо куба: `arrayMap(x -> ifNull(x, 0), sumForEach(v)) AS s`).

### CH-16. Читай колонку как массив, только если таблица выгружена с array_type_cast=True
- **Почему:** без флага gp_to_click кладёт массив GP строкой `'{a,b,c}'`. Бой 28.09, «Синхронизировать столбцы»:
  «Argument 2 of function arrayMap must be Array. Found Nullable(String)» — реестр целей выгружался без флага.
- **Как:** до того как писать `arrayMap` или `has` по колонке, проверь флаг в параграфе выгрузки (GP-20, 06-helicopter-gp.md).
  Без флага бери нужное из другой таблицы (путь юнита — из справочника) или разбирай строку.
- **Проверка:** стенд читает флаги из параграфа выгрузки и без флага кладёт массив строкой.
- **Уверенность:** [бой] (28.09) [стенд 24.8].
- **Образец:** HRBP_HUB:stand/ch.py (`array_cast_tables()`); HRBP_HUB:proteus/hrbp-hub.data.sql (плечо `kpi`: юнит цели —
  по справочнику, а не по `unit_path`).

### CH-17. Типизируй пустые массивы и не пиши кортежный тип в строке CAST
- **Почему:** `CAST(NULL AS Array(String))` — Code 70, `toNullable([1])` — Code 43, `[(3, 'a'), (3, ['b'])]` — Code 386
  (стенд, 08.10). Три вставки SQL v5 adoption (18.09) упали с «Некорректный SQL»: в строке CAST стоял тип
  `'Array(Tuple(UInt8, String))'`. Механизм проверки форка неизвестен, ClickHouse 24.8 и sqlglot 15–30 такой CAST принимают.
- **Как:** пустой массив — `CAST([], 'Array(String)')` (Nullable(Array) не бывает). Пустые ветки ключей —
  `arrayFilter(t -> t.2 != '', [(toUInt8(N), x)])`, без CAST к кортежному типу. Массив внутри кортежа со скалярами —
  `arrayMap(c -> (3, c), arr)`.
- **Проверка:** гейт сохранения (SP-04, 02-superset-path.md) и grep любого кортежного типа в строковом литерале по SQL
  поставки: `rg -n "'[^']*Tuple\(" proteus/*.data.sql` — совпадений быть не должно. Гейт этот CAST не поймает (sqlglot его
  пропускает), поэтому grep обязателен.
- **Уверенность:** [бой] (18.09, кортежный CAST) [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (макрос `qa`: `CAST([], 'Array(String)')`).

## E. Чтение и вычисления

### CH-18. Храни иерархию путём фиксированной длины и читай ветку диапазоном
- **Почему:** при 100 тыс. сотрудников и 10 тыс. юнитов читать нужно только ветку области. Стенд 24.8, 2 млн строк,
  `ORDER BY path_s`: диапазон `[p, p || '0')` читает 3 гранулы из 245, `startsWith` и `LIKE` — тоже 3, а `position(…) = 1` —
  все 245. `hasAny(path, …)` по всей таблице читает всё.
- **Как:** путь — id фиксированной длины (12 hex, GP-15, 06-helicopter-gp.md) через «/», таблица `ORDER BY (path_s)`. Ветка:
  `path_s >= p AND path_s < concat(p, '0')`, где `p` — путь юнита без хвостовой «/», а «0» (48) — следующий символ после
  «/» (47). В диапазон попадают сам юнит и его потомки. Все символы hex не меньше «0», поэтому соседний id, продолжающий
  префикс, в диапазон не попадёт; если в id есть символы меньше «0» («-», «.», пробел), попадёт — отсюда hex фиксированной
  длины. Внутри диапазона уточняй `hasAny(path, scope)` (зона из нескольких корней) — он работает уже по гранулам ветки.
  Плечо, которому в этом режиме нечего читать, получает в общем скаляре пустой диапазон `('', '')`: без второй версии SQL
  и без ветвления Jinja по данным.
  ```sql
  FROM (SELECT * FROM prod_proteus.<куб>
        WHERE path_s >= tupleElement({{ EX }}, 1) AND path_s < tupleElement({{ EX }}, 2)) AS cb
  CROSS JOIN ctx
  WHERE notEmpty(ctx.roots) AND hasAny(cb.path, ctx.scope)
  ```
- **Проверка:** `EXPLAIN indexes = 1` на стенде — гранулы ветки ≪ всех. Регресс: ответ по диапазону равен ответу по
  `hasAny(path, scope)`.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (`ex0`: `lo` / `hi`; плечи куба и атрибутов, пустые `alo` / `ahi`).

### CH-19. Читай гранулами: префикс ключа, PREWHERE, прямая граница партиции, одна строка на сущность
- **Почему:** по выражению `dateDiff(…) < n` ClickHouse партиции не отбрасывает: 69 частей из 69 против 61 из 69 при прямой
  границе (стенд, 08.10). adoption 30.09 так читал факт целиком. detail_list КП: атрибуты сотрудника одинаковы во всех его
  аллокациях, и упаковка по одной строке на сотрудника дала 2,3–2,6 → 1,3 с (вместе с упаковкой до окна, DS-15, 05-dataset.md).
- **Как:**
  - фильтры датасета — равенством или диапазоном по префиксу `order_by` выгрузки (PREWHERE 24.8 поставит сам,
    `optimize_move_to_prewhere = 1`);
  - флаги численности, даты, признаки — явным `PREWHERE`;
  - отсечение партиций — прямой границей на колонку партиционирования (`log_dttm >= <дата>`) в дополнение к `dateDiff`;
  - одна строка на сущность из таблицы связей — `LIMIT 1 BY id`, поля сущности — одним `ANY LEFT JOIN … USING (id)`.
  ```sql
  (SELECT * FROM {{ T_EMP }} PREWHERE {{ glob() }} LIMIT 1 BY mdm_employee_rk)
  …
  ANY LEFT JOIN (SELECT mdm_employee_rk, {{ line_of(EMPC) }} AS eline FROM (… LIMIT 1 BY mdm_employee_rk)) AS e USING (mdm_employee_rk)
  ```
- **Проверка:** `EXPLAIN indexes = 1`: части и гранулы до и после. Prewhere виден в `EXPLAIN` как «Prewhere filter».
- **Уверенность:** [стенд 24.8].
- **Образец:** detail_list:proteus/detail-list.data.sql (макросы `universe()`, `flagged()`, `ANY LEFT JOIN` полей
  сотрудника у КП); adoption:Виджеты/pa-one.data.sql (граница `log_dttm`).

### CH-20. Проверяй вхождение в список через IN по константе (кортеж или `[…]`), а не has/hasAny по литералу
- **Почему:** `has([…], x)` и `hasAny(arr, […])` перебирают литерал линейно на каждой строке, а `IN` по кортежу строит
  хеш-множество. Стенд 24.8, новый анализатор (08.10): 1 млн строк и 500 значений — `has` 3,09 с против `IN` 0,35 с;
  `hasAny(путь из 13, [500])` — 26,8 с против `arrayExists(x -> x IN dl, путь)` 0,57 с; 20 млн строк и 2 000 значений —
  `has` 251 с против `IN` 0,52 с. Константа-массив `WITH […] AS dl` для `IN` так же хороша, как кортеж (1 млн строк × путь
  13, 500 значений: 0,63 против 0,69 с; `x IN dl` — 0,09 с у обоих; перепроверено 09.10), а `hasAny(dl, путь)` даже на 50
  значениях — 3,1 с против 0,41 с у `arrayExists` (стенд, 08.10). Список, повторённый литералом в каждом условии, ещё и раздувает текст запроса:
  2 000 логинов давали 1,8 МБ (detail_list, 29.09).
- **Как:** список фильтра объявляй один раз константой WITH на верхнем уровне и пиши `x IN dl_x`. Для массивов (путь юнита) —
  `arrayExists(x -> x IN dl_x, path)`. Короткие списки (до ≈20 значений) через `has(qa(...), x)` безопасны.
  ```sql
  WITH ('Офис 1', 'Офис 2') AS dl_f_office_desc, ['a1b2c3d4e5f6'] AS dl_mu
  SELECT … WHERE ifNull(toString(office_desc), '') IN dl_f_office_desc
             AND arrayExists(x -> x IN dl_mu, {{ mu_rks() }})
  ```
- **Проверка:** A/B на масштабе с худшим списком (500–2 000 значений). Регресс сверяет ответ `IN` и `hasAny` на малом списке.
- **Уверенность:** [стенд 24.8].
- **Образец:** detail_list:proteus/detail-list.data.sql (константы `dl_f_*` и `x IN dl_f_*` в макросе `fcond`). Там же
  антиобразец: у `mu` / `lu` стоит `hasAny(dl_mu, …)` при списке до 50 юнитов — перевести на `arrayExists(x -> x IN dl_mu, …)`.

### CH-21. Перекодируй значения в коды через transform, а не indexOf
- **Почему:** `indexOf` — линейный поиск по массиву на каждой строке. Стенд 24.8, 20 млн строк, словарь 800 значений (08.10):
  `indexOf` по константе — 79,5 с, по скаляру-подзапросу — 78,8 с, `transform` по константе — 0,59 с, `transform` по массиву
  из скалярного подзапроса — 0,54 с, LEFT JOIN со словарём — 0,83 с. adoption pa_one v2 (30.09): ×20 на столбец
  (0,16 против 0,008 с).
- **Как:** словарь — один скаляр, код — `transform` с нулём «нет в словаре». Где хватает посимвольной замены, используй
  `translate` вместо регулярки.
  ```sql
  toString(transform(x, tupleElement({{ DZ }}, 3), arrayEnumerate(tupleElement({{ DZ }}, 3)), toUInt32(0)))
  ```
- **Проверка:** A/B (CH-31) на масштабе боя. Регресс сверяет коды `transform` и `indexOf` на малом словаре.
- **Уверенность:** [стенд 24.8].
- **Образец:** adoption:Виджеты/pa-one.data.sql (макрос `cd`: `transform` по словарю из скаляра `DZ`). У HRBP_HUB
  `indexOf(zf.N, …)` в плече справочника — кандидат на замену.

### CH-22. Отдавай ряд строкой без хвостовых нулей одной регуляркой и режь окно до arrayJoin
- **Почему:** A/B HRBP на масштабе (07.10): поиск краёв через `arrayFirstIndex` / `arrayLastIndex` замедлял запрос в 2,5
  раза, вторая регулярка для ведущих нулей — в 1,6 раза. Окно, отрезанное до `arrayJoin` и `sumForEach`, вдвое уменьшает
  данные в свёртке. Итог: ответ зоны HRBP 249 → 151 КБ (−39 %) и 2,57 → 2,26 с, супер-HRBP 2 434 → 2 084 КБ.
- **Как:** `replaceRegexpOne(arrayStringConcat(a, ','), '(,0)+$', '')`: `1,2,0,0` → `1,2`, `0,0,0` → `0`, `1,0,10` без
  изменений. Ведущие нули окна передавай префиксом «N@» из известного смещения. Чарт дополняет ряд до длины сетки
  (DS-05, 05-dataset.md).
  ```sql
  arrayMap(i -> if(i * wl >= length(a), '',
           concat(pf, replaceRegexpOne(arrayStringConcat(arraySlice(a, i * wl + 1, wl), ','), '(,0)+$', ''))), range(24)) AS o
  ```
- **Проверка:** A/B (CH-31). Регресс разбирает строки так же, как чарт (`parseArr`), и сравнивает с массивами куба.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (верхний SELECT: резка плоского массива `a` на 24 колонки, макрос `win`).

### CH-23. Давай каждому юниту ряд одной длины, даже без строк под фильтрами
- **Почему:** если у юнита нет строк под фильтрами, его массив пустой, и чарт не сопоставит месяцы.
- **Как:** массив месяцев собирай `sumForEach(arrayMap(i -> if(i = idx, v, 0), range(n)))` по строкам «юнит × месяц» и
  добавь в UNION ALL нулевую строку на каждый юнит. Если сетку можно сделать в ETL — делай плотную сетку там
  (GP-12, 06-helicopter-gp.md).
  ```sql
  SELECT u1 AS rk, i1 AS idx, sum(e0) AS e … FROM (
    SELECT … FROM <факт> WHERE … GROUP BY u1, i1, …
    UNION ALL
    SELECT rk AS u1, toUInt32(0) AS i1, toFloat64(0) AS e0, … FROM pick
  ) GROUP BY u1, i1
  ```
- **Проверка:** регресс — все массивы ответа одной длины, юнит без людей под фильтром даёт нули, а не пустоту.
- **Уверенность:** [стенд 24.8].
- **Образец:** TeamPulse:Team Pulse/Поставка — TeamPulse Hub/2. Proteus — датасет teampulse_hub.sql (CTE `mm` и `arr`).

### CH-24. Строй дерево на N уровней одним GROUP BY … WITH ROLLUP с ключами из данных
- **Почему:** один проход — одна подстановка контекста и одно чтение ветки, а раскрытие строк в чарте обходится без
  запроса. Две ловушки. При `group_by_use_nulls = 1` ключи итоговых строк становятся NULL. На новом анализаторе 24.8
  константные ключи в строках итогов НЕ обнуляются (стенд: `a b` во всех трёх строках, на старом — `'' ''`, `a ''`, `a b`).
- **Как:** ключи `k1…kN` — элементы пути ниже выбранного юнита (где путь кончился — «·»). Уровень строки — число непустых
  ключей. Ключи берутся только из данных и через `ifNull`. «·» после «·» и «·» без соседей-подразделений отбрасывай.
  ```sql
  SELECT [ifNull(k1, ''), ifNull(k2, ''), ifNull(k3, '')] AS ks,
         arrayMap(x -> ifNull(x, 0), sumForEach(v)) AS s
  FROM (SELECT …, if(length(rel) > 0, rel[1], '·') AS k1, … FROM <ветка куба>)
  GROUP BY k1, k2, k3 WITH ROLLUP
  ```
- **Проверка:** матрица CH-03 с `group_by_use_nulls = 1`. Регресс: сумма строк уровня = строка родителя.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (плечо «куб, дерево „Команд“»: `WITH ROLLUP`, `lv`, `pid` путём).

### CH-25. Строй узлы дерева из уникальных путей
- **Почему:** путей у строк источника в разы больше, чем уникальных путей. Дерево КП detail_list (07.10, ответ тот же байт
  в байт): 0,91 → 0,34 с на вкладке УС, 1,45 → 0,54 с на вкладке КП.
- **Как:** `SELECT DISTINCT arrayJoin(<пути>)`, затем префиксы и `GROUP BY` пути.
  ```sql
  FROM (SELECT splitByString(char(31), lp) AS ps
        FROM (SELECT DISTINCT arrayJoin({{ kp_paths() }}) AS lp FROM ({{ cube_emp('*') }})))
  ```
- **Проверка:** A/B (CH-31), ответ байт в байт.
- **Уверенность:** [стенд 24.8].
- **Образец:** detail_list:proteus/detail-list.data.sql (плечо «дерево КП целиком»).

### CH-26. Сворачивай историю до размножения ключа, а мету подтягивай после сжатия
- **Почему:** ускорение куба adoption v6 (22.09), доказанное 17 контрольными суммами: цепочка 11,39 → 3,21 с, промежуточный
  набор 31,5 → 8,8 млн строк. `any()`-мета на уровне «ключ × логин × бакет» стоила +11 с, узкий проход после сжатия —
  1,55 с. Отдельный проход «разложить по бакетам» после дневной предагрегации ничего не менял и стоил 0,88 с.
- **Как:** бакет `if(k < n2, k, -1)` — сразу в первом GROUP BY по сырому факту, первое касание — `max(k) AS kmax` в том же
  GROUP BY. Во ВСЕХ оконных условиях ставь нижний порог `k >= 0`, иначе свёрнутый хвост утечёт в текущий период.
  Строковую мету (имена, владельцы) подтягивай после сжатия факта до нужного зерна. «Вернувшиеся» — `has(ks_win, k + 1)`,
  без `lagInFrame`.
- **Проверка:** контрольные суммы до и после (A/B, CH-31). Регресс сверяет числа с физическими пределами окна: дней
  активности у человека не больше, чем дней в окне (adoption 22.09: «1614 дней» за 30-дневное окно из-за `countIf` по сетке
  «отчёт × день»; PR-12, 15-process.md).
- **Уверенность:** [стенд 24.8].
- **Образец:** adoption:Виджеты/pa-reports-body.data.sql (CTE `kx`: «Мета подтягивается ПОСЛЕ сжатия факта до пар»).

### CH-27. Зажимай позицию бита least(x, 63) и не отдавай в JS маски длиннее 53 бит
- **Почему:** ClickHouse вычисляет выражение и под ложным `AND`, и внутри `if`: `bitTest(1, 70)` — Code 12,
  `bitShiftLeft(1, 70)` — Code 69 (стенд, 08.10). Число в JS — double, точное до 2^53 (`2**53 + 1 === 2**53`).
- **Как:** `bitTest(msk, toUInt8(least(k, 63)))` всегда, даже под условием `k < n`. Маски длиннее 53 бит дели на окна
  (текущее и прошлое по n бит) или отдавай строкой (hex). Как строить маски в ETL — GP-13 (06-helicopter-gp.md): в GP
  `bigint` знаковый, там предел сдвига — 62.
- **Проверка:** регресс с позицией бита > 63 в данных. Чарт сверяет `bitCount` маски с отдельным счётчиком.
- **Уверенность:** [стенд 24.8].
- **Образец:** adoption:Виджеты/pa-one.data.sql (`bitTest(msk, toUInt8(least(fd_k, 63)))`).

## F. Размер запроса, кэш, процесс

### CH-28. Пиши длинные списки литералом `[…]` или кортежем, не `array(…)`; размер запроса считай после reindent
- **Почему:** в 24.8 по умолчанию `max_query_size` 262 144 байт (превышение — «Syntax error: failed at position 262145»,
  легко принять за ошибку SQL) и `max_ast_elements` 50 000. Литерал `[…]`, кортеж `IN (…)` и `WITH (…) AS dl` на 60 000
  значений проходят, а `array('v0', …)` из 60 000 аргументов — Code 168 TOO_BIG_AST (стенд, 08.10). Superset 2.0.1 перед
  ClickHouse делает `format(reindent=True)`. После него вид filters detail_list с носителями раздувается 193,8 → 841,8 КиБ:
  IN-список в строке ×2,2, кортеж в WITH ×1,7, литерал `[…]` ×1,0, потому что sqlparse читает его одним именем.
- **Как:** списки фильтров — константами WITH один раз (CH-20). Компактнее всего после reindent — `WITH ['a', 'b', …] AS dl`
  и `x IN dl`: литерал-массив не раздувается (×1,0), а `IN` по нему так же быстр, как по кортежу (1 млн строк, 500 значений:
  0,09 с у обоих, стенд 09.10); кортеж раздувается ×1,7. `array(…)` — только когда в значениях есть «]» (так требует
  лексер, SP-07, 02-superset-path.md), и не на десятки тысяч аргументов. Бюджет размера меряй на тексте после пути
  Superset (обёртка + reindent) для худших носителей (SP-16, 02-superset-path.md).
- **Проверка:** регресс рендерит худший случай (максимум значений по каждому носителю), прогоняет путь Superset 2.0.1 и
  проверяет < 256 КиБ. В бою: `getSetting` для `max_query_size`, `max_ast_elements`, `max_parser_depth` (открытый вопрос;
  на стенде 262 144 / 50 000 / 1 000).
- **Уверенность:** [стенд 24.8] [исходник 2.0.1] (reindent) [не проверено в бою] (`max_query_size` боя не снят).
- **Образец:** detail_list:proteus/detail-list.data.sql (константы `dl_*` в WITH; бюджет `stand/check.py` пока мерит до
  reindent — после пути Superset вид filters с носителями выходит за предел).

### CH-29. Упорядочивай записи в упакованных кодах по признаку, от которого зависят соседние значения
- **Почему:** коды куба почти не жмутся: ответ панели detail_list 3,1 МБ на проводе принимался 7,2 с (07.10). Если соседи
  по номеру из одного юнита, их коды (юнит, офис, город, стрим, HRBP) идут подряд одинаковыми, и сжатие на проводе лучше.
- **Как:** номер записи — `row_number() OVER (ORDER BY cityHash64(<путь юнита>), id)`.
- **Проверка:** размер ответа после zstd или gzip на стенде до и после. В бою — Network → `chart/data` → Size до и после.
- **Уверенность:** [стенд 24.8] (−5 % на случайной синтетике) [не проверено в бою].
- **Образец:** detail_list:proteus/detail-list.data.sql (макрос `cube_emp`: `eo`).

### CH-30. Не включай кэш запросов ClickHouse без замера
- **Почему:** в бою кэш результатов ClickHouse выключен (08.10). Если его включить (`use_query_cache = 1`), в 24.8 запрос с
  `today()`, `now()` или `currentUser()` упадёт с Code 704: по умолчанию `query_cache_nondeterministic_function_handling = throw`.
  TTL кэша по умолчанию 60 с. «Свой у каждого пользователя» относится к пользователю подключения Proteus (он сервисный и
  один), то есть для зрителей кэш фактически общий. Ответы чартов и так кэширует Superset на 12 ч (F19, 01-platform.md; ключ — SP-21, 02-superset-path.md).
- **Как:** если владелец предложит включить кэш, предупреди о Code 704 и о том, что выигрыш при кэше Superset мал. Окна
  дат считай от даты свежести из данных (DS-07, 05-dataset.md), а не от `today()`, где это возможно.
- **Проверка:** стенд: `SELECT … WHERE today() > … SETTINGS use_query_cache = 1` → Code 704.
- **Уверенность:** [стенд 24.8] [вывод] (последствия для боя).
- **Образец:** нет в проектах (кэш выключен); `today()` есть в TeamPulse:Team Pulse/Поставка — TeamPulse Hub/2. Proteus —
  датасет teampulse_hub.sql (CTE `cal`).

### CH-31. Доказывай каждую оптимизацию A/B на масштабе боя с ответом байт в байт
- **Почему:** интуиция ошибалась. Соединение со словарём вместо `dense_rank` не ускорило (1,08 против 1,18 с у УС, у КП
  медленнее). Двухступенчатая агрегация adoption ускорила вход на 10 % (2,46 → 2,2 с), но замедлила выбор отчёта на 0,3 с
  (1,1–1,4 → 1,5–1,8 с) и откачена 30.09. `arrayJoin` уровнем выше не помог.
- **Как:** стенд масштаба боя (синтетика с боевой кардинальностью, ST-05, 13-stand.md). Новый анализатор. Попеременные прогоны
  A и B (10 штук или лучшее из трёх). Ответ новой версии байт в байт со старой на сетке «логины × юниты × фильтры × режимы».
  Отвергнутые варианты записывай с числами в NOTES / analysis и не возвращайся к ним без нового довода.
- **Проверка:** скрипт «старая версия против новой» (`same.py`) — 0 расхождений. Таблица времени A/B в коммите.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:stand/same.py (832 случая) и HRBP_HUB:stand/scale.py; detail_list:docs/analysis.md (замеры
  отвергнутых вариантов).
