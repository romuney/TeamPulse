# 13. Стенд и проверки (ST)

**Зачем глава.** Боя агент не видит: ClickHouse, Superset и песочницу чарта приходится повторять у себя. До поставки
стенд отвечает на три вопроса. Тот ли ответ: числа, доступ, сходимость между чартами. Дойдёт ли текст до ClickHouse
целым: путь Superset 2.0.1, проверка при сохранении, ключ кэша, бюджет текста. Переживёт ли чарт песочницу и борд:
iframe, `onerror`, CSS, кросс-фильтры, тур. Здесь — как собрать такой стенд и в каком порядке его гонять. Что именно
должно выполняться в SQL и в чарте, решают главы 02–11; здесь — инструменты, режимы и пороги. Готовые куски — `kit/`.

**Главное в 5 пунктах.**
1. **ST-01.** ClickHouse стенда — 24.8 (chdb 2.1.1 в venv на Python 3.12). Прогон падает, если `version()` не 24.8. Новый chdb (26.x) — только второй движок для сверки ответа.
2. **ST-12.** Каждый запрос стенда проходит путь Superset 2.0.1: Jinja в песочнице, sqlparse 0.3.0 **с патчем лексера**, обёртка с `GROUP BY`, `reindent`. Сейчас патч не ставит ни один стенд — и дыра с апострофом в датасете DL им не видна.
3. **ST-08.** Ответ сверяй двумя путями: независимым расчётом по миру и оракулом — прежним боевым датасетом на тех же данных.
4. **ST-22.** Чарт проверяй в модели борда: iframe `sandbox="allow-scripts"`, высокая ячейка, `onerror`, гасящий чарт, полосы Windows, области из JSON поставки, канал скриншотов.
5. **ST-30, ST-33.** Перед сдачей — один гейт на **файлах поставки** (сжатая сборка, подставленные id): 0 провалов, иначе папку поставки не трогать.

Метки уверенности — как в 01-platform.md: [бой], [стенд 24.8], [исходник 2.0.1], [владелец дд.мм], [вывод],
[не проверено в бою].

## A. Движок и данные

### ST-01. Ставь ClickHouse 24.8 в отдельный venv и падай, если `version()` не 24.8
- **Почему:**
  - Бой — ClickHouse 24.8.15.1 с новым анализатором (SQL Lab владельца 08.10). Это непубличная сборка из ветки `24.8`: тега `v24.8.15.1-lts` нет, исходники для сверки бери с ветки.
  - Системный chdb 4.4.0 — это ClickHouse 26.9.2.1. Там `use_variant_as_common_type` по умолчанию `true`: `if(Int64, UInt64)` молча даёт `Variant`, а 24.8 падает Code 386. Adoption 23.09: «no supertype for Int64, UInt64» в бою при зелёном стенде.
  - На 26.9 старый анализатор не выключается («the analyzer is mandatory since v26.9»): половину матрицы режимов (ST-03) там не прогнать.
  - Время на новом движке врёт: на 24.8 adoption медленнее вдвое (каталог 0,91 → 1,47 с, панель 1,35 → 2,6 с).
- **Как:**
  - venv на Python 3.12 + `chdb==2.1.1`. Колёс chdb 2.1.1 под Python 3.13 нет (pip, 08.10); на 3.13 годится `chdb==3.1.2` — тоже 24.8.4.1.
  - Сессия — до любого запроса (в chdb 2.x движок инициализируется один раз на процесс). Первой проверкой:

    ```python
    import chdb.session as cs
    S = cs.Session(DB)
    VERSION = S.query('SELECT version()', 'CSV').bytes().decode().strip().strip('"')
    assert VERSION.startswith('24.8.'), 'стенд не на ClickHouse 24.8: ' + VERSION
    print('ClickHouse', VERSION)                        # первая строка вывода каждого прогона
    ```

  - Системный chdb 4.x держи вторым движком: только для сверки ответа, с `SET use_variant_as_common_type = 0`. Время на нём не меряй, режимы со старым анализатором пропускай с пометкой в выводе.
- **Проверка:** первая строка каждого прогона — «ClickHouse 24.8.4.1 · режим …»; на другом движке основной прогон падает.
- **Уверенность:** [бой] — версия и анализатор; [стенд 24.8] — Variant и Code 386, обязательный анализатор 26.9. «Падать» — новое требование: HRBP сейчас подстраивается под любой движок, DL и TP версию не проверяют.
- **Образец:** HRBP_HUB:stand/ch.py (`VERSION`, `MAJOR`, `use_variant_as_common_type = 0` для ≥ 25, `ANALYZER_OFF`); установка — kit/setup.sh.

### ST-02. Создавай таблицы стенда так, как их создаёт gp_to_click: всё Nullable, массивы — только с `array_type_cast`
- **Почему:**
  - HRBP 28.09: «Синхронизировать столбцы» упала в бою с «Argument 2 of function arrayMap must be Array. Found Nullable(String)». `hrbp_hub_kpi` выгружали без `array_type_cast`, массив приехал строкой, а стенд держал его массивом.
  - Adoption 22.09: Code 349 (NULL в CAST) — в бою колонки Nullable, на стенде нет.
- **Как:**
  - Режим `nullable`: все колонки Nullable, и элементы массивов тоже; `SETTINGS allow_nullable_key = 1`. Второй режим `plain` — без Nullable. Регресс гоняй на обоих.
  - Массивом колонка становится только у таблиц, которые параграф выгрузки грузит с `array_type_cast=True`; у остальных массив GP приезжает строкой `'{a,b}'`. Флаги читай из **текста параграфа выгрузки**, а не держи своим списком:

    ```python
    def array_cast_tables(upload_paragraph_text):
        out = set()
        for call in upload_paragraph_text.split('gp_to_click(')[1:]:
            m = re.match(r"\s*'(\w+)'", call)
            if m and re.search(r'array_type_cast\s*=\s*True', call):
                out.add(m.group(1))
        return out                                  # остальным: Nullable(String) со значением '{a,b,c}'
    ```

  - `ORDER BY` таблиц стенда — как в выгрузке (`order_by` параграфа): от него зависит чтение диапазоном (04-clickhouse.md, CH-19).
- **Проверка:** `python3 stand/ch.py load nullable` и `… plain`; регресс зелёный на обоих. Таблица без флага печатается с пометкой «массивы строкой».
- **Уверенность:** [бой] (HRBP 28.09, adoption 22.09).
- **Образец:** HRBP_HUB:stand/ch.py (`array_cast_tables`, `ch_type`, `load(mode)`); правило выгрузки — 06-helicopter-gp.md, GP-20.

### ST-03. Гоняй каждый запрос одной функцией по всей матрице режимов и сравнивай подписи ответов
- **Почему:** профиль ClickHouse Proteus снят не весь: `prefer_column_name_to_alias`, `join_use_nulls`, `group_by_use_nulls` в бою неизвестны (F14, 01-platform.md). Adoption 23.09: Code 215 в бою (HAVING по алиасу-омониму) — на стенде он воспроизводится только сочетанием «новый анализатор + `prefer_column_name_to_alias = 1`». Обратный случай (алиас `toInt64(0) AS n` прячет колонку `n` в WHERE, adoption 30.09) по умолчанию даёт пустой ответ, а верный — только при `prefer`. Нужны оба режима.
- **Как:**
  - Список режимов — 04-clickhouse.md, CH-03 (по умолчанию, старый анализатор, каждая настройка отдельно, «все вместе» со старым и с новым анализатором). Режимы — снаружи текста датасета: `SETTINGS` дописывает стенд, не датасет.
  - Одна функция для всех проверок: датасет, файлы SQL Lab, `same.py`.

    ```python
    def run_matrix(sql, modes=MODES):
        sig = {}
        for name, st in modes.items():
            if VERSION.startswith('26.') and 'allow_experimental_analyzer = 0' in st:
                continue                                  # на 26.9 старого анализатора нет
            rows, _ = run(sql, st)                        # run дописывает '\nSETTINGS ' + st
            dump = sorted(json.dumps(r, sort_keys=True, ensure_ascii=False) for r in rows)
            sig[name] = hashlib.md5('\n'.join(dump).encode()).hexdigest()[:12]
        assert len(set(sig.values())) == 1, sig           # печать «режим → подпись» при расхождении
        return rows
    ```

  - Порядок строк сравнивай отдельно, там, где он что-то значит (05-dataset.md, DS-25).
- **Проверка:** регресс печатает «режим → подпись»; все подписи одинаковы на 24.8 Nullable и plain.
- **Уверенность:** [стенд 24.8] + [бой] (Code 215, 23.09). Режим «новый анализатор + все» есть только у TP; HRBP сравнивает отсортированные строки без него.
- **Образец:** TeamPulse:Team Pulse/stand/dataset.py (`CFG`, пять режимов, сверка байт в байт); detail_list:stand/check.py (раздел режимов ClickHouse).

### ST-04. Гоняй GP-параграфы на PostgreSQL 16 тем же текстом, что уедет в Helicopter
- **Почему:** Greenplum недоступен. PostgreSQL 16 принимает больше, чем GP6 (основа — PG 9.4.26), поэтому одного «прошло на PG16» мало.
- **Как:**
  - Текст параграфов читай из того же YAML или файлов параграфов, что уйдут владельцу. Снимай только GP-специфику: `distributed by / randomly / replicated`, `set optimizer`.
  - `current_date` стенда — день после даты мира: ноут проверяет свежесть источника, а мир застыл на своей дате.
  - Стоп-проверки и диагностику исполняй вместе с параграфами; каждый оператор — отдельно, чтобы видеть, где упало.
  - Подмножество GP6 проверяй grep'ом перед прогоном: нельзя `LATERAL` (в GP6 «LATERAL Join Type — NO») и всё, что появилось после PG 9.4 (`ON CONFLICT`, новые jsonb-функции). `FILTER` у агрегатов и `GROUPING SETS / ROLLUP / CUBE` в GP6 **есть** — их не запрещай (правила SQL — 06-helicopter-gp.md, GP-01).
- **Проверка:** `python3 stand/run_gp.py [--seed-kpi]`: все параграфы зелёные, стоп-проверки напечатали ожидаемое, grep подмножества пуст.
- **Уверенность:** [стенд 24.8] (PG 16 вместо GP); подмножество GP6 — [исходник] (feature summary и грамматика GP6). Grep подмножества пока не сделан ни в одном проекте: в HRBP оно записано только комментарием.
- **Образец:** HRBP_HUB:stand/run_gp.py (`to_pg`, `statements`, `TODAY = W.D + 1 день`).

### ST-05. Строй синтетический мир детерминированным, масштаба и кардинальности боя, с ломающими случаями
- **Почему:**
  - Adoption 23.09: клик в бою шёл 3–5 с (SQL Lab — 2,33 с), на стенде — 0,15 с: в синтетике у человека было 1–2 AD-группы, в бою — сотни. После «толстых» групп стенд показал 1,17 с на отчёт и 2,7 с на весь Proteus.
  - HRBP: время почти не зависит от объёма — это цена планирования плеч, и видно её только на масштабе и повторами (ST-18).
- **Как:**
  - Мир — из seed, одинаковый при каждом запуске. Масштаб и кардинальности — из разведки боя (DV-31, 14-delivery.md): число сотрудников, юнитов по уровням, значений справочников, элементов массивов на человека.
  - Две базы: малая — для правильности (быстрые прогоны), боевого масштаба — для времени и веса ответа. Ориентиры проектов: HRBP — 100 тыс. сотрудников и 10 тыс. юнитов на 12 уровнях; DL — 100 тыс. сотрудников и 200 тыс. аллокаций.
  - Обязательные ломающие случаи:
    - переводы, реорганизация, расформирование, переименование, повторный найм, декрет;
    - уровни 2 и 13 (глубже пути), юнит с двумя родителями;
    - спецсимволы в значениях: апостроф (`O'Brien`), «]», `--`, `;`, слэш в конце, тире;
    - логины всех видов доступа: полный, частичный, особые правила, **без строки доступа** (`nobody`);
    - пустые значения и значения «не указано».
  - Логины мира — синтетические (`a.user`, `hr.super`, `b.kotov`, `nobody`). Реальных логинов в мире нет.
- **Проверка:** `python3 stand/world.py` дважды даёт одинаковые таблицы (md5). Сводка мира печатает масштаб и кардинальности рядом с числами разведки боя.
- **Уверенность:** [бой] (расхождение стенда и боя у adoption).
- **Образец:** detail_list:stand/world.py (100 тыс. сотрудников, 200 тыс. аллокаций, логины всех видов доступа); HRBP_HUB:stand/world.py и stand/scale.py (100 тыс., 10 тыс. юнитов, глубокая ветка до 13-го уровня).

### ST-06. Патологию боя, которой нет в мире, проверяй на испорченной копии источника
- **Почему:** DL 27-я поставка (08.10): в бою у дерева УС 52 090 узлов на 12 249 листов — уровни ниже юнита заполнены им же. Мир стенда таких повторов не давал, и правило `nodup` проверить на нём было нельзя.
- **Как:**
  - Копия источника — в отдельной базе стенда (`pad`), испорченная так же, как бой:

    ```sql
    CREATE TABLE pad.src AS prod.src;
    INSERT INTO pad.src SELECT * REPLACE (
        coalesce(nullIf(lvl5, ''), nullIf(lvl4, ''), nullIf(lvl3, '')) AS lvl5 /* … каждый уровень ниже — так же */)
    FROM prod.src;
    ```

    (`* REPLACE` — только на стенде; в SQL Lab его не используй, 01-platform.md, PL-04.)
  - Сверки на копии:
    1. ответ датасета на копии равен ответу на чистом источнике;
    2. итог с фильтром по глубокому юниту тот же;
    3. проверка непустая: «узлов как есть» больше, чем узлов в ответе.
  - Без правила проверка должна падать: так видно, что она что-то ловит.
- **Проверка:** раздел регресса «копия с повторами»: 0 провалов с правилом, провал без него. DL: УС на копии — 49 503 узла как есть → 26 103 в панели, столько же, сколько без повторов.
- **Уверенность:** [стенд 24.8] + [бой] (повторы — ответ файла 10 DL, 08.10). Эффект правила в бою ждёт ответа владельца.
- **Образец:** detail_list:stand/check.py (`padded_check`); правило данных — 05-dataset.md, DS-21.

### ST-07. Агрегат-источник симулируй «по людям» с `truth.json`; запрос разведки проверяй на симуляции
- **Почему:**
  - TP 08.10: макет складывал детей в родителя, а в боевом `hr_structure_overall` строка юнита уже включает поддерево — сумма строк месяца в 9,6 раза больше численности. Ловится только симуляцией, которая строит агрегат так же, как бой.

- **Как:**

### ST-08. Сверяй ответ датасета с независимым расчётом и с оракулом прежнего датасета
- **Почему:**
  - Сходство «на глаз» пропускает съехавший слот, потерянный JOIN и лишнее окно. Независимый расчёт ловит их число в число.
  - Требование владельца при замене отчёта — доступ не слабее прежнего. Это видно только по оракулу: прежний боевой датасет, исполненный на тех же данных. DL так нашёл, что прежний датасет у логина без строки доступа падает («Scalar subquery returned empty result»).
- **Как:**
  1. **Независимый расчёт** (`expect.py`) читает только мир (`world.py`), а не SQL датасета, и считает так, как считает чарт (для счётчиков «до Применить» — та же семантика, что `cond()` датасета; 05-dataset.md, DS-12). Сверка — по всем слотам, компонентам, логинам, юнитам и разрезам.
  2. **Оракул** — SQL прежнего датасета из выгрузки борда владельца (`datasets/…yaml`), отрендеренный и исполненный на стенде как есть: те же сотрудники, те же поля, те же маски доступа (03-access-cache.md, AC-04).
  3. Если в чарте есть своя модель счёта (куб, «Будет N»), её копия на стенде (`cube_count`) сверяется и с независимым расчётом, и с итогом датасета.
- **Проверка:** раздел «независимый расчёт» и «оракул» регресса — 0 провалов на всех логинах мира. Ориентиры: HRBP `check.py` — 491 проверка на 26.9 и 493 на 24.8; DL — 365 / 0.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:stand/expect.py (расчёт по миру); detail_list:stand/ch.py (`current` — оракул из выгрузки, `cube_count`) и stand/check.py (`oracle`, `independent`).

### ST-09. Строй регресс на инвариантах сходимости между чартами, уровнями и версиями

### ST-12. Пропускай каждый запрос стенда через одну функцию пути Superset 2.0.1 — с патчем лексера sqlparse
- **Почему:**
  - В ClickHouse уходит текст после Jinja, `strip_comments`, обёртки и `reindent`, а не исходник (02-superset-path.md, SP-01). chdb выполнит всё, поэтому поломки пути видит только модель пути.
  - В 2.0.0 и 2.0.1: `sqlparse==0.3.0  # PINNED!` плюс патч лексера в `superset/sql_parse.py` — своё правило строкового литерала первым в `SQL_REGEX`. В нём `\'` кавычку **не** экранирует.
  - **Ни один стенд четырёх проектов патч не ставит.** Проверка 08.10: датасет списка DL на пути с патчем падает от значения `office_desc=O'Brien; x` («Virtual dataset query cannot consist of multiple statements»), а `O'Brien -- x` теряет хвост строки как «комментарий». Без патча (как стенд DL) — всё проходит.
  - На sqlparse 0.4.4 код Superset 2.0.x даже не импортируется (`sqlparse.keywords.FLAGS`). Стенд HRBP «как 2.1 на 0.4.4» не повторяет ни 2.0, ни 2.1 (2.1.0 — это 0.4.3).
  - В 2.0.1 Jinja — `SandboxedEnvironment(undefined=DebugUndefined)` без расширений. Все стенды подключали `jinja2.ext.do`, три из четырёх — обычный `Environment`.
- **Как:** одна функция для `check`, `live`, `click`, `mock`, `same`, SQL Lab-файлов:

  ```python
  import re, sqlparse
  from sqlparse import keywords, tokens
  assert sqlparse.__version__ == '0.3.0'                  # нет sqlparse — падать, а не пропускать шаги
  keywords.SQL_REGEX.insert(0, (re.compile(r"'(''|\\\\|\\|[^'])*'", keywords.FLAGS).match,
                                tokens.String.Single))   # как superset/sql_parse.py 2.0.1; ДО первого вызова
  from jinja2 import DebugUndefined
  from jinja2.sandbox import SandboxedEnvironment

  def superset201(text, ctx, measures, limit=50000):
      env = SandboxedEnvironment(undefined=DebugUndefined)  # без extensions: {% do %} — ошибка, как в бою
      env.filters['where_in'] = where_in
      sql = env.from_string(text).render(**ctx)            # filter_values, url_param, current_username, …
      assert '{{' not in sql and '{%' not in sql, 'неизвестная переменная осталась текстом'
      sql = sqlparse.format(sql.strip('\t\r\n; '), strip_comments=True)
      if len(sqlparse.split(sql)) > 1:
          raise ValueError('Virtual dataset query cannot consist of multiple statements')
      # + «только чтение»: ParsedQuery … is_select / is_unknown (detail_list:stand/ch.py, superset20)
      cols = ', '.join(measures)
      wrapped = 'SELECT %s FROM (%s) AS virtual_table GROUP BY %s LIMIT %d' % (cols, sql, cols, limit)
      return sqlparse.format(wrapped, reindent=True)        # это и уходит в ClickHouse
  ```

  - **Режим сохранения** — отдельный вызов: `filter_values` отдаёт объект AlwaysTrue (истинный, итерация пустая, `+` со списком — ошибка, как «unsupported operand type(s) for +: 'AlwaysTrueObject' and 'list'»), логин — сохраняющего. Дальше разбор **без** `strip_comments` (одна инструкция, только SELECT), затем текст + `\nLIMIT 1000` исполняется **без обёртки** (так же «Синхронизировать столбцы», F9 в 01-platform.md). AlwaysTrue — поведение форка, в ванильном 2.0.1 его нет.
  - `current_username` и `url_param` кладут значение в ключ кэша, только если регулярка нашла вызов (ST-16).
  - Более новые sqlparse (0.4.4, 0.5.5, 0.6) гоняй через `PYTHONPATH` только как запас на обновление Proteus.
- **Проверка:** контрольный прогон пути: `'O\'Brien; x'` после `format(strip_comments)` и `split` даёт 2 инструкции — патч стоит; `'O''Brien; x'` — 1. Ответ после `reindent` равен прямому запуску.
- **Уверенность:** [исходник 2.0.1] — пин, патч, Jinja, порядок шагов; [стенд 24.8] — поломка датасета DL с патчем; [не проверено в бою] — пин sqlparse форка не виден, AlwaysTrue — [бой].
- **Образец:** готовая функция — kit/superset201.py. Ближе всех из проектов — detail_list:stand/ch.py (`superset20`, `dataset`, `AlwaysTrue`, `url_param`): добавить вставку правила лексера, `DebugUndefined`, убрать `ext.do`. ### ST-14. Гоняй враждебный ввод через путь sqlparse, а не прямо в ClickHouse
- **Почему:** лексер sqlparse 0.3.0 (с патчем) читает `[…]` как имя T-SQL до первой «]», а `\'` не считает экраном кавычки. Тогда строка и код меняются местами: `strip_comments` вырезает «комментарий» прямо из строки, `;` становится концом инструкции. chdb такие тексты выполняет, поэтому прямой прогон ничего не находит. DL 07.10: юнит КП со «]» ронял запрос списка — нашёл только стенд пути.
- **Как:**
  - Набор значений для **каждого** носителя фильтра и параметра адреса:
    `]`, `[`, `a ] -- b`, `]';--`, `x // y`, `# x`, `a; b`, `O'Brien`, `O'Brien; x`, `x'); DROP TABLE t;--`, слэш в конце (`x\`, `x\\`), обратная кавычка, управляющие символы, пустая строка, очень длинное значение, чужие ключи и значения, носители другой вкладки, испорченная ссылка, худший объём (2 000 логинов + 500 значений).
  - Каждое значение — в нескольких контекстах (кортеж `IN (…)`, `[…]`, `array(…)`) и через путь ST-12.
  - Ожидается:
    1. запрос цел, одна инструкция;
    2. `strip_comments` удалил только комментарии (токены sqlglot до и после совпадают, ST-15);
    3. ответ точный: значение найдено или отброшено правилом, а не обрезано;
    4. эхо в `meta` без мусора.
  - Значения с длинным и коротким тире на chdb не проверить (ST-21) — пункт «не проверено».
- **Проверка:** раздел «враждебный ввод» регресса — 0 провалов. Контроль, что набор работает: со старым экранированием `\'` раздел обязан падать.
- **Уверенность:** [стенд 24.8] (20 значений × 2 экранирования × 3 контекста, 08.10: с `''` и `array(…)` проходят все 20).
- **Образец:** detail_list:stand/check.py (раздел враждебного ввода) и stand/parse.py — без патча лексера, добавить его; правила экранирования — 02-superset-path.md, SP-06…SP-11.

### ST-16. Проверяй ключ кэша регуляркой Superset по сырому тексту; эмулируй логин в ключе только при её совпадении
- **Почему:**
  - 07.10 в трёх проектах ключ кэша был общим на всех: вызов `current_username()` стоял в `{% set %}`, а регулярка `ExtraCache.regex` 2.0.1 ищет вызов только внутри `{{ … }}` на одной строке.
  - Adoption в ту же ночь поставил правку, которая прошла регресс и не сработала в бою: эмуляция стенда клала логин в ключ при **любом** вызове. Понадобились три итерации.
  - Регулярка видит и комментарии: `{# {{ current_username() }} #}` и `-- {{ … }}` тоже делают кэш личным.
- **Как:**
  - Регресс читает **сырой** текст каждого датасета двумя регулярками: 2.0–4.0 и 4.1+ (вторая видит и `{% %}` — запас на обновление Proteus):

    ```python
    RX_20 = re.compile(r"\{\{.*(current_user_id\(.*\)|current_username\(.*\)"
                       r"|cache_key_wrapper\(.*\)|url_param\(.*\)).*\}\}")      # точка не ловит \n
    # RX_41 — дословно из superset/jinja_context.py 4.1.1 (detail_list:stand/parse.py, CACHE_RX)
    assert RX_20.search(personal_text_without_comments), 'логин не попадёт в ключ'
    assert not RX_20.search(shared_raw_text) and not RX_41.search(shared_raw_text), 'общий кэш станет личным'
    assert not RX_20.search("{% set me = current_username() %}")              # анти-пример: не видит
    ```

  - Датасет с личным ключом: вызов **находится** (в коде, не в комментарии). Датасет с общим ключом: **не находится нигде**, включая комментарии, и обеими регулярками. Регулярка смотрит ещё в предикат автозаполнения, `extras.where`/`having` и RLS (`has_extra_cache_key_calls`) — их тоже проверь или держи пустыми.

### ST-20. Тяжёлые проверки запускай процессом на вкладку или режим; процесс без итога — провал
- **Почему:** chdb и Python не отдают память между разделами. DL 06.10: обе вкладки в одном процессе дошли до 14 ГБ и упали по OOM, по одной — до 10,7–11 ГБ.
- **Как:**

  ```python
  for mode in modes:                                         # главный процесс только раздаёт и суммирует
      pr = subprocess.Popen([sys.executable, '-u', __file__, mode], stdout=subprocess.PIPE,
                            stderr=subprocess.STDOUT, text=True)
      seen = False
      for line in pr.stdout:
          print(line, end='', flush=True)
          m = re.match(r'(\d+) проверок, провалов: (\d+)', line.strip())
          if m:
              seen, total, bad = True, total + int(m.group(1)), bad + int(m.group(2))
      code = code or pr.wait() or (0 if seen else 1)        # убит — итога нет — провал
  ```

- **Проверка:** итоговая строка «Обе вкладки: N проверок, провалов: 0» и код выхода 0.

- **Образец:** detail_list:stand/check.py (`main`: процесс на вкладку, `seen`).

### ST-21. Учитывай поправки на chdb и записывай их в «не проверено»
- **Почему:** без поправок стенд расходится с боем или ложно падает, а часть поведения на chdb не проверить вовсе.
- **Как:**

  | Особенность chdb | Что делать |
  |---|---|
  | нет `base64Encode` (Code 46 в 2.1.1) | стенд вырезает вызов и кодирует в Python; размер ответа тот же |
  | длинное и короткое тире превращаются в `--` даже внутри строки (`SELECT '–—'` → `----`, длина 4) | значения с тире на стенде не проверить — строка в «Что не проверено» |

  | тяжёлые вставки после psycopg2 в том же процессе зависают (chdb 2.x) | заливка масштаба — отдельным процессом |

- **Проверка:** поправки собраны в одном месте `stand/ch.py` с комментарием «почему»; каждая непроверяемая вещь — строкой в CLAUDE.md, раздел «Что не проверено стендом».

### ST-27. Лови мигания и скачки покадровой записью внутри iframe
- **Почему:** скачок выпадашки из видео коллег (DL, 06.10) глазами на стенде не ловился. Adoption: запись поймала дёргание 16 → 304 → 16 px при закрытии выпадашки.
- **Как:** внутри iframe ≈900 мс пиши положение и ширину элемента в каждом видимом кадре; все кадры должны совпасть с итогом. Родитель с задержкой (`?delay=`) обязателен: без неё гонки не видно.

  ```js
  await frame.evaluate(() => {
    window.__fr = [];
    const t0 = performance.now();
    (function tick() {
      const d = document.querySelector('[class$="-dd"]');
      if (d) { const cs = getComputedStyle(d), r = d.getBoundingClientRect();
               if (cs.display !== 'none' && +cs.opacity > 0) window.__fr.push(Math.round(r.left) + '/' + Math.round(r.width)); }
      if (performance.now() - t0 < 900) requestAnimationFrame(tick);
    })();
  });
  // … открыть выпадашку, подождать 700 мс; все кадры одинаковы и справа от панели
  ```

- **Проверка:** шаг прогона «выпадашка не мелькает и не растёт» — все кадры равны первому.
- **Уверенность:** [бой] — симптом с видео воспроизведён и снят.
- **Образец:** detail_list:stand/click.cjs (запись `__ddfr` в шаге выпадашки); adoption:.stand/audboard.mjs (probe дёрганий).

### ST-32. Собирай SQL Lab-файлы из тех же шаблонов и исполняй их на стенде путём 2.0.1
- **Почему:**
  - Проверочные запросы, написанные руками, отстают от датасета: файл 11 DL («где время») вставляет SQL панели как есть и в 27-й поставке изменился вместе с ним.

  - Сборщик берёт отрендеренный текст датасета (без Jinja) из того же исходника, что и папка поставки, и вставляет его в свой запрос.
  - Регресс:
    1. файл в папке поставки равен текущей сборке (иначе «пересобрать: `--rebuild`»);

    5. у каждого запроса — комментарий «Ждали: …» с ожидаемыми числами на стенде.
  - Руками проверочные SQL не правят.
- **Проверка:** `python3 stand/diag.py --run`, `python3 stand/timing.py --run` (DL), `python3 .stand/check_one.py <папка> --rebuild` (adoption §8).
- **Уверенность:** [бой] — запрет `system`; [исходник 2.0.1] — `strip_comments` в SQL Lab [не проверено в бою].
- **Образец:** detail_list:stand/diag.py (`build`: запрос из `ch.sql`, assert на «system»), stand/timing.py; adoption:.stand/check_one.py (раздел 8: рендер = шаблон, исполняется, метка `777777` не встречается сама по себе). Формат файлов — 14-delivery.md, DV-27, DV-28.

### ST-33. Проверяй сдачу одним гейтом; при любом провале папку поставки не трогай
- **Почему:** маршрут проверок — десяток команд, и легко отдать файл без одной из них: HRBP проходит его вручную, у adoption ESLint и сборки нет вовсе, у TP нет пути Superset. Ни в одном проекте нет единого гейта.
- **Как:** один скрипт (`stand/verify.sh` или `pack.py --verify`) по порядку, с остановкой на первом провале:
  1. `pack.py --check` против прошлой папки (что изменилось — список файлов для «Что нового»);
  2. датасеты: `check.py` (24.8 Nullable и plain, режимы, оракул, независимый расчёт, враждебный ввод, обёртка, ключ кэша), второй движок — сверка ответа;
  3. `parse.py` — гейт сохранения на исходнике и на файлах поставки;
  4. `superset.py` — бюджет не хуже прошлой поставки; `same.py` — против тега прошлой поставки, если датасет переписан;
  5. чарт: `node --check`, ESLint no-undef, `check.py` скилла — на исходнике;
  6. сборка (`pack.py`), `node --check` сборки, печать КБ и секунд отправки;
  7. на файлах поставки (`DIST=1`): живой прогон, тур, гонка фильтров;
  8. SQL Lab-файлы: исполняются, без запретных слов.

  Итог — «можно отдавать» или «что упало». Пока гейт не зелёный, коммит — «WIP — не для установки», папка поставки прежняя (15-process.md, PR-22).
- **Проверка:** вывод гейта с итогами по каждому шагу кладётся в тело коммита поставки.
- **Уверенность:** [вывод] — отдельные шаги проверены в проектах, единого гейта нет ни в одном.
- **Образец:** состав шагов — detail_list:CLAUDE.md (таблица «Куда идти» и раздел «Стенд»); HRBP_HUB:CLAUDE.md (маршрут датасета: `check.py` → `scale.py` → `superset.py` → `same.py`). Шаблон — kit/.
