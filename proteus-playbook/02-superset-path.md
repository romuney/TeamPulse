# 02. Путь SQL датасета через Superset 2.0.1 (SP)

**Зачем глава.** В ClickHouse уходит не тот текст, который ты написал. Сначала его рендерит Jinja, потом sqlparse
с патчем Superset вырезает комментарии и делит текст на инструкции (по исходнику 2.0.1 — 0.3.0, бой похож на 0.4.x —
поэтому моделей две, SP-02). Затем Superset оборачивает его в `SELECT … GROUP BY …
LIMIT`, переформатирует (`reindent`) и только после этого отдаёт ClickHouse. При сохранении датасета есть ещё
проверка форка. Где-то на этом пути строки ломаются, текст раздувается, а ключ кэша теряет логин. chdb всё это
выполнит без ошибок, поэтому такие поломки видит только модель пути. В главе — схема пути, ловушки на каждом шаге,
бюджеты текста и механика ключа кэша. Политика доступа и кэша — в 03-access-cache.md.

**Главное в 5 пунктах.**
1. **SP-02.** Гоняй путь в двух моделях лексера — sqlparse 0.3.0 с патчем 2.0.1 и 0.4.4 с патчем 2.1.3/3.0; датасет обязан пройти обе. Без патча Superset модель не годится.
2. **SP-06, SP-07.** Кавычку экранируй удвоением `''`, а не `\'`. Литерал `[…]` пиши только тогда, когда внутри нет «]», иначе — `array(…)`.
3. **SP-13.** Считай, что обёртка чарта делает `GROUP BY` по всем «Измерениям»: строки ответа уникальны, порядок и обрезка произвольны.
4. **SP-15, SP-16.** Бюджет текста — КБ, токены, скобки и время `reindent`. `max_query_size` меряй по тексту после обёртки и `reindent`.
5. **SP-20, SP-24.** Логин попадает в ключ кэша, только если вызов стоит внутри `{{ … }}` на одной строке. Cache timeout −1 кэш не выключает.

Метки уверенности — как в 01-platform.md: [бой], [стенд 24.8], [исходник 2.0.1], [владелец дд.мм], [вывод],
[не проверено в бою].

## Модель пути

### SP-01. Моделируй путь текста целиком: в ClickHouse уходит текст после strip_comments, обёртки и reindent
- **Почему:**
  - Всё, что лексер sqlparse прочёл не так, как ClickHouse, может испортиться на шаге 3. DL 07.10: юнит КП со «]» давал «multiple statements». Проверка 08.10: апостроф в значении режет запрос (SP-06).
  - Длина и скобки стоят секунд на шагах 0 и 7. HRBP 08.10: «Применить» 20 с при 2–2,5 с ClickHouse.
  - `max_query_size` считается по тексту после шага 7 (SP-16).
  - Сбитый лексер портит текст и на шаге 7: `reindent` вставляет и схлопывает пробелы внутри строк, которые принял за код. Прогон kit 08.10: HRBP `',"it":'` → `', "it":'`, adoption `translate(x, '\t\n\r', '   ')` → аргумент `' '` и Code 36 на любом открытии в модели 0.3.0.
  - chdb выполняет всё, поэтому стенд, который отдаёт отрендеренный текст прямо в ClickHouse, этих ошибок не видит.
- **Как:** Каждый SQL поставки на стенде проходит одну функцию «путь 2.0.1» в обеих моделях лексера (SP-02). Её ответ сверяй с прямым запуском. Суть модели:

  ```python
  import re, sqlparse                                   # две модели лексера — SP-02
  def superset201(rendered, measures, row_limit=50000):
      s = sqlparse.format(rendered.strip('\t\r\n; '), strip_comments=True)
      if not s:
          raise ValueError('Virtual dataset query cannot be empty')
      if len(sqlparse.split(s)) > 1:
          raise ValueError('Virtual dataset query cannot consist of multiple statements')
      if sqlparse.parse(s)[0].get_type() not in ('SELECT', 'UNKNOWN'):
          raise ValueError('Virtual dataset query must be read-only')
      cols = ', '.join(measures)
      wrap = 'SELECT %s \nFROM (%s) AS virtual_table GROUP BY %s\n LIMIT %d' % (cols, s, cols, row_limit)
      return sqlparse.format(wrap, reindent=True)        # ЭТОТ текст исполняет ClickHouse
  ```

  Варианты рендера: сохранение (AlwaysTrue, SP-05), открытие по умолчанию, худший набор носителей, враждебный ввод (SP-11), ссылка (SP-23). Готовая модель — `kit/superset201.py` (CLI и модуль: `render`, `chart_path`, `save_path`, `lexer_problems`), стенд — 13-stand.md:

  ```bash
  for PY in ~/.venvs/proteus-kit/bin/python ~/.venvs/proteus-sp044/bin/python; do   # обе модели (kit/setup.sh)
    $PY kit/superset201.py proteus/report.data.sql --user b.kotov --cols auto --run --db stand/.chdb24 --hostile
  done
  ```
- **Проверка:** На стенде ответ ClickHouse на текст после пути равен ответу на отрендеренный текст (сравнение множеств строк — обёртка с GROUP BY порядок не держит и склеивает дубли), код выхода `superset201.py` — 0 в обоих venv. Если два прямых запуска одного текста дают разный ответ (pa_body_one adoption: `groupArray` без сортировки), сверка невозможна — сначала сделай ответ детерминированным (`arraySort` перед `arrayStringConcat`). В бою — DevTools → Response → `result[0].query`: это текст после шага 7.
- **Уверенность:** [исходник 2.0.1]; косвенно [бой]: 20 с на «Применить» в HRBP совпали с моделью стенда (18,6–20,5 с).
- **Образец:** TeamPulse:proteus-playbook/kit/superset201.py (путь 2.0.1 буквально, обе модели, `--run`, `--hostile`). В проектах: detail_list:stand/ch.py (`superset20`, `dataset` — обёртка с GROUP BY) и HRBP_HUB:stand/superset.py (шаги со временем) — обоим не хватает патча лексера (SP-02).

### SP-02. Гоняй путь в модели боя — Superset 2.1.0: sqlparse 0.4.3 с патчем лексера; 0.4.4 — запас
- **Почему:**
  - Proteus сообщает `version_string` 2.1.0 (сниппет консоли, 09.10, F1). Superset 2.1.0 закрепляет `sqlparse==0.4.3` и при импорте `superset/sql_parse.py` ставит первым правилом лексера свой строковый литерал `'(''|\\\\|\\|[^'])*'` (`insert(0)` с `keywords.FLAGS`, как 2.0.1). В нём `\'` кавычку **не** экранирует.
  - Модель «0.4.3 + патч» сходится с боем: датасеты adoption pa_one и pa_body_one в ней проходят (в бою работают с 30.09 и 07.10), а в модели «0.3.0 + патч» (Superset 2.0.x) падают после `reindent` (Code 36), сохранение pa_one даёт «Only `SELECT` statements are allowed». Прогон kit 09.10 по четырём проектам: ответы модели 0.4.3 и 0.4.4 совпали вариант в вариант.
  - Цена разбора считается в модели боя: pa_one adoption — 13 451 токен, `reindent` ≈ 5 с, весь разбор ≈ 8 с на холодный запрос; на тексте без сбоя версии близки (HRBP 34 КБ — ключ 1,53–1,69 с, `reindent` 5,4–5,9 с).
  - Ни один стенд четырёх проектов патч не ставил: HRBP гонял 0.4.4 без патча, DL — 0.3.0 без патча, adoption и TeamPulse sqlparse не гоняли. Поэтому дыра с `\'` (SP-06) и «]» в `[…]` (SP-07) не была видна никому.
- **Как:** venv модели боя (`kit/setup.sh` ставит его первым: sqlparse 0.4.3, jinja2 3.0.3). **До первого вызова** sqlparse поставь ту же вставку, что Superset:

  ```python
  import re, sqlparse
  from sqlparse import keywords, tokens
  RX = r"'(''|\\\\|\\|[^'])*'"
  if hasattr(keywords, 'FLAGS'):                        # 0.4.3 (Superset 2.1.0 — бой) и 0.3.0 (2.0.x)
      keywords.SQL_REGEX.insert(0, (re.compile(RX, keywords.FLAGS).match, tokens.String.Single))
  else:                                                 # 0.4.4 — запас: как Superset 2.1.3 / 3.0
      from sqlparse.lexer import Lexer
      keywords.SQL_REGEX.insert(25, (RX, tokens.String.Single))
      Lexer.get_default_instance().set_SQL_REGEX(keywords.SQL_REGEX)
  ```

  - Датасет обязан пройти модель боя: одна инструкция, лексер в фазе (SP-12), ответ после пути равен прямому запуску. 0.4.4 — запас на обновление форка до 2.1.3+; 0.3.0 больше не нужен.
  - Нет sqlparse или патч не встал — проверка **падает**, а не пропускает шаги молча.
  - sqlparse 0.5.5 и 0.6 гоняй через `PYTHONPATH` как запас на обновление Proteus до 4.x (SP-08, SP-17).
- **Проверка:** На стенде `SELECT 'O\'K; c' AS t` после `format(strip_comments)` и `split` даёт 2 инструкции — значит, патч стоит; `SELECT length(['x', '[y]']) AS n, 'a -- b' AS s` цел (`2`, `a -- b`). В бою — те же два запроса в SQL Lab по одному (checklists/backend-probe.md, п. 2.1–2.2) и точный пин — `kit/server-probe.sh`.
- **Уверенность:** [бой] — версия 2.1.0 (09.10); [исходник 2.1.0] — пин и патч; модель сходится с поведением боя adoption — [стенд 24.8]; пин самого форка — [вывод] до ответа `server-probe.sh`.
- **Образец:** TeamPulse:proteus-playbook/kit/superset201.py (`lexer_patch`) и TeamPulse:proteus-playbook/kit/setup.sh. В проектах патча нет; ближе всех — detail_list:stand/ch.py (`superset20`, но на 0.3.0 и без патча).

### SP-03. Рендери Jinja как Superset 2.0.1: песочница, DebugUndefined, без `do`
- **Почему:**
  - В 2.0.1 — jinja2 3.0.3, `SandboxedEnvironment(undefined=DebugUndefined)`, расширений нет.
  - `{% do %}` даёт TemplateSyntaxError, то есть датасет не сохранится.
  - Неизвестная переменная печатается текстом `{{ x }}`, и ошибка всплывёт только в ClickHouse. `x.attr` и `x()` дают UndefinedError.
  - Все четыре стенда подключали `jinja2.ext.do`, три — ещё и обычный `Environment`. `{% do %}` сейчас нет ни в одном датасете, но стенд его пропустил бы.
- **Как:**

  ```python
  from jinja2 import DebugUndefined
  from jinja2.sandbox import SandboxedEnvironment
  env = SandboxedEnvironment(undefined=DebugUndefined)          # без extensions
  env.filters['where_in'] = where_in                            # удваивает кавычку, как в 2.0.1
  out = env.from_string(text).render(filter_values=fv, get_filters=gf, url_param=up,
                                     current_username=cu, cache_key_wrapper=ckw)
  assert '{{' not in out and '{%' not in out, 'неизвестная переменная осталась текстом'
  ```

  - Добавление в список — `{% set _ = lst.append(v) %}`.
  - `current_username(add_to_cache_keys=True)` и `url_param` на стенде пишут значение в ключ только тогда, когда регулярка нашла вызов (SP-20).
- **Проверка:** Шаблон с `{% do x.append(1) %}` на стенде падает. После рендера каждого варианта в тексте нет `{{` и `{%`.
- **Уверенность:** [исходник 2.0.1] [не проверено в бою] — форк мог поменять окружение.
- **Образец:** TeamPulse:proteus-playbook/kit/superset201.py (`render`: окружение 2.0.1 буквально — `safe_proxy`, `ExtraCache`, `where_in`). В проектах ближе всех detail_list:stand/ch.py (`render`: SandboxedEnvironment, `AlwaysTrue`, `url_param`) — убрать `ext.do`, добавить `DebugUndefined`.

## Сохранение датасета

### SP-04. Проходи проверку форка при сохранении: без алиасов в GROUP BY, без кортежного типа в строке CAST, с гейтом sqlglot 23–30
- **Почему:**
  - 29.09 датасет DL не сохранился: «Некорректный SQL запрос: →… GROUP BY intDiv(rn - 1, 500) AS ch )…←». ClickHouse такой текст принимает, chdb тоже.
  - Первый SQL поставки DL давал 40 ошибок sqlglot.
  - 18.09 у adoption три вставки упали на `CAST([], 'Array(Tuple(UInt8, String))')`.
  - Строки «Некорректный SQL запрос» нет в Superset 2.0.1, 4.1 и 5.0, sqlglot в 2.0.x тоже нет — значит, это код форка. sqlglot 10.6–30.0 воспроизводит отказ на алиасе в GROUP BY, а кортежный CAST пропускает. Проверка форка — не только sqlglot.
- **Как:**
  - Номер пачки или ключ — колонкой подзапроса, а не алиасом в GROUP BY:

    ```sql
    -- нельзя:  … GROUP BY intDiv(rn - 1, 500) AS ch
    SELECT ch, groupArray(x) AS xs FROM (SELECT intDiv(rn - 1, 500) AS ch, x FROM …) GROUP BY ch
    ```

  - Пустой типизированный массив кортежей — без типа строкой: `arrayFilter(t -> t.1 != 0, [(toUInt8(0), '')])`. Пустой массив строк `CAST([], 'Array(String)')` в бою проходит. Подробнее о типах — 04-clickhouse.md, CH-17.
  - Гейт на стенде: каждый вариант рендера (сохранение, открытие, «всё сразу») — как есть и в обёртке — разбирается sqlglot 23.17, 25.34, 26.33, 28.10 и 30.0 (`read='clickhouse'`): ровно один оператор `Select`/`Union`/`Subquery`, без изменяющих узлов. Алиас в GROUP BY ищи и по токенам — даже если какая-то версия sqlglot его пропустила.
  - Отказ только в старых sqlglot — предупреждение, а не стоп: pa_one adoption (CTE `pr AS (…)`) sqlglot 18.17–23.17 отвергают, 25.34+ принимают, а в бою он сохранён 30.09. sqlglot < 15 моделью не годится: он отвергает `CAST([], 'Array(String)')`, который в бою проходит.
- **Проверка:** На стенде `kit/sqlgate.py <датасет> --user <логин> --cols auto --sqlglot-dirs <каталоги 23.17,25.34,28.10,30.0>` (или `stand/parse.py` DL) — 0 ошибок. В бою — Save датасета без красной ошибки.
- **Уверенность:** [бой] — оба инцидента и сохранение pa_one; [исходник 2.0.1] — sqlglot нет в 2.0.x; механизм проверки форка неизвестен, кортежный CAST — эмпирика боя.
- **Образец:** TeamPulse:proteus-playbook/kit/sqlgate.py (гейт сохранения: sqlglot 23–30, алиас по токенам, CAST, SETTINGS, лексер); detail_list:stand/parse.py (`VARIANTS`, «только SELECT»).

### SP-05. Пиши шаблон так, чтобы он рендерился и исполнялся с AlwaysTrueObject: списки только циклом
- **Почему:**
  - При сохранении датасета форк отдаёт из `filter_values()` объект `AlwaysTrueObject`. Он истинный; цикл по нему и `|first|default(…, true)` работают (HRBP читает так `depth_f` и `tr_f` и сохраняется в бою), а `+`, `|length` и индекс — падают. В апстриме такого объекта нет.
  - 23.09 сохранение pa_strip в adoption упало: «unsupported operand type(s) for +: 'AlwaysTrueObject' and 'list'».
  - Сохранение и синхронизация **исполняют** ветку «без фильтров» с логином сохраняющего (01-platform.md, F9). Тяжёлая или ломкая ветка по умолчанию — это отказ при Save.
- **Как:**

  ```jinja
  {% set UNITS = [] %}
  {% for v in (filter_values('unit_f') or []) %}{% if UNITS|length < 50 and (v|string)|length <= 64 %}{% set _ = UNITS.append(v|string) %}{% endif %}{% endfor %}
  {% set MODE = (filter_values('mode_f')|first|default('list', true)) %}{% set MODE = MODE if MODE in ['list', 'filters'] else 'list' %}
  ```

  - С результатом `filter_values` — только цикл или `|first|default(…, true)` с белым списком после. Никаких `+`, `|length`, `[0]` по сырому значению.
  - Дефолтная ветка — первый экран (зона пользователя) и лёгкая.
  - Логин сохраняющего может не иметь строки доступа — ветка отказа (AC-02) обязана быть валидным SQL.
  - Сохранение и синхронизация исполняют `<текст>\nLIMIT 1000` без обёртки, комментарии не вырезаются. Верхний `LIMIT` датасета заменяется меньшим из своего и 1000. `SETTINGS` или `FORMAT` в хвосте дают Code 62, поэтому в теле датасета их нет вовсе (04-clickhouse.md, CH-04).
- **Проверка:** На стенде каждый SQL поставки рендерится в режиме AlwaysTrue и исполняется на chdb 24.8 как `<текст>\nLIMIT 1000` без обёртки. В бою — Save без ошибки.
- **Уверенность:** [бой] (adoption 23.09; HRBP — `|first|default` сохраняется); [исходник 2.0.1] — путь синхронизации (`get_virtual_table_metadata`, `set_or_update_query_limit`).
- **Образец:** detail_list:proteus/detail-list.data.sql (блок «носители кросс-фильтра» — циклы с пределами); adoption:.stand/stand.py (`render(always_true=True)`); TeamPulse:proteus-playbook/kit/superset201.py (`--save-only`: AlwaysTrue + `LIMIT 1000`, исполнение на chdb).

## Лексер sqlparse и экранирование

### SP-06. Экранируй кавычку удвоением `''`, а слэш — раньше кавычки
- **Почему:**
  - Под патчем Superset `\'` строку не продолжает: лексер считает её закрытой. Дальше строки и код меняются местами, `strip_comments` вырезает «комментарии» (`--`, `//`, `# `) прямо из строк, а `;` из строки становится концом инструкции.
  - Проверка 08.10 на 0.3.0 с патчем: `'O\'Brien; x', 'https://h/p'` → 2 инструкции и обрезанный `https:`. `'O''Brien; x'` — цело.
  - Сквозной тест «макрос → путь 2.0.1 → chdb»: значение `O'Brien; x` → «Virtual dataset query cannot consist of multiple statements»; `a\` вместе с `b'c -- d` → Code 62. С `''` все случаи верны.
  - На текущем датасете списка DL носители `office_desc=O'Brien; x` и `login=x'y; z` дают «multiple statements».
  - В модели 0.4.4 + патч (SP-02) тот же `O'Brien; x` ошибки не даёт, а лексер сбит, и после `reindent` ClickHouse отвечает **другое** (HRBP, списки DL; прогон kit 08.10). Тихая порча хуже ошибки: `''` нужен в обеих моделях.
  - ClickHouse и sqlglot понимают `''` так же, как `\'`.
- **Как:** Один макрос строкового литерала на датасет. Сначала обратный слэш → `\\`, затем кавычка → `''`. Слэши в конце значения — по SP-08.

  ```jinja
  {% macro qs(v) -%}
  {%- set s = v|string -%}{%- set t = s.rstrip('\\') -%}
  {%- if t|length < s|length -%}concat('{{ t|replace('\\', '\\\\')|replace("'", "''") }}', repeat(char(92), {{ s|length - t|length }}))
  {%- else -%}'{{ s|replace('\\', '\\\\')|replace("'", "''") }}'{%- endif -%}
  {%- endmacro %}
  ```

  - Штатный `where_in` удваивает кавычку, но слэш не трогает: перед ним слэш экранируй сам. Пример — adoption `q()`: `replace('\\', '\\\\')`, затем `|where_in`.
  - Внутри `[…]` без «]» апостроф безопасен: sqlparse читает весь литерал одним именем (SP-07). Под ударом кортежи `IN (…)`, `array(…)` и одиночные литералы.
- **Проверка:** На стенде пропусти через путь 2.0.1 в обеих моделях значения `O'Brien; x`, `x'); DROP TABLE t;--`, `it's -- x` в каждом носителе. Ожидание: одна инструкция, лексер в фазе, ответ точный (SP-11).
- **Уверенность:** [стенд 24.8] + [исходник 2.0.1] [не проверено в бою].
- **Образец:** adoption:Виджеты/pa-reports-body.data.sql (`q()` + `where_in`, `jes` — `replace("'", "''")`). В HRBP (`qs` в hrbp-hub.data.sql), DL (`qs` в detail-list.data.sql) и TeamPulse (`qs` в файле 2) стоит `\'` — заменить на `''`. Ответ от этого не меняется.

### SP-07. Пиши литерал `[…]` только без «]» внутри, иначе `array(…)`
- **Почему:**
  - sqlparse (и 0.3.0, и 0.4.4, с патчем и без) читает `[`, перед которым не буква, цифра, «_», «]» или «)», как начало имени T-SQL до первой «]». В 0.3.0 такое имя может содержать «[», в 0.4.3+ — нет.
  - Если «]» есть где угодно внутри литерала — в значении фильтра или в строке кода (класс регулярки `'^[\\s\\p{P}]*$'`, `'[a-z]+'`), — имя кончается посреди строки. После этого кавычки идут вразнобой.
  - DL 07.10: юнит КП со «]» ронял запрос списка («multiple statements»).
  - TP 08.10: `['a]','b -- c']` срезает хвост вместе с GROUP BY, `[']x','y;z']` — 3 инструкции.
  - Прогон kit 08.10, обе модели: HRBP `has(['a]b'], uid)` и TP — ответ после пути другой.
  - Adoption сейчас: в pa_one список `[lvl3, lvl4, if(match(…, '^[\\s\\p{P}]*$'), …), …]` закрывается «]» внутри регулярки макроса `ou`. Получается токен-имя на 8 088 знаков и 1 842 токена вместо ≈ 7 800. Пока `strip_comments` вырезает там только пробелы, но первое значение с `--` или `;` в этой зоне испортит запрос.
- **Как:** Макрос массива выбирает форму по содержимому. Литерал в коде, внутри которого есть регулярка с классом `[…]` или строка со «]», пиши через `array(…)`.

  ```jinja
  {% macro qa(values) -%}
  {%- if values|length == 0 -%}CAST([], 'Array(String)')
  {%- else -%}{%- set br = [] -%}{%- for v in values if ']' in v|string -%}{%- set _ = br.append(1) -%}{%- endfor -%}
  {{ 'array(' if br else '[' }}{% for v in values %}{{ qs(v) }}{% if not loop.last %}, {% endif %}{% endfor %}{{ ')' if br else ']' }}
  {%- endif -%}
  {%- endmacro %}
  ```

  - `[…]` без «]» внутри даже выгоднее: один токен вместо трёх на значение, `reindent` его не раздувает (SP-16).
  - `array(…)` из 60 000 значений упирается в `max_ast_elements` (Code 168), литерал `[…]` — нет.
- **Проверка:** Гейт лексера (SP-12): каждое имя sqlparse, начинающееся с `[`, кончается на скобке массива по sqlglot. Враждебный ввод `a]b`, `[c`, `d']`, `]';--` (SP-11).
- **Уверенность:** [стенд 24.8] (DL 07.10 на SQL 21-й поставки; TP и adoption 08.10) [не проверено в бою].
- **Образец:** detail_list:proteus/detail-list.data.sql (макрос `qa`). Adoption pa_one (`ou(…)` внутри `[…]`), HRBP и TP (`qa` всегда `[…]`) — перевести.

### SP-08. Слэши в конце значения пиши как `concat('…', repeat(char(92), N))`, одиночный слэш в коде — `char(92)`
- **Почему:**
  - Под патчем 2.0.1 литерал `'a\\'` разбирается верно: 1 инструкция. В модели 0.4.4 с патчем 2.1.3/3.0 — тоже (прогон kit 08.10: хвост `a\` — ок во всех проектах).
  - sqlparse ≥ 0.4.4 без патча считает его незакрытым и молча режет хвост. На 0.5.5+ получаем «Maximum grouping depth exceeded (100)» — так DL 07.10 поймал это на base64 кода в датасете (стенд на 0.5+/0.6).
  - Это страховка на обновление Proteus.
- **Как:** Макрос `qs` из SP-06 уже отрезает хвостовые слэши. В коде датасета литерал из одного слэша не пиши — пиши `char(92)`:

  ```sql
  replaceAll(x, char(92), concat(char(92), char(92)))      -- экран слэша в JSON-строке
  ```
- **Проверка:** Путь на sqlparse 0.4.4 и 0.6 (`PYTHONPATH`) со значениями `x\`, `x\\`, `\` — одна инструкция, `strip_comments` убрал только комментарии.
- **Уверенность:** [стенд 24.8] (0.4.4 без патча режет; 0.3.0 и 0.4.4 с патчем Superset — нет).
- **Образец:** detail_list:proteus/detail-list.data.sql (`qs` с `repeat(char(92), N)`, макрос `vesc`).

### SP-09. Не пиши `\x..` в литералах: разделитель — `char(31)`, класс управляющих — `'[[:cntrl:]]'`
- **Почему:** sqlglot ≥ 23 перепечатывает `'\x1F'` как `'\\x1F'`, и значение меняется (hex `1F` → `5C783146`). Superset 4.1.0 SQL чарта не перепечатывает, а 5.0 при флаге `OPTIMIZE_SQL` — да. Для 2.0 это страховка. `\t`, `\n`, `\\`, `\0` и `\'` перепечатку переживают.
- **Как:** Разделитель пути — `char(31)`, управляющие символы — `replaceRegexpAll(x, '[[:cntrl:]]', ' ')`. В Jinja (`.split('\x1e')`) `\x` допустим — до SQL он не доходит.
- **Проверка:** grep `\\x[0-9A-Fa-f]{2}` по отрендеренному SQL — 0. Раздел «круг sqlglot» на стенде: перепечатанный запрос отдаёт тот же ответ.
- **Уверенность:** [стенд 24.8] (sqlglot 23.17 / 26.33 / 30.0 + chdb); [исходник 2.0.1] — версии Superset.
- **Образец:** detail_list:proteus/detail-list.data.sql (`char(31)`, `'[[:cntrl:]]'`); detail_list:stand/check.py (раздел 4 — круг sqlglot).

### SP-10. Не держи `--`, `//`, `# `, `/*` и `;` в литералах самого датасета без нужды
- **Почему:** Пока лексер в фазе, `--` в строке безвреден. Но стоит ему сбиться (апостроф с `\'`, «]» в `[…]`), и sqlparse вырежет из строки «комментарий» или разрежет запрос по `;`. Проверка 08.10 на DL: из-за одного апострофа в носителе `strip_comments` срезал хвост адреса борда `https://…` в `meta`. Комментарии в 0.3.0 — `--`, `//`, `# ` и `/* … */`, в 0.4.4 — `--`, `# ` и `/* … */`. Проверка 09.10 на 0.3.0 и 0.4.4 с патчем: после `'O\'Brien'` строки `'x /* y'` и `'z */ w'` склеиваются в `'x  w'` — всё между ними вырезано.
- **Как:** Адрес борда и подобные константы собирай без `//`: `concat('https:', char(47), char(47), '<хост>/…')`, или отдавай только путь `/superset/dashboard/<id>/` — хост чарт возьмёт из `document.referrer` (08-sandbox.md). Разделители — `char(…)`. Это вторая линия защиты, первая — SP-06 и SP-07.
- **Проверка:** grep по отрендеренному тексту вне комментариев: `'[^']*(--|//|# |/\*|;)[^']*'` — каждый случай обоснован.
- **Уверенность:** [стенд 24.8] — механизм (sqlparse 0.3.0 и 0.4.4 с патчем); [вывод] — правило как страховка.
- **Образец:** нет; DL держит адрес борда `BOARD_URL` литералом в `meta` — перевести на `concat` или путь.

### SP-11. Гоняй враждебный ввод через путь Superset, а не прямо в ClickHouse
- **Почему:** chdb выполняет всё. Поломки лексера видит только путь SP-01 с патчем SP-02. HRBP и adoption гоняли враждебные значения прямо в ClickHouse, DL — через путь без патча. Апострофную дыру не поймал никто. С патчем 20 значений × 2 экрана × 3 контекста дают: `[…]` со значением `a ] -- b` или `]';--` → Code 62 при любом экране; `\'` + `x'); DROP TABLE t;--` → «multiple statements»; `''` + `array(…)` → все 20 проходят, ответ точный. Прогон kit 08.10 (8 хвостов, обе модели): в модели 0.4.4 `O'Brien; x` при `\'` не падает, а тихо меняет ответ (HRBP, DL); у adoption в модели 0.3.0 даже `a\` и `Отдел «Альфа» — 1` дают Code 36, потому что лексер сбит самим текстом датасета (SP-12).

  4. лишнее отброшено пределами (AC-14), эхо в `meta` без мусора;

- **Проверка:** На стенде — раздел «враждебный ввод» регресса, 0 провалов. Длинное и короткое тире chdb превращает в `--` даже внутри строки — такие значения на стенде не проверить (13-stand.md).

### SP-12. Ставь гейт лексера: строки sqlparse равны строкам sqlglot, `strip_comments` убрал только комментарии, ответ после пути тот же
- **Почему:**
  - Сбой лексера бывает и без пользовательского ввода, на самом тексте датасета. Adoption 08.10: рендер pa_head (2,5 КБ) уже рассинхронизирован — строковые токены sqlparse по 159–639 знаков захватывают код (18 строк против 49 у sqlglot). pa_one — 104 против 388.
  - Сбитый лексер портит текст не только в `strip_comments`, но и в `reindent`: тот вставляет и схлопывает пробелы внутри строк, принятых за код. Прогон kit 08.10: HRBP `',"it":'` → `', "it":'`, TeamPulse `'","m0":"'` → `'", "m0":"'`, adoption `translate(x, '\t\n\r', '   ')` → `' '` и Code 36 на каждом открытии (в модели 0.3.0).
  - Поэтому одной проверки «одна инструкция» мало: гейт смотрит текст до и после обёртки и сверяет ответ.
- **Как:** Для каждого варианта рендера, в обеих моделях (SP-02), проверяй три вещи:

  ```python
  from sqlglot.dialects.clickhouse import ClickHouse
  def toks(s):                                     # sqlglot кладёт комментарии в токены, а не в поток
      return [(t.token_type, t.text) for t in ClickHouse().tokenize(s)]
  src = text.strip('\t\r\n; ')
  out = sqlparse.format(src, strip_comments=True)  # под патчем SP-02
  assert toks(src) == toks(out), 'sqlparse вырезал не только комментарии'   # TokenError на out — тоже провал
  # 2) каждая строка sqlglot (STRING) — строка sqlparse (String.Single) с теми же границами
  #    либо целиком внутри имени [...] sqlparse; лишних строк у sqlparse нет
  # 3) ответ chdb на текст после обёртки и reindent = ответу на src (множеством строк)
  ```
- **Проверка:** На стенде `kit/superset201.py … --run` в обоих venv (раздел «Лексер» без ✗, сверка ответа) или `strings_problem` и `superset20_problem` в `stand/parse.py` DL — на всех вариантах, включая SQL Lab-файлы (`kit/sqlgate.py --sqllab`): SQL Lab тоже вырезает комментарии этим лексером.
- **Уверенность:** [стенд 24.8] (chdb + sqlparse 0.3.0 и 0.4.4 с патчем).
- **Образец:** TeamPulse:proteus-playbook/kit/superset201.py (`lexer_problems`, `--run`); detail_list:stand/parse.py (`strings_problem`, `superset20_problem`).

### SP-13. Считай обёртку чарта с GROUP BY по всем «Измерениям»: строки уникальны, порядок и обрезка произвольны
- **Почему:**
  - **Бой, 09.10:** «Показать SQL запрос» у каталога adoption (борд 60260) кончается так: `) AS virtual_table GROUP BY section, g, k, parent, n LIMIT 50000` — `GROUP BY` по всем «Измерениям» и лимит строк чарта в обёртке. Текст датасета внутри — уже после `reindent`.
  - Сохранённый `query_context` у `react_sanbbox` — `"columns":[…],"metrics":[],"url_params":{}`. В 2.0.1 и 2.1.0 `need_groupby = bool(metrics is not None or groupby)` → True → `GROUP BY` по всем колонкам.
  - На chdb 24.8 (оба анализатора) с такой обёрткой первая строка ответа — не `meta`, а `"x","456"`. `meta` оказывается на 143-й позиции, а при `LIMIT 990` из 1 000 строка `end` уцелела. Без GROUP BY порядок держался.
  - GROUP BY ещё и **склеивает одинаковые строки** ответа молча.
  - ORDER BY по роли в HRBP (06.10) появился из гипотезы «лимит режет фасеты», а настоящей причиной была функция имени в чарте.
- **Как:** На пути это значит три вещи:
  1. Каждая строка ответа уникальна по всем выходным колонкам, иначе GROUP BY её склеит. Нужны дубли — добавь номер.
  2. Внутренний ORDER BY до чарта не доживает: порядок восстанавливает JS.
  3. Обрезку видно только по числу строк: `data.length` ≥ лимита строк (GROUP BY + LIMIT при обрезке отдаёт ровно N строк) или число строк в `meta` ≠ `data.length`; ответ держи на порядки меньше лимита строк.

  Как это сделать в датасете и чарте (окно `count() OVER ()` в `meta`, плашка «ответ обрезан») — 05-dataset.md, DS-24 и DS-25.
- **Проверка:** На стенде модель обёртки — с GROUP BY, лимит меньше и больше ответа (`kit/superset201.py` строит её так по умолчанию). В бою — меню чарта «Показать SQL запрос» / DevTools → Response → `result[0].query`.
- **Уверенность:** [бой] (обёртка с GROUP BY и LIMIT 50000, 09.10) + [исходник 2.1.0] + [стенд 24.8].
- **Образец:** detail_list:stand/ch.py (`dataset`: обёртка с GROUP BY, ответ 10–200 строк, итоги в `meta`); adoption:skills/proteus-echarts-builder/SQL.md (порядок — в JS).

### SP-14. Не выводи носители кросс-фильтра в SELECT датасета
- **Почему:** Если носитель — колонка датасета, Superset вешает на внешний запрос `WHERE col IN (…)` (шаг 6), для Array-колонок ClickHouse падает. Пустой список по такой колонке даёт «Filter value list cannot be empty». Фильтр по колонке, которой в датасете нет, внешний запрос пропускает. Борд 59922, вердикт 17.09.

Фильтр по несуществующей колонке SQL не меняет, но меняет ключ кэша — так делается принудительный перезапрос без побочек (SP-21). Контракт эмита (`op` обязателен, `value = []` не эмитить) — 09-multi-chart.md.
- **Проверка:** Grep: имён носителей нет среди колонок SELECT и в FIELDS.md. На стенде модель обёртки с фильтрами носителей: внешний WHERE не появляется.

## Цена разбора и пределы

### SP-15. Держи бюджет текста — КБ, токены, скобки и время reindent в обеих моделях лексера — регрессией
- **Почему:** `reindent` обёртки стоит ≈ токены² × вложенность скобок. Замер на 0.3.0 с патчем: без скобок 5,5 / 11 / 22 тыс. токенов — 0,34 / 1,15 / 4,07 с; `f(c)` — ×2,6–3,1; `f(g(c))` — ×5,6–7,2 (2 000 колонок — 29 с). HRBP 08.10: 33,6 КБ, 15 930 токенов, 1 212 скобок → reindent 5,9–9,2 с, разбор ради ключа 1,5–2 с на каждом шаге, «Применить» 20 с в бою. После правки 13,6 КБ, 510 скобок → reindent 1,05–1,8 с, ключ 0,53 с, «Применить» 5–6 с на стенде (в бою не подтверждено). Reindent удваивает текст: 13,6 → 25,3 КБ. Сбитый лексер прячет скобки и токены в «строки» и «имена», поэтому модель 0.3.0 может сильно занизить цену: pa_one adoption — 0,3 с разбора в ней против 8,0 с в модели 0.4.4 (SP-02).
- **Как:**
  - Повторяющиеся выражения сворачивай: одна лямбда над плоским массивом вместо выражения у каждой из N колонок, резка на колонки один раз наверху (05-dataset.md, DS-23), общие скаляры — в WITH (04-clickhouse.md, CH-06). Чистка строки — одним `arrayStringConcat(arrayMap(…))`, а не `clean()` у каждой из 110 колонок (DL КП: 11 119 → 4 407 токенов).
  - Бюджет — в регрессе. Печатай КБ, токены лексера, число «(», время `format/split/parse` и `reindent` на худшем рендере в обеих моделях, в расчёт — большее. Падай, если новая версия дороже прошлой поставки или выше порога. Сравнение «было / стало» сейчас нигде не автоматизировано — его делают руками.

### SP-16. Меряй max_query_size по тексту после обёртки и reindent; длинные списки задавай константами WITH
- **Почему:**
  - `max_query_size` 262 144 байт (24.8 по умолчанию; боевое значение не снято) считается по тексту, который пришёл в ClickHouse, то есть после шага 7.
  - `reindent` выравнивает перенесённые элементы по колонке открывающей скобки. Если длинная строка стоит перед скобкой, все следующие строки сдвигаются на её длину. DL (худший случай: 2 000 логинов + 600 значений): панель 193,7 → **841,8 КиБ** после обёртки и reindent, причём 664 КБ из 842 — пробелы. Строка JSON-литерала эха в 90 372 знака стоит перед скобкой, следующие строки сдвинуты на 90 378 пробелов. Список КП — 194,2 → 226,6 КиБ (запас 11 %). Панель в бою стоит вне всех областей и носителей не получает, так что 842 КиБ — гипотеза «если панель попадёт в свою область»; список у предела по-настоящему.
  - Рост от формы списка: IN-список в строке — ×2,2, кортеж в WITH — ×1,7, литерал `[…]` — ×1,0 (sqlparse читает его одним именем). Какую форму списка выбрать с учётом `max_ast_elements` — 04-clickhouse.md, CH-28.
  - DL 29.09: 2 000 логинов литералом в каждом условии — 1,8 МБ запроса, константами WITH — 195,5 КиБ.
  - Превышение выглядит как «Code: 62. Syntax error: failed at position N … Max query size exceeded», где N — начало первого не влезшего токена (262 145 или, у длинного литерала, его начало). Его легко принять за ошибку SQL.
- **Как:**
  - Список носителя — один раз: `WITH ('a', 'b', …) AS dl_ids … WHERE id IN dl_ids` (04-clickhouse.md, CH-20). Для коротких `has`/`hasAny` — `[…]` без «]» (SP-07). `ARRAY JOIN` по алиасу WITH старый анализатор не принимает (04-clickhouse.md, CH-12).
  - Длинный литерал (эхо, JSON) не ставь в одну строку перед конструкцией со скобками и переносами. Собирай эхо в самом конце SELECT или из коротких частей.
  - Проверку `< 256 КиБ` делай на `superset201(...)` (SP-01) для худших носителей и в байтах UTF-8 (кириллица — 2 байта).
- **Проверка:** На стенде `len(superset201(render(worst)).encode()) < 262144` с запасом 10 %. В бою — `getSetting('max_query_size')` в файле «где время».
- **Уверенность:** [стенд 24.8] [не проверено в бою] — боевое значение.
- **Образец:** detail_list:proteus/detail-list.data.sql (константы WITH для логинов и значений). Проверка DL меряет текст до reindent — перенести на текст после пути; `kit/superset201.py` уже меряет после reindent.

### SP-17. Держи худший рендер короче 10 000 токенов и мельче 100 уровней вложенности — запас на sqlparse ≥ 0.5.4
- **Почему:** В sqlparse 0.5.4 появились `MAX_GROUPING_TOKENS = 10000` и `MAX_GROUPING_DEPTH = 100`: превышение там молча пропускает группировку. С 0.5.5 — исключения «Maximum number of tokens exceeded (10000).» и «Maximum grouping depth exceeded (100).». Superset 4.1+ требует sqlparse ≥ 0.5.0. В 2.0.1 предела нет — это запас на обновление Proteus. Считается `len(tlist.tokens)` плоского оператора, и каждый пробельный символ — отдельный токен. Замеры: DL КП 11 119 → 4 407 после `line_of`; HRBP 5 740–6 043, TP 5 360. Уже за пределом: худший набор DL (2 000 логинов + 600 значений) — 10 744–12 646 у списков, обычные списки (до 500 логинов) — до 6 тыс.; adoption pa_one в модели 0.4.4 с выбором отчёта и ЦА — 13 459. В 2.0.1 это не ошибка, после обновления Proteus — отказ.
- **Как:** Счёт токенов: `sum(1 for _ in sqlparse.lexer.tokenize(text))` на худшем рендере (2 000 логинов, 500 значений). Глубину проверяй прогоном `sqlparse.parse(text)` на 0.5.5 или 0.6 через `PYTHONPATH`: исключения быть не должно. Сокращение — SP-15 и SP-18.
- **Проверка:** На стенде регресс «токенов < 10 000» и прогон на sqlparse 0.6.
- **Уверенность:** [исходник 2.0.1] (sqlparse 0.5.4 / 0.5.5 `engine/grouping.py`) — сейчас это запас, а не боевая ошибка.
- **Образец:** detail_list:stand/parse.py (`TOKENS_MAX`, `tokens`).

### SP-18. Снимай отступы фильтром `{% filter replace %}`, комментарии пиши в `{# #}`
- **Почему:** Каждый пробельный символ и каждый SQL-комментарий — токены sqlparse на шагах 0, 3 и 7. На 0.4.4 у HRBP это дало −25 % токенов и −20 % reindent. У DL на 0.3.0 — −20–33 % токенов при почти том же reindent. Мера дешёвая, но вторичная: главная цена — скобки (SP-15). У TP — 1 393 ведущих пробела на 10,7 тыс. знаков.
- **Как:** Весь SQL — внутри фильтра. Литералов с переводом строки в датасете не держи — фильтр их испортит.

  ```jinja
  {% filter replace('\n                ', '\n')|replace('\n        ', '\n')|replace('\n    ', '\n')|replace('\n  ', '\n') %}
  WITH
    acc AS (
      SELECT …
  {% endfilter %}
  ```

  Пояснения — в `{# … #}`, а не в `-- …`. В датасете с общим кэшем не пиши в комментариях `{{ current_username() }}` и подобного: регулярка ключа читает сырой текст вместе с комментариями (SP-20).
- **Проверка:** На стенде токены до и после (SP-15). Ответ ClickHouse тот же.
- **Уверенность:** [стенд 24.8].
- **Образец:** HRBP_HUB:proteus/hrbp-hub.data.sql (обёртка `{% filter replace %}` вокруг всего SQL).

### SP-19. Не ставь минусы `{#- … -#}` на стыке токенов SQL
- **Почему:** Минусы съедают пробелы с обеих сторон и склеивают соседние токены: `1AND`, `xWHERE`. Adoption 30.09, сборка pa_one v2.
- **Как:** На стыке двух токенов SQL — `{# #}` без минусов. Минусы — только там, где с обеих сторон Jinja или перевод строки.
- **Проверка:** На стенде гейт sqlglot (SP-04) и исполнение на chdb ловят склейку.
- **Уверенность:** [стенд 24.8] (adoption 30.09).
- **Образец:** adoption:Виджеты/pa-one.NOTES.md (грабля сборки v2).

## Ключ кэша, параметры адреса, время жизни

### SP-20. Знай, что видит ExtraCache.regex: вызов внутри `{{ }}` одной строкой в сыром тексте, предикате, WHERE/HAVING и RLS
- **Почему:** Логин или параметр адреса попадает в ключ кэша только через рендер. А рендер ради ключа Superset делает, только если регулярка нашла вызов (`has_extra_cache_key_calls`):

  ```python
  # Superset 2.0.0 … 4.0.2 (jinja_context.py): без DOTALL, «{{» до вызова и «}}» после — на одной строке
  r"\{\{.*(current_user_id\(.*\)|current_username\(.*\)|cache_key_wrapper\(.*\)|url_param\(.*\)).*\}\}"
  # Superset 4.1+: ещё и {% … %}
  r"(\{\{|\{%)[^{}]*?(current_user_id\([^()]*\)|current_username\([^()]*\)|current_user_email\([^()]*\)|cache_key_wrapper\([^()]*\)|url_param\([^()]*\))[^{}]*?(\}\}|\%\})"
  ```

  Регулярка читает:
  1. **сырой** текст датасета — вместе с `{# #}` и `--`-комментариями;
  2. «Предикат запроса автозаполнения»;
  3. `extras.where` и `having` чарта;
  4. правила RLS.

  Проверено на 2.0.1:
  - **не видит:** `{% set u = current_username() %}`, `{% set _ = cache_key_wrapper(x) %}`, `{% set L = url_param(…) %}`, вызов на трёх строках `{{\n current_username()\n}}`;
  - **видит:** `{{ qs((current_username() or '')|string|trim|lower) }}`, `'{{ cache_key_wrapper(current_username()) }}'` и даже закомментированный `{# {{ current_username() }} #}`. Последний включает рендер ради ключа, но логин в ключ не кладёт: вызова при рендере нет.

  Если регулярка нашла хотя бы один вызов, в ключ попадает **всё**, что при рендере вызвало `cache_key_wrapper`, — включая вызовы из `{% set %}`.
- **Как:** Политика (где логин нужен, где запрещён) — 03-access-cache.md, AC-06…AC-09. Механика:
  - вызов, который должен попасть в ключ, — в `{{ … }}` на одной строке;
  - в датасете с общим кэшем — ни одного совпадения ни в одном из четырёх мест, даже в комментариях;
  - регресс проверяет обе регулярки по сырому тексту.
- **Проверка:** На стенде регресс регулярок (AC-08). В бою — `cache_key` в Response у двух пользователей при тех же фильтрах: разный — ключ личный, одинаковый — общий.
- **Уверенность:** [исходник 2.0.1] + [бой] (три инцидента 07.10: HRBP, DL, adoption).
- **Образец:** detail_list:stand/parse.py (`CACHE_RX` — обе регулярки, `cache_problem`); TeamPulse:proteus-playbook/kit/superset201.py (`cache_key_report`: что попало в ключ и вердикт «личный / общий / рендер впустую / ОПАСНО»).

### SP-21. Знай состав ключа кэша и эмить фильтры в каноническом порядке
- **Почему:** Состав по исходнику 2.0.1:

  ```
  ключ данных = md5( QueryObject.to_dict()     # columns, filter (с порядком значений!), extras, row_limit,
                                               # time_range, post_processing …; url_params и form_data НЕ входят
                   + datasource.uid
                   + extra_cache_keys          # только если ExtraCache.regex нашла вызов (SP-20)
                   + RLS-правила пользователя
                   + datasource.changed_on )
  ключ qc-…   = md5({datasource, queries, result_type, result_format})   # пользователя в нём нет
  ```

  При каждом GET `qc-…` ключ данных пересчитывается под текущим пользователем. `json.dumps(sort_keys=True)` сортирует только ключи словарей, порядок значений в списке фильтра входит в ключ.
- **Как:**
  1. Значения в маске кросс-фильтра сортируй, а порядок носителей держи постоянным. Тот же выбор в другом порядке кликов — другой ключ и холодный запрос. HRBP не сортирует: значения идут в порядке выбора.
  2. Лимит строк чарта входит в ключ: меняешь лимит — кэш холодный.
  3. Замена JS чарта ключ **не** меняет: `form_data` не входит, ответ берётся из кэша.
  4. Save датасета с реальной правкой меняет `changed_on`, и кэш холодный у всех. Пересохранение без правки `changed_on` не меняет (SQLAlchemy 1.3 не делает UPDATE при равных значениях): чтобы сбросить кэш, поменяй поле, например «Описание» = номер поставки (AC-12).
  5. Принудительный перезапрос без побочек — уникальная метка в фильтре по несуществующей колонке (SP-14).
- **Проверка:** В бою — `cache_key` у одного пользователя при двух порядках кликов: должен совпасть. На стенде — эмит чарта отдаёт отсортированные значения (09-multi-chart.md).
- **Уверенность:** [исходник 2.0.1] [не проверено в бою] — прирост попаданий в кэш не измерен; «пересохранение без правки не меняет `changed_on`» — опыт на SQLAlchemy 1.3.24 [вывод].
- **Образец:** adoption (сортировка значений маски с 29.09, `pa-reports-body.chart.js`).

### SP-22. Плати за логин в ключе осознанно: рендер и разбор на каждом расчёте ключа
- **Почему:**
  - Если регулярка нашла вызов, Superset на каждом расчёте ключа строит запрос целиком: Jinja, `format`, `split`, `parse`, `is_select` — даже когда ответ потом берётся из кэша.
  - Холодное «Применить» в асинхронном режиме: POST (ключ) + воркер (ключ и запрос, reindent, `parse_sql`) + каждый GET `qc-…` (ключ). Это ≥ 4 рендера и разбора и 1 reindent. Из кэша — один POST и один разбор.
  - HRBP: 17-я поставка добавила логин в ключ, и правка безопасности умножила цену длинного SQL. 34 КБ разбирались ≈ 1,5–2 с на каждом шаге → «Применить» 20 с (08.10).
  - DL: разбор ради ключа у списка 0,38–0,57 с, у панели 0,65 с. Пока у панели был ключ по логину, её холодное открытие стоило ≈ 4,2 с разбора у каждого.
- **Как:** Правку кэша (добавление логина в ключ) выпускай вместе с бюджетом SQL (SP-15) и замером шагов. Персональный датасет держи коротким, тяжёлое и общее выноси в датасет без логина (AC-06, AC-11).
- **Проверка:** На стенде `kit/superset201.py` (раздел «Ключ кэша»: цена холодного открытия и открытия из кэша) или `superset.py` проекта: «холодное Применить» ≈ 4 × ключ + reindent + ClickHouse. В бою — Timing у POST и GET `qc-…`.
- **Уверенность:** [исходник 2.0.1] + [бой] (HRBP 20 с, 08.10).
- **Образец:** HRBP_HUB:stand/superset.py (шаги на холодное и из кэша); detail_list:stand/superset.py.

### SP-23. Читай параметры адреса через `url_param(…, escape_result=False)` своим экраном и только в датасете с личным ключом
- **Почему:**
  - Superset 2.0.1 кладёт параметры адреса дашборда (кроме `standalone` и `edit`) в `form_data.url_params` каждого чарта, `buildQueryObject` — в `queries[0].url_params`. `url_param()` читает оттуда и при `add_to_cache_keys=True` кладёт значение в ключ — но только если рендер ради ключа вообще случился (SP-20).
  - Ветка `request.args` у `url_param` (без экрана и без ключа) срабатывает, если имя параметра совпало с параметром адреса самого POST `chart/data`: `form_data`, `dashboard_id`, `force`.
  - `escape_result=True` экранирует литерал диалектом драйвера. Свой макрос с `''` (SP-06) надёжнее.
  - Владелец 08.10 хотел пересылать борд с фильтрами — так в DL появилась «Ссылка на вид».
- **Как:**

  ```jinja
  {% set LINK = ((url_param('dl_f', escape_result=False) or '')|string)[:12000] %}
  ```

  - Значение проходит те же циклы, пределы и белые списки, что носители (AC-14). Носители кросс-фильтра главнее ссылки.
  - Датасет обязан иметь вызов в `{{ … }}`, который открывает рендер ради ключа: логин или сам `url_param`. Иначе кэш не различит две ссылки.
  - В датасете с общим кэшем `url_param` не пиши вовсе — регулярка 4.1+ найдёт его и в `{% set %}`.
  - Имя параметра — не `form_data`, `dashboard_id`, `force`, `standalone`, `edit`.
  - Длина ссылки в закодированном виде — ≤ 4 000 знаков, пока предел в бою не проверен: у gunicorn по умолчанию 4094 байта, у nginx — 8 КБ. Permalink при открытии раскрывается в тот же адрес.
  - `+` в значении кодируй как `%2B`: строка запроса читает `+` как пробел.
- **Проверка:** На стенде ссылка, враждебная ссылка и ссылка с носителями проходят путь SP-01. Две разные ссылки дают разные ключи. В бою — DevTools → Payload → `queries[0].url_params`: передаёт ли их `react_sanbbox`, не проверено.
- **Уверенность:** [исходник 2.0.1] [не проверено в бою].
- **Образец:** detail_list:proteus/detail-list.data.sql (блок «Ссылка на вид»: `url_param` только в виде list, логин в `{{ }}` открывает рендер).

### SP-24. Оставляй «Время жизни кэша» пустым или 0; −1 кэш не выключает
- **Почему:**
  - Цепочка 2.0.1 идёт по `is not None`: таймаут запроса → чарт → датасет → база. Затем `if cache_timeout_rv:` — 0 считается ложью → `DATA_CACHE_CONFIG["CACHE_DEFAULT_TIMEOUT"]` → `CACHE_DEFAULT_TIMEOUT`. Proteus в ответах отдаёт `cache_timeout` 43 200 с (12 ч).
  - 0 у чарта обрывает цепочку на чарте: таймаут датасета и базы уже не берётся, сразу берётся умолчание.
  - Ветки «−1 = force» в 2.0.1 нет, она появилась в 3.0.0. −1 уходит в бэкенд кэша как срок жизни, а в Redis (cachelib 0.4.1) это запись **без срока**.
  - Adoption 07.10 поставил −1 «чтобы выключить кэш». Владелец: «Cache timeout −1 Proteus не выполняет (ответ всё равно в кэше)».
- **Как:** В инструкции — раздел «Вкладка „Настройки“ датасета и чарта»:
  - «Время жизни кэша» — пусто или 0 (это 12 ч). Дольше не ставь: связанные чарты должны показывать данные одной даты.
  - «Фильтры автозаполнения» — выключены, «Предикат автозаполнения» — пуст: его читает регулярка ключа (SP-20).
  - «Описание» — номер поставки.
  - Свежесть дают ключ (логин, фильтры), `changed_on` и «Обновить дашборд». −1 не советуй никогда.
- **Проверка:** В бою — Response → `cache_timeout` = 43 200. После Save датасета с правкой первое открытие холодное (POST 202).
- **Уверенность:** [бой] — 43 200, −1 не выключил; [исходник 2.0.1] — цепочка и cachelib; бэкенд кэша Proteus неизвестен.
- **Образец:** detail_list:Поставка — Детальные списки/0. Инструкция.md (раздел про вкладку «Настройки» датасета).

### SP-25. Не клади `force=true` в ссылки и не включай автообновление дашборда; голый `force` в адресе — норма
- **Почему:**
  - В 2.0.1 `?force=true` в адресе борда, «Обновить дашборд» и автообновление (`DASHBOARD_AUTO_REFRESH_MODE = 'force'`) идут мимо кэша для **каждого** чарта: холодный запуск всего борда.
  - Голый `force` без значения в адресе POST `chart/data` — норма 2.0.1. `getUrlParam(force)` даёт `null`, urijs печатает его ключом без значения, а сервер `force` из адреса не читает — только из тела. HRBP 07.10 видел «force в адресе» — это, скорее всего, норма.
- **Как:** «Обновить дашборд» — только по делу: замер, прогрев общего кэша, после Save. Признак холодного запуска в DevTools — `force=true` со значением в адресе или `"force": true` в теле запроса.
- **Проверка:** В бою — адрес борда без `force`, Payload POST без `"force": true` при обычном открытии.
- **Уверенность:** [исходник 2.0.1] [не проверено в бою] — значение `DASHBOARD_AUTO_REFRESH_MODE` у форка не снято.
- **Образец:** HRBP_HUB:Поставка — HRBP HUB v2/0. Инструкция.md (протокол DevTools, предупреждение про `force`).
