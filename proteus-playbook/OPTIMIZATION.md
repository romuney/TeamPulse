# Как ускорять борды Proteus — выжимка

Коротко и с цифрами: что тормозит борды в Proteus и что с этим делать. Собрано на четырёх проектах (HRBP HUB, «Детальные
списки», Proteus Adoption, TeamPulse) и проверено на стенде с версиями боя. Подробности, доказательства и код — в главах
гайда (коды правил в скобках). Состояние на 09.10.2026.

## Платформа — факты боя (09.10)

| Что | Значение |
|---|---|
| Proteus | форк **Superset 2.1.0**; путь SQL, ключ кэша и `cache_timeout` — как у 2.0.1 |
| Разбор SQL | sqlparse 0.4.3 + патч лексера Superset: каждый запрос форматируется (`reindent`) перед ClickHouse |
| Обёртка чарта | `SELECT … FROM (датасет) AS virtual_table GROUP BY <все «Измерения»> LIMIT 50000` |
| ClickHouse | 24.8.15.1, новый анализатор, `prefer_column_name_to_alias = 1`, `max_execution_time` 30 с, `max_query_size` 256 КиБ |
| Запросы чартов | асинхронные (POST → ожидание → забор результата), кэш ответов — Redis, 12 ч |
| Код чарта | уходит на сервер в **каждом** запросе данных (`form_data.jsx`) |
| Сеть владельца | отправка ≈ 50 КБ/с, приём ≈ 0,5 МБ/с |
| Бой против стенда | холодный запрос ≈ 2× медленнее стенда на той же версии ClickHouse, тёплый — так же |

## Сначала — где время

«Долго грузится» раскладывается на пять слагаемых. Сначала замер, потом рычаг (checklists/perf-triage.md, PL-03):

1. **Отправка кода чарта** — размер JS ÷ 50 КБ/с, на каждом открытии и каждом «Применить».
2. **Разбор Superset** — рендер шаблона, ключ кэша, `reindent`. Растёт примерно как токены² × вложенность скобок.
3. **ClickHouse** — SQL Lab тем же текстом, холодно и тепло (PL-05).
4. **Приём ответа** — размер ответа на проводе ÷ 0,5 МБ/с.
5. **Браузер** — разбор ответа и отрисовка.

Пункты 1, 2 и 4 видны в DevTools → Network → `chart/data` (Timing, Size), пункт 3 — в SQL Lab.

## Рычаги, по отдаче

### 1. Сжимать код чарта (CJ-21, DV-06) — секунды на каждом запросе
- В поставку — сборка terser 5.51.2 (`kit/min.cjs`): −40–45 %, поведение то же (smoke скилла: тот же вердикт на 10 чартах).
- HRBP HUB 408 → 237 КБ (≈ 8,0 → 4,6 с на запрос); «Детальные списки» 215 → 129 КБ; TeamPulse 524 → 333 КиБ вместе со
  сжатием строки CSS; листы Adoption −45 %.
- Картинки и большие строки внутри JS — тоже в каждом запросе: уменьшать или не класть.
- Загрузчик «код из ответа датасета» — не делать: сломал чарты у владельца (16-antipatterns.md).

### 2. Держать текст SQL коротким (SP-15…SP-17)
- `reindent` в Superset дорогой и раздувает текст выравниванием: 34 КБ датасета давали ≈ 10 с; цель — ≤ 1 с на худшем
  рендере.
- Отступы снимать `{% filter replace %}`, комментарии — только `{# #}`, выражения не повторять по колонкам: плоский
  массив вместо 24 копий.
- После обёртки и `reindent` — < 256 КиБ. Длинные списки — константами `WITH`. Длину значений фильтров ограничивать:
  значение в 3 000 знаков даёт > 256 КиБ после `reindent`.

### 3. Кэш: один холодный запрос на всех, а не на каждого (AC-06…AC-09)
- Логин попадает в ключ кэша, только если вызов `current_username()` стоит внутри `{{ … }}` одной строкой. Ставить его
  туда, где ответ зависит от пользователя, — и только там.
- Ответ, одинаковый для всех, — отдельный датасет без логина: кэш общий. Так ушло «таблица быстро, фильтры долго»
  в «Детальных списках».
- «Время жизни кэша» — пусто или 0 (это 12 ч); −1 кэш не выключает. Тяжёлое общее — считать заранее в ETL (GP-14).

### 4. ClickHouse 24.8 (04-clickhouse.md)
- Мерить в профиле боя: новый анализатор + `prefer_column_name_to_alias = 1` (CH-02, CH-03).
- Контекст запроса (доступ → юниты → месяц) — один скаляр, а не цепочка CTE в каждом плече: HRBP −0,7…−2 с (CH-06).
  CTE — это подстановка, а не материализация (CH-05).
- Читать диапазоном ключа сортировки (путь фиксированной длины), а не весь куб (CH-18, CH-19).
- `transform` вместо `indexOf`; регулярка вместо `arrayFirstIndex` / `arrayLastIndex` (было ×2,5 времени) (CH-21, CH-22).
- «Сначала отобрать, потом упаковать»: `ORDER BY … LIMIT` по отфильтрованной таблице, чистка и упаковка — только для
  выбранных (DS-15).

### 5. Вес ответа (05-dataset.md)
- Длинный список — колонками со словарём и base64: «Детальные списки» 1,37 → 0,68 МБ на проводе, JSON в 3–4 раза
  меньше (DS-18, DS-17).
- Только аддитивные компоненты, проценты — в JS; время — позиция в массиве, без хвостовых нулей (DS-04, DS-05, CH-22).
- Всё для взаимодействий — в одном ответе: раскрытие, переключение вида, поиск — без нового запроса (DS-11, MC-19).
- Строк — на порядки меньше лимита 50 000 (DS-24).

### 6. Несколько чартов (09-multi-chart.md)
- Тяжёлая панель и лёгкий список — два чарта, два запроса параллельно (MC-17).
- Число, зависящее от выбора чарта A, считает датасет соседа B, который и так перезапрашивается, — «один запрос, два
  чарта» (MC-15).

### 7. Браузер (07-chart.md)
- Графики — свой SVG по измеренной ширине, ECharts не рисует; анимация — только при первом показе (CJ-09).
- Точечные обновления DOM при вводе; в DOM — только текущая страница таблицы; ответ разбирать один раз (CJ-13, CJ-15, CJ-17).

## Обязательно вместе с ускорением — правильность

Ускорение не должно менять ответ: каждая правка проверяется «ответ в ответ» с прошлой версией (CH-31, ST-11).
- **Литералы в шаблоне:** кавычку удваивать (`''`), не `\'`; список со «]» — `array(…)`, не `[…]`. Иначе значения
  фильтров с `'` или `]` молча дают неверные цифры — так было в HRBP HUB, «Детальных списках» и TeamPulse, исправлено 09.10
  (SP-06, SP-07).
- **Обёртка с GROUP BY:** строки ответа уникальны, порядок восстанавливает JS, обрезку видно по числу строк
  (`data.length` ≥ лимита) — не по `ORDER BY` и не по последней строке (SP-13, DS-25).
- **Песочница гасит чарт на любую ошибку окна:** `overflow:hidden` и обёртка `window.onerror` от «ResizeObserver loop»
  (SB-03).

## Что не помогло

| Делали | Что вышло |
|---|---|
| Загрузчик кода чарта из ответа датасета | чарты сломались у владельца, откат (DL, 22-я поставка) |
| Логин в ключе кэша у общего ответа | холодное первое открытие у каждого коллеги |
| `ORDER BY` по роли для защиты от обрезки | обёртка с `GROUP BY` порядок не держит |
| `SETTINGS` в тексте датасета | Proteus не принимает; профиль задаёт кластер |
| Замеры старым анализатором | направление оптимизации бывает обратным |
