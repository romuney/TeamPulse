списков» (DL), Proteus Adoption и TeamPulse (TP). Находки — вход для задачи «улучшить поставки», раздел 7. Правила —
по кодам глав. Замеры JS — [RESULTS.js.md](RESULTS.js.md).

`pip install --target`). Стенд — 4 vCPU; бой медленнее в 1–2 раза (ST-19). Время шагов от прогона к прогону гуляет

## 0. Главное

Пункты 1–11 — те же темы и номера, что в прогоне 08.10 (на них ссылаются главы); 12–15 — новое во втором проходе.
Третий проход (проверка самих инструментов скептиком: с нуля по README, враждебный ввод в инструменты, сверка с
исходником 2.0.1) — раздел 11; числа разделов 1–10 он не меняет.

1. **`\'` в макросе литерала ломает путь** в HRBP, DL (все 4 датасета) и TP (SP-06). Значение `O'Brien; x` в любом
   носителе даёт в М1 «Virtual dataset query cannot consist of multiple statements» (2–8 инструкций), в М2 — одну
   инструкцию со сбитым лексером, и ответ после пути **другой** (HRBP, DL 1–4). Значение `O\'K` ломает DL и HRBP в обеих
   моделях, хотя DL экранирует слэш раньше кавычки: патч 2.0.1 читает `\\` и `\'` не так, как ClickHouse. В adoption
   кавычка удваивается (`''`) — в М2 проходят все 15 хвостов, кроме «]» и длинного значения (п. 14).
2. **«]» внутри литерала `[…]` сбивает лексер в обеих моделях** (SP-07): HRBP `has(['a]b'], uid)` и TP
   `has(['Hqa]b'], …)` — ответ после пути другой; adoption — Code 36 (значение в `qa` и регулярка `'^[\\s\\p{P}]*$'`
   внутри `[…]`). DL верен: его `qa` переходит на `array(…)`.
3. **reindent меняет строковые литералы, когда лексер сбит, — и теперь это видно без chdb.** `superset201.py` сверяет
   токены ClickHouse (sqlglot) обёртки до и после `format(reindent)`: сбитый лексер отдаёт reindent «код» внутри
   строки, и тот правит в ней пробелы. Гейт лексера (SP-12) поэтому обязателен и для текста после обёртки:
   - HRBP `',"it":'` → `', "it":'`, TP `'","m0":"'` → `'", "m0":"'` (хвост `a]b`);
   - DL 3–4 в М2: `'sort'` → `'\n      sort'` в эхе `meta` (хвост `O'Brien; x`) — ответ меняется молча;
   - adoption в М1 на **любом** открытии: `translate(x, '|\t\n\r', '    ')` → `' '`, отсюда Code 36.
4. **Модель М1 противоречит бою adoption** (SP-02). В М1 pa_body_one и pa_one на любом открытии, по умолчанию тоже,
   падают Code 36, а сохранение pa_one — «Only `SELECT` statements are allowed» (WITH первой строкой + сбитый лексер →
   `get_type() = UNKNOWN`). В бою оба работают (pa_one — с 30.09, каталог — 07.10). В М2 всё проходит, ответ тот же.
   Вывод [вывод][не проверено в бою]: в Proteus sqlparse ≥ 0.4.3, а не пин 0.3.0 из 2.0.1; датасет должен пройти обе

## 2. Враждебный ввод (`--hostile --hostile-set full`)

К каждому значению носителя и параметра адреса дописывается хвост; носитель, которого нет в наборе, получает сам хвост.
- **ок** — одна инструкция, лексер в фазе, reindent тронул только пробелы, ответ на chdb тот же;
- **MULTI(n)** — «multiple statements», n — сколько насчитал sqlparse;
- **≠** — ответ после пути другой;
- **Code N** — ClickHouse отверг текст после пути;
- **SIZE** — текст после reindent больше `max_query_size`;
- `*` — лексер сбит; **R** — reindent изменил текст запроса.

## 6. Пробы для боя: какой лексер у Proteus

Два запроса SQL Lab, по одному на выполнение. Тексты — в [README.md](README.md), раздел «Проверка в бою».

| Запрос | М1 (0.3.0 ± патч) | М2 (0.4.4 + патч) | 0.4.4 без патча |
|---|---|---|---|
| `SELECT length(['x', '[y]']) AS n, 'a -- b' AS s` | обрезан до `…AS n, 'a` → ошибка | `2`, `a -- b` | `2`, `a -- b` |
| `SELECT 'O\'K; c' AS t` | 2 инструкции → ошибка | 2 инструкции → ошибка | `O'K; c` |

Если первая проба вернула `2`, бой работает как М2. Тогда «]» в литерале `[…]` по-прежнему опасна (п. 2), `\'` портит
ответ тихо (п. 1), а сбой лексера adoption на регулярке в `[…]` в бою не возникает (п. 4). Верхняя граница
версии уже известна — п. 12.
