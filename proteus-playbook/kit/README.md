# kit — инструменты стенда Proteus

**Зачем.** Это общие инструменты для любого борда в Proteus. Они проверяют поставку до того, как владелец вставит её
руками: что Superset 2.0.1 сделает с SQL датасета до ClickHouse, пройдёт ли SQL сохранение, сколько стоит разбор, как
собрать папку поставки и как сжать и проверить JS чарта. Правила, на которых они построены, описаны в главах:
02-superset-path.md (SP), 03-access-cache.md (AC), 04-clickhouse.md (CH), 13-stand.md (ST) и 14-delivery.md (DV).
Результаты прогонов на четырёх проектах лежат в [RESULTS.md](RESULTS.md) (Python) и [RESULTS.js.md](RESULTS.js.md) (JS).

| Файл | Что делает | Правила |
|---|---|---|
| `setup.sh` | venv на Python 3.12 с версиями боя; второй venv с sqlparse 0.4.4; node-пакеты (terser, eslint, playwright) | ST-01 |
| `superset201.py` | путь Superset 2.0.1 над SQL датасета: рендер, ключ кэша, strip_comments, обёртка, reindent, бюджеты, враждебный ввод, сверка на chdb | SP-01…SP-23, AC-07…AC-09, AC-14, ST-12…ST-17 |
| `sqlgate.py` | гейт сохранения и SQL Lab: sqlglot 23–30, алиас в GROUP BY, `\x`, кортежный CAST, SETTINGS/FORMAT/`;`, лексер, предел sqlparse ≥ 0.5.5, `system` | SP-04, SP-09, SP-12, SP-17, CH-04, CH-17, PL-04, ST-15, ST-32 |
| `pack_template.py` | шаблон сборщика папки поставки: COPIES, сжатие JS, id чартов, штамп, `--check`, `--gate` | DV-03…DV-06, DV-09, DV-24, DV-30 |
| `min.cjs`, `eslint.chart.cjs`, `board-check.js`, `sbx/` | JS: сжатие, no-undef, разметка борда, модель песочницы | раздел «JS» ниже |

Скратч (миры chdb, дампы, логи) держите вне репозиториев. Данные боя в kit не кладите (AC-16).

## Установка

```bash
bash kit/setup.sh                     # ~/.venvs/proteus-kit и ~/.venvs/proteus-sp044, node-пакеты глобально
KIT_VENV=/путь SP044_VENV=/путь bash kit/setup.sh
SP044=0 bash kit/setup.sh             # без второго venv
NPM=0 bash kit/setup.sh               # без node-пакетов
SIDE=0 bash kit/setup.sh              # без каталогов версий sqlglot / sqlparse для sqlgate.py
BROWSER=1 bash kit/setup.sh           # ещё и Chromium для kit/sbx (≈150 МБ)
```

Скрипт берёт `uv`, если он есть, иначе `python3.12 -m venv`. В конце он печатает версии и `SELECT version()` из chdb.
Должно быть `24.8.4.1`, `true` (новый анализатор), `262144` (`max_query_size`).

| Пакет | Версия | Почему |
|---|---|---|
| chdb | 2.1.1 | = ClickHouse 24.8.4.1 (в бою 24.8.15.1). 3.0–3.2 — тоже 24.8, а 4.x — уже 26.x и годится только вторым движком (ST-01) |
| sqlparse | 0.3.0 | Superset 2.0.1: `sqlparse==0.3.0  # PINNED!`. Патч лексера Superset ставит `superset201.py` |
| sqlparse (второй venv) | 0.4.4 | вторая модель: Superset 2.1.3 / 3.0 с тем же литералом. Бой adoption ведёт себя так (RESULTS.md, п. 4) |
| jinja2 / markupsafe | 3.0.3 / 2.0.1 | как в `requirements/base.txt` 2.0.1; на Python 3.12 ставятся (проверено 08.10). Не встанут — скрипт возьмёт jinja2 3.0.x/3.1 и скажет об этом |
| sqlglot | 26.33.0 | модель проверки форка «Некорректный SQL запрос». Версии 23–30 дают тот же отказ на алиасе в GROUP BY. Версии < 15 не годятся: они не знают `CAST(x, 'T')` и роняют рабочие датасеты |
| pyyaml, psycopg2-binary | любые | выгрузки Proteus (YAML) и стенд GP на PostgreSQL 16 |
| terser / eslint / playwright | 5.51.2 / 10.1.0 / 1.56.1 | версии закреплены: с другим terser `pack --check` расходится |

Другие версии sqlglot и sqlparse ставятся каталогом, а не в venv: скрипт кладёт sqlglot 23.17 / 25.34 / 28.10 / 30.0 в
`~/sg/<версия>` и sqlparse 0.5.5 / 0.6.0 в `~/sp/<версия>` (`SG_DIR`, `SP_DIR` — другие места) и в конце печатает
готовые `--sqlglot-dirs "…" --sqlparse-dirs "…"` для `sqlgate.py` (в кавычках: пути с пробелами). Руками —
`pip install --target ~/sg/23.17.0 sqlglot==23.17.0`. Каталог считается готовым, только если пакет берётся из него и
версия та: после прерванной установки скрипт ставит пакет поверх, а не пишет «уже стоит». Повторный запуск безопасен.

## Python

### superset201.py — путь Superset 2.0.1 над SQL датасета

Повторяет исходник 2.0.1 буквально:
- `jinja_context.py`: `SandboxedEnvironment(undefined=DebugUndefined)`, `safe_proxy`, `ExtraCache`, `where_in`;
- `sql_parse.py`: патч лексера и `ParsedQuery`;
- `connectors/sqla/models.py`: `get_rendered_sql`, `get_from_clause`, `get_query_str_extended`, `get_df`;
- `connectors/sqla/utils.py`: сохранение и синхронизация столбцов.

Для каждого варианта рендера инструмент печатает:

1. **Сохранение** (AlwaysTrueObject, логин сохраняющего). В контексте Jinja — только макросы и «Параметры шаблона»
   (`--template-params`): переменных запроса чарта (`columns`, `filter`, `row_limit`…) при сохранении нет. Нет
   `strip_comments`, «только SELECT», одна инструкция, затем текст + `"\nLIMIT 1000"`. С `--run` этот текст
   исполняется на chdb (SP-05).
2. **Открытие** (`--user`, `--filters`, `--url-params`, `--template-params`). Шаги `strip('\t\r\n; ')` →
   `format(strip_comments)` → `split` → `ParsedQuery` / «только чтение» → обёртка
   `SELECT <Измерения> FROM (…) AS virtual_table GROUP BY <Измерения>\n LIMIT N` → `format(reindent)` → `parse_sql`
   (SP-01, SP-13). Если носитель — колонка датасета, к обёртке добавляется `WHERE … IN` (SP-14). Сразу же проверяется,
   что reindent поменял только пробелы: токены ClickHouse (sqlglot) обёртки до и после одинаковы. Сбитый лексер даёт
   reindent «код» внутри строки, и тот правит пробелы в литерале — это ловится без chdb (SP-12).
3. **Размеры и бюджеты.** КБ рендера, датасета, обёртки и текста после reindent. Токены лексера, «(» по тексту и по
   лексеру, глубина скобок. Время каждого шага. Жёсткие пределы: `max_query_size` 262 144 Б после reindent,
   токенов датасета < 10 000, глубина < 100 (SP-15…SP-17). Мягкие ориентиры: reindent ≤ 1 с, разбор ради ключа ≤ 0,5 с.
   Токены считаются так же, как предел sqlparse ≥ 0.5.5: каждый пробел — отдельный токен. Поэтому текст после reindent
   в 2–7 раз «длиннее» датасета (отступы); если итог больше 10 000, это печатается заметкой — в 2.0.1 предела нет.
4. **Ключ кэша.** `ExtraCache.regex` 2.0–4.0 и 4.1+ по сырому тексту и по тексту без `{# #}` (SP-20, AC-07…AC-09).
   Инструмент показывает, какие значения при рендере открытия попали в ключ и каким вызовом, и выносит вердикт:
   - **ЛИЧНЫЙ** — логин (`current_username` / `current_user_id`) в ключе;
   - **ПО ЗНАЧЕНИЯМ** — в ключе только параметры адреса или `cache_key_wrapper`: у всех с той же ссылкой ключ один;
   - **ОБЩИЙ** — вызовов нет, ключ без рендера;
   - «рендер впустую» — регулярка видит вызов, но он не исполнился (комментарий, неисполненная ветка);
   - **ОПАСНО** (ошибка) — вызов исполнился, а регулярка 2.0 его не видит (`{% set %}`, макрос без `{{ }}`, несколько
     строк); или логин / параметр адреса взяты с `add_to_cache_keys=False`. Ответ, зависящий от значения, которого нет
     в ключе, уйдёт из кэша другому.

   Если регулярка видит вызов только в комментарии `{# … #}`, это предупреждение: ключ держится на комментарии.
   `--extra-text` (WHERE/HAVING чарта, RLS) при открытии рендерится тем же процессором, как в `get_sqla_query` 2.0.1, и
   его вызовы тоже кладут значения в ключ. `--save-only` всё равно оценивает ключ по рендеру открытия. Тут же — цена в
   Superset: холодное открытие (POST + воркер + забор `qc-…`) и открытие из кэша (SP-22).
5. **Лексер.** Видит ли sqlparse строки так же, как ClickHouse (sqlglot), и убрал ли `strip_comments` только
   комментарии (SP-12).
6. **`--run`.** Прямой запуск отрендеренного текста против текста после пути. Сравнивается множество строк по
   «Измерениям», потому что GROUP BY схлопывает дубли и не держит порядок. Если ответ разный, прямой запуск повторяется
   ещё раз: ответ может быть недетерминирован, тогда сверка невозможна, и это отдельная находка. Если упал только прямой
   запуск, печатается предупреждение «сверка не проведена» — итог «ок» без сверки не выдаётся. Перед `SETTINGS`
   (`--settings`, `--matrix`) хвостовые `;` срезаются, как у Superset.
7. **`--hostile`.** Значения носителей и параметров адреса получают хвост из набора `O'Brien; x`, `a]b`, `x -- y`,
   `x // y`, `# x`, `a\`, `a;b`, `Отдел «Альфа» — 1`. С `--hostile-set full` — ещё остальное из набора SP-11: `[a`,
   `x /* y`, `y */ z`, `` `b` ``, `O\'K`, табуляция и управляющий символ, 3 000 знаков кириллицы. Если носитель шаблон
   спрашивает, а вы его не задали, туда подставляется сам хвост. Проверка: одна инструкция, лексер в фазе, reindent
   тронул только пробелы, ответ на chdb тот же. Ошибки, которые уже есть при открытии, не повторяются (SP-11, ST-14).
   «Дошло до SQL: нет» значит, что шаблон отбросил значение своими пределами (AC-14) — это норма.

```bash
PY=~/.venvs/proteus-kit/bin/python          # модель 0.3.0 + патч 2.0.1
PY44=~/.venvs/proteus-sp044/bin/python      # модель 0.4.4 + патч 2.1.3 / 3.0 — гоняйте и её

# личный датасет (логин в ключе), колонки — из верхнего SELECT, исполнение на мире стенда
$PY kit/superset201.py proteus/report.data.sql --user b.kotov --cols auto --run --db stand/.chdb24 --hostile

# 5 колонок, носители из файла, параметр адреса, функция, которой нет в chdb 2.1.1
$PY kit/superset201.py "Поставка/1. Датасет.sql" --user a.user --cols role,k,v,n,j \
    --filters @stand/worst.json --url-params '{"dl_f": "flt:office_desc=Офис 1"}' \
    --run --db stand/.db --ch-sub 'base64Encode\(=>(' --matrix

# только сохранение; JSON для регресса; тексты шагов — в скратч
$PY kit/superset201.py dataset.sql --save-only --json > /tmp/ss.json
$PY kit/superset201.py dataset.sql --dump /tmp/ss_dump --open-only

# «Параметры шаблона» датасета и полный набор враждебных значений
$PY kit/superset201.py dataset.sql --template-params '{"days": 90}' --hostile --hostile-set full --run --db stand/.db
```

Флаги: `--limit` (лимит строк чарта, 50 000), `--no-groupby` (обёртка без GROUP BY для сравнения), `--settings`
(можно несколько; по умолчанию — профиль боя `PROD_SETTINGS`: новый анализатор + `prefer_column_name_to_alias = 1`,
SQL Lab 09.10; `--settings ''` — голые умолчания chdb) или `--matrix` (профиль боя, новый анализатор, старый, новый с
`join_use_nulls`/`prefer_column_name_to_alias`/`group_by_use_nulls` — CH-03), `--extra-text` (предикат автозаполнения, WHERE/HAVING чарта, RLS — их тоже читает
регулярка ключа), `--no-patch` (лексер без патча Superset), `--max-reindent-s`, `--max-key-s`, `--no-escape-dialect` и
`--no-double-percents` (экран `url_param(escape_result=True)`, см. ниже). `--dump` пишет тексты шагов открытия и текст
сохранения (`….save.sql`, с `LIMIT 1000`).

Код выхода: 0 — чисто, 1 — ошибка пути, лексера, бюджета, ключа или сверки, 2 — ошибка вызова: нет файла датасета;
`--db` не существующий каталог (chdb иначе молча создаст пустой мир по опечатке, в том числе в репозитории проекта);
неверная регулярка `--ch-sub`; `--filters` / `--url-params` / `--template-params` не JSON-объект.

Что инструмент делает с плохим входом: любая ошибка шаблона (деление на ноль, `range` больше 100 000 в песочнице,
`.pop()` пустого списка) — строка отчёта, как отказ Superset, а не трассировка. Датасет, пустой после рендера и
`strip_comments`, — «Virtual dataset query cannot be empty». Файл не в UTF-8 — ошибка с номером строки. BOM в начале
файла убирается с предупреждением: в поле Proteus его не вставят, а sqlglot на нём падает. Носитель с ложным значением
(`null`, `""`, `0`, `false`, `[]`) — фильтра нет: `get_filters` 2.0.1 пропускает его до обёртки в список.

**Модулем** — из своего `stand/check.py`, чтобы каждый вариант регресса шёл путём Superset (ST-12):

```python
import sys; sys.dont_write_bytecode = True                  # без kit/__pycache__ в репозитории playbook
sys.path.insert(0, '<playbook>/kit')
import superset201 as ss
ss.lexer_patch()                                            # до первого разбора
text, warns = ss.read_sql('proteus/report.data.sql')       # BOM, \r\n, не UTF-8 — как у CLI
r = ss.render(text, user='a.user', filters={'unit_f': ['u1']}, url_params={}, save=False)
assert not r.error, r.error
p = ss.chart_path(r.text, ['role', 'k', 'v', 'n', 'j'])     # p['error'], p['steps'], p['texts']['executed']
assert not p['error'] and not ss.lexer_problems(r.text)
rows, sec, err = ss.ch_run(p['texts']['executed'], db='stand/.db',
                           subs=[(r'base64Encode\(', '(')])  # subs — чего нет в chdb 2.1.1 (ST-21); не нужно — уберите
key = ss.cache_key_report(text, r)                          # key['verdict']; key.get('error') — ОПАСНО
```

**Чего модель не знает:**
- `SQL_QUERY_MUTATOR` форка;
- RLS в тексте запроса (для оценки ключа клаузу RLS можно дать через `--extra-text`);
- драйвер ClickHouse форка. От него зависит экран `url_param(escape_result=True)`: SQLAlchemy 1.3
  `String().literal_processor` удваивает кавычку, обратный слэш не трогает, а у драйвера с paramstyle
  `format`/`pyformat` удваивает и `%`. `compile_sqla_query` затем сворачивает `%%` всего текста, и процент значения
  остаётся удвоенным: `50%` → `50%%`. Модель так и делает; флаги `--no-escape-dialect` и `--no-double-percents`
  выключают экран. Свой экран через `escape_result=False` надёжнее (SP-23) [исходник 2.0.1][вывод — драйвер не снят];
- `request.args`: если параметр есть в адресе самого запроса `chart/data`, 2.0.1 берёт его оттуда, без экрана и мимо ключа
  кэша. Дашборд так параметры не шлёт (они в `form_data.url_params`), поэтому модель эту ветку не повторяет;
- собственную проверку форка при сохранении — её закрывает `sqlgate.py`;
- версию sqlparse в бою — поэтому моделей две.

На стенде есть поправки к chdb (ST-21):
- `base64Encode` нет — заменяется через `--ch-sub`;
- длинное и короткое тире в тексте запроса chdb превращает в `--`, поэтому значения с тире на стенде не проверить.

### sqlgate.py — гейт сохранения и SQL Lab

```bash
$PY kit/sqlgate.py proteus/report.data.sql --user a.user --cols auto \
    --sqlglot-dirs ~/sg/23.17.0,~/sg/25.34.0,~/sg/28.10.0,~/sg/30.0.0 \
    --sqlparse-dirs ~/sp/0.5.5,~/sp/0.6.0
$PY kit/sqlgate.py --sqllab "Поставка/10. Проверка на бою.sql" "Поставка/0. Инструкция.md"
```

Каталоги версий — рядом, не в venv: `pip install --target ~/sg/23.17.0 sqlglot==23.17.0`,
`pip install --target ~/sp/0.6.0 sqlparse==0.6.0`. Гейт перезапускает себя с `PYTHONPATH=<каталог>` для каждого и
проверяет, что модуль взят именно оттуда. Каталога нет, он пуст или проверка в нём упала — код 2 с причиной: иначе гейт
молча шёл бы версией из venv, а шапка обещала бы 23.17 или 0.5.5.

Для датасета проверяются три текста:
- **сохранение** — AlwaysTrue, и тот же текст с `LIMIT 1000`;
- **открытие** — `--user`, `--filters`, `--url-params`, `--template-params`;
- **обёртка чарта**.

В каждом тексте ищутся:
- ошибка разбора sqlglot в формате форка «…→место←…»;
- больше одного оператора или не запрос;
- алиас в GROUP BY — ищется по токенам, даже если sqlglot его пропустил (SP-04);
- `\x..` в литерале (SP-09);
- кортежный тип строкой в CAST (CH-17);
- SETTINGS, FORMAT, `;` в середине, `AS MATERIALIZED` (CH-04). FORMAT — только как предложение `FORMAT <имя формата>`:
  колонка или алиас `format` (`SELECT format AS f`) ошибкой не считается;
- остатки Jinja;
- сбой лексера sqlparse (SP-12);
- с `--sqlparse-dirs` — предел разбора sqlparse ≥ 0.5.5: 10 000 токенов и глубина 100 (SP-17, ST-15). Шаги те же, что
  у Superset: `format(strip_comments)` и `parse` датасета, `format(reindent)` и `parse_sql` обёртки. Датасет сверх
  предела — ошибка. Обёртка после reindent и SQL Lab — предупреждение: в 2.0.1 предела нет, в Superset 4.1+ нет
  reindent, это запас на обновление форка. Каждый пробел отступа — отдельный токен, поэтому после reindent текст
  в 2–7 раз «длиннее»: HRBP — 5 905 токенов в датасете и 18 466 после reindent (RESULTS.md, п. 13).

Одна и та же причина в нескольких вариантах печатается одной строкой: место в тексте — из первого варианта, варианты —
в скобках. Файл читается как в `superset201.py` (BOM, UTF-8, пустой датасет); нет файла или `--filters` не объект —
код 2.

**`--sqllab`** проверяет файл для SQL Lab (PL-04, ST-32). Из `.md` (и `.MD`) берутся блоки кода с языком `sql` — в
тройных обратных кавычках или тильдах, регистр не важен (`SQL`), отступ блока в списке допустим; блок `sqlite` не
берётся. Проверки:
- слово `system` в любом месте, даже в комментарии, — ошибка;
- `SHOW` — ошибка;
- `REPLACE` — предупреждение: отказ на нём боем не подтверждён;
- один запрос: если в файле сборник, каждый запрос проверяется отдельно, а на файл выдаётся предупреждение;
- первым словом SELECT или DESCRIBE; WITH — предупреждение, не проверено в бою;
- **`LIMIT N BY` на верхнем уровне** — ошибка. SQL Lab 2.0.1 считает его лимитом строк: `query.limit = min(N, окно)`,
  затем LIMIT заменяется на N + 1, и на экране остаётся N строк всего ответа (`sqllab/command.py`, `sql_lab.py`;
  [исходник 2.0.1][не проверено в бою]). Обычный `LIMIT N` безвреден.

### pack_template.py — шаблон сборщика папки поставки

Скопируйте файл в `stand/pack.py` проекта и заполните блок «НАСТРОЙКИ»: `REPORT`, `DELIVERY`, `DATE` (дату — руками,
иначе `--check` разойдётся на следующий день), `BOARD_IDS`, `COPIES` и `KEEP` (файлы, которые пишет человек, —
по умолчанию `0. Инструкция.md`).

COPIES — это кортежи `(исходник, «N. Название.ext», вид, [(строка, замена)], [флаги min.cjs])`. Подстановка варианта
(DV-04) требует, чтобы строка встречалась в исходнике ровно один раз. Виды:

| Вид | Что делает сборщик | Шапка |
|---|---|---|
| `dataset` | `{% set BUILD = '…' %}` → поставка/дата/sha12 (для эха в `meta.build`, DV-09) | `{# … #}` (в SQL не попадает) |
| `sqllab` | падает на `system` и `SHOW` | `-- …` |
| `js` | `node kit/min.cjs 'шапка' --check --budget КБ --kbps 50` + `node --check`; печатает КБ и секунды отправки (DV-06) | preamble terser |
| `css` | заглушки `chart-id-000000…` → id из `BOARD_IDS`, в комментариях — целым словом; заглушка в коде не на месте id (цвет `#000000`) — сборка падает; нет id — заглушка остаётся, и шапка просит Ctrl+H (DV-24, DV-05) | `/* … */` |
| `snippet` | то же целым словом (сниппет DevTools, DV-30); цвет `'#000000'` в коде — сборка падает, иначе он молча стал бы id | `// …` |
| `json` | проверка `json.loads`, без шапки | — |
| `py` | шапка `#` | `# …` |
| `raw` | байт в байт, без декодирования (картинка, xlsx); подстановок нет | — |

```bash
python3 stand/pack.py            # пишет только изменившиеся файлы; печатает «файл → новый / записан / без изменений»
python3 stand/pack.py --check    # ничего не пишет (и папку не создаёт); «ok / РАЗНЫЕ / НЕТ / ЛИШНИЙ»; код 1 при расхождении
PLAYBOOK_PY=~/.venvs/proteus-kit/bin/python python3 stand/pack.py --gate   # + kit/sqlgate.py по SQL поставки
```

Сборка идёт в два прохода: сначала собираются все файлы, а пишутся, только если собрались все. Иначе папка остаётся
наполовину новой, и «Заменить в «Что нового»» следующей сборки не назовёт уже переписанные файлы. Сборщик падает с
текстом «СБОРКА НЕ ПРОШЛА, ничего не записано: …» (код 1), если:
- строка варианта встречается не ровно один раз;
- заглушка id не уникальна (цвет `#000000`) или осталась после подстановки;
- боевой id уже стоит в коде исходника. Комментарий и цвет не в счёт: в комментарии `kit/board-check.js` есть пример
  с id 802568 — сниппет из него собирается и с этим id в `BOARD_IDS`;
- в SQL Lab-файле есть `system` или `SHOW`;
- JSON не разбирается; исходника нет; исходник не в UTF-8 (тогда — вид `raw`);
- JS не сжался, не прошёл `node --check` или больше бюджета `JS_BUDGET_KB`.

Неизвестный флаг — код 2: опечатка `--chek` не собирает и не пишет. Заметки в строке файла: заглушка из `BOARD_IDS`, не
встреченная ни в одном CSS / сниппете; комментарий исходника с заглушкой и просьбой «замените (Ctrl+H)» — после
подстановки он просит владельца заменить уже боевой id (так в шапке исходника CSS DL; просьбу о Ctrl+H пишет сам
сборщик, когда id нет).

Файл в папке, которого нет в `COPIES` и `KEEP`, печатается строкой «ЛИШНИЙ»: сборщик его не удаляет, а `--check` из-за
него падает (номер файла закреплён за объектом Proteus, старый файл путает владельца — DV-01). Скрытые файлы
(`.DS_Store` от Finder), `Thumbs.db` и `desktop.ini` не в счёт. Имена сравниваются в NFC: копия имени в NFD («й», «ё»
разложены — так бывает после архивов и старых дисков macOS) рядом с NFC — «ЛИШНИЙ».

Шаблон проверен на «Детальных списках»: 13 файлов 27-й поставки (датасеты 1–4 подстановками MODE / VIEW / логина
панели, JS 5–8, CSS 9, SQL Lab 10–11, сниппет 12, JSON) собираются из исходников DL и совпадают с поставкой DL, кроме
строки штампа и шапки CSS (RESULTS.md, разделы 9 и 11).

Строка «Заменить в «Что нового»» — готовый список файлов для раздела инструкции (DV-11). Он считается против прошлой
сборки в папке, а не против прошлой поставки: собрали дважды до сдачи — копите список сами или считайте от git-тега
поставки (DV-34). Где лежит kit: переменная `PLAYBOOK_KIT`, по умолчанию `<корень>/kit`. `NODE_PATH` берётся из
окружения, без него — `npm root -g`.

### Проверка в бою: какой лексер у Proteus

Это два запроса для SQL Lab, по одному на выполнение. В них нет `system`. [вывод][не проверено в бою]

```sql
SELECT length(['x', '[y]']) AS n, 'a -- b' AS s
```
- sqlparse 0.3.0 (с патчем или без) читает `['x', '[y]` как имя T-SQL, принимает `-- b' AS s` за комментарий и
  вырезает его. Ожидание: синтаксическая ошибка ClickHouse.
- sqlparse ≥ 0.4.3. Ожидание: `n = 2`, `s = 'a -- b'`.

```sql
SELECT 'O\'K; c' AS t
```
- Патч Superset стоит (любая версия 2.0–3.x). Ожидание: две инструкции, ошибка.
- Патча нет. Ожидание: `t = O'K; c`.

Если первый запрос ответил `2` и `a -- b`, бой работает как второй venv (0.4.4). Тогда модель 0.3.0 нужна только как
запас.

Верхняя граница уже известна: файл 10 DL (≈15 тыс. токенов лексера) 08.10 исполнился в SQL Lab Proteus. SQL Lab 2.0.1
вырезает комментарии через `sqlparse.format(strip_comments=True)`, и sqlparse 0.5.5 на этом тексте падает «Maximum
number of tokens exceeded (10000).» (0.5.4 — нет; проверено на той же версии файла). Значит, в бою sqlparse < 0.5.5
[вывод: бой + исходник 2.0.1]. Вместе с adoption (п. 4 RESULTS.md) — скорее всего 0.4.3–0.5.4.

### min.cjs — сжатая сборка и её проверка

```bash
export NODE_PATH=$(npm root -g)
node kit/min.cjs 'Отчёт: сборка proteus/report.chart.js; правки — в исходнике' < proteus/report.chart.js > out.js
node kit/min.cjs 'шапка' --check --budget 250 < proteus/report.chart.js > out.js   # + проверка сборки и бюджет, КиБ
node kit/min.cjs 'шапка' --check --css-var TP_CSS < build/chart.js > out.js        # строку CSS сжать до terser
node kit/min.cjs --verify 'Поставка/5. Чарт.js'                                    # проверить готовую сборку
```

- Параметры terser — как у detail_list:stand/min.cjs, сборки которого работают в бою с 23-й поставки: `ecma 5`,
  `toplevel false` и в compress, и в mangle, `keep_fargs`, без комментариев, `ascii_only false`, шапка — `preamble`
  (`*/` в шапке экранируется). Без флагов вывод байт в байт как у DL: проверено `cmp` на 10 чартах четырёх проектов.
- На вход — уже ES5: terser с `ecma 5` синтаксис не понижает (CJ-02). Макет на современном JS сначала проходит Babel
  (CJ-23).
- `--check` проверяет сборку:
  - разбор acorn как ES5;
  - `option = …` на верхнем уровне, и последним, если так в исходнике. Хвост terser `…}(),option={…};` тоже считается
    верхним уровнем;
  - все имена верхнего уровня исходника на месте, в том числе `var`, которые terser перенёс в `for (var …)`;
  - нет кода из строки (CJ-22) — как у ESLint `no-eval`, `no-new-func`, `no-implied-eval`: `eval` и `Function` (с `new` и
    без, `.call` / `.apply` / `.bind`), они же через `window.` / `self.` / `globalThis.`, косвенный `(0, eval)(…)`, строка
    в `setTimeout` / `setInterval`. Метод `eval` своего объекта (`o.eval()`) — не находка;
  - версия terser — 5.51.2, иначе предупреждение.
- При провале `--check` код выхода 1 и stdout пуст. Перенаправление `> файл` при этом оставит пустой файл, поэтому
  сборщик проверяет код выхода до записи. `kit/pack_template.py` так и делает.
- `--verify <файл>` — те же проверки готовой сборки, но без сверки имён: исходника нет.
- `--budget КиБ` — сборка больше бюджета даёт код 1. `--kbps N` — скорость для оценки «≈ с отправки на запрос»; по
  умолчанию 50 — замер владельца 07.10.
- `--css-var ИМЯ` сжимает строку `var ИМЯ = "…"` верхнего уровня до terser: убирает комментарии и лишние пробелы. Строки,
  `url(…)`, `var(…)`, экранированные знаки (`\:`, `\31 `), значения кастомных свойств (`--x: …` — CSSOM хранит их
  текстом) и пробел перед `:` остаются как есть. Пробел после `:` снимается только в объявлениях: в селекторе и в условии
  `@media` / `@supports` он значим (`.a: hover` браузер отбрасывает, а `.a:hover` — рабочее правило). Комментарий уходит
  без следа (`div/**/.a` — это `div.a`, а не потомок `div .a`); между двумя словами (`#a/**/iframe`, `and/**/(`,
  `1px/**/2px`) на его месте остаётся пустой `/**/`: и пробел, и склейка поменяли бы смысл. Правила CSSOM до и после
  совпадают на 7 файлах проектов, на враждебном наборе из 53 правил и на 96 вариантах этих файлов со случайными
  комментариями (RESULTS.js.md, разделы 1 и 8). CSS, собранный конкатенацией, сжимайте в своём сборщике:
  `require('<kit>/min.cjs').cssMin(css)`.
- Сводка «N Б → M Б (КиБ, −%), ≈ с отправки при 50 КБ/с» идёт в stderr, сборка — в stdout. Коды выхода: 0 — сборка
  годится, 1 — сжатие или проверка не прошли, 2 — неверный вызов или не запустилось (нет файла, нет terser): ничего не
  проверено. Глубина разбора у acorn и terser конечна: цепочку из тысяч `a + b + …` (≈4 000 частей) они не разберут — так
  и пишется, разбейте её.
- Модулем: `const { minifyChart, verify, cssMin } = require('<kit>/min.cjs')`.
  `await minifyChart(src, шапка, { cssVars: ['TP_CSS'] })` → `{ code, notes }`; `verify(code, src)` →
  `{ ok, fails, warns, info }`.
- validate.py и `check.py` скилла гоняйте только на исходнике. На сборке они дают 7–14 ложных FAIL по форме текста
  (C1, H3, D2, S1, S3, S5, S14…). Браузерные E-коды на сборке и на исходнике совпали на 10 чартах из 10 (ST-30,
  13-stand.md).

### eslint.chart.cjs — no-undef для чарта

```bash
cd <корень проекта>    # файлы — внутри текущего каталога: с -c ESLint 9+ берёт его базой
node $(npm root -g)/eslint/bin/eslint.js -c <playbook>/kit/eslint.chart.cjs --no-config-lookup proteus/*.chart.js
```

- Цель — 0 ошибок. Ошибками считаются `no-undef` (ReferenceError в бою гасит чарт, S7), `no-eval`, `no-new-func` и
  `no-implied-eval` (CJ-22).
- ESLint 9+ молча пропускает явно названный файл в двух случаях: файл вне текущего каталога («File ignored because
  outside of base path») и файл не `*.js` («File ignored because no matching configuration was supplied»): одно
  предупреждение, 0 ошибок, код 0, а файл не проверен. Конфиг ловит оба случая сам (страж в начале `eslint.chart.cjs`,
  09.10): файл или каталог вне текущего каталога — ESLint падает с подсказкой «запустите из каталога…» (код 2); файл
  с другим расширением (сборка `.min`, файл без расширения) проверяется как `*.js`; заведомо не JS (`.md`, `.json`,
  `.sql`, `.css`…) пропускается, как раньше, — `proteus/*` не падает на соседних файлах. Шаблоны glob страж не трогает.
  Если «outside of base path» или «no matching configuration» всё же видно у JS-файла (другая версия ESLint, вызов
  через API) — это провал: файл не проверен.
- Предупреждения:
  - `no-restricted-globals` с причиной: `localStorage`, `sessionStorage`, `indexedDB` (SecurityError, SB-02); `fetch`,
    `XMLHttpRequest`, `WebSocket`, `EventSource` (CSP, SB-01); `location` (адрес борда — SB-17); `history`, `alert`,
    `confirm`, `prompt`, `open`;
  - `no-console`;
  - `no-unused-vars`, кроме параметров и `catch`.
- Глобалы — объединение конфигов HRBP и DL плюс то, что на деле берут чарты adoption и TeamPulse:
  - контракт: `data`, `applyCrossFilter` (readonly), `option` (writable);
  - окно, документ, таймеры, `requestAnimationFrame`, наблюдатели;
  - `atob`, `btoa`, `TextDecoder`, `escape`, `Blob`, `URL`, `URLSearchParams`, типизированные массивы;
  - `Map`, `Set`, `Symbol`, `Promise`, `Reflect` — для помощников Babel.

  Встроенные ES5 (`JSON`, `Math`…) ESLint даёт сам.
- Голые `parent`, `top`, `self`, `frames`, `screen`, `open`, `name`, `status`, `event` не объявлены нарочно. Это частые
  имена локальных переменных, а забытый `var` с ними в браузере не падает: код тихо берёт свойство окна. Пишите
  `window.parent.postMessage(…)` и `window.top`.
- Новый нужный глобал добавьте в `SANDBOX` в начале файла, с причиной. Сжатую сборку гонять можно: ошибок у неё
  столько же, сколько у исходника.

### board-check.js — разметка живого борда (DevTools)

Агенту:

   - `VH_TOL` — допуск числа высоты (2 px: верх ряда дробный);

2. В сборщике укажите вид `snippet`: `kit/pack_template.py` подставит боевые id и проверит, что заглушек не осталось.
   В поставку положите файл «N. Проверка на бою — разметка борда (DevTools).js». В инструкцию перенесите шаги из шапки
   сниппета и подсказку про `allow pasting`.
3. На стенде гоняйте тот же текст: на каркасе проекта (detail_list:stand/live.py `?sk=1`) или
   `kit/sbx/run.cjs --board-check`.

Владельцу: открыть борд на нужной вкладке, не в режиме правки → F12 → Console (контекст «top») → вставить → Enter →
прислать вывод целиком. Сниппет только читает (`getBoundingClientRect`, `getComputedStyle`, `document.styleSheets`) и
печатает всё одним `console.log`. Он написан на ES5, ESLint даёт 0 ошибок.

Что печатает сниппет:
1. Окно и режим правки: в режиме правки числа не советует. Если консоль смотрит в iframe чарта, просит выбрать «top».
2. CSS борда — `<style class="CssEditor-css">`, так его кладёт Superset 2.0–4.0 (`injectCustomCss`):
   - есть ли элемент и не пуст ли он;
   - длину текста;
   - сколько блоков в тексте и сколько правил принял браузер (отброшенный блок — ошибка в тексте или незнакомый
     селектор). Комментарии и строки снимаются одним проходом, `@import` без блока — тоже правило;
   - есть ли в нём наши id — целиком, как `chart-id-N` без цифры после: id 80256 не находится в `chart-id-802568` и в
     цвете `#802568`;
   - остались ли заглушки `chart-id-000000`.
3. По каждому id: ячейка, видна ли она, iframe (размер, атрибуты, `display`, щели вокруг), канал скриншотов. Ячейка без
   iframe попадает в итог.
4. Поля слева, справа и между чартами против `EXPECT`; горизонтальная прокрутка.
5. Вкладки — свои (ячейка внутри них) или верхнего уровня (полоса в шапке, вне `.grid-container` — так у
   DashboardBuilder 2.0.1). Вложенные вкладки где-то ещё в сетке — не наши: если опорная ячейка (верхняя левая из
   `CHART_IDS`) не во вкладках, сниппет пишет «ряд не во вкладках» и меряет от шапки до первого блока сетки:
   - от линии вкладок до ряда;
   - от шапки до вкладок. У вкладок верхнего уровня цель 0: полоса — часть шапки;
   - ряды над вкладками: от шапки до первого ряда и от последнего ряда до вкладок, с id их чартов;
   - вид активной вкладки;
   - украшения на `::before` и `::after` (BC-19).
6. Ряд: верх, высота, высота из раскладки, зазор до низа окна. Число правила «высота по экрану» берётся из CSS страницы
   в обеих записях браузера: `100vh - Npx` и `-Npx + 100vh`. Оно сверяется с «верх ряда + `EXPECT.bottom`» для того
   ряда, чей `.resizable-container` правило задевает (не обязательно опорного: ряд «Ссылки» над вкладками), и сниппет
   даёт готовое «замените N на M (Ctrl+H)» (BC-18). Правило есть, но не задевает ни одну нашу ячейку — расхождение.
7. Правила CSS с нашими id — задевают ли они что-то сейчас. Не задевает ни одно — значит, у форка другие классы (BC-23).
8. Цепочку ячейки вверх, до 24 уровней: классы, поля, отступы, фон, `overflow`, `sticky`.
9. Строку `ИТОГ:` — число расхождений и какие.

Классы `.grid-container`, `.dashboard--editing`, `.dashboard-header-container` и `style.CssEditor-css` в форке живьём не
подтверждены (BC-23). Поэтому сниппет печатает цепочку и все правила, а не только вердикт.

### sbx/ — модель песочницы Proteus

```bash
export NODE_PATH=$(npm root -g) PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers
node kit/sbx/run.cjs proteus/report.chart.js proteus/report.mock.json                         # прогон и сводка
node kit/sbx/run.cjs chart.js mock.json --css 'Поставка/4. CSS борда.css' --id 000000 --ch 1300 \
     --clicks clicks.json --shot out.png                                                      # CSS, сценарий, снимок
node kit/sbx/run.cjs panel.js panel.mock.json --id 222222 --cols 3 \
     --also list.js list.mock.json 000000 9 --css board.css --w 1400 --clicks dl.clicks.json # два чарта в ряду
node kit/sbx/run.cjs chart.js mock.json --catch listener --frame src --no-scrollbars          # другие допущения о форке
node kit/sbx/run.cjs chart.js mock.json --board-check --json > report.json                    # + сниппет, вывод JSON
```

- Родитель (`parent.html`) локальный сервер `run.cjs` отдаёт по адресу `/superset/dashboard/<--board>/`. В нём:
  - меню 53 px и липкая шапка 64 px;
  - сетка 2.0.1: `.grid-container` с полями 24 / 32 px, ячейки по 12 колонкам (колонка = (ширина + 16) / 12 − 16);
  - холдер `.dashboard-component-chart-holder.dashboard-chart-id-N` (класс id — на самом холдере) с полем 16 px, рамкой
    2 px и шапкой чарта `.chart-header[data-test="slice-header"]`; атрибуты `data-test` — как у 2.0.1;
  - `#chart-id-N > .react_sanbbox > iframe` и `img.echarts-plugin` рядом. Атрибуты размера iframe ставятся при монтаже и
    равны размеру чарта по коду 2.0.1: ширина — `floor(ячейка − 32)`, высота — `floor(высота --ch − 32)` минус шапка
    (`offsetHeight` + её `margin-bottom`, у спрятанной — 0 + 4). Берутся из раскладки, а не из CSS борда (S2). Бой:
    iframe 1309×1052 в ячейке 1341×1088 (шапка спрятана) — то же «− 32 / − 36». Без CSS борда iframe у 2.0.1 на 4 px
    вылезает из поля ячейки: рамку 2 × 2 px код не вычитает;
  - emotion-правила 2.0.1 (`Chart.jsx`): `.chart-container{min-height:Hpx}`, `.slice_container{height:Hpx}`, H — высота
    чарта; они стоят раньше CSS борда, и цепочка растяжки снимает их сама (`min-height:0`, BC-04);
  - CSS борда (`--css`) — в `<style class="CssEditor-css">` последним в `<head>`, как у 2.0.1. id в нём — те же, что
    `--id` и `--also`; id — числа, у каждого чарта свой.
- iframe (`inner.html`): `sandbox="allow-scripts"` и CSP `connect-src 'none'`. Хост `[_echarts_instance_]` с корнем в px:
  заглушка с подгонкой по ResizeObserver или настоящий echarts (`--echarts <путь>/echarts.min.js`). Обработчик ошибок
  окна стоит до кода чарта и гасит чарт (хост пуст). Код запускается на каждый ответ в том же окне.
- Чего не знаем о форке, гоняйте в обоих вариантах:
  - `--exec fn|script` — как запускается код: `new Function`, как на стендах проектов, или глобальный `<script>`, как в
    хосте smoke;
  - `--catch onerror|listener` — чем песочница ловит ошибки (S8);
  - `--frame srcdoc|src` — от этого зависит `document.referrer` (SB-17);
  - `--iframe-attrs mount|follow` — пересчитывает ли Proteus атрибуты iframe при смене окна;
  - `--no-scrollbars` — полосы как на Mac. По умолчанию полосы как в Windows: с ними и воспроизводится
    «ResizeObserver loop» (SB-03).
- После эмита родитель перезапускает чарт тем же ответом (`--rerun self|all|none`, `--emit-delay 300` мс) — так Proteus
  ведёт себя после кросс-фильтра с самовлиянием. `--no-header` прячет шапку чарта так, как прячет её CSS борда
  (`display:none`; в DOM она остаётся, как у 2.0.1).
- Сценарий читается и проверяется до запуска браузера: массив шагов, `frame` — один из id прогона. Ошибка — код 2 с
  номером шага.
- Шаги сценария `--clicks` (пример — `sbx/clicks.example.json`):
  - `click`, `dblclick`, `hover`, `fill` + `value` — селектор внутри iframe; `i` — номер совпадения, `frame` — id чарта;
  - `press`, `rerun`, `data` (новый ответ из файла), `resize` [w, h];
  - `parentClick` и `parentMove` [x, y] — по борду;
  - `scroll`, `eval` (выражение в iframe), `wait` (мс), `shot`, `name`.
- Вывод по чарту:
  - первый прогон (мс, есть ли `option`), число прогонов;
  - узлы в хосте после прогона и в конце (0 — чарт погас);
  - iframe и его атрибуты, щель или вылет iframe против области ячейки;
  - прокрутка документа iframe и `overflow` у html и body;
  - что видит чарт (`origin`, `referrer`).
- Вывод по шагу:
  - эмиты `applyCrossFilter`;
  - маркер канала скриншотов (текст после IEND в PNG) и размер iframe до → после;
  - прочие сообщения;
  - ошибки окна («→ ЧАРТ ПОГАС»).
- Коды выхода: 0 — ошибок окна нет; 1 — были (в бою чарт погас бы; отклонённый промис тоже считается); 2 — неверный
  вызов или не запустилось (нет файла, id не число или повторяется, ошибка в сценарии).
- Модель не заменяет живой прогон проекта (каркас с вкладками, области кросс-фильтров по JSON, ответы датасета на стенде)
  и бой. Её выводы — [вывод], пока бой их не подтвердил (RESULTS.js.md, раздел 7).
