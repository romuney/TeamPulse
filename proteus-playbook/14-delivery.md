# 14. Поставка владельцу (DV)

**Зачем глава.** В бой файлы несёт владелец: руками вставляет SQL, JS, CSS и JSON в редакторы Proteus и Helicopter,
руками запускает проверки в SQL Lab и DevTools. Поставка — единственный канал «агент → бой», и каждая её неясность
стоит круга переписки или поломки борда. Здесь — как устроить папку поставки, как её собирать, как писать инструкцию,
какие шаги дать владельцу после вставки и как одним запросом снять факты боя. Что должно быть внутри SQL, JS и CSS —
главы 02–11; здесь — упаковка, порядок и обратная связь.

**Главное в 5 пунктах.**
1. **DV-01.** Одна постоянная папка поставки на отчёт; номер файла закреплён за объектом навсегда; правка звучит как «замени из файла N целиком».
2. **DV-03.** Папку собирает скрипт из исходников: сжатый JS, подставленные id, SQL Lab-файлы; `--check` сверяет копии. Руками пишутся только инструкция и ответы владельца.
3. **DV-11.** «Что нового» — сверху и по одному формату: **«Заменить: файлы N, M (порядок)»**, что не менялось, было → стало в числах, что проверить за минуту, что прислать.
4. **DV-13.** Шаги установки — со стоп-точками «готово, когда»; «красное на любом шаге — дальше не идти, прислать текст ошибки целиком».
5. **DV-27, DV-28.** Факты боя снимай одним read-only SELECT, собранным из того же исходника: без Jinja, без слова `system`, с метками прогона в самом запросе.

Метки уверенности — как в 01-platform.md: [бой], [стенд 24.8], [исходник 2.0.1], [владелец дд.мм], [вывод],
[не проверено в бою].

## Эталонная папка поставки

Пример нумерации для отчёта из одного датасета и одного чарта; у отчёта из нескольких чартов номера идут подряд
(DL: 1–4 датасеты, 5–8 чарты, 9 CSS, 10–12 проверки на бою).

```
Поставка — <Отчёт>/                                   ← одна на отчёт (лист), в ветке, которую читает владелец
  0. Инструкция.md                                    ← руками: текущее состояние, «Что нового», установка, симптомы
  0б. SQL Lab — разведка <источник> одним запросом.sql ← до проекта датасета (DV-31), маскирован
  1. Helicopter — ноут <Отчёт>.yaml                   ← только для новой установки
  1а. Helicopter — изменённые параграфы.md            ← ноут уже стоит (DV-17)
  2. Датасет «<имя>».sql                              ← по файлу на датасет; варианты — из одного исходника (DV-04)
  3. Чарт «<имя>».js                                  ← сжатая сборка одной строкой (DV-06)
  4. CSS борда.css                                    ← весь CSS отчёта, id подставлены (DV-24)
  5. JSON-метаданные борда.json                       ← блок chart_configuration по свежей выгрузке (DV-25)
  6. SQL Lab — проверки после выгрузки.sql            ← с «Ждали:» (06-helicopter-gp.md, GP-22)
  7. Проверка на бою — один запрос.sql                ← DV-27
  8. Проверка на бою — где время.sql                  ← DV-28
  9. Проверка на бою — разметка борда (DevTools).js   ← DV-30
  Проба — <что>/                                      ← только на время пробы непроверяемого (DV-08)
История поставок.md                                   ← рядом с папкой или в docs/ (DV-12)
inbox/                                                ← входящее от владельца: выгрузки, JSON, ответы SQL Lab (DV-32)
```

Буква — дополнение к номеру (1а, 2b — запасной вариант датасета без новой витрины). Номера не переиспользуются и не
сдвигаются: «файл 3» — всегда чарт.

## Скелет инструкции

```markdown
# <Отчёт> — что куда вставлять
<2–3 строки: что за отчёт, сколько чартов и датасетов, что не трогаем (прежний борд работает)>

**Текущая поставка: N от дд.мм · коммит <sha12>.** Ветка репозитория: <имя>.

| Файл | Куда вставлять | Менялся в поставке |
|---|---|---|
| `2. Датасет «…».sql` | новый виртуальный датасет `<имя>`, база <…> → SQL | N |
…
Файлы 2 и 3 … — пары: <чем отличаются, «пары не путать»>.

## Если у вас стоит поставка ≤ K
| У вас стоит | Заменить (порядок) | Почему такой порядок |

## Что нового (N-я поставка, дд.мм — <главное словами владельца>)     ← последние 2–3, остальное — История
## С чего начать (первая установка)       ← таблица «шаг | где | что сделать | готово, когда»
## 1. Датасеты (и вкладка «Настройки»)
## 2. Чарты (настройки — чек-листом)
## 3. Дашборд: раскладка, JSON-метаданные, CSS
## 4. Проба на копии борда и на коллеге
## 5. Замена на проде и откат
## 6. Если что-то не так                  ← симптом дословно → причина → что сделать
## 7. Что проверено до поставки           ← числа проверок, таблица скорости «было / стало»
## 8. Проверки на бою                     ← SQL Lab-файлы, протокол DevTools с бланком, сниппет разметки
## 9. Что стендом не проверено            ← что подтвердить в бою и чем
```

## A. Папка и сборка

### DV-01. Держи одну постоянную папку поставки на отчёт; номер файла закрепи за объектом навсегда
- **Почему:** 25.09 владелец запутался в пяти датированных папках «Обновление <дата>» по одному листу adoption и решил: одна папка «<Лист> — актуальные файлы». HRBP прошёл 19 поставок за 11 дней по схеме «замени файл N» без путаницы.
- **Как:**
  - Одна папка на отчёт (лист): по файлу на объект Proteus или Helicopter. Номер закреплён навсегда; буква — дополнение к номеру (0б, 1а, 2b).
  - Любая правка — «замени из файла N **целиком**». Внутри файла владелец ничего не правит, кроме заглушек, названных в шапке (DV-05).
  - Новых датированных папок не заводи. Применённые и перекрытые удаляй в том же коммите, где они стали ненужными.
  - Папка живёт в той ветке, которую читает владелец; ветку называй в инструкции (15-process.md, PR-23).
- **Проверка:** в репозитории одна папка поставки на отчёт; `ls` папки совпадает с таблицей файлов инструкции (DV-02).
- **Уверенность:** [владелец 25.09].
- **Образец:** HRBP_HUB:Поставка — HRBP HUB v2/ (0–5, 1а); detail_list:Поставка — Детальные списки/ (0–12). Не повторять: adoption (рядом с «Единый лист — актуальные файлы» лежат старые «Обновление 2026-09-19 / 21 / 22 / 25»).

### DV-02. Начинай инструкцию с таблицы «Файл → куда вставлять → менялся в поставке»
- **Почему:** владелец вставляет руками 10+ файлов, JS одной строкой глазами не сравнить. Без колонки «менялся» тот, кто пропустил поставки, сам складывает строки «Заменить:» из нескольких разделов, а они ссылаются друг на друга («Остальное из 25-й — в силе»).
- **Как:**
  - Первая таблица: файл; куда вставлять (имя датасета, тип чарта, место в Proteus — «Edit dashboard → CSS, в конец»); в какой поставке файл менялся последний раз.
  - Колонку «менялся» заполняет сборщик (по манифесту или тегу прошлой поставки, DV-34), а не человек.
  - Под таблицей одной строкой — чем отличаются парные файлы: «1–4 — один SQL, отличаются строками MODE / VIEW; 5–8 — строкой `ns`; пары не путать».
  - В таблице — все файлы папки, включая JSON и проверки.
- **Проверка:** сборщик сверяет список файлов папки с таблицей инструкции.
- **Уверенность:** [бой] — таблица работает в четырёх проектах; колонка «менялся» — [вывод] (есть только у TP — статусом).
- **Образец:** detail_list:Поставка — Детальные списки/0. Инструкция.md (таблица «Файл | Куда вставлять» и строка про пары); TeamPulse:Team Pulse/Поставка — TeamPulse Hub/0. Инструкция.md (колонка статуса).

### DV-03. Собирай папку поставки скриптом из исходников; перед сдачей — `--check`
- **Почему:** копии, сделанные руками, расходятся с исходником. Adoption: файл 5 отличается от `Виджеты/` строкой `WITH_CA = true`, равенство JS-копий не проверяется ничем, а регресс читал папку поставки — грабля 23.09. HRBP: файлы 4 и 5 пишутся руками и под `--check` не попадают.
- **Как:**
  - `stand/pack.py` собирает всё вставляемое: датасеты (варианты из одного исходника), сжатый JS (DV-06), CSS с id (DV-24), SQL Lab-файлы (DV-27, DV-28), сниппет DevTools (DV-30), 1а (DV-17), блок JSON (DV-25).
  - Подстановки — функцией, которая требует ровно одно вхождение:

    ```python
    def one_line(text, old, new):
        assert text.count(old) == 1, 'в исходнике должна быть ровно одна строка: ' + old.strip()
        return text.replace(old, new)
    ```

  - Пишет только изменившиеся файлы и печатает их список («→ 3. Чарт «…».js») — это готовая строка «Заменить:» для «Что нового» (DV-11).
  - `pack.py --check` сверяет каждую копию с тем, что собралось бы сейчас; код 1 при расхождении. Части, зависящие от версии инструмента (deflate, terser), сравнивай канонизированно.
  - Нет node или нужной версии terser — сборщик падает, а не кладёт несжатый файл.
  - Шапка собранного файла: «СОБРАН АВТОМАТИЧЕСКИ — не правьте здесь; исходник <путь>; сборка — `python3 stand/pack.py`».
  - Руками пишутся только `0. Инструкция.md` и ответы владельца (`inbox/`).
- **Проверка:** `python3 stand/pack.py --check` — все строки «ok» (DL 08.10: 11 из 11); со сборщиком из kit — ещё `--gate`: `kit/sqlgate.py` по датасетам и SQL Lab-файлам поставки (13-stand.md, ST-33).
- **Уверенность:** [стенд 24.8] + [бой] (расхождение копий у adoption, 23.09).
- **Образец:** detail_list:stand/pack.py (`one_line`, `copies`, `canon`, `--check`); шаблон — kit/pack_template.py.

### DV-04. Собирай варианты из одного исходника: вариант — одна строка, адреса и id — заглушки
- **Почему:** четыре датасета и четыре чарта DL не расходятся при правках с 29.09: в 27-й поставке датасеты 1 и 2 — по 59 677 байт, 3 и 4 — по 59 628; JS 5 и 6 — 138 595 и 138 597 байт, 7 и 8 — 65 495 и 65 497 (разница — строка `ns`). У adoption три чарта несут скопированный общий код (канал, тур, тултипы) и правятся в трёх местах. Свой `ns` даёт каждому чарту на борде свои состояние, стили и тултип (07-chart.md, CJ-05).
- **Как:**
  - Датасеты отличаются строками `{% set MODE = 'us' %}` и `{% set VIEW = 'list' %}`, JS — строкой `ns: 'dl'`; сборщик меняет их через `one_line` (DV-03).
  - Режим чарт берёт из `meta` ответа, а не из своей строки: тогда пара «JS ↔ датасет» перепутана — видно сразу (07-chart.md, CJ-19).
  - id чартов (`BOARD_IDS`) и адрес борда (`BOARD_URL`, `https://<proteus>/superset/dashboard/<id>/`) в исходниках — заглушками; те же заглушки даёт стенд своим чартам. Адрес борда живёт в датасете (`meta.board`), а не в коде чарта (08-sandbox.md, SB-17).
  - Варианты для разных бордов (тестовый и боевой) — разные таблицы `BOARD_IDS` в сборщике, а не правка файла владельцем.
  - Общий код нескольких чартов (канал между чартами, движок тура, тултип) — один модуль в репозитории, который сборщик вклеивает в каждый JS; копии, правленные руками, расходятся [вывод].
- **Проверка:** `diff` двух собранных вариантов показывает только строки варианта; `pack.py --check` зелёный.
- **Уверенность:** [стенд 24.8]; общий модуль — [вывод].
- **Образец:** detail_list:stand/pack.py (`CHARTS`, `DATASETS`, `sql_for`, `BOARD_IDS`, `BOARD_URL`); detail_list:stand/ch.py (`view_text`); kit/pack_template.py (`COPIES`, `one_line`).

### DV-05. Выбирай заглушки уникальными и проверяй число их вхождений
- **Почему:** adoption 30.09, единый лист v2: метка id «12345» — «заменить всё» сломало таблицу перекодировки кириллицы `cz`, в ней есть эти цифры. TP: заглушка «ID» и совет «Ctrl+H ID → число» — поиск без учёта регистра заденет `dashboard-chart-id-` и `GRID_ID` (риск, не случившийся инцидент). DL 06.10: id чартов владелец менял руками в четырёх местах.
- **Как:**
  - Заглушка не встречается в тексте ни в каком другом виде: `000000`…`333333` (id чартов), `777777` (id объекта в SQL Lab-файле), `ваш_логин`. Не годятся «12345», «ID», «LOGIN».
  - Что подставляет сборщик — подставляет он: заглушка была, боевого значения до подстановки не было, после — заглушек не осталось (10-board-css.md, BC-20).
  - Что подставляет владелец (свой логин в SQL Lab) — одно место, если запрос позволяет; иначе шапка называет число мест, а сборщик его проверяет: «Ctrl+H `ваш_логин` → ваш логин (все 5 мест)».
  - Регресс проверяет, что заглушка сама по себе в шаблонах не встречается.
- **Проверка:** `pack.py --check` и регресс SQL Lab-файлов (13-stand.md, ST-32).
- **Уверенность:** [бой] (adoption 30.09; DL 06.10); риск «ID» — [вывод].
- **Образец:** detail_list:stand/pack.py (`css_for`, `board_check` — ровно одно вхождение); adoption:.stand/check_one.py (`LAB_ID = '777777'`, «все N места» в шапке).

### DV-06. Клади в поставку сжатую сборку JS; сборщик печатает её цену и падает сверх бюджета
- **Почему:** Proteus кладёт код чарта в `form_data.jsx` каждого POST `chart/data` — при открытии, «Применить», каждом кросс-фильтре, даже при ответе из кэша. DevTools владельца 07.10: отправка ≈50 КБ/с; 169 КБ уходили 5,8 с (F11, 01-platform.md). Подробно о сжатии и параметрах terser — 07-chart.md, CJ-21.
- **Как:**
  - Файл чарта в поставке — сборка terser 5.51.2 (`stand/min.cjs` = kit/min.cjs): `ecma: 5`, верхний уровень не трогать (`option`, `data`, `applyCrossFilter`), без комментариев, `ascii_only: false`.
  - Шапка сборки (`preamble`): отчёт, номер поставки и sha12 исходника, «правки — в исходнике <путь>; сборка — `python3 stand/pack.py`».
  - Сборщик печатает «N КБ, ≈M с отправки при 50 КБ/с» по каждому чарту и падает сверх бюджета отчёта; после сборки — `node --check` и `kit/min.cjs --verify` сборки (ES5, глобальный `option`, нет `eval` и `new Function`). В `kit/pack_template.py` это уже есть (`--budget`, по умолчанию 150 КБ ≈ 3 с); в `stand/pack.py` DL — нет.
  - Нет node или terser нужной версии — сборщик падает, а не кладёт несжатый файл (DV-03).
  - Читаемый исходник того же коммита остаётся в репозитории: строка ошибки из консоли боя в сборке ничего не скажет — просить текст ошибки целиком (DV-13).
  - Ориентиры: DL список 232 → 138,6 КБ (≈2,8 с), панель 114 → 65,5 КБ; HRBP 405,8 → 236,7 КБ; adoption лист 568 → 311 КБ; TP 536 → 340 КБ со сжатым CSS.
- **Проверка:** вывод сборщика; живой прогон на файлах поставки (13-stand.md, ST-30). В бою — DevTools → `chart/data` → Payload до и после поставки.
- **Уверенность:** [бой] — замер отправки; сборки DL стоят в бою с 21-й поставки (в 22-й их заменил загрузчик, в 23-й — снова сборка); выигрыш у HRBP, adoption, TP — [вывод] [не проверено в бою].
- **Образец:** kit/min.cjs и kit/pack_template.py (`minify`: `--check --budget --kbps 50`); detail_list:stand/min.cjs и stand/pack.py (`minified`) — без вывода сборки байт в байт тот же, что kit.

### DV-07. Клади код чарта целиком в поле JS; загрузчик кода из ответа датасета из сборки убери
- **Почему:** 22-я поставка DL (07.10) перенесла код в строку `js` ответа датасета, а в поле JS — загрузчик 5 КБ. У владельца сломались все четыре чарта: «Зачем ты сломал js чарты». В 23-й — откат. Причину не выяснили: что было на месте чарта и в консоли, владелец не прислал (07-chart.md, CJ-22).
- **Как:** в поле JS — полная сжатая сборка (DV-06). Флаг `LOADER_ON = False` недостаточен: код загрузчика, ветки сборщика и разделы регресса под него лучше убрать из репозитория в ветку или архив, чтобы их нельзя было включить случайно. Вернуть приём можно только пробой (DV-08), с разрешения владельца и после выяснения причины поломки.
- **Проверка:** в папке поставки нет строк `role = 'js'` в датасетах и нет файлов загрузчика; grep по сборщику — нет `LOADER`.
- **Уверенность:** [бой] (поломка 07.10, откат 23-й поставкой); убрать код загрузчика из сборки — [вывод]. Спорно: DL оставил код и проверки загрузчика намеренно, для будущей пробы с разрешения владельца; держать их в отдельной ветке, а не за флагом, — предложение гайда.
- **Образец:** detail_list:stand/pack.py (`LOADER_ON = False` и шапка с историей отката) — оставить только откат, ветки убрать.

### DV-08. Проверяй непроверяемое вне песочницы пробой на одном чарте копии борда
- **Почему:** урок 22-й поставки DL (DV-07). Adoption 07.10: слой затемнения тура поверх страницы в бою не появился, причина неизвестна — две итерации вслепую.
- **Как:**
  - Что считать непроверяемым: загрузчик кода, `eval` / `new Function` в чарте, новые API браузера, новые каналы к родителю, CSS «поверх страницы», правила разворота iframe на новом борде.
  - Такое изменение — подпапка «Проба — <что>/» с одним чартом на копии борда, запасным файлом (прежняя версия) и разделом «Откат» в той же поставке.
  - Заранее напиши, что прислать: текст на месте чарта, скриншот целиком, консоль F12 целиком, однострочник проверки маркера (DV-13).
  - В одной поставке — не больше одного такого изменения. В основную папку оно попадает только после подтверждения пробы.

### DV-09. Ставь штамп версии в каждый файл и в ответ; чарт показывает несовместимость текстом
- **Почему:** ни в одном проекте по экрану не видно, что стоит. У DL `meta.ver = '3'` — версия формата, а шапка JS без номера поставки; у HRBP метки нет; шапки JS adoption говорят «v7 2026-09-22» при правках 07.10. Рассинхрон SQL и JS adoption (30.09) находили по косвенным пометкам «старый SQL».
- **Как:** два разных признака.
  - **Штамп сборки** — «что стоит»: сборщик вписывает «поставка N · дата · sha12 исходника» в `preamble` JS (`CFG.build`), в `{% set BUILD = '…' %}` датасета с эхом в `meta.build`, в комментарий CSS и в шапки SQL Lab-файлов. N и дата — поставка, в которой **этот файл** менялся последний раз, а не текущая: с номером текущей поставки на каждой поставке «изменятся» все файлы, и «Заменить:» (DV-11) потеряет смысл. Дата — константой в сборщике, не «сегодня»: иначе `--check` разойдётся на следующий день.

    ```python
    h = sha12(source)                                       # меняется только вместе с исходником
    prev = re.search(r"поставка \S+ · \S+ · " + h, old_file_text or '')   # прошлый штамп с тем же sha12
    BUILD = prev.group(0) if prev else 'поставка %s · %s · %s' % (DELIVERY, DATE, h)
    sql = one_line(sql, "{% set BUILD = '' %}\n", "{% set BUILD = '%s' %}\n" % BUILD)
    js = one_line(js, "  build: '',\n", "  build: '%s',\n" % BUILD)
    ```

  - **Версия формата** — «совместимы ли»: `meta.ver` ответа против списка форматов, которые читает чарт. Несовместимо — плашка «датасет поставки N, чарт поставки M — замените файл K» (07-chart.md, CJ-19).
  - Чарт показывает штамп в подсказке «Как работать» или ⓘ: владелец присылает скриншот, и видно, что стоит.
  - Сообщения канала между чартами тоже несут версию: получатель пишет «в чарте N старая сборка», а не молчит (09-multi-chart.md, MC-16).
  - «Описание» датасета = номер поставки из его штампа: при замене SQL это ещё и реальная правка, которая сбрасывает кэш (DV-22).
- **Проверка:** скриншот подсказки после установки показывает тот же номер, что колонка «менялся в поставке» первой таблицы инструкции (DV-02); повторная сборка без правок исходников не меняет ни одного файла.
- **Уверенность:** [вывод] — штампа нет ни в одном проекте.
- **Образец:** частично — adoption:Виджеты/pa-one.chart.js (пометка причины «в pa_one старый SQL»); kit/pack_template.py (`stamp`, `{% set BUILD %}` в виде `dataset`, дата константой `DATE`) — но там в шапку каждого файла идёт текущий `DELIVERY`: при подъёме номера «изменятся» все файлы, взять номер из прошлой шапки, как выше.

### DV-10. Делай форматы совместимыми в обе стороны; порядок установки пиши явно и с причиной
- **Почему:** владелец ставит файлы не одновременно и не всегда подряд. HRBP 16-я поставка (07.10): старый чарт не читает короткие массивы → нули и прочерки, поэтому «сначала чарт». Adoption 30.09: «никто не смотрел» при 2 134 пользователях — в датасете стоял старый SQL.
- **Как:**
  - Меняя формат ответа, сначала выпусти JS, который читает **и прежний, и новый** формат (DL 21-я: колонки вместо пачек — чарт читает оба; HRBP: массив с «@» и без).
  - Новый SQL **добавляет** строки и секции, которые старый JS пропускает, а не меняет существующие. Тогда порядок установки любой.
  - На старом ответе чарт пишет причину («обновите датасет — файл 2»), а не пустоту.
  - Совместимость односторонняя — порядок в заголовке «Что нового» с причиной («сначала 3, потом 2: старый чарт новый ответ не прочтёт») и строка «поставлено в неверном порядке» в таблице симптомов (DV-14).
  - Протокол канала между чартами (сообщения тура, эхо фильтров) меняй во всех участниках одной поставкой и пиши «заменить все N файлов»: частичная замена молча ломает функцию — adoption 07.10, «кнопка ничего не запустит» (09-multi-chart.md, MC-16).
- **Проверка:** на стенде старый JS (по тегу прошлой поставки) на новом ответе и новый JS на старом ответе — без ошибок консоли, с понятным текстом.
- **Уверенность:** [бой] (HRBP 07.10, adoption 30.09).
- **Образец:** HRBP_HUB:proteus/hrbp-hub.chart.js (`parseArr` — массив с «@» и без); detail_list:proteus/detail-list.chart.js (чтение колонок `c` и прежних пачек `r`).

### DV-11. Пиши «Что нового» сверху и по одному формату
- **Почему:** владелец ставит поставки по верхнему разделу и не всегда подряд. Цена в числах даёт ему самому выбрать компромисс (DL 17-я: «ответ 13 и 19 МБ, gzip 2,3 и 3,1, было ≈7 МБ»). Недочёт DL 27-й: файл 11 собирается из SQL панели и изменился вместе с ней, а в «Что нового» назван не был.
- **Как:**

  ```markdown
  ## Что нового (N-я поставка, дд.мм — <главный эффект словами владельца>)

  **Заменить: файлы 2, 3 и 8 (сначала 3, потом 2: старый чарт новый ответ не прочтёт).** Файл 8 собран из датасета 2.
  Не менялись: 1, 4–7, 9 — можно не трогать. Если не стоит поставка K — поставьте и файл 4.

  **<Симптом словами владельца>.** Причина: … Сделано: … Было → стало: ClickHouse <было> → <стало> с (стенд),
  ответ <было> → <стало> МБ (на проводе ≈<было> → <стало> МБ). Нельзя: … — потому что …
  - **Проверить:** <что увидеть за минуту на экране, в DevTools или SQL Lab>.
  - **Прислать:** <что и зачем>. Не легло — <что сделать, откат>.
  ```

  - Список «Заменить» — из вывода сборщика (DV-03): все изменённые файлы, включая собранные из изменённого.
  - Порядок замены — с причиной (DV-10); зависимость от прошлых поставок — явно.
  - Абзац на изменение: симптом словами владельца → причина → что сделано → было → стало в числах (время ClickHouse, МБ ответа и на проводе, время в браузере) → чего нельзя и почему.
  - Разницы для пользователей нет — так и напиши: «для пользователей ничего не меняется».
  - После замены датасета — предупреждение о холодном кэше с числами (DV-22).
  - Одновременно с разделом обнови строку файла в первой таблице, пункты «что проверить на пробе», «если что-то не так», «что проверено», «что не проверено».
- **Проверка:** сборщик сверяет «Заменить:» верхнего раздела со списком изменённых файлов (предложение); владелец ставит по одному разделу без вопросов.
- **Уверенность:** [бой] — формат держится 19 поставок HRBP и 27 поставок DL.
- **Образец:** detail_list:Поставка — Детальные списки/0. Инструкция.md (раздел 27-й поставки); HRBP_HUB:Поставка — HRBP HUB v2/0. Инструкция.md (раздел 17-й — срочная правка).

### DV-32. Начинай с выгрузки борда владельца; входящее от владельца держи отдельно от поставки

- **Как:**
  - Первая работа по борду — выгрузка владельца в репозиторий: `charts/` (с ключом `jsx`), `datasets/`, `dashboards/`. Это эталон «как стоит сейчас».

  - Данные сотрудников во входящем — только агрегатами; сырое после разбора удаляй (03-access-cache.md, AC-16).
- **Проверка:** в папке поставки нет файлов, которых не собирает сборщик и не описывает инструкция.

### DV-33. Копи мелкие правки до конца дня; срочно выпускай только безопасность и поломки
- **Почему:** DL 06.10 — 12 поставок за день (9–20-я), многие из одного файла (только CSS — 10-я, 14-я, 16-я; только JSON — 18-я). Владелец устаёт, растёт риск поставить вперемешку. HRBP — 19 поставок за 11 дней.

### DV-34. Ставь git-тег на каждую поставку и считай от него всё «что изменилось»
- **Почему:** тегов поставок нет ни в одном из четырёх репозиториев. `same.py` берёт «прошлую версию» по памяти, список 1а ведётся руками (`CHANGED_DATE = '06.10'`), матрицу «у вас стоит ≤ N» никто не считает.
